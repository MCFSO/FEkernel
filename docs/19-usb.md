## 1. 为什么现在有意义

### 1.1 真机上没有 USB HID 就没有输入

今天的键鼠**只有 PS/2**（`12-drivers.md:32-33` 的两行：`kbd` 占 `0x60..0x64` + IRQ1，
`mouse` 同端口 + IRQ12）。这是**一个正在消失的接口**：很多近年主板与笔记本
已经没有 PS/2 口，或者只有一个组合口、默认走 USB 控制器。

★ 所以这条不是"多一个驱动"，而是**"这台系统在真机上能不能被人操作"** ★
`08-kernel-completion.md` 的 C3 判据是"键盘输入进 shell：行编辑、回车执行、退格可见"，
而它今天**只在 PS/2 存在的机器上成立**。这个前提从来没写下来过。

### 1.2 可移动介质是最常见的"系统外数据来源"

今天系统的数据来源是**一块固定盘**：`blkd` 发布 `/dev/blk0`（ATA IDE），
`fsd` 在启动时打开它（`user/servers/fsd/main.c:1386-1388` 的注释与代码写得明白：
"init 保证 blkd 先起来（单元表里 fsd 声明 require `/dev/blk0`）"）。

**没有任何"把外面的数据拿进来"的路径**：没有网络栈（`10-posix-layer.md` §7：
没有 TCP/IP 栈），没有 USB。U 盘是这类路径里**最常见、也最不需要新机制**的一条——
它需要的全部东西（MMIO、DMA、中断、块服务）**今天都已经有了**（§2）。

### 1.3 ★ 一条必须写清楚的区分：从 U 盘**启动**不需要 USB 驱动 ★

★ 这条不写下来，后人一定会误以为"支持 U 盘启动"是 USB 驱动的一部分。★

`01-milestones.md:19`（M11）的判据是"**真机从 U 盘启动进入图形控制台**"。
那条路上的 USB 是**固件**在管：

```
U 盘（FAT32，含 EFI/BOOT/BOOTX64.EFI = Limine）
        ↓  ①UEFI 固件的 USB 大容量存储驱动读 FAT32
   Limine（EFI 应用）
        ↓  ②Limine 用固件的块 I/O 协议读 limine.conf 与 kernel.elf
   FEKernel
        ↓  ③此后内核不再碰 U 盘
```

- ① 是 **UEFI 固件**的能力（UEFI 规范把 USB 大容量存储列为**可选**支持，
  但主流固件都实现了）。`tools/mkfat.py` 造的就是那块 FAT32 卷
  （`tools/run_qemu.py:160-169` 记着"用**我们自己构建的** disk.img，而不是 QEMU 的
  `-drive fat:` 目录合成"，两者格式不同）。
- ② Limine 用的是固件的 Block I/O Protocol，不是它自己的 USB 驱动。
- ③ **启动之后，系统里没有任何东西能再读那块 U 盘。** 这正是 D8 要补的。

★ 一句话 ★ **D8 不解决"能不能从 U 盘启动"，它解决"启动之后能不能读 U 盘"。**
两者唯一的交集是：真机上插着的那块 U 盘，在固件阶段被读过、在系统阶段读不到——
**同一个物理设备，两套互不相干的软件栈**。★

### 1.4 ★ 今天到底有什么：全树核实（不是"我记得"）★

核实方式：全树搜 `xhci|ehci|uhci|ohci|usb|USB` → **只有 2 处命中**：

| 命中 | 它是什么 | 它不是 |
|---|---|---|
| `user/include/fe_pci.h:58` | `#define FE_PCI_CLASS_SERIAL 0x0C /* 串行总线（USB、SMBus…） */` | 只是一个**类代码常量**，没有任何消费者 |
| `tools/run_vbox.py:131` | `"--usb", "off",` | VirtualBox 的 `modifyvm` 参数，**把 USB 关掉**（与 `--audio none`、`--nic1 none` 同一批"最小化客户机"的开关） |

另外全树搜 `xhci`/`ehci`/`uhci`/`ohci` → **0 处**；
搜 `qemu-xhci`/`usb-storage`/`usb-kbd`/`usb-tablet` → **0 处**
（`tools/run_qemu.py` 的 QEMU 命令行里**一个 USB 设备都没有**，
见 `:170` 的 IDE 盘与 `:181-182` 的 virtio-blk）。

**现有用户态驱动**（`user/libdrv/`，4 个 .c）：`ata.c`、`ps2.c`、`virtio.c`、`virtio_pci.c`。
**现有服务**（`user/servers/`）：`blkd`、`fsd`、`consoled`、`kbd`、`mouse`、`flaky`
（`devfs` 在内核侧）。

★ 结论 ★ **USB 是这块系统上最大的一块空白**，而它需要的机制**一样都不缺**（§2）。

### 2.2 DMA 窗口与物理地址

| USB 要什么 | 今天有什么 | 证据 |

过期的用法去写，然后在"表项被写了两遍"这件事上浪费一天。

### 2.5 多路等待

| USB 要什么 | 今天有什么 | 证据 |
|---|---|---|
| 驱动主循环要"等设备中断 + 等客户端请求"合流 | ✅ **内核机制完成**：`fe_wait_any` | `11-kernel-next.md:153`（§8 节标题）及其 4 组自检（含 3 条反向） |
| 用户态怎么调 | ⬜ ★ **只有内核 API，没有用户态入口** ★ | `12-drivers.md:303-305` 逐字："内核侧的 `fe_wait_any` 已经实现并验证……**但它今天只有内核 API，没有用户态入口**" |
| 为什么故意不急着定 ABI | 要一次定死三件事（等待目标数组怎么跨 syscall 边界传…） | `12-drivers.md:307-309` |
| 第一个真实调用者出现了吗 | ★ **没有** ★ | `01-milestones.md:1400-1402` 逐字："`wait_any` 的用户态 ABI 仍然挂着：virtio 的完成判据是 used ring 下标，**它并不需要'等中断与等请求合流'**，所以 §8 预期的那个'第一个真实调用者'实测没有出现。**不要为了兑现文档里的一句话而造一个调用者。**" |

★ **这对 D8 的含义（本文的判断，需要 D8a 实测确认）** ★
D8a **不需要** `wait_any`：xHCI 的完成判据是**事件环上的一个 TRB**
（与 virtio 的 used ring 下标同族），单线程轮询事件环就够了。
★ 但 D8b/D8c 是**服务**（要同时等 USB 中断与客户端请求），
到那时 `wait_any` 才第一次有真实需求——D7 那份 ABI 的"第一个真实调用者"
很可能是 `usbd` 而不是 blkd。**这一条要写进 D7 的账上，不要在 D8a 里顺手定 ABI。** ★

（一次性的测试程序 `user/bin/usbprobe` 完全不需要它——它按 §3 的判据跑完就退出。）

### 2.6 ★ 结论（一句话）★

> **USB 驱动是纯用户态的事，完全不碰内核。**
> 认领（资源池 + `fe_mmio_map`）、DMA（`fe_mem_alloc_dma` + `fe_mem_info`）、
> 中断（`fe_irq_register[_ex]` + 通知对象一位）、MSI-X（`fe_irq_msi_alloc`）
> ——**四样全在，而且都被真实设备实测过**（M14 / M17 / M18）。
> 这正好落在 `00-architecture.md` 的 P1 与 `12-drivers.md:21-27` 那张表上：
> **内核提供三种硬件手段的「认领 + 检查」，驱动住在用户态（ring 3）。**

★ 唯一"不够用"的是 §2.5 的 `wait_any` 用户态 ABI，而它**不挡 D8a**；
到 D8b/D8c 时它才成为真需求（或者证明又不需要——**那也是一个结论**）。★

## 3. 三刀切分

写法仿 `11-kernel-next.md` §4：每刀一个**可证伪的终点** + **失败时最先看哪里**，
而且**每一刀都能在 QEMU 里验**（不必等真机——这是刻意的，见 §4）。

### D8a：xHCI 核心——"能看见设备了"

| 项 | 内容 |
|---|---|
| **终点（可证伪）** | 一个 `user/bin/usbprobe` 程序：`pcid`/devmgr 那条链拿到 xHCI 的 BAR 与 MSI-X 能力偏移 → 认领并映射 → 建**命令环 / 事件环 / 传输环**（TRB）→ 复位控制器（`USBCMD.HCRST`）→ 端口上电与复位 → 用**控制传输**读回某一台真实设备的**设备描述符**，并打印它的 `VID/PID/类/协议` |
| **反向对照** | ① **不认领 BAR 就直接访问** → 必须是**明确的拒绝或 `#GP`**，不是"读到全 1 然后继续"（判据在 `12-drivers.md:39-40` 已有先例：`drvdeny` 被 CPU 逐条指令拒绝）；② **端口上没有设备时** → 必须报"无设备"并在有限步内返回，**不是超时挂死**（★这一条是本刀最重要的一条★：xHCI 的端口状态机在"没插东西"时的行为与"插了但没起"不同，混在一起会让人以为是驱动写错了）；③ 复位后**回读 `USBCMD.HCRST` 必须归 0**，否则报"控制器没有响应复位" |
| **依赖** | §2.1（资源池 + `fe_mmio_map`）、§2.2（DMA 对象给环与上下文）、§2.3（MSI-X；**也可以先用轮询事件环**）、一个 **PCI capability 链遍历器**（见下）、`12-drivers.md` §9 已有的 DMA 用法范例 |

| **失败时最先看哪里** | ① 认领 BAR 失败（`FE_ERR_NOENT`）→ BAR **还没被 devmgr 申报进池子**（`12-drivers.md:227-228`：那条链"还没接"曾是事实，现在接上了但**每次都要走一遍**）；② 认领成功但读寄存器全是 `0xFFFFFFFF`/`0` → 很可能踩了 `fe_pci.h:143-146` 那个坑（BAR 探测没写回原值）；③ 事件环永远没有 TRB → 先查**环的物理地址**是不是 `fe_mem_info` 拿的（用普通指针的物理地址必错，见 `fe_drv.h:46`）；④ 端口复位超时 → 先确认"这个端口上到底有没有设备"，别把"没设备"当"复位失败" |

★ **D8a 不做什么**（写清楚，防止它长成 D8b）★ 不实现任何**类驱动**——

### D8b：大容量存储——"能读一块真盘了"

| 项 | 内容 |
|---|---|
| **终点（可证伪）** | **Bulk-Only Transport（BOT）** + SCSI `INQUIRY` / `READ CAPACITY(10)` / `READ(10)`：从 U 盘读回**一个已知扇区**，与新发布的服务 `/dev/usbblk0` 读出的同一扇区**逐字节相符**；并让现有 `fsd` 能挂上去（见下） |
| **反向对照** | ① **读一个超出容量的 LBA** → 必须被**拒绝**并且**不能静默返回垃圾**（`M14` 已经有同族的判据："越界 LBA 被拒"，`01-milestones.md:22`）；② **介质不存在时**（QEMU 里 `-device usb-storage` 不给 `drive=`，或真机上空读卡器）→ 必须是"无介质"这个**独立的结论**，而不是"读失败"（★这与 M14 照出来的那条同源：`01-milestones.md:1378-1382`"这台机器上没有那样硬件"必须是一个独立类别★）；③ CSW 的 **status 非 0** 时驱动必须报错而不是把残留数据当结果 |
| **依赖** | D8a；`blkd` 的块协议（`user/include/fe_blk.h`）与它"发布到 devfs"的做法（`user/servers/blkd/main.c:198` 的 `g_dev_path = "/dev/blk0"`、`:1257`、`:1488`）；`fsd` 怎么找块设备（`user/servers/fsd/main.c:1386-1388`） |
| **★ 一个必须定死的口径 ★** | "**让 `fsd` 挂上去**"有两种代价完全不同的做法，**动手前必须选一个并写下来**：**(i)** `fsd` 加一个"块设备可配"的入口（今天它硬编码 `fe_devfs_open("/dev/blk0")`，`user/servers/fsd/main.c:1387`）；**(ii)** 只做 `usbblk` 客户端（像 `blkread`/`blkbench` 那样自己开 `/dev/usbblk0`），**不碰 `fsd`**。★ 建议先做 (ii)：它拿到"能读一块真盘"的证据，而完全不改已有服务——`M14` 就是这么做的（"老路径不受影响：`blkread`、`fsd` 一行不改"，`01-milestones.md:1374`）。★ |
| **失败时最先看哪里** | ① `INQUIRY` 返回全 0 → CBW 的 `dCBWSignature`/长度字段或**端点方向**写错（BOT 的 CBW 是 OUT、CSW 是 IN，写反的症状是"设备不响应"）；② `READ CAPACITY` 给了个荒谬的大数 → 字节序（SCSI 是大端）；③ 读回的数据**每隔几个字节错一次** → transfer buffer 的**物理地址算错**或 DMA 对象不够大（`fe_mem_info` 的 `page_count` 要核）；④ 换台机器就好 → 见 §4（QEMU 与真机的 U 盘不是同一个设备） |

### D8c：HID（键鼠）——"真机上能打字了"

| 项 | 内容 |
|---|---|
| **终点（可证伪）** | 从 xHCI 控制传输拿 **HID 报告描述符**（或者直接用 **boot protocol**，见下）→ 在 **interrupt IN 端点**上轮询/收包 → 解码成键码 → **发布到控制台**（与今天 `kbd` 服务同样的出口）。判据：**QEMU 里注入一次按键，控制台出现对应字符** |
| **反向对照** | ① **与现有 PS/2 路径的输出逐字对照**：同一个字符经 PS/2 与经 USB 进来，控制台上应当**一模一样**（这一条把"输出格式悄悄变了"挡在门外）；② 松开按键后**不能重复出字符**（HID 的报告是"当前按下的集合"，不做差分就会连发——这类 bug 只在按下时看不出来）；③ 非 boot-protocol 设备（报告描述符里有报告 ID）→ 必须**明确报"暂不支持"**，而不是把报告 ID 当键码解出来 |
| **依赖** | D8a；`user/servers/kbd/main.c`（今天 PS/2 的出口：认领端口 `:132`、登记 IRQ `:145`、阻塞等通知 `:209`）；`user/servers/consoled/main.c`（控制台出口） |
| **★ 为什么"boot protocol"值得先行 ★** | USB HID 的**报告描述符**是一套小型描述语言（用法页/用法/集合/嵌套），解析器本身就是一个项目。而 HID 规范为**键盘与鼠标**定义了 **boot protocol**：报告格式固定为 8 字节（键盘）/ 3 字节（鼠标）。★ **先做 boot protocol 就能拿到"真机能打字"这个全部价值**，而把描述符解析推后 ★——这与项目一贯的"不写'以后可能需要'的机制"一致。**代价写在明处**：不支持多媒体键、不支持非 boot 子类的设备 |
| **失败时最先找哪里** | ① 一个字符都不出 → 先确认控制器有没有把 `usb-kbd` 认出来（D8a 的描述符打印）；② 出字符但**顺序错乱/丢字符** → interrupt IN 端点的**轮询间隔**（`bInterval`）与"上一次报告还没取走"的竞态；③ 只出一次 → 端点没有重新武装（xHCI 的 transfer ring 是一次性的，每个 TRB 完成后要重挂） |

## 5. 代价与"什么时候会咬人"

### 5.1 为什么 xHCI 是 USB 里最难的一块

**USB 主机控制器有四代**：UHCI（USB 1.1，Intel）、OHCI（USB 1.1，非 Intel）、
EHCI（USB 2.0）、xHCI（USB 3.x，且向下兼容 2.0/1.1）。

★ **选 xHCI 的理由是"它同时覆盖 2.0 与 3.0"，代价是它是四代里最复杂的** ★：

| 复杂度来源 | 具体是什么 |
|---|---|
| **三种环** | 命令环（Command Ring）、事件环（Event Ring）、**每个端点一条**传输环（Transfer Ring）。它们不是同一种东西：命令与传输是"软件写、硬件读"，事件是"硬件写、软件读"，**方向相反** |
| **上下文（Context）** | 设备上下文（Device Context）、**每个端点一个**端点上下文（Endpoint Context）、输入上下文（Input Context）。它们由驱动填写、由控制器读，字段多且互相引用（`Slot ID` / `DCI` / `EP State`） |
| **端口状态机** | `Powered → Disabled → Enabled → Reset → Addressed → Configured`，每一步都有超时与失败分支。"没插设备"与"插了但没起来"是**不同的状态**（D8a 的反向对照 ② 就是这一条） |
| **TRB 的类型与链式** | Transfer Request Block 有十几种类型，`Cycle Bit`（生产者/消费者判据）、`Chain Bit`、`IOC`（完成后是否产生事件）等标志互相影响 |
| **两种速度域** | USB 2.0 与 3.0 在同一个控制器下走不同的协议与端口寄存器组 |

★ **这不是"多写一千行"，是"多写一千行且每一段的错误都表现为超时"** ★——
所以 §3 的每一刀都有一条"失败时最先看哪里"，而且 D8a 刻意**只做到描述符**。

### 5.2 建议的"够用版"边界（写清楚，不是遗漏）

| 不做 | 理由 | 何时该做 |
|---|---|---|
| **hub**（不枚举下级端口/不解析 hub 描述符） | ★ 代价极高：hub 是"设备"也是"控制器"（要遍历它的端口、分配地址、处理它自己的状态机）。而**直连根端口**已经能覆盖"键盘 + 一个 U 盘"，这正好是 §1 的两条价值 ★ | 真机上要插 hub 时（笔记本常见：内置 hub 后面挂着摄像头/蓝牙） |
| **热插拔**（运行期插拔） | 见 §5.3——**它要求的东西不只是驱动** | 见 §5.3 |
| **错误恢复**（`USBSTS.HSE` 后的控制器复位与端口重建、`Transaction Error` 重试） | 出错恢复的每一段都难验证（要能**制造**错误），而"不恢复"的代价是**设备掉线后要重启系统** | 真机长期运行时 |
| **多设备**（同时多个 slot） | 单设备足以证伪三刀；多设备要多一套 slot 分配与带宽管理 | D8c 之后 |
| **USB 2.0/3.0 双速度的正确切换** | 只跑 xHCI 报出来的第一个可用端口 | 真机上遇到只认 3.0 的设备时 |
| **USB 音频/摄像头/打印机等类驱动** | 与 §1 的两条价值无关 | 有需求时 |

★ 一句话 ★ **够用版 = "直连根端口上的一个键盘或一个 U 盘，插着不动"。**
这不是"半成品"，是一条**能把 §1 的两条价值兑现**的线；上面那张表的每一项
都要**单独**去付代价。★

### 5.3 ★ 热插拔会咬人：`devmgr` 的枚举是启动期做的 ★

**核实（这一条我逐个文件读过）**：

| 事实 | 证据 |
|---|---|
| PCI 枚举**跑完就退出**，是一次性工具 | `user/bin/pcid/main.c` 是 `int main(void)` 跑完 `return` 的程序（打印"发现 N 个 PCI 功能"后结束，见 `12-drivers.md:255-257` 的实测日志）；边界表里逐字写着"**跑完就退出**——它今天是一次性工具。要常驻得先有事件来源（热插拔），而'谁产生热插拔事件'（ACPI 注意按钮 / PCIe 存在检测）是个新问题，**不该现在猜**"（`12-drivers.md:270`） |
| `devmgr` 的"发现/申报/授予"是一次性的动作链 | `user/bin/devmgr/main.c:34-37` 的用法：`devmgr --declare --grant-task <id>`——**显式指定**要申报哪个设备、授予哪个任务 |
| `init` 的启动表是**静态的**，依赖关系在编译期写死 | `user/bin/init/main.c` 的单元表（`:659`/`:675`/`:699`/`:755`/`:803` 等处的 `.require = { "/dev/blk0", NULL }`），以及 `:778`/`:797` 的 `.provides = "/dev/blk0"` / `"/dev/vblk0"` |
| `fsd` 在启动时**一次性**打开块设备 | `user/servers/fsd/main.c:1387` 的 `g_blk = fe_devfs_open("/dev/blk0")`；`:1386` 的注释："init 保证 blkd 先起来（单元表里 fsd 声明 require /dev/blk0）" |

★ **所以"热插拔"在今天的要求不是"驱动多写一段"，而是三件事一起变** ★：
1. **有事件来源**（今天没有任何东西会告诉系统"刚刚插进来一个设备"）；
2. **`devmgr` 要能在运行期被调用**（今天的形态是一次性工具 + 显式 BDA 参数）；
3. **消费者要能"后到"**（`fsd` 今天在启动时打开一次块设备；一个后出现的
   `/dev/usbblk0` 它根本不会去看）。

★ 本文的判断（**标为判断，不是实测**）★
**D8a/D8b/D8c 三刀都不该包含热插拔**——它们全部可以在"设备**插着开机**"
这个前提下验收，而那个前提在 QEMU 里天然成立（`-device` 是启动参数）。
热插拔应当**单独立项**，因为它的第一件事是"事件来源从哪来"，
而那是一个**新机制**的问题（ACPI/PCIe 存在检测），不是 USB 的问题。

★ 待查（我核不到的部分，不猜）★ 见 §6 第 8 条。

### 5.4 "什么时候会咬人"（把时间点写清）

| 咬人的地方 | 什么时候 | 症状 |
|---|---|---|
| capability 链遍历器是 virtio 专用的（§3 D8a 的缺口） | **D8a 第一天** | 找不到 MSI-X 能力偏移 → `fe_irq_msi_alloc` 拿不到 `cap_off` |
| MSI-X 表项"由谁写"的文档冲突（§2.3 那条提醒） | **D8a 第一天** | 表项被写两遍 / 或者照着头文件写却发现内核已经写过了 |
| 端口"没设备"与"复位失败"混在一起 | D8a 端口初始化 | **超时挂死**，而现象是"驱动卡住" |
| DMA 对象不够大 / 物理地址算错 | D8b 第一次真读 | 数据每隔几字节错一次 |
| 报告描述符（非 boot 设备） | D8c 扩展时 | 把报告 ID 当键码 |
| `wait_any` 用户态 ABI | **D8b/D8c 做成服务时** | 又回到"两条线程 + 自写唤醒逻辑"（`12-drivers.md:298-301` 的两条别扭写法） |
| **热插拔** | 真机上拔了再插 | 系统再也看不见那个设备（§5.3） |
| `FE_VMA_MAX = 32`（`kernel/include/fe/mm/vma.h:65`） | D8 的服务 + 每个 DMA 对象都可能占区间 | 跑到一半 `FE_ERR_NOSPC`（与 `17-libcxx-build.md` §4.1 同一个边界，只是触发者不同） |

★ 最后一条值得单独说 ★ `17-libcxx-build.md` §4.1 已经核实过
"每线程一个区间 + 每个 arena chunk 一个区间"，而 USB 会**再加一批**：
xHCI 的每个 DMA 对象（命令环、事件环、每个端点的传输环、设备上下文、
transfer buffer）都是一次 `fe_mem_alloc_dma` + `fe_mem_map`。
**32 个区间在"一个键盘 + 一个 U 盘"下够不够，今天不知道**——
这是一条**待实测**，判据是"数一数 D8a 建完环之后 `vma` 表里用掉几格"。

## 7. 与现有工作的关系

### 7.1 它**不挡** C1/C2/C3

`08-kernel-completion.md` §1 的完成判据里，C1/C2 已完成（帧缓冲移交 + 屏幕可读文字），
C3（"键盘输入进 shell"）也已标记 ✅——**但 C3 的成立有一个从未写下来的前提：
这台机器上有 PS/2**（§1.1）。USB 补的是那个前提，**不是 C3 的实现**。

所以：

| 判据 | 它今天缺什么 | USB 挡它吗 |
|---|---|---|
| **C1/C2**（帧缓冲 + 可读文字） | 已完成 | ❌ 不挡 |
| **C3**（键盘进 shell） | 已完成（**限有 PS/2 的机器**）；USB 让它在没有 PS/2 的真机上也能成立 | ❌ 不挡（它是**加固**，不是前置） |
| **C7**（磁盘 ≥200 MB/s） | 已完成（M14，QEMU 上 2253 MiB/s） | ❌ 不挡 |
| **C8/C9**（A/B 分区化 / 多核） | 未完成 | ❌ 不挡 |

★ 更直接地说 ★ `17-libcxx-build.md` §6 里列的那些才是真正的下一批：
**K6 `exec`**（`docs/15-exec.md` 的设计已就绪）、**K5 异常处理者**
（`docs/18-user-fault-handler.md` 已经在做）、**`mprotect`**（`17` §2.9）。
**USB 一样都不挡，也一样都不被它们挡。** ★

### 7.2 它**不挡** Qt 路线

`16-selfhost-path.md` 的路线（S1–S10）需要的全部东西是：
目标侧编译器、libc++、libm、POSIX 头、shell、构建系统、`exec`、内存与磁盘。
★ **USB 不在那条路上** ★——Qt 的构建不需要任何 USB 设备，
`QPluginLoader` 也不需要。两者**完全正交**。

（唯一的交集是"真机可用性"这个更大的目标：一台**没有输入设备**的真机
既不能跑 Qt 程序，也不能被人使用。但那属于"系统可用"而不是"自举"。）

### 7.3 建议顺序

```
现在：K6 exec（用户已定，见 docs/15）          ← 它挡 S7，也挡 shell
      K5 异常处理者（docs/18，正在进行）
      mprotect（17 §2.9 的那一条）
        ↓
然后：D8a（xHCI 核心）                          ← 一条独立的、纯用户态的、可独立证伪的线
      D8b（大容量存储）
      D8c（HID）
        ↓
之后：热插拔（§5.3 的三件事，需要单独立项）
```

★ **为什么 D8a 可以随时插进来做** ★
它**不依赖任何未完成的内核项**（§2.6 的结论：四样机制全在，且都被真实设备实测过），
它也**不被任何未完成的内核项阻塞**——`exec`/K5/`mprotect` 与 USB 没有交集。
所以它的"最划算时机"不是某个依赖点之后，而是**当有人能独占构建与 QEMU 的时候**
（今天不行：另一个代理正在用）。

★ **反过来，D8a 有一个别的项目没有的好处** ★
它是本项目**第一个真正"用户态自己完成一切"的驱动**：不新增 syscall、
不改内核、不改 `libfe`。如果它做成了，`12-drivers.md` 的整个 D 清单
（D1–D7 全是内核侧）就终于有了一个**消费者**——
而如果它居然需要动内核，那说明 §2 的核实有漏，**那本身就是最值钱的结论**。
