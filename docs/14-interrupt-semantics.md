# 中断的更多语义（D5）

> 今天的实现已经能做一件事：**把一根中断线变成通知对象上的一位**。
> 本文处理它做不到的三件事：**共享一根线**、**触发方式与极性的显式契约**、
> **MSI / MSI-X**。
>
> 每一项都先写"为什么这样做 / 代价是什么 / 边界在哪"，再写实现。

## 1. 现状（以及它为什么不够）

| 能力 | 今天 | 不够在哪 |
|---|---|---|
| 投递 | `gsi_isr` → 置位通知对象的第 `1<<irq` 位 | 够用 |
| 电平线的风暴防护 | 投递后立即在 IOAPIC 里屏蔽，驱动 `fe_irq_ack` 后放行 | 够用，但**只对独占线成立** |
| 触发方式/极性 | 由 ACPI 的中断源覆盖表决定（MADT） | 驱动**看不到也核对不了**它拿到的是哪种 |
| 共享一根线 | **不允许**：`find_irq` 命中就返回 `FE_ERR_BUSY` | 两台设备接在同一条 PCI INTx 上时，第二个驱动起不来 |
| MSI / MSI-X | 没有 | 真实驱动（Linux）默认走 MSI；INTx 是退路 |

★ 共享这条为什么现在就需要 ★ 不是"以后可能要"：QEMU 上第二台 virtio
设备**就是**同一条 IRQ11。今天 `vblkd` 拿走了 IRQ11，再加一个 virtio 设备
（比如 D6/网络）就会撞上 `FE_ERR_BUSY`——也就是"加一台设备需要改内核之外
的东西"这件事已经开始了。

## 2. D5a：共享一根中断线

### 2.1 只允许**电平触发**的线共享

这是整个设计的支点，值得说清楚：

- **边沿线的共享是丢中断的**：设备 A 与 B 接同一条边沿线上，A 的中断正在
  被处理时 B 拉了一次边沿——那一次**没有第二次跳变可检测**，
  B 的中断就永久丢了。这不是实现问题，是边沿语义本身的性质。
- **电平线可以共享**：线保持拉高直到所有设备都被服务完，所以
  "谁拉的不重要，重要的是线还高着"——这正是共享所需要的。

所以规则定为：**边沿线的第二次登记一律 `FE_ERR_BUSY`**，并把原因写进日志。
想共享就该用 MSI（§4），那是"每台设备一条独立消息"的机制。

代价：一个 ISA 边沿设备（键盘、ATA）无法与别人共享它的线。今天没有这种需求，
而"拒绝"比"允许然后偶发丢中断"诚实。

### 2.2 投递：**置位所有登记者**，而不是挑一个

- 线的身份不携带"是哪台设备"的信息，所以内核**无法**挑。让登记者去查
  自己的设备是唯一正确的做法（PCI 共享中断的标准做法）。
- 于是契约变成：**登记为共享的人必须接受伪唤醒**。它每次被叫醒都得
  问自己的设备"是你吗"，不是就立刻返回。这一条必须写进用户态文档，
  因为它改变了驱动的写法。

### 2.3 电平线：屏蔽 → **所有人都确认** 才放行

独占时是"投递后屏蔽，`fe_irq_ack` 放行"。共享时那样做是错的：
先确认的那个人会**立刻放行**，而线还高着（另一个设备还没被服务），
于是立刻再投递一次——CPU 被同一个中断淹没。

所以把 `masked` 从布尔改成**计数**：

```
投递：让所有登记者都"欠一次确认"（pending = 登记者数），屏蔽线
确认：pending--；归零才放行
```

代价（写清楚）：**一个不确认的登记者会把整条线卡住**，其余设备一起饿死。
独占时这个代价只落在自己头上，共享时落在邻居头上。今天的缓解办法是
"驱动退出/被终止时 `fe_irq_release_owner` 会替它确认并重算 pending"——
也就是**退出路径必须参与**，这正是把它放在那一处的原因。

### 2.4 谁有权把一条线声明为可共享

仍然是**设备管理器**（资源池的入池接口已经支持 `shared` 标记）。
内核不认识"这条线接了几台设备"——那是拓扑，是策略。
内核只回答："这段资源是不是被标记为可共享"，以及"共享的人有没有遵守
电平线这条物理约束"。

这与 D1/D2 的分工是同一条：**发现是策略（用户态），裁决是机制（内核）**。

## 3. D5b：触发方式与极性的显式契约

今天驱动拿到的是"内核按 ACPI 配好了"，而它**看不到结果**。两件事要补：

1. **如实报出来**：登记成功后，驱动能问"我这条线是电平还是边沿、
   高有效还是低有效、GSI 是多少、向量是多少"。
2. **允许声明要求**：驱动可以说"我要求电平"。不匹配就拒绝登记，
   而不是让它带着错误的假设跑起来——那类错误的症状是"偶发丢中断"，
   而那种症状会被归因到驱动自己的逻辑上，排查代价极高。

★ 为什么要允许声明而不只是报告 ★ 报告是"事后知情"，声明是"事前拒绝"。
对**中断**来说，带着错的触发方式跑比直接失败更糟：它不会立刻崩，
只会在负载高的时候偶发丢事件。

代价：驱动要写对（写错会被拒，这是好事）；内核多一个字段与一条判据。

## 4. D5c：MSI / MSI-X

### 4.1 为什么它比 INTx 重要

- **没有共享问题**：每台设备（每个向量）一条独立消息，"是谁"由向量本身
  携带，驱动不需要"问自己的设备是不是我"。
- **没有电平/边沿问题**：MSI 是消息写，天然边沿语义，不需要 ack/屏蔽。
- **真实驱动默认走它**：Linux 的 `pci_alloc_irq_vectors()` 优先 MSI-X。

### 4.2 谁发现、谁编程

MSI 的能力结构在 **PCI 配置空间**里，而配置空间是**已经入池的资源**。
所以分工与 D1/D2 一致：

| 步骤 | 谁 | 为什么 |
|---|---|---|
| 发现设备有 MSI/MSI-X 能力、读到能力结构的偏移与表大小 | **用户态**（设备管理器） | 那是 PCI 协议知识，是策略 |
| 分配向量、写 MSI 地址/数据、把向量绑到通知对象 | **内核** | 向量与 LAPIC 是内核的机制；而且"分配向量"与"写设备寄存器"必须**原子**——分两步做会出现"设备已经会写 MSI 了，但没人处理那个向量"的窗口 |
| 使能设备侧的 MSI（capability 的 enable 位） | **内核**（同一次配置空间写里） | 同上 |

★ 内核因此需要能写配置空间 ★ 注意这与"端口是独占资源"不冲突：
资源池约束的是**用户任务之间**不互相踩；内核在系统调用里为**这一次**
MSI 编程写配置空间，是一段机制，不是策略。而且它必须原子。

### 4.3 MSI 的地址与数据怎么来

x86 上 MSI 是"往一个固定的物理地址写一个 32 位数"：

- 地址 = `0xFEE00000 | (dest_apic_id << 12)`（LAPIC 的 MSI 窗口）
- 数据 = `vector | (edge << 15) | (assert << 14) | (physical << 2)`

内核知道 LAPIC 基址与自己 CPU 的 APIC ID，所以这两个值都由内核算，
**不让用户态填**——用户态填的话，它可以把中断投到任意向量上，
那等于绕过了"向量归内核分配"这条边界。

代价：这套地址/数据的编码是 x86 专有的，写在 `arch/x86_64` 里；
将来换架构要重写这一段（这与"中断投递是通知对象上的一位"这个**跨架构**
的形态无关，那一层不动）。

### 4.4 MSI-X 比 MSI 多什么

> ★ **本节"表项归属"（下面第 2/3 步）已被 §8.1 的实测推翻：表项改由内核代写。往下读之前先看 §8.1。** ★
> 本节保留的是**当时的设计**（原设计：驱动映射 BAR，内核只往驱动交进来的
> 用户地址里写 16 字节）——**§8.1 记录了它为什么在真实设备上走不通**
> （MSI-X 表在 **BAR1**，而驱动只映射了 **BAR4**）。
> ★ 另外，本节的"第 N 个表项"读作"由谁决定表项号"时要注意：**今天写进去的
> 永远是第 0 项**——用户态这层 ABI（`fe_irq_msi_alloc(nt, bus, dev, fn,
> cap_off, &mi)`）**没有表项号参数**，`kernel/arch/x86_64/syscall.c` 固定传
> `flags = 0`。要支持别的表项，改的是 syscall 那一层的参数，
> **不是**让驱动自己写表。★

MSI-X 有一张**表**（在某个 BAR 里），每个表项可以指向不同向量。
表在 BAR 里意味着**要映射那段 BAR 才能写**——而 BAR 的映射是驱动
自己的事（资源池 + `fe_mmio_map`）。

所以 MSI-X 的分工多一步：

1. 内核从配置空间读出 **表在哪个 BAR、偏移多少、表项数**（这是能力结构里的字段）；
2. 用户态（驱动）映射那段 BAR；
3. 内核按"第 N 个表项在 BAR 内偏移 X"计算地址并写入。

★ 为什么不让内核去映射 BAR ★ 那要求内核持有 BAR 的映射并且知道
它属于谁——正是资源池要避免的。让驱动交一段**已经映射好的虚拟地址**
进来，内核只往里面写 16 字节，是这条链上最少的内核知识。

代价：ABI 上要传一个用户指针，而"内核写用户内存"要按 uaccess 的规矩来
（逐页校验，失败返回 FAULT 且不改设备状态）。

## 5. 验收口径

每一项都要有**能被证伪的断言**与**反向对照**：

| 项 | 正向 | 反向 |
|---|---|---|
| D5a 共享 | 两个登记者都能收到同一个中断（各自的位都被置） | 边沿线的第二次登记被拒（BUSY）；未确认时**不放行**（pending 不归零） |
| D5a 屏蔽计数 | 两个都确认之后线才放行 | 只确认一个 → 线仍处于屏蔽（**这一条是防"先确认的立刻放行"那个 bug 的**） |
| D5b 契约 | 报告出来的模式与 ACPI 一致 | 声明"要求电平"而实际是边沿 → 拒绝登记 |
| D5c MSI | 设备侧的 MSI 被真的使能，中断经 MSI 到达（而不是 INTx） | MSI 未使能时设备仍走 INTx（说明"经 MSI 到达"不是运气）；非设备的配置空间位置必须被拒 |

★ D5c 的"真的走了 MSI"怎么证明 ★ 与 D4 的"真的走了 DMA"同一个问题。
判据不能是"中断来了"（INTx 也会来），而必须是**只有 MSI 才有的东西**：
写进设备的 MSI 地址/数据被设备接受（读回确认）、
并且 **INTx 那条线被屏蔽掉了**——两条路都在时，把其中一条关掉再看
中断还来不来，才能把"哪条路"分开。

## 6. D5a / D5b 实测（QEMU + WHPX）

### 内核自检（`fe_selftest_irq`，失败项 0）

这一组有四十多条断言，`CHECK` 失败时**报出行号**——"失败项: 2"那种输出
无法定位任何东西，本轮就因此多绕了两步。

先问实情、再按实情推导判据（**这一点是被一台机器教会的**）：

```
本机实情: IRQ11=电平，IRQ20=边沿
[IRQ] 拒绝：调用者要求电平触发，而 IRQ20 实测是边沿触发
[IRQ] 拒绝：IRQ20 是**边沿**触发，不能共享（边沿共享会丢中断，要共享请走 MSI）
[IRQ] 拒绝：调用者要求边沿触发，而 IRQ11 实测是电平触发
[IRQ] IRQ11（电平）**共享登记**第 2 家：任务 11
=> 中断投递失败项: 0
```

★ 第一版把"IRQ15 是边沿"写死在断言里，11 项一起红 ★
这台机器上 ACPI 把**未列出的 ISA 中断一律报成"电平、低有效"**
（`fe_acpi_irq_to_gsi` 的默认值，那是 ISA 的正确惯例；只有 irq ≥ 16
才按边沿）。所以判据改成"**声明成它本来的样子必须成功、声明成相反的
样子必须失败**"——与环境无关。

反向对照（每条都对应一个真实故障）：

| 断言 | 它防的是什么 |
|---|---|
| 边沿线的第二个登记者 → `BUSY` | 允许共享边沿 = 偶发丢中断，而那种错误查不出来 |
| 共享线上**只确认一个 → 仍然屏蔽** | 先确认的立刻放行 = 线还高着 → 立刻重投 → 中断风暴 |
| 不在册的人确认 → `ACCESS` | 任何人都能把线提前放行 |
| 共享线上不带 owner 的确认 → `INVAL` | "谁在确认"答不出来，语义不明 |
| 一家退出 → 线还在、向量没释放、邻居仍收得到 | 一命中就掐整条线 = 把邻居的中断一起打死 |
| **欠着账的那家退出 → `pending` 不该多减** | 线在还有人欠账时被放行 → 风暴（本轮的真 bug，见 §7.1） |

### 真实路径（`user/bin/irqtest`，失败项 0）

同一台真实设备（virtio-blk 的 IRQ11，**电平**）被**两个任务**同时登记：

```
[irq] IRQ11 -> GSI 11 向量 97，电平，共享者 2
[child] 已共享登记 IRQ11（电平，共享者 3）
[child] 收到真实中断并已确认
    OK   第一个登记者收到**真实设备**中断（共享线上不止一家）
    OK   第一个登记者确认
    OK   第二个登记者也收到了真实中断并确认（共享是**双向**成立的）
    OK   所有中断收完之后磁盘**仍然可用**（线没被卡住）
```

三个共享者是 `vblkd` + 监督者 + 孩子。**中断有物理来源**：
irqtest 通过 `/dev/vblk0` 发真实读请求让 virtio 设备抬高中断线，
所以"收到中断"不是合成的。

★ 最后那条断言才是关键 ★ 共享线最危险的失败模式不是"收不到中断"，
而是"某个登记者没确认 → 线被永久屏蔽 → 邻居一起停摆"。
它在这里的表现就是**最后那次读失败**。

## 7. D5a 查出来的两个内核缺陷

两个都不在中断代码里——它们是**共享这条新路径第一次走**才暴露的。

### 7.1 `pending` 是"逐家"的，不是"有人退出就减一"

退出的登记者若**已经确认过**，它的离开不该再从欠账计数里减一次：
那会让线在"还有人在欠账"时被放行，而线还高着 → 立刻重投 → 中断风暴。
反过来说，**欠着账就跑**的人必须被清掉（否则 `pending` 永远归不了零，
整条线连同邻居卡死）。两个方向都要对，所以判据是**它自己那一格 `owes`**。

这个是自检抓出来的：`只确认一个 → 仍然屏蔽` 通过之后，
"欠账的那家退出"那一条立刻红了。

### 7.2 `pool_merge()` 会吃掉共享标记（更隐蔽的那个）

`fe_resource_release_owner` 之后会把相邻的空闲池条目合并，**但它从不看
`flags`**。于是：

```
[资源] 入池 IRQ 0xb+1 flags=0x1          ← init 申报"可共享"，正确
[资源] 认领 IRQ11（任务 35）：池中条目 0xb+2 flags=0x0   ← 变成了长度 2、不共享
```

init 申报的 `[11,1)` 与引导期就有的 `[12,1)`（鼠标）**相邻**，
一次归并把两条并成 `[11,2) flags=0`——共享标记被 `entry_alloc` 的 memset
抹掉，`sharers[]` 也被 `entry_free` 丢掉。后果是**第二个驱动认领同一条线
拿到 BUSY，而池子里明明写着"（共享）"**。

为什么以前没暴露：共享池条目到今天只有 PS/2 端口那**一条**，
它从不与邻居相邻，所以合并逻辑从没碰过共享条目。

两条不能合并共享条目的理由，缺一不可：
1. 单个 `flags` 字段**表达不了**"这一段里有一部分可共享"；
2. 合并会丢掉被并掉那一条的 `sharers[]`，那些任务从"已认领"变成
   "没记录"，归还时再也摘不掉自己。

代价：相邻的共享条目各占一格，池子碎一点。共享区间很少，
碎一点可以接受；"合并之后含义变了"不可接受。

### 7.3 一个 API 顺序问题（小，但会误导）

`sys_irq_register` 是"先认领资源、再登记"，而触发方式的检查原来只长在
登记里。于是"我声明的模式写错了"会**先**撞上资源池的错误
（共享线上同一个任务再认领一次拿到 `EXIST`），报出来的是"你已经持有它"
——**而调用者真正写错的是那个参数**。参数错误不依赖任何状态，
就该先报，所以把契约检查提到了认领之前（`fe_irq_mode_ok`）。

## 8. D5c 实测：MSI-X 真的生效（QEMU + WHPX）

### 8.1 一个设计改动：表项由**内核**写，而不是驱动

原设计（§4.4）是"内核不碰别人的 BAR，让驱动自己写那 16 个字节"。
**实测把它推翻了**：QEMU 的 virtio-blk-pci 把 MSI-X 表放在 **BAR1**，
而驱动只映射了 **BAR4**（virtio 四类结构所在的那一段）——于是驱动为了写
16 个字节还得再认领一个 BAR、再映射一次。那不是"更干净的分工"，
是把一次写放大成一条资源链。

改成：内核用 `fe_vmm_map_mmio` 把表项所在的那 16 字节映射进**它自己已有的
MMIO 窗口**写一次。它本来就要读那个 BAR 的**地址**（不然算不出表项在哪），
所以"知道 MSI-X 表在哪"这件事躲不掉；而这样做**不产生任何所有权声明**，
资源池里 BAR1 归谁完全不受影响。

顺带少了一件事：原设计里"驱动能往别人的表项里填向量"这个能力面没有了——
内核只写它自己分配的那个向量。护栏多了一条：**表项落在可用内存上就拒绝**
（设备说表在哪是设备说的，而我们马上要往那个物理地址写数据）。

### 8.2 两个开关，分属两层，少一个都不生效

实测踩到的坑：内核把 MSI-X 的使能位置了、表项也写对了，**中断就是不来**。
原因是 virtio 协议层还有一个开关：

| 开关 | 在哪 | 谁管 |
|---|---|---|
| MSI-X Enable（能力结构 bit 15） | PCI 配置空间 | **内核**（与向量分配原子） |
| `queue_msix_vector`（common cfg 0x1A） | 设备的 MMIO | **驱动**（协议知识） |

`queue_msix_vector` 的默认值是 **0xFFFF = 不用 MSI-X、走 INTx**。
只写表项不写它，设备根本不会去发那条消息。两件事分属两层，
各由该管的人管——但**必须都做**。

### 8.3 怎么证明"真的走了 MSI-X"

与 D4 的"真的走了 DMA"同一个问题：判据不能是"中断来了"（INTx 也会来）。
这里的做法是——**这条路上完全不登记 INTx**，然后：

1. 辅助线程去等 `1 << mi.irq` 那一位；
2. 主线程发一次**真实读请求**（设备只有真干了活才会写那条消息）；
3. 那一位被置上 ⇒ 只可能是 MSI-X 送来的，因为**那条路是唯一存在的路**。

```
[MSI] MSI-X 已使能：00:04.0 cap 0x98 → 伪中断 32 向量 97（addr 0xfee00000 data 0x4061）
  [blkd] MSI-X 表项已由内核写入（表在 BAR1，内核用自己已有的 MMIO 窗口写）
  [blkd] 已告诉设备用 MSI-X 表项 0（回读 queue_msix_vector=0，设备确认了）
  [blkd] MSI-X 中断**已到达**（辅助线程被那一位唤醒；读请求成功）
         —— 这条路上**没有登记 INTx**，所以只可能是 MSI-X 送来的
```

### 8.4 一个真实的取舍：两条真实路径测试抢同一个开关

**一个设备的中断方式只有一种**：MSI-X 一旦使能，设备就**不再拉 INTx**。
于是 D5c（要 MSI-X）与 D5a 的真实路径测试（要 INTx 共享线）抢同一个开关。

`blkd` 的选择是：**验证完就把 MSI-X 关掉**，让设备退回 INTx——
证据已经在上面那行拿到了（"没有登记 INTx 却收到中断"不可伪造），
而共享线需要设备持续拉 INTx 才能被验。

**代价写在明处**：这个驱动的稳定状态仍是 INTx，真实驱动应当常开 MSI-X。
```
  [blkd] MSI-X 已关掉（返回 0）：设备退回 INTx，好让 irqtest 的共享线测试也能拿到真实中断
=== 中断共享测试结束，失败项 0 ===
```

### 8.5 反向对照（不碰真设备的那一半）

MSI 的**参数校验**全部走拒绝路径，在自检里验（自检不该去动真设备的配置空间
——那会让它依赖机器，也会在别人的机器上改掉设备状态）：

| 断言 | 它防的是什么 |
|---|---|
| 偏移 0x40（virtio 能力，不是 MSI）→ `INVAL` | 照着一个不是能力结构的偏移写配置空间，可能改掉 BAR 或命令寄存器 |
| **设备不存在**（配置空间读回全 1）→ `INVAL` | "设备不存在"与"设备没有 MSI"必须同一条拒绝路径 |
| 偏移 0x30 / 0x99（越界、未对齐）→ `INVAL` | 能力结构只能在 0x40..0xFF 且 4 字节对齐 |
| 表项落在可用内存上 → `ACCESS` | 设备说表在哪是**设备说的**，而内核马上要往那个物理地址写 |

## 9. 顺带照出来的用户态 API 缺口：线程入口不能返回

D5c 的验证需要一个"等中断"的辅助线程，而它**第一次不小心返回了**，
症状是 `出错指令 0x0`、任务名只显示 `user`。

根因：内核给用户线程搭的初始栈是"被调用的函数"那一格，
而**那一格是零**——入口一旦 `ret` 就跳到地址 0。

既有的用户线程（contest / hxtest）都是显式退出、从不返回，
所以这条约定从没被写下来过，也从没暴露过。现在写进了
`user/include/fe_user.h` 的 `fe_thread_create` 说明里：
**入口必须以 `fe_exit()` 收尾**。
