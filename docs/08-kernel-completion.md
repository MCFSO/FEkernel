# 做成"能用的内核"：完成判据与路线

> 目标不是"再加几个功能"，而是**把这条链整个走通**：
>
> ```
> 开机 → 屏幕上出现控制台 → 键盘敲进 shell → 用命令创建并写文件
>      → 重启后文件还在、内容正确 → 全程速度可用（磁盘 ≥200 MB/s）
>      → A/B 更新与写保护在可写 FS 之上仍然成立 → 多核可用
> ```
>
> 这条链上任何一环缺失，前面的都只是演示。本文记录**每一环的判据与状态**。

## 1. 完成判据（可测，不含形容词）

| # | 判据 | 怎么验 | 状态 |
|---|---|---|---|
| C1 | 内核把帧缓冲交给用户态服务，**自己不再画** | `consoled` 认领 MMIO 成功；内核侧无任何后续写屏 | ✅ **已完成** |
| C2 | 屏幕上能显示可读文字（自绘字形，非抄字体） | 写字符后**读回像素**与位图逐点比对 + 屏幕截图 | ✅ **已完成** |
| C3 | 键盘输入进 shell：行编辑、回车执行、退格可见 | 注入扫描码 → 屏幕上出现对应字符与命令回显 | ✅ **已完成** |
| C4 | shell 能执行内建命令并拉起外部程序 | `ls` / `cat` / `echo` / `fs` / `clear` / `exit`；外部程序 `spawn` + 等退出码 | ✅ **已完成** |
| C5 | 文件系统**可写**：创建、写入、追加、删除 | `echo hi > /home/a.txt` 之后 `cat` 读回一致 | ✅ **已完成** |

## 2. 阶段划分与顺序（按"谁卡着谁"）

| 阶段 | 内容 | 为什么在这个位置 | 状态 |
|---|---|---|---|
| **S1 交互面** | `consoled`（帧缓冲所有者）→ 键盘输入 → shell（行编辑 + 内建 + spawn） | 没有它，后面每一项都无法**被人使用**；而且 shell 是后续所有验证的"手动测试工具" | 🔵 进行中（S1.1 完成） |
| **S2 可写文件系统** | fsd 写路径（FAT 表、目录项、簇分配、截断、删除）+ A/B 槽改成分区 | 有了 shell 才能**手动**验证写路径；而槽改分区是写路径的前置（否则块级拷贝的目录项会指向另一个槽） | ⬜ |
| **S3 性能地基** | 批量共享内存 IPC → AHCI/virtio-blk DMA → fsd 缓存 | 182 KB/s 的磁盘不叫"能用"；而且 C7 是 C5/C6 的体验前提（写个文件等 3 秒不能接受） | 🔵 **下一项**（D4：virtio-blk + DMA + 共享内存批量） |
| **S4 多核** | 按 `06-smp.md`：每 CPU 数据 → AP 上线 → IPC fastpath → 中断定向 → TLB | 它是放大器：在 182 KB/s 的磁盘上做多核等于给没气的轮胎换发动机 | ⬜ |
| **S5 收尾** | 双环境全量验收、文档、`docs/01` 里程碑更新 | — | ⬜ |

★ **S1 排在 S2 前面的理由** ★
shell 不只是"给用户看的界面"，它是**验证工具**：有了它，
"文件能不能写"可以靠手打一条命令来验，而不是再写一个一次性测试程序。
把验证工具先做出来，后面每一步的验证成本都会下降。

## 3. S1 已落地的部分（S1.1：帧缓冲控制台）

### 所有权移交

```
引导期：Limine 给内核帧缓冲信息 → 内核画一条蓝带（自检用）
        ↓ 内核把帧缓冲的**物理区间**放进资源池
移交后：consoled 用 fe_mmio_map 认领并映射 → 之后**只有它**碰屏幕
```

★ **这是一次真正的所有权移交，不是"多给一个使用者"** ★
两边都画就会互相盖掉，而用户态看到的"自己以为的屏幕内容"与真实像素不一致——
那类不一致查起来非常贵（你分不清是自己画错了还是别人盖掉了）。
所以内核在把帧缓冲入池之后**不再写屏**；引导期那条蓝带被控制台起来时的整屏重画覆盖掉。

### 交给用户态的是**物理**地址

`FE_SYS_FB_INFO` 返回 `phys` 而不是内核那条 HHDM 线性地址：
帧缓冲是设备内存，必须走**关缓存**的 MMIO 映射。
顺带把像素的 mask/shift 一起给了——16 位 5-6-5 与 32 位 BGR 的差别
只能靠它们表达，让用户态"按 bpp 猜"换台机器就是颜色错乱。

### 字体是生成的，不是抄的

`tools/mkfont.py` 里字形用 **ASCII art** 描述（95 个字形，5x7），
生成 `font5x7.h`。三个理由：

1. **可读**：位图表是 95 组十六进制数，肉眼无法核对；ASCII art 一眼就能看出字形对不对；
2. **可校验**：宽度写错在生成时报错——直接手写位图时，那种错表现为"某个字符永远缺一角"，没人会发现；
3. **自研**：字形是自己在 5x7 网格上画的，没有任何现成字体文件。

### 自检方式：读回像素

控制台唯一的硬自检是"**写一个字符 → 把像素读回来 → 与字形位图逐点比对**"。
帧缓冲是可读的 MMIO，所以"我以为我画上去了"可以被证伪。
再加一条**反向对照**：故意用错误的颜色去比对，必须**比不中**——
没有它，"一致"可能只是因为比对函数永远返回真。

实测（QEMU + WHPX）：

```
[consoled] OK   帧缓冲 MMIO 已认领并映射
         文本网格 106 列 x 44 行（缩放 2x，字符格 12x18 像素）
[consoled] OK   文本网格至少 80x20
[consoled] OK   写入的像素与字体位图逐点一致（帧缓冲真的收到了）
[consoled] OK   反向对照：用错的颜色比对不通过（比对函数真的在比）
[consoled] OK   发布 /dev/console
```

屏幕上的实际内容（`tools/qemu_shot.py` 从 QEMU monitor 抓的 screendump）：

```
FEKernel console (consoled)
========================
framebuffer owned by a user-space service
mode 1280x800 106x44 text cells
_
```

★ **两个证据缺一不可** ★
"读回像素与位图一致"证明代码按预期写了；"截图里有字"证明**写的地方就是屏幕**。
只有前者时，如果 MMIO 映射指到了另一块内存，自检会照样通过而屏幕一片空白——
这个可能性是真实存在的（自检读的也是同一块内存，它自己证明不了自己在屏幕上）。

### 字体只覆盖 ASCII（一个要记住的边界）

第一次截屏里中文全是 `?`：

```
FEKernel ??????
```

因为字体是 ASCII 32..126 共 95 个自绘字形。这不是 bug，是"自绘 5x7 字体"的边界：
CJK 要 16x16 点阵、几千个字形，是另一个工程。
所以约定是：**代码注释用中文，屏显字符串一律 ASCII**。
这条必须写下来，否则下一个人往屏显里塞中文，屏幕上就是一串问号而他不知道原因。

### 屏幕抓取工具化

`tools/qemu_shot.py`：启动 QEMU → 等 N 秒 → 通过 monitor 发 `screendump` → 转成 PNG。
（QEMU 只写 PPM，所以顺带写了 `tools/ppm2png.py`，只用 zlib + struct，不引 Pillow。）

★ 它默认会**重建 disk.img** ★
因为 `build.py` 只重建 `build/esp`，**不重建 `disk.img`**。
改了用户态程序却直接跑 QEMU，跑的其实是旧二进制——
我第一版就是这么被骗的：改了屏显字符串，截出来的图一模一样，
第一反应是"改动没生效"，实际是"盘没重建"。
这已经是本项目第 N 次栽在"看着旧产物下结论"上，所以这次把重建**做进工具里**，
而不是指望自己下次记得。

## 4. SIMD 打开后暴露的一个潜伏 bug（值得单记）

打开 SIMD 的当次运行，`bench` 的 RPC 服务线程 #GP 了，出错指令在**用户代码**里、错误码 0。

根因：**用户线程的初始栈少了 8 字节对齐**。

```
SysV ABI：函数第一条指令处 rsp % 16 == 8（call 压过返回地址）
        进程入口才是 rsp % 16 == 0（没有返回地址）

内核线程那条路早就写对了（stack_top - 8，注释都写明了）
用户线程那条路写的是 top - 16  ← 把线程入口当成了进程入口
```

这个错**一直存在**，但在用户态不能用 SIMD 时没有症状：
只有编译器用对齐的 SSE 搬移（`movaps`）往栈上溢出时才会 #GP。
**一打开 SIMD 它就现形了。**

教训不是"这次记得减 8"，而是：
**"没有症状"不等于"没有问题"**。打开一个新能力（SIMD、多核、大地址空间）
往往会把旧代码里本来就错、只是碰巧没被触发的地方照出来。
所以"打开 SIMD"这件事的价值不止是性能——它同时是一次**对既有假设的压力测试**。

## 5. 性能账（把 SIMD 的代价也记上）

| 项 | 打开 SIMD 前 | 打开后 | 说明 |
|---|---|---|---|
| 系统调用 | 118 ~ 129 周期 | **126 周期** | 无变化（内核不碰向量寄存器，syscall 不做 FPU 保存） |
| 线程让出 | 2134 ~ 2375 | **2608** | +10~20%：切换时多了 XSAVE/XRSTOR（832 字节状态） |
| IPC 往返 | 5836 ~ 6002 | **7001** | +17%，同上（RPC 内含两次切换） |
| memcpy（缓存内） | 5344 MB/s（逐字节） | **54446 MB/s** | 10 倍 |
| memcpy（25 MB） | 42957 | **52516 MB/s** | +22% |

★ **这是诚实的账** ★ 打开 SIMD 换来的是"一整类工作能做 + 拷贝快一个数量级"，
代价是**切换路径慢 15%**——因为每个线程的向量状态必须被保存和恢复。
这笔交易在"性能要优"的口径下是划算的，但它不是免费的，所以数字要摆出来。

后续可做的优化（不是现在）：只有真正用过 FPU 的线程才需要保存/恢复
（`XSAVEOPT` 已经能跳过未修改的部分，但"从未用过"这个判断需要额外跟踪）；
或者对纯内核线程跳过恢复（它们的区永远是初始态）。

### 教训：证据必须带上"这是哪一次运行"

第 1 条假警报的成因值得单独记，因为它这一轮出现了**两种形态**：

1. **截图是时序相关的。** 我把"截图里没有"直接读成了"实现有问题"，
   而截图反映的是**某一时刻**的屏幕。VBox 引导到 consoled 需要更久，
   120 秒对 QEMU 够、对 VBox 不够，于是抓到的是一张"半路"的图。
   修法不是"下次等久一点"（那是靠记性），而是**让证据自己带条件**：
   抓屏前先确认串口日志里已经出现目标状态（如 `[consoled] 发布 /dev/console`）。
2. **两个环境的日志是两个文件。** 我一边后台跑 VBox、一边前台跑 QEMU，
   却去读了 `serial.log`（QEMU 的），差点据此认定
   "VBox 的帧缓冲地址也是 0x80000000"——而 VBox 的真实情况
   （1024x768、XSAVE 而非 XSAVEOPT）完全不同。

★ 这两条与前面几轮反复出现的"看着旧产物下结论"是同一个根：
**先确认证据属于哪一次运行、哪一个环境、哪一个时刻，再下结论。** ★

## 7. 本轮"全面测试 → 修"的结果（3 个真 bug + 1 个假警报）

用户的要求是"测试哪里出问题了就修哪里"。下面每一条都是**测出来的**，
不是猜的；每条都写清"症状 → 根因 → 修法"，因为症状与根因的距离正是这类问题的全部难度。

| # | 症状 | 根因 | 修法 | 怎么证明修好了 |
|---|---|---|---|---|
| 1 | 控制台客户端报"INFO 请求有应答"失败，看起来像 IPC 不通 | `consoled` 回复时**复用了请求的消息头**，而内核是按 `hdr.payload_len` 拷贝载荷的——那个长度是**请求**的 8 字节，于是 24 字节的 `con_info` 只回了 8 字节 | 抽出 `con_reply(reply, data, len)`，每次**新建**头。结构上让"忘了设长度"不可能再发生 | `contest` 全绿；截图里客户端写的字真的出现在屏幕上 |
| 2 | 注入 `dx=5, dy=+5`，驱动解出 `dx=5, dy=-261` | PS/2 的增量是"**无符号字节 + flags 里的符号位**"组成的 9 位补码。原代码 `(i64)(i8)pkt[2]` 先按有符号解释一次，**然后又减 256**——符号用了两次。数据字节 <128 时看不出来 | 抽出 `decode_packet()`：数据字节按**无符号**读，符号只看 flags；并加一张**合成包自检表**（含 ±255 边界、0x80 无符号、两个符号位分别与同时置位） | 自检 9 个用例全过；注入的 4 个包解码全部合理 |
| 3 | 一次"测鼠标"的启动**偷偷做了 A/B 更新并重启**，表现成"卡住、鼠标服务没起来" | 启动请求（`fek.update=1`）是**藏在构建产物里的状态**：`run_qemu.py --ab-update` 把它写进 `build/esp/limine.conf`，而直接调 `mkfat.py` 的工具（抓屏、注入鼠标）不会清掉它 | 新增 `tools/bootcfg.py`：**建镜像的人必须显式声明**请求（`mkfat.py --update-request/--reboot-request`），mkfat 每次都把它归一化成调用者要的样子 | 三条路径分别验证：带参数→标记在；不带→标记被擦掉 |
| 4 | VBox 截图里看不到控制台 | **假警报**：截图是在客户机还没跑到 consoled 时抓的（VBox 引导比 QEMU 慢） | 抓屏/注入工具改成**轮询日志直到目标状态出现**，而不是睡固定秒数 | 同一份工具在 VBox 上抓到了控制台 |

### 新增的两个测试工具（都属于"把证据做扎实"）

| 工具 | 作用 | 为什么必须存在 |
|---|---|---|
| `tools/qemu_mouse.py` | 用 monitor 注入鼠标事件，验用户态鼠标驱动 | **鼠标路径此前从未被触发过**：初始化全绿，但"3 字节包解出来对不对"没有任何证据。VBox 没有鼠标注入手段，所以这件事只能在 QEMU 上做 |

### 为什么按键用"推送"而不是"拉取"

这是本轮唯一的设计取舍，值得写清楚：**拉取式接口在我们的 IPC 上做不到干净**。

服务端要么轮询（烧 CPU 且有延迟），要么**挂起回复**——控制台读一行就是这么做的。
但按键服务同时还要**等 IRQ 通知**，而我们的 IPC 没有 select：
一个线程没法同时"等中断"和"等请求"。那就要给 kbd 加线程（IRQ 线程 + 服务线程 +
谁来唤醒谁），要么接受轮询。

推送式没有这个问题：**消费者创建端点，生产者往里发**。
kbd 保持单线程——等 IRQ → 解码 → 发出去；控制台的输入线程阻塞在自己的端点上，
天然事件驱动、零轮询。代价是**这个端点只有一个消费者**（要多个消费者就得加
一个输入多路复用服务，现在没有这个需求）。

这也解释了为什么键盘与块设备/文件系统的接口形态不同：
**块设备是"请求-应答"，按键是"事件流"**。形态跟着语义走，不是跟着习惯走。

### 屏幕是两个线程的共享资源

控制台现在有两条线程（输入 + 服务），屏幕、光标、行缓冲都是共享的。
没有锁会出现：客户端的输出插进用户正在敲的那一行中间、光标残影、行缓冲被撕开。
这类问题**在单核上也会发生**（抢占点就在两条线程之间），不是多核才有的。
所以加了一把进程内的 test-and-set 自旋锁 + `fe_yield()` 退避——
临界区是"画几十个像素"或"改几个字节"，纳秒级；不引入等待队列等更复杂的机制，
因为没有需求。

★ **丢唤醒** ★ 是这里唯一微妙的点：服务线程判断"没有行"准备挂起时，
输入线程可能正好把行放好并判断"没有读者"——两边都以为对方会处理。
所以"检查有没有读者"与"看有没有行"必须在**同一个临界区**里完成，
代码里用 `deliver_line_locked()` 的命名把这条约束写在脸上。

### 写路径做了什么

| 部件 | 说明 |
|---|---|
| `blk_write` | 经 blkd 写扇区（单次 1 个：载荷 = 16 字节头 + 512 字节数据） |
| `fat_set` | 写 FAT 项，**两份 FAT 都写**（只写一份的话掉电后文件系统自相矛盾） |
| `clus_alloc` | 带**分配提示**的空闲簇扫描（每次从头扫的话盘越满越慢） |
| `dir_add` | 往目录里加条目；目录满了就**扩一个簇**挂到链尾 |
| `dir_lookup` / `dir_update_entry` | 定位并改写已有条目（追加、截断、删除都要） |
| `make_8_3` | 名字校验与转换：**不合规就明确报错**，不静默截断 |
| `blk_flush` | 一次操作结束时刷一次（不是每扇区刷——那是 A/B 更新器踩过的坑） |

### 三个刻意的取舍（都写在代码注释里）

1. **只支持 8.3 名字创建。** 长名（LFN）要生成 UTF-16 分片、算校验和、
   做 `NAME~1.TXT` 去重——几百行，价值是"名字更好看"，不是"能不能存东西"。
   不支持时给出明确原因，**不静默失败、不截断**。
2. **不支持空洞写**（跳过文件末尾往后写）。中间的空档填零还是保留旧数据，
   规范里两种都见过——而调用者从不需要它。明确拒绝好过猜。
3. **时间戳写 0。** 没有 RTC，"把当前时间写进去"只能靠瞎编，
   而**瞎编的时间戳比没有时间戳更糟**（看起来像真的）。加 RTC 之后再补。

### 顺带修掉的三个问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | 写受保护区域被报成 "I/O error" | blkd 在保护检查不过时回**空载荷**（请求根本没到设备），设备出错时回 `status=0`。两者对用户的含义完全不同：一个是"设计如此"，一个是"盘坏了"。现在分开报：`blocked: the running slot is write-protected (use /home)` |
| 2 | 屏幕上的 599 字节 abc…xyz | 那是 `contest` 的"接近载荷上限"测试串——**测试数据糊在用户界面上**。现在长载荷照样测，但写完**退格擦掉**；屏幕上只留一行 `console: /dev/console write path OK` |
| 3 | **退格不能跨行回卷** | 为了"擦掉上面那段测试串"才发现：`console_putc` 的 `\b` 在行首就停住了，跨行内容擦不干净。终端的退格本来就该回卷——这是它的语义，不是特例 |

### K2/K3：两个"从来没被执行过"的内核路径（这一轮最值钱的东西）

K3 让"枚举任务"成立，K2 让"进程真的会死"。两件事合起来第一次**执行了
任务的销毁路径**——而那条路一直是死代码：僵尸线程不被回收、对任务的引用
永远不放，`fe_object_destroy` 的任务分支从来没跑过。

第一次跑就掉出两个缺陷：

| # | 症状 | 根因 |
|---|---|---|
| 1 | 每个跑完的程序都留在任务表里（第一次跑 `ps` 时表里躺着二十多个"已退出"），连同端口 / MMIO / IRQ / devfs 名字 / 地址空间一起泄漏 | `fe_sched_reap()` 写好了却**没有任何调用者**；`fe_thread_join` 只释放它自己等的那一个。僵尸**持有任务引用**，所以任务永不销毁 |
| 2 | **销毁一个刚跑完的程序，另一个正在跑的进程（fsd）在自己的代码上取指 #PF**；紧接着 `fe_pmm_free_frames 参数非法: base=0x0` 的 panic | `fe_vmm_space_destroy` 把叶子项背后的帧**一律**还给 PMM——包括内存对象映射的帧（归对象所有，可能有别的任务在映射）和 MMIO（根本不是 RAM）。页表被写坏之后，遍历又把"present 但地址为 0"的中间层项当真表走，`pt_from_phys(0)` 指向物理 0，把低端内存当页表念了一遍 |

修法与完整分析见 `13-tasks-and-kill.md` §5。这里只记**方法学**的部分：

★ 一条被这一轮坐实的判断标准 ★ **"写完了"与"跑过了"是两件事，
而只有后者能让文档里那句"已完成"成立。** 这个项目已经栽过两次同一形状：
K3 的步长错误（没有调用者的 ABI）和这一轮的两个缺陷（没有执行者的路径）。
两次的构建、启动、整机自检**全部通过**。

所以补一条纪律：**新增或修改一个内核机制时，先问"
上一次有人执行这条路径是什么时候"**。如果答案是"从来没有"，
那么它现在的状态是"未验证"，不管它在文档里写成什么。

★ 排查过程本身也有一条教训 ★ 我从"任务被销毁时还有活线程"猜起，
猜了三次（引用计数、CR3、双重销毁）都是错的；每一次都不是靠想,
而是靠**把调用者地址、表指针、项下标打出来**纠正的。
内核带调试信息，所以 `__builtin_return_address(0)` + `llvm-addr2line`
能把"某处释放了物理帧 0"这种毫无指向性的报错直接定位到一行。
**先加一行证据，再改一行代码**——这次的每一步修正都是上一行证据逼出来的。

### D4 收尾：清掉探针，并把"跳过"分成三类

按纪律 2 用 `edit` 逐处删掉了 `blkd` 里的三处 `[blkd·探针]`（grep 复核后为 0）。
同一轮里补上了一个**结构上缺了一格**的东西：一台机器上**没有**某样硬件时，
单元该怎么办。

原来 `init` 只有两种"没启动"：依赖没就绪（**算失败**）、负向测试的预期跳过
（是**测试结论**）。加上 virtio 之后出现了第三种——这台机器上根本没有那个设备。
它与前两种的含义完全不同：既不是缺陷，也不是测试结果。混进去之后
`失败项 N` 这条汇总在 QEMU 和 VBox 上会给出不同的含义，而那正是最容易
让人误判的地方。于是 `struct unit` 多了 `needs` 字段，并在日志里明说：

```
[init] 跳过 vblkd：本机没有 virtio-blk 设备 —— **硬件前提不成立，不算失败**
```

★ 判据顺序也是结论的一部分 ★ 硬件前提必须在**依赖检查之前**判。
因为设备不在时 `/dev/vblk0` 永远出不来，"依赖未就绪"这条判断**必然**也会成立；
先判它，报出来的原因才是真的，否则报的是由它派生的假原因
（"某个服务没起来"）。**报错指向错误的原因，是排查里最贵的一种浪费。**

### 一种最难发现的失败形状：内核自检全过，用户态整个没起来

D4 收尾时 VBox 上出现：内核 11 项自检全 OK，`M5 里程碑自检全部通过`，
而**整个用户态没起来**——init 认领设备管理器身份被拒，接着读未认领的
PCI 配置空间端口触发 #GP，任务被终止。

根因见 `11-kernel-next.md` §9：`fe_resource_note_init` 原先写在
`fe_process_create` 返回**之后**，而新线程在它返回**之前**就已经在就绪队列上。
**QEMU 上从不出现，VBox 上每次出现。**

★ 为什么值得单记 ★ 日志里那两行顺序就是全部线索：

```
[资源] 拒绝：任务 init(14) 不能认领设备管理器
[init] /slot_a/init 已启动（任务 14, 主线程 15）—— 内核到此交棒
```

**用户态的报错出现在"已启动"之前**，说明它在被创建的那一刻就跑了。
如果只看"内核自检通过 + 用户态失败"这个形状去归因，很容易一路查到
设备管理器身份、权限位图、PCI 端口这些**都正确**的地方。
**先看日志的时间顺序，再猜机制。**

### 测试与工具自己错了八处（比被测对象错更难发现）

D4 期间 `blkbench` 有数次"红"，**没有一次**是被测对象的错
（前 5 条出在 D4 那一轮；第 6–8 条是后来几轮各自栽的，来源逐条标注）：

| # | 症状 | 根因 |
|---|---|---|
| 1 | "反向：声明长度大于对象真实大小必须被拒" 一直红 | 断言照着一句**与实现不符的注释**写。实现并不拒、**而且不该拒**（驱动从不写超过 `sectors*512` 的字节，而那个长度已被独立核对 ≤ 对象真实大小）。一个**正确**的驱动被判红。改法：两个方向分开验，都验在真正的护栏上（`buf_len < want`、`want > 对象真实大小`），并改掉那句注释 |
| 2 | "反向：拿普通内存当 DMA 缓冲被拒" 一直红 | 测试代码自己手搓了一遍协议，只传 1 个句柄；而协议里 `handle[0]` 是回复端点、`handle[1]` 才是数据缓冲。驱动于是把普通内存对象当成回复端点，状态码回进了不是端点的地方。**那一版的"失败"说明的是测试自己的 bug。** 改法：调**同一条**请求函数，只换缓冲对象 |
| 3 | 两个吞吐数字都是 `5000 us` | 正好一个时钟刻度。那个时钟粒度是毫秒级，而被测代码本身只有几毫秒，**测出来的主要是时钟**。与 `simdtest` 踩过的是同一个坑（那里两个数字都成了 0 us）。改法：测量用 `rdtsc`，`fe_clock_ns` 只用来标定 TSC 频率；预热 + 取最快；并同时报"周期/KiB"这个不依赖频率假设的数字 |
| 4 | "反向：认领 0x1F0 被拒" 变红 | 断言把设备写死在代码里（当时只对着系统盘跑）。程序现在可以对着任何设备跑，而对 virtio 盘来说 `0x1F0` 与它无关，"认领成功"是**正确**结果。**测试绑死在一个设备上，换设备就报假失败**。改法：按驱动报出的后端类型选判据，判据本身不变 |
| 5 | `check_init.py` 报"单元表与参考不一致"**之后**紧接着打印"均与参考一致" | 成功提示写在了 `if ref["order"]:` 里面，于是它会紧接着两条不一致的告警说"一致"。**一份自相矛盾的报告比没有报告更糟**：只看最后一行的人会以为没事 |
| 6 | ★ **增量构建会骗人** ★ 用备份/`git` 之外的手段覆盖源码后重跑 `python tools/build.py`，**退出码 0、日志里没有任何 error**，但跑出来的内核**还是旧的**：自检仍然是红的、串口里打印着**源码里已经不存在**的字符串。日志干净、构建"成功"，而产物是上一版的 | `Copy-Item` **保留 `LastWriteTime`**，而 `tools/build.py` 的 `newer_than`（`tools/build.py:178-187`，`build_group` 在 `:190-198` 用它决定要不要重编）**只按 mtime 判定**——旧的 `.o` 比"刚被复制过来、mtime 还是老的"源码新，于是**全部被跳过**，构建只是把旧目标文件重新链接了一遍。★ 判据（两条独立证据）：① 旧内核里能打印出**源码中 0 处**的字符串；② `Remove-Item -Recurse -Force build\obj\kernel` **强制全量重编**之后，新内核二进制里那些字符串的计数是 **0**。旁证（另一个代理本轮实测）：假内核 **861664** 字节 vs 真内核 **783832** 字节 ★ |
| 7 | ★ **用 PowerShell 写文件会破坏编码/行尾，把 diff 淹没** ★（**另一个代理本轮实测**）覆盖源码之后 `git diff` 里**看不见真实改动**：整个文件被当成"全文件重写"，只剩一整片 `+`/`−`；极端情况下 git 干脆把它当二进制 | PowerShell 的 `>` / `Set-Content` 往返会改写**编码与行尾**（引入 UTF-16 或 CRLF）。★ 但**不能**用"本仓库统一是 UTF-8 + LF"来防——**实测不是**：`git ls-files --eol` 点出来 **114 个 LF / 82 个 CRLF / 1 个 mixed**（2026-10-01 点数），同一个仓库里两种行尾都有。所以判据只能是"**这一个文件与它在 index 里的样子一致**"：写之前 `git ls-files --eol <file>` 看一眼，写之后再比一次。★ 判据：`git diff` 里应当**只有真实改动**——那一轮的真实改动是 `sched.c 195+/4-`、`schedtest.c 91+`、`main.c 10+`、`sched.h 28+`；出现"整文件重写"就说明编码/行尾被改了，**先修这个再看内容** ★ |
| 8 | ★ **判据可能建立在错前提上** ★（**提出者自述、实现时核实**）要求"`mprotect` 不许绕过写保护"，而这条判据**无处落地**：`kernel/protect.c` 的保护清单收的是**磁盘 LBA**（`fe_protect_add(lba, count, …)`），而 `mprotect` 改的是**虚拟地址**——两个地址空间，今天不存在"内存地址 ∈ 保护清单"这种关系。它不是"没通过"，而是**前提就错了** | ★ 教训：**写判据之前，先核实它所指的两个东西是不是真的在同一个空间里** ★ 判据与实现都"看起来对"的时候，错的前提**不会被任何断言抓到**（两边都通过、都合理）。处理：撤回该判据，换成真正该挡的边界（范围落在**同一个 VMA** 内 + **W^X**，`kernel/mm/vma.c:242-284`，并在那里写明"第三条边界不存在"，免得下一个人再查一遍）。★ 同族第二例：**"本仓库统一是 UTF-8+LF"** 也是错前提（实测 `git ls-files --eol` = 114 LF / 82 CRLF / 1 mixed，见第 7 条）——两例的共同形状是"**把一个来自别处的常识当成了本仓库的事实**" ★ |

★ 这八条的共同教训 ★ **测试也是代码，它说的每句话同样要有证据。**
第 1 条尤其值得记：**注释承诺一个不存在的护栏，比没有注释更糟**——
它会让后来的人（包括写断言的我自己）以为那道墙在那儿。

### 三条同族的方法论（"判据比意图宽松"这一族）

上面第 6 条与下面两条是同一族错误：**不是被测对象错，也不是测试代码写错，
而是"这次验证根本没有验证到它想验证的东西"。** 它们的共同形状是
**判据比意图宽松**——断言看起来在测某件事，实际测的是更弱的一件事。

**（一）增量构建：验收看产物，不看退出码。**
第 6 条的完整做法：
- **覆盖源码之后必须强制重编**（`Remove-Item -Recurse -Force build\obj\kernel`，
  必要时连 `build\obj` 整个删掉）——因为 `Copy-Item` 保留 mtime，
  而 `newer_than` 只认 mtime；
- **验收方式改成"在产物里找符号/字符串"**，而不是"看 build 的退出码"：
  用 `[System.IO.File]::ReadAllBytes` + 索引查找（与本节上面那条
  "核查手段很便宜"是同一个手法）。字符串**在**产物里而日志里没有
  ⇒ 不是构建问题；字符串**不在**产物里 ⇒ 先修构建，别急着推断机制。
- 一句话：**"构建成功"与"跑的是新代码"是两件事**，中间隔着一个 mtime。

**（二）"把修复和判定同时做掉"= 这次验证作废。**
实例（`kernel/task/process.c:577-591` 的注释记着全过程）：自检探针收尾时，
`keep` 参数原来传 `NULL`；后来**同时**把它改成 `fe_thread_current()`、
**并且**加了"调用者不该被标记"的断言。于是断言**再也不可能触发**——
`keep = self` 本身就保证了 `self` 不被标记，那次"否证"是**假否证**：
它证明的是"我传对了参数"，不是"旧行为有问题"。
正确做法：**先把断言加上、保持旧行为跑一次**（这一次才真正证明或否证），
再改行为。重做时的做法就写在那段注释里：把 `keep` 临时改回 `NULL`、
断言留在原地——这次打印里第一次出现
`收尾：D1（任务 d1-notify id=26，清前共 1 个线程）的 1 个探针已清理`，
**假设到此才算真正被否证**。
- 一句话：**一次实验只能改一个变量**；"修复"与"判定"是两个变量。

**（三）"非 NULL"不是判据，"等于谁"才是。**
实例：一条反向对照用 `took != NULL` 判定"等待者拿到了锁"，而那个
`took` 是从 `fe_resource_lock_holder()` 读回来的——**一个悬空指针也能满足
`!= NULL`**，于是断言**假绿**。改成"holder 必须等于那个**活着的**等待者线程"
之后它才如实变红。今天树里两种写法都还在：
`kernel/resource.c:882` 已经是钉死身份的形式（`CHECK(took == c)`），
而 `kernel/resource.c:1029` 仍是 `CHECK(took != NULL)`——**它属于同一族、
但还没改成钉身份的形式**，下一次碰那一处时应该一起改掉
（写成 `took == z`，或至少断言那个指针对应的线程仍在册且状态正确）。
- 一句话：**凡是"存在 / 非空 / 变了"这类判据，都要再问一句"是哪一个"。**

★ 这三条为什么值得单列 ★ 它们的代价不在"抓不到 bug"，而在**"以为抓到了"**：
表里第 6 条（增量构建）让人对着旧内核调了半天新代码；（二）留下一条
**永远不会响**的断言（比没有断言更危险：它看起来像一道墙）；
（三）让一条本该变红的对照假绿，把一个真缺陷放了过去。
**验证本身也是要被验证的。**

### 测量的中立性：**诊断打印也是被测系统的一部分**

★ 这一条**不属于**上面那一族 ★ 上面三条说的是"**判据太弱**"（测的不是它想测的
东西）；这一条说的是"**观测动作本身改变了被测对象**"——属于*测量没有中立性*。
两者都让断言看起来通过，但修法完全不同：一个要改断言，一个要改**测量手段**。

实测（**另一个代理本轮实测**；原文同时留在 `kernel/sched/sched.c:47-53` 的注释
与那次提交的说明里）：

- 串口是**轮询输出**（`fe_serial_putc` 忙等 THR），**一行要上百微秒到毫秒**，
  而节拍是 **1 ms**——在调度路径上打一行，等于给那一次调度**插进一个"时间片"**；
- 于是：**加了诊断打印之后，同一段基准的切换数从 10 万涨到 24 万**。
  也就是说，那一轮"公平性变差了"的结论里，有一部分是**打印自己造成的**。

**结论（可以直接照抄的规矩）**：

1. **"公平性 / 代价"这类判据最终只能用计数器**——每次切换只加几个数、
   几十条指令、**不打印**；打印只能用于**定性定位**（"是谁被选中 / 谁没被选中"），
   不能用来量代价。落地形状：`sched.c:44-69` 的那组 `g_st_*` 公平性计数器
   （`g_st_picked` / `g_st_switched` / `g_st_idle_run` / `g_st_kept_lower` …），
   以及 `fe_selftest_yield()` 的判据——**让出 2000 次所用的节拍数 ≤ 8000**
   （`kernel/sched/schedtest.c:436`，已挂在 `main.c:617`）。
2. **诊断打印要有闸门**：只在"可疑窗口"里打、且**限量**（看门狗与选人记录都是
   `最多 64 行`）——否则串口本身就成了被测系统里最大的那个噪声源。
3. **量代价用"时间/计数"，不要用"轮数"**：轮数是循环变量，被饿的时候它一个不少，
   只是每轮等很久（同一轮排障里踩过：`20000 轮让出`看起来像时间预算，
   实际上什么都不是；`schedtest.c:418-421` 把这条写进了注释）。
4. ★ 与表里第 3 条的区别 ★ 第 3 条（两个吞吐数字都是 `5000 us`）是"**尺子太粗**"；
   这一条是"**尺子会碰坏被测物**"。两者都不该用"看起来通过了"当结论。

另有一处是**驱动**的错，但它只在反向对照里显形：越界 LBA 那一支把应答回在了
`reply` 上，而 `reply` 是内核在 `call` 路径给的回复能力；批量读走的是 `send`
（它才能带句柄），这条路上 `reply` 根本无效。于是应答被扔进不是端点的地方，
客户端永远等不到——症状是**越界读把整个程序挂住**，而不是"越界读被拒"。
正向路径每一支用的都是 `client_reply`，所以怎么测吞吐都是好的。
