# 写保护：强制点与接口设计（M8 后半 · 步骤 1）

> 本文只定**写路径的强制点与接口**，不含实现。
> 上游设计见 `03-protection.md`（WRP + WFP 两代机制移植）。

## 1. 先把威胁模型摆清楚

| 攻击者 | 能做到什么 | 这一道挡得住吗 |
|---|---|---|
| **A. 被替换/有 bug 的 `fsd`** | 通过 blkd 写任意 LBA。FAT32 解析器是巨大攻击面 | ✅ **挡得住**——这是本道防线的主要目标 |
| **B. 被替换的 `blkd`** | 直接操作 ATA 端口，自己发写命令 | ❌ 挡不住（见第 2 节）→ 靠第 3 道防线 |
| **C. 高权限客户端程序** | 只能通过 fsd 写，无法直接接触块设备 | ✅ 挡得住（它连 blkd 的句柄都没有） |
| **D. 被替换的内核** | 一切 | 不在范围内 |
| **E. 物理接触 / 离线改盘** | 直接改扇区 | ❌ 挡不住 → 靠第 3 道防线 |

## 2. 强制点在哪里（这是本设计最重要的一句话）

> **强制点是 `blkd`，不是内核。**

原因是硬件事实，不是设计取舍：ATA PIO 的端口是**读写同体**的，
内核没有办法让一个任务"能读这个设备但不能写它"。端口权限位图是整段授予的，
而 blkd 要发读命令就必须能写命令寄存器。

所以内核能提供的是**策略**（哪些扇区受保护、谁都不能改），
blkd 提供的是**执行**（每次写之前问内核一次）。内核无法阻止一个不问的 blkd。

这不是缺陷，而是**用户明确选定的边界**（"blkd 持控制器，内核做写白名单"）。
把它写清楚比含糊过去重要——含混的边界会让人以为得到了比实际更强的保证。

**这样安排仍然值得做**，因为：

- 攻击面从"一个 FAT32 解析器"缩小到"一个几百行的 PIO 驱动"；
- **策略住在内核内存里**，fsd 改不了、客户端改不了、也没有配置文件可以被编辑；
- 接口与将来换 AHCI/DMA 时一致——那时若内核接管命令队列，同一套接口不用改。

## 3. 接口

### 3.1 内核侧：受保护区间表

```c
/* 保护模式。目前只有一种；留给将来（如"只读"vs"连读都禁止"）。 */
#define FE_PROT_DENY_WRITE  1u

#define FE_PROT_MAX_EXTENTS 64

/* 登记一段禁止写入的扇区区间 [lba, lba+count)。
 * 需要保护能力（见 3.3）。与已有区间重叠会被拒绝（FE_ERR_EXIST），
 * 保证表里永远是一组互不相交的区间，检查逻辑因此可以是简单的线性扫描。 */
fe_status_t fe_protect_add(u64 lba, u64 count, u32 mode);

/* 解除保护。**本轮不给任何任务这个能力**——登记之后谁都解不开，
 * 这就是"谁来了都删不了"的字面含义。将来由签名更新包触发。 */
fe_status_t fe_protect_remove(u64 lba, u64 count);

/* 写入前检查。[lba, lba+count) 与任何受保护区间**相交即拒绝**。
 * 返回 FE_OK 或 FE_ERR_ACCESS。与调用者是谁无关——不看任务、不看权限，
 * 只看表。这样"谁能写"就完全由表决定，没有第二条判断路径。 */
fe_status_t fe_protect_check_write(u64 lba, u64 count);

/* 违规记录：拒绝了谁、想写哪里、什么时候。 */
struct fe_protect_violation {
    u64 task_id;
    u64 lba;
    u64 count;
    u64 tick;
};
u32 fe_protect_get_violations(struct fe_protect_violation *out, u32 cap);
u64 fe_protect_violation_count(void);
```

系统调用号（沿用现有的分段习惯）：

```c
FE_SYS_PROTECT_ADD    = 0x70,   /* (lba, count, mode) */
FE_SYS_PROTECT_CHECK  = 0x72,   /* (lba, count) -> 0 / FE_ERR_ACCESS */
FE_SYS_PROTECT_STAT   = 0x73,   /* 取违规记录 */
/* 0x71 留给 REMOVE，本轮不实现 */
```

### 3.2 blkd 侧：唯一的改动

```c
static int ata_write_sector(u32 lba, const u8 *in)
{
    /* ★ 在碰端口之前问内核。★
     * 位置很关键：放在这里而不是放在 fsd 里——fsd 是被怀疑的那一方，
     * 让被怀疑者自己检查等于没检查。 */
    if (fe_protect_check_write(lba, 1) != FE_OK) {
        return -1;              /* 内核会记下这次违规 */
    }
    ... 原来的 PIO 写序列 ...
}
```

写请求走和读一样的 IPC 协议，新增 `BLK_OP_WRITE`。

### 3.3 谁能登记保护

两个选项：

**(a) 能力对象**：内核在启动时造一个保护对象，只把带 `FE_RIGHT_PROTECT` 的句柄装进 init 的句柄表。
    只有 init（以及它显式转交的对象）能登记。与"能力不可伪造"一致，可撤销、可转交。

**(b) 硬编码 `task == init`**：更简单，但把"谁可信"写死在代码里，且无法表达转交。

**倾向 (a)**。新增 `FE_RIGHT_PROTECT = (1u << 9)`，`FE_RIGHT_ALL` 相应改成 `0x3FF`。
需要新增对象类型 `FE_OBJ_PROTECT`——它本身不承载数据，只是能力的载体。

## 4. 受保护区间从哪来（这里有个容易踩的坑）

### 4.1 为什么不能"编译进内核"

直觉上最硬的方案是把区间表编进内核镜像（改它就得重编内核）。
但这里有个**两遍构建**问题：

```
编译内核 → 内核大小决定镜像布局 → 布局决定受保护文件的簇号
        → 簇号要编进内核 → 内核大小变了 → 布局又变了 → …
```

除非引入收敛检测与迭代构建，否则拿到的是一份**上一轮的**布局。

### 4.2 采用：`mkfat.py` 生成清单，作为引导模块随镜像一起加载

```
1. build.py 编内核与用户程序
2. mkfat.py 建镜像，**同时**生成 /etc/protect.list，内容是受保护区间的
   LBA 列表，以及每个区间对应哪个路径（给人看）
3. Limine 把 protect.list 当作**模块**加载（与用户程序一样）
4. ramfs 暴露它 → init 读它 → 调 fe_protect_add() 逐条登记
```

**没有收敛问题**：清单是在建镜像的过程中生成的，描述的就是**这一次**的布局，
两者天然自洽。

**顺序保证**：init 在**拉起任何服务之前**登记保护（此时 blkd 还没运行，
不存在"保护生效前先被人写一笔"的窗口）。

**边界（诚实说）**：protect.list 是从磁盘加载的，能写磁盘的人可以改它。
这一道因此只挡到"blkd 之下"——正与第 1 节的威胁模型一致。
封死它要靠第 3 道防线（清单签名 + 内核内置公钥），那时清单本身的签名由内核验。

## 5. 保护范围的口径

要防的是"删不掉"，而删一个文件有三条路：删目录项、改 FAT 链、改数据。
所以区间必须覆盖**目录项所在扇区 + FAT 项所在扇区 + 数据簇**。

FAT32 的目录项是 32 字节，而块层粒度是 512 字节扇区——存在**粒度不匹配**。
三个口径：

| 口径 | 内容 | 代价 |
|---|---|---|
| **(a) 保护"系统区"** | `/bin`、`/sbin`、`/boot`、`/EFI`、`/init` 及其目录项与 FAT 项；只留 `/home` 可写 | 同扇区里的无关文件被连带保护（本镜像里系统目录本来整个都要保护，所以不亏） |
| (b) 精确到文件 | 每个受保护文件的簇 + 它那条目录项所在扇区 | 目录项与无关文件同扇区时仍然连带；实现复杂得多 |
| (c) 保护 FAT 与全部目录区 | 只留数据区可写 | 连"新建文件"都不行，fsd 没法验证写路径 |

**倾向 (a)**：语义与 WRP 一致（系统文件受保护、用户数据不受），
实现是"扇区区间的集合"，正好是块层能表达的粒度。

> ★ 与 `mprotect` 的边界（2026-10-01 补记，只加这一句）★ 本节说的"受保护区间"
> 全部是**磁盘 LBA 区间**（`fe_protect_add(lba, count, …)`，`kernel/protect.c`）；
> 它与虚拟地址是**两个不同的地址空间**，今天**不存在**"内存地址 ∈ 保护清单"
> 这种关系——所以 `mprotect` 那条路上**没有可判的交集**，它挡的是另外两条边界
> （范围必须落在**同一个 VMA** 内 + **W^X**，见 `kernel/mm/vma.c:242-284`）。
> 若将来真要有"某段**内存**受保护"，那需要**另立机制**（保护对象是物理帧或
> 虚拟区间，不是 LBA）。完整记录见 `11-kernel-next.md` §12 的
> "一条被撤回的判据"。

## 6. 违规之后

本轮（最小但完整）：

1. **拒绝**写入，向 blkd 返回 `FE_ERR_ACCESS`，blkd 向 fsd 返回 I/O 错误；
2. **记录**到内核里的环形缓冲（任务 id、lba、count、tick）；
3. **打印**一条醒目日志（带限速，避免被刷屏）。

将来：违规时向一个监控服务发通知（`fe_notification_signal` 到约定的位），
由它决定是否杀掉那个服务。**本轮不做**——在没有监控服务之前先做，
只会多一条没人看的信号。

## 7. 验证方案（这一条是承重的）

新增一个**负向测试**程序 `/bin/protwrite`：

1. 通过 devfs 打开 `/dev/blk0`；
2. 读一个**受保护**扇区，把内容存下来；
3. 尝试写同一个扇区（改一个字节）；
4. 读回来，**必须与步骤 2 的内容逐字节相同**；
5. 读内核的违规计数，**必须增加了 1**。

第 4 步是磁盘层面的证据，第 5 步是内核层面的证据。**两步都要有**：
只有第 4 步的话，"写失败了"也可能是 PIO 写坏了；只有第 5 步的话，
"内核记了一笔"不代表盘上没被改。

同时加一个正向对照：往**非保护**区（`/home`）写一个扇区，必须成功——
否则无法区分"保护生效"与"写功能整个是坏的"。

## 8. 决策记录

| # | 问题 | 决定 |
|---|---|---|
| A | 保护范围口径 | **系统区**（`/bin` `/sbin` `/boot` `/EFI` `/init` 及其目录项与 FAT 项），只留 `/home` 可写 |
| B | 解除保护 / 签名更新包 | **不做签名，也不做密钥文件** —— 见下面的说明 |
| C | 违规响应 | 拒绝 + 记入内核环形缓冲 + 醒目日志 |
| D | 清单缺失或表为空 | 放行 + 醒目告警；部分重叠一律拒绝 |

### 关于 B：为什么不做签名

原计划是"签名清单 + 内核内置公钥"，让清单本身不可伪造。**撤回了**，理由：

1. **内核里手写密码学是大忌。** 裸机内核没有库可链，要么自己实现 RSA/Ed25519
   （上千行大数运算与域运算，每一个细微错误都是静默的安全漏洞），
   要么不做。这不是"工作量"问题，是"不该由我在这里做"的问题。
2. **密钥文件不该进这个仓库。** 私钥落在项目目录里，等于把信任根放在了版本控制里。
3. 真要做的时候，正确的位置是**用户态服务**——它可以链接现成的密码库
   （`cryptography` / libsodium / monocypher 之类），而不是让内核去实现密码学。
   那时内核只提供"验证结论存哪里、谁能读"的机制。

### 因此这一道防线的真实边界（诚实说）

`/etc/protect.list` 是从磁盘加载的、**没有认证**，所以：

- ✅ 挡得住：被替换的 `fsd`、被替换的客户端、任何软件层的高权限程序。
  **它们无法让 blkd 写受保护扇区**——这是本道防线的主要目标。
- ❌ 挡不住：改写了磁盘上 `protect.list` 的人（下次引导保护范围就变了）、
  被替换的 `blkd`（它可以直接不问）、离线改盘。

后三者属于第 3 道防线（内容哈希 + 发现篡改），而第 3 道防线**同样不需要内核做密码学**：
哈希与验签都可以放在一个用户态服务里，内核只需要保存"哪些组件被判定为完好"这个结论。

### 一条顺带得到的性质：保护是**单调**的

因为不做签名、也就不做更新包，所以**本轮没有"解除保护"这条路径**——
`fe_protect_add` 只能让保护更严，永远不会更松。

这带来一个意外的好处：**"谁能登记保护"这个问题消失了**。
只能加不能减的接口，开放给任何任务都是安全的（最坏情况是某个任务多保护了一段扇区，
那是让它自己更难写，不是攻击）。所以不需要为它设计能力对象，
也就少了一层"谁是可信的"的判断——而那种判断正是最容易出错的地方。
