## 1. 口径：什么是"内核侧补全"，它与"做一个 POSIX 系统"差在哪

### 1.1 两件事，不是程度不同的同一件事

| | 做一个 POSIX 系统 | 本项目要做的 |
|---|---|---|
| 交付物 | 一个**操作系统**：内核 + libc + shell + 工具 + 服务 | **一个内核**（`00-architecture.md:4`：本项目做的是内核，不是操作系统） |
| 依据什么 | 一个具体实现的**行为**（"它这么做，我也这么做"） | ★ **公开标准（POSIX，IEEE 1003 / ISO 9945）的规范条文** ★ 见 §1.2 |
| "POSIX 完整"的含义 | 用户拿得到 `fork`/`kill`/`poll`/`pthread` 这些**接口** | 内核**不再阻塞**这些接口的实现（= 支持 POSIX 标准所要求的**机制**） |
| 谁写用户态那一半 | 我们 | **不是我们**（第三方也可以拿这套内核去写真正的 POSIX 层） |
| 本文的判据 | 一个程序能跑 | **每一条"用户态做不到"的机制，内核里都有，且都有可证伪的判据** |

**为什么这不是文字游戏**：一个内核可以**机制齐备**而 POSIX 层一行都不写
（今天的 `user/libposix` 就是半成品，而它在本项目里的身份是**测试客户端**——
`10-posix-layer.md` §5 的分层、`11-kernel-next.md` §5 的定位）。
反过来，一个 POSIX 层写得再全，也变不出内核没提供的东西：
`pthread_join` 等不到线程（今天 `fe_thread_create` 只返回一个 id）、
`pthread_cond_wait` 睡不下去（今天没有"等一个用户地址"）、
`mmap(fd)` 拿不到页（今天 VMA 没有文件后备，`kernel/include/fe/mm/vma.h:54-58`）。
**这三条都不是"多写点用户态代码"能补的。**

### 1.2 ★ 口径：支持 POSIX **标准** ≠ 向 Linux 靠拢 ★

★ **这一节是 2026-10-01 用户明确的口径纠正，与 §1.1 那条（内核侧补全）
是两件事，必须一起读** ★

> **POSIX 在本项目里的定位是「支持一个公开标准」，不是「向 Linux 靠拢」。**

**一句话把两者的关系写死**：

> ★ **支持 POSIX ≠ 向 Linux 靠拢：POSIX 是公开标准（IEEE 1003 / ISO 9945），
> Linux 是它的一个实现；本项目按规范实现，不抄实现。** ★

#### 1.2.1 用词（写文档与代码注释时统一照这个）

| 用 | 不要用 |
|---|---|
| "支持 POSIX 标准" / "POSIX 标准要求的机制" / "按标准实现" | ~~"POSIX 兼容"~~ / ~~"向 Linux 对齐"~~ / ~~"Linux 兼容性"~~ / ~~"像 Linux 那样"~~ |

★ **为什么"兼容"这个词要避开** ★ 它在中文技术语境里几乎总是指"二进制/行为
兼容某个**具体实现**"（"Windows 兼容"、"Linux 兼容"）。而本项目的目标是
"**按一份公开规范实现能力**"，不是"表现得像某个具体内核"。用词会反过来
塑造设计："兼容 Linux"的下一句几乎必然是"那 Linux 怎么做？"，
而"按标准实现"的下一句是"规范条文怎么写的？"——**这两个问题会导出不同的设计**。

★ 一个立刻能看见的差别 ★ POSIX 标准**允许**实现有扩展，而"向某个实现靠拢"
会把那个实现的**扩展**也当成要求。§1.2.4 把这条变成了逐条适用的判据。

#### 1.2.2 为什么这条与项目铁律一致（不是例外，是同一件事）

本项目**已经在别的领域这么做了**：这些全部是**按公开规范实现**的，而且
一条代码都没有抄——

| 领域 | 按哪份公开规范 |
|---|---|
| FAT32 磁盘格式 | 公开的 FAT 规范（`00-architecture.md:231` 的"允许"清单里逐字列了它） |
| Limine 引导协议 | 引导器的**公开接口**（同一行清单；内核只通过 `.limine_requests` 段拿信息，`00-architecture.md:49`） |
| PCI / USB / xHCI | 公开的总线与设备规范（`12-drivers.md` 的 D3/D8 全按这个做；`19-usb.md`） |
| TCP/IP | RFC（`00-architecture.md:231` 的同一行清单） |

**POSIX 只是同一类东西：一份公开标准。** 所以：

> **"支持 POSIX"与"不抄任何现有内核"不冲突。两者的分界线是：
> 规范可以读、可以按它实现；实现不许抄。**

这条分界线与 `00-architecture.md` §8 的边界声明**逐字一致**
（`:227-232`："实现代码 100% 本项目自研"；"**允许**：……CPU 手册规定的数据结构……
FAT32 公开规范、TCP/IP RFC"；"**禁止**：复制 Linux/BSD/其它内核的任何 C 代码
或数据结构设计"）。★ **本次口径纠正没有放宽 §8 一个字** ★

#### 1.2.3 哪一条边界仍然有效（不要被上一条冲掉）

★ **"支持标准"约束的是能力清单，"不靠拢 Linux"约束的是实现形态；
两者一起写才完整。** ★

| 仍然有效 | 出处 |
|---|---|
| ★ **不做 Linux 二进制兼容** ★ 不实现 Linux 的 syscall 号空间、不实现 Linux 的 ELF 加载约定、不实现 `/proc` 的布局 | `10-posix-layer.md:21` 与 `:28-31`（"不是 Linux 二进制兼容"这半句**一个字都没动**）；§1.2.5 逐条展开 |
| ★ **内核里不出现 POSIX 的名字** ★ 内核不认识 `open`/`errno`/`SIGKILL`，只认识句柄/端点/通知/任务；一旦出现 `#define O_CREAT`，这条路线就变成"把 Linux 抄进来" | `10-posix-layer.md:128-131` 与本文 §1.4 |
| **内核提供机制、POSIX 的语义留在用户态** | 同上；`10-posix-layer.md` §5 的边界表 |

★ 换句话说 ★ **"支持 POSIX 标准"要求的机制，几乎全部是"用户态做不到的那一半"
（这正是 §2 主表列的东西）；而"不靠拢 Linux"要求的是：那些机制在**内核**里以
中性的形式存在（等待对象、句柄、通知、页表），而不是以 Linux 的接口形式存在。**

#### 1.2.4 ★ 一条必须逐条执行的判据：标准要求 vs Linux 的附加行为 ★

本文每一条都要能回答一个问题：

> **这条要求是 POSIX 规范里写的，还是某个实现（Linux）自己加的？**

| 判定 | 怎么做 |
|---|---|
| **规范要求** | 做（如果它是"用户态做不到"的那一半），并在本文里给出**规范层面的理由** |
| **某个实现的附加行为** | ★ **不做** ★ 并在本文里**明写它是附加行为**——不许含糊过去 |

★ 已经用这条判据筛过的两处（正文里各有一处）★

| 项 | 判定 | 处理 |
|---|---|---|
| **`mremap`** | ★ **不是 POSIX 接口**（POSIX 里没有它，它是 Linux 专有） ★ | 见 §2.16：**不以"POSIX 完整性"为理由做它**；将来某个具体程序（Qt/libc++ 的分配器）真的用它，那时按"有一个具体程序因此跑不了"的纪律评估 |
| **`/proc` 的布局** | ★ **Linux 的附加行为**（POSIX 没有规定 procfs） ★ | 见 §2.17：不做；真要它，它是**用户态服务**在 VFS 上拼出来的，数据源是 `TASK_LIST` |

★ **这一条正是用户这次纠正要防的东西**：如果某条要求**本质上只能靠"照某个
实现的做法"才能满足**，本文必须如实写出来（并说明是哪一半），而不是把它混进
"POSIX 要求"里悄悄做掉。★ **本文到目前为止没有发现"只有照 Linux 才能满足"
的 POSIX 要求**；发现一条就补一条，并同时写清"这是标准要求"还是"这是 Linux
的附加行为"。★

#### 1.2.5 依据公开标准，而不是依据某个实现（三条今天就能核对的分界）

★ 这一节把 §1.2 的口径变成**可核对的三条**——判据是"这条边界今天的代码在哪一行"。★

**(1) syscall 号空间是**我们自己的**。**
`kernel/include/fe/syscall.h:1-2` 逐字写着："FEKernel 系统调用 ABI
（**自定义，刻意区别于 Linux/POSIX**）"；`00-architecture.md:96` 同一条。
★ 后果要说清 ★ 一个**按 POSIX 写的程序**（源码级）不需要知道任何 syscall 号——
它调 `write()`，而 `write()` 是 libc 的事。**只有二进制兼容才需要号对上。**
→ 所以"支持 POSIX 标准"**不需要** Linux 的号空间，而"实现 Linux 二进制兼容"
**必须**要它（那正是 `10-posix-layer.md:21` 的"不是"一行拒绝的东西）。

**(2) 可执行文件格式的**加载约定**是我们自己的。**
内核的 ELF 装载器按自己的约定处理（`kernel/ld/elf.c` 的段登记、`PT_TLS`
处理见 `11-kernel-next.md:119-120`），初始栈按 System V AMD64 psABI 的**通用**
约定摆放（`kernel/include/fe/process.h:14-19`）。
★ 这里要区分两件事（**最容易混的一处**）★

| | 判定 |
|---|---|
| "初始栈上 `argc/argv/envp` 怎么摆" | ★ **是 ABI 惯例，不是 Linux 特有的约定** ★ 它由 System V AMD64 psABI 规定，而 POSIX 层的 `_start`（`user/libfe/start.asm`）必须按它写。**它不构成"Linux 二进制兼容"**（兼容 Linux 二进制要的是"Linux 的 ELF 解释器路径、`auxv`、`AT_*` 一整套"）。★ 注意 `user/libfe/start.asm:4-9` 的注释写的是"内核按 **Linux x86-64 的约定**摆好初始栈"——**那是行文方便，不是设计依据**；同一条约定的正式出处是 psABI，而本项目是 `-ffreestanding -nostdlib`，与 glibc 无关 ★ |
| "内核从哪装载、怎么找 `/init`" | ★ **我们自己的** ★ 内核从 ramfs/引导模块装载（`00-architecture.md:29-30`），路径与槽位（A/B）由**我们**的引导链决定 |

**(3) 没有 `/proc`，也不需要它来做"支持标准"。**
**没有 procfs**（`16-selfhost-path.md` 的头文件核对表里没有它；
`10-posix-layer.md:268` 记着它的一个后果："POSIX 里没有'我在哪'的接口（没 procfs）"）。
★ **POSIX 标准不要求 procfs** ★ ——它要求的是 `sysconf`/`uname` 这一类接口，
而那些可以走一条**只读的系统自述 syscall**（K8，§2.11）。
→ **"支持标准"不会把我们推向 `/proc` 的布局**；`/proc` 的布局是 Linux 的附加行为
（§1.2.4 的第二行）。

### 1.4 内核对 POSIX 的态度：提供机制，不认名字

★ **既有硬规则，本次不变** ★（`10-posix-layer.md` §5 末尾那段）：

> **内核里不出现 POSIX 的名字。** 内核不认识 `open`、`errno`、`SIGKILL`；
> 它只认识句柄、端点、通知、任务。一旦内核里出现 `#define O_CREAT`，
> 这条路线就变成了"把 Linux 抄进来"（★ 在 §1.2 的口径下这句话也可以读成：
> **标准里的语义不该被搬进机制层**——两条读法指向同一条分层纪律 ★）。

所以本文所有条目都按同一个形状落地：

```
POSIX 标准要求的语义（用户态，libposix 或第三方）  ← "SIGTERM 该杀谁" / "errno 填什么"
        ↓ 只能经由已有的机制表达
内核的机制（不认识 POSIX）                      ← 句柄 / 端点 / 通知 / 等待 / 页表
```

**这条规则直接决定了机制该怎么设计**，不是一句自律口号。三个现成的例子：

1. **信号**：内核不该有 `signal()`、也不该有 `SIGTERM`。它该有的是
   "**把一次异常现场/一次终止请求交给一个端点**"的投递点（K5 就是这个，
   `18-user-fault-handler.md` §2.0）。`SIGTERM` 用哪一号、要不要屏蔽、
   `EINTR` 之后重不重启系统调用，**全是用户态的表**。
2. **fd 继承**：内核不该有 fd 表（它今天确实没有，`10-posix-layer.md` §2 的
   实地勘察结论）。它该有的是"**spawn 时随任务句柄一起安装一组初始句柄**"。
3. **`sysconf`**：内核不该回答 `_SC_OPEN_MAX`（那是 libc 的常量），
   它该回答"**物理内存有多少页、有几个 CPU、一页多大**"（K8，
   `10-posix-layer.md:78`）。

★ 反过来也要说清楚 ★ 有些条目**看起来**像内核缺口，其实是纯用户态的事，
本文把它们明确标成"用户态"，免得"内核侧补全"变成"把 libposix 的活搬进内核"。
判断标准只有一条：**用户态**能不能**单独**做到（不依赖"内核恰好没提供的那件事"）。

## 2. 主表：POSIX 要什么 / 内核要给什么 / 今天有没有

### 2.0 怎么读这张表

- **归属**只有三种：**内核**（用户态单独做不到）、**用户态**（内核不该碰）、
  **两者**（内核给机制、用户态给语义）。
- **"今天有没有"**一列只写**我读到的**（`文件:行号`）；没有读到的写"待查"。
- ★ **每一节末尾都有一行"标准判定"** ★（★ 2026-10-01 按 §1.2.4 的判据补的 ★）
  它回答**同一个问题**：**这一条是 POSIX 标准里写的，还是某个实现（Linux）自己加的？**
  三种取值，处理方式完全不同：

  | 判定 | 怎么做 |
  |---|---|
  | ★ **标准要求** ★ | 做（如果它是"用户态做不到"的那一半）；做不到就是**要如实声明的缺口**，**不许**用"标准没要求"抹掉 |
  | ⚠ **不是标准（某个实现的附加行为）** | ★ **不做** ★ 并明写它是附加行为（今天属于这一类的：`epoll`、`timerfd`、`mremap`、`ptrace`、`/proc` 的布局、Linux 的 `signalfd`/`SA_RESTORER`） |
  | ⚠ **我们的实现形态 / 实现限制** | 既不是标准要求、也不是"不做"：**标准只规定可观察语义，形态是我们的选择**（例如"内核不认 fd""缺页不在内核里同步读文件""`FE_VMA_MAX = 32`"）。★ 这一类要写清"它带来什么代价"，但**不能**记成缺口 ★ |
  | ❓ **待查** | 我读到的证据不足以判定时如实写"待查"，并在 §6 记一条 |

  ★ 这三者的分界正是 §1.2.3 那句话：**"支持标准"约束能力清单，"不靠拢 Linux"
  约束实现形态** ★ ——所以**只有第一类才是"要做到的能力"**，
  第二类是**明确不做**，第三类**做了也不算"像 Linux"**。
- ★ **本文的重要发现都写在"与候选描述不符"的小节里** ★ 它们比"某条做没做"
  值钱：用户给的清单是候选，**以代码为准**。

### 2.1 `fork` / COW —— POSIX 完整性**不必须**它

**事实（我读到的）**：

- "没有 fork"是**写下来的设计决定**，不是遗漏：`kernel/include/fe/process.h:10-12`
  逐字写着"**没有 fork**。Linux 自己也在往 posix_spawn 上靠（glibc 就是用
  `clone(CLONE_VM|CLONE_VFORK)+execve` 实现的），而微内核里复制整个地址空间
  既昂贵又没什么用——服务之间共享数据走 IPC 与内存对象，不靠继承"。
  ★ 注意这里的"Linux 自己也在往 `posix_spawn` 上靠"是**论据**，不是**依据**：
  依据是 POSIX 标准里 `posix_spawn` 与 `fork` 是**两个并列的**接口
  （§1.2.4 的判据：支持标准 = 提供标准要求的机制，不是模仿某个实现的做法）★
- 同一条在 `10-posix-layer.md` §4（第 84-102 行）展开过，
  用户态那份实现明确写着它提供的是 `posix_spawn` 而不是"用 spawn 冒充 fork"
  （`user/libposix/spawn.c:4-8`）。
- `kernel/sched/sched.c` 里**没有**任何写时复制路径的证据：我读到的 `fe_vmm_map`
  调用点全部是"新分配一帧然后映射"（`kernel/task/user.c:481`、
  `kernel/task/user.c:475-490` 的预映射循环），没有"共享父页 + 置只读"的形状。
  ★ 严格地说：我只能说"我没读到 COW 的实现"，**全仓有无 COW 字样的完整核实
  见 §6 待查第 1 条**（不要把"没读到"说成"不存在"）。

**COW `fork` 要付的代价（逐项，不是一句话）**：

| 要新增什么 | 为什么 `posix_spawn` 换不来 | 谁来付 |
|---|---|---|
| 页表复制 + 逐页置只读 + COW 位（`FE_PTE_*` 里加一位） | 复制整棵用户页表是**新的页表层机制**（今天只有 `fe_vmm_map`/`fe_vmm_protect`） | 内核 |
| 每一级页表在写时的处理 | 写一个"共享的中间层页表"必须深拷贝那一层，否则两个地址空间会互相改对方的映射 | 内核 |
| 帧的写时复制与引用计数 | 今天的帧所有权是"内存对象持有"或"任务持有"（`FE_PTE_NOFREE`，`11-kernel-next.md:365-369`），COW 要引入第三种"多空间共享" | 内核 |
| `fork` 之后**只有调用线程**存活（POSIX） | 线程副本的语义（谁的内核栈、谁的 TLS、谁的 FPU 区）要与 K6 的"杀其它线程"共用一套推理 | 内核 |
| 子进程要继承 fd 表 / 信号处置 / 进程组 / 会话 / 内存锁 | 这四样今天**两样没有**（fd 继承见 §2.2、信号见 §2.4），`fork` 会**同时**要求它们 | 两者 |
| VMA 表要真复制（今天 `FE_VMA_MAX = 32` 的定长表） | `kernel/include/fe/mm/vma.h:61-70` 写明"定长让插入/查找没有分配失败路径"是**刻意的**；复制它要么定长对拷、要么引入失败路径 | 内核 |
| COW 的判据本身 | 需要"父写一页之后子看不到、子写一页之后父看不到、**帧数没有翻倍**"三条同时成立，否则测的是"复制了一份"而不是 COW | 内核 |

**"文档化为唯一刻意偏离（用 `posix_spawn`）"要付的代价**：

| 付什么 | 具体 |
|---|---|
| 有一类程序**永远编不过/跑不对** | 任何把"复制我自己"当算法的程序：`fork` 之后父子都跑用户代码、靠 `fork` 返回值分流的那种（管道实现的经典写法、`daemon()`、部分 shell 的作业控制） |
| 需要一份**如实的偏离声明** | 写在 `10-posix-layer.md`（文件头已明确说提供的是 `posix_spawn`），并在 `posix_spawn` 失败路径上**不假装**（今天已经是这样：`file_actions` 返回 `ENOSYS`，`user/libposix/spawn.c:81-101`） |
| 不能声称"POSIX 完整" | 只能声称"**内核侧不阻塞 POSIX**"——`fork` 是**标准里的一项**，缺它就是缺。这一条必须与 §1.1 的口径一起读：**"内核侧补齐"不等于"POSIX 齐了"** |
| 好消息：内核侧的代价**接近零** | 因为 `posix_spawn` 要的东西已经全有了（spawn + wait + exec），今天**只差 fd 继承与 envp**（§2.2、§2.15） |

**推荐：不实现 COW `fork`，把它文档化为"唯一刻意偏离"。**

**理由落在"用户态做不到什么"上**（不是偏好）：

1. COW `fork` 需要的机制**没有一个**是"用户态做不到、必须内核提供"的**独占**
   需求——它需要的页表操作**恰恰是内核已经为 `mmap`/`mprotect` 提供的那些**
   （`fe_vmm_map`、`fe_vmm_protect`、`fe_vma_protect_range`），而
   "复制一个地址空间"这件事的**结果**可以用 `spawn` 表达。
   **换句话说：它是"用户态做不到"的，但也是"用户态不需要"的。**
2. 反过来，§2.8（`futex`）、§2.7（`pthread_join`）、§2.10（文件后备缺页）
   是**真的做不到**：它们要的是"内核原子地做两件事"（检查+入队 / 判死+收尸 /
   查区间+取页），用户态无论怎么写都只能近似，而近似的失败形态是
   **丢唤醒 / 卡死**（`17-libcxx-build.md` §2.6：`-smp 1` 下自旋不是慢而是锁死）。
   **把工夫花在这三条上，POSIX 设施的解锁数量多一个数量级。**
3. 项目一贯的纪律（`10-posix-layer.md:100-102`）：不做"以后可能需要"的机制，
   但把**不做**的理由写清楚。`fork` 的连锁需求（进程组/会话/信号处置/fd 继承）
   是**四件事**，而其中两件今天完全没有。

★ 什么时候该改主意 ★ 出现一个**非它不可**的真实程序时（例如某个必须支持
`fork` 的 shell），并且到那时先评估"给它打补丁用 `posix_spawn`"——
`10-posix-layer.md` §4 已经把这个决策门写下来了。
**判据不是"标准里有这一项"，而是"有一个具体程序因此跑不了"。**

**标准判定（§1.2.4 的判据落到本行）**：★ **标准要求** ★ ——
`fork()` 与 `posix_spawn()` **都是 POSIX 标准里的接口**（两条并列的子进程创建途径）。
→ 所以"不做 `fork`"是一条**要如实声明的能力缺口**，**不能**用 §1.2.4 的第二行
（"某个实现的附加行为，不做"）把它划掉。
★ 唯一的安慰是"它不挡别人"：`posix_spawn` 那一半**是**标准的，而且今天只差
fd 继承与 `envp`（§2.2、§2.15）。★

### 2.2 fd 继承与 `posix_spawn` 的 `file_actions`

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| `file_actions` 的三个 `add*` 全部**明确返回 `ENOSYS`**（不是假装成功） | `user/libposix/spawn.c:81-101`（`addopen` `:81`、`addclose` `:89`、`adddup2` `:96`） |
| `posix_spawn` 收到非 NULL 的 `file_actions` 就返回 `ENOSYS` | `user/libposix/spawn.c:122-125` |
| fd 表**不跨任务继承**的理由写在文件注释里："内核的 `fe_process_spawn` 不认识 fd，而用户态的 fd 表不跨任务继承（子进程是全新的地址空间与句柄表）" | `user/libposix/spawn.c:72-80` |
| 内核侧的 spawn 签名里**没有任何句柄数组**参数 | `kernel/include/fe/process.h:125-126`（`fe_process_spawn(parent, path, argv, argc, out_handle)`） |
| `user/libposix/posix.c` 的 fd 表是**进程内的静态数组** | `user/libposix/posix.c:55`（`POSIX_FD_MAX 64`）、`:75`（`static struct fd_entry g_fd[POSIX_FD_MAX]`） |

**内核侧要什么**：一条"**spawn 时随新任务安装一组初始句柄**"的能力。形状上有
两种，代价不同：

| 候选 | 形状 | 代价 / 安全含义 |
|---|---|---|
| **A. spawn 扩展参数** | `FE_SYS_PROCESS_SPAWN` 增加"句柄数组 + 目标句柄号"两个参数 | 要处理"安装失败时整个 spawn 回滚"（今天是原子的，加了之后必须仍然原子）；**能力检查仍然在句柄表这一层**（把 fd 0/1/2 对应的端点转交出去，权限只能收窄，见 `kernel/include/fe/syscall.h:487-492`） |
| **B. 先 spawn、再经端点转交** | 子进程先起、父进程把句柄发过去、子进程自己装进 fd 表 | ★ **今天就能做，一行内核都不用改** ★ 但有一个真实的竞态窗口：子进程在收到句柄之前就已经在跑用户代码——它可能已经 `open` 了别的东西，占掉了 fd 号。标准里的 `file_actions` 语义要求"**在子进程执行任何用户代码之前**"完成重定向 |

★ **推荐 A**，理由不是性能，而是**语义**：`file_actions` 的全部意义就是
"在 exec 之前做完"，B 做不到这一点（它只能做到"尽早"）。这与
`09-handle-transfer.md` 的能力模型不冲突——转交的仍然是句柄，权限仍然只收窄。

**判据（可证伪）**：① 正向：父进程 `dup2` 一个文件到 fd 1 之后 spawn，
子进程 `write(1, ...)` 的内容落进**那个文件**；② 反向：不做 `file_actions`
时同一个子进程写到**控制台**（证明重定向真的生效了，不是"恰好都写控制台"）；
③ 反向：转交一个父进程**没有** `FE_RIGHT_TRANSFER` 的句柄 → 转交失败且
spawn 整体回滚（子进程不存在）。

**归属：内核（机制）+ 用户态（语义）**。内核只做"安装一组句柄"，
"fd 3 对应哪个端点"永远是 libposix 的事实（`10-posix-layer.md:120`）。

**标准判定**：★ **标准要求** ★ —— `posix_spawn_file_actions_addopen/addclose/adddup2`
与"重定向在子进程执行任何用户代码之前完成"都是标准里的语义
（`<spawn.h>`，POSIX 的 spawn 那一族）。
→ 所以 `ENOSYS` 是**如实的能力缺口**，不是"某个实现的附加行为"。
★ 反过来说：**"fd 表不跨任务继承"是我们的实现形态**（内核不认识 fd），
标准只要求"结果是那三个动作生效"——实现形态可以不同，这正是 §1.4 的分层。★

### 2.3 `dup` / `dup2` / `close-on-exec`

**事实（我读到的）**：

| 项 | 今天在哪 | 说明 |
|---|---|---|
| `dup` / `dup2` | **已在用户态做掉**：`user/libposix/posix.c:426-438`（`dup`）、`:440-458`（`dup2`） | 内核里没有 `dup` 这个概念，也不该有 |
| fd 号复用最小空闲号 | `user/libposix/posix.c:154-164`（`fd_alloc`） | 标准里的程序依赖这一点（shell 的重定向），文件头 `:11-13` 写明了理由 |
| `close-on-exec` | **完全没有** | 全仓搜 `FD_CLOEXEC`/`O_CLOEXEC` → 见 §6 待查第 2 条（我只能确认 `fcntl.h` 里有 `O_APPEND`，`17-libcxx-build.md:274`） |
| `fcntl` | **完全没有**（`fcntl.h` 里有常量，没有实现） | 同上 |
| "`exec` 之后句柄表保留"这一点**已经成立** | `kernel/include/fe/process.h:197-199`：exec 换的是地址空间，"身份（句柄表 / 资源认领 / devfs 名字 / 任务 id / 父子关系）一个字不动"；`15-exec.md` §2/§6 展开 | ★ **这条是本节的结论：`close-on-exec` 需要的底座已经有了** ★ |

★ **与候选描述不符的一点** ★ 候选里说"`dup`/`dup2` 已经在用户态做掉了"是**对的**，
但**它们今天的语义有一处不满足标准**，而这一处**恰好是用户态自己造成的**，
不需要内核：

- 文件头注释（`user/libposix/posix.c:15-17`）声明："同一个文件 open 两次是两个
  独立的偏移；dup 出来的两个 fd 则**共享**偏移。"
- 实现里为此**定义了**一个共享节点指针：`user/libposix/posix.c:68-71`
  （`struct fd_shared *shared;`）。
- 但 `dup` 的实现是**整条条目结构体对拷**（`user/libposix/posix.c:436`
  `g_fd[n] = *e;`），`dup2` 同样是整条对拷（`:456` `g_fd[newfd] = *e;`），
  **`shared` 这个指针从来没有被分配、也没有被任何一行读过**：
  全仓搜 `fd_shared` 只有两处命中——`user/libposix/posix.c:71` 的声明，
  以及 `user/include/fe_user.h:728` / `user/libfe/libfe.c:328` 里**同名的另一个**
  东西（`fe_resource_pool_add` 的 `shared` 参数，与它无关）。

  → 也就是说：**`dup` 之后两个 fd 各自持有偏移的一份副本，改一个不影响另一个**，
  而这与它自己头上写的那条语义相反。**这是"文档在骗人"的又一例**
  （同族：`10-posix-layer.md` §9 的"声明了却没实现"×4）。
  **它不需要内核**：把 `shared` 真正分配出来（或者在 `fd_entry` 里改成
  "偏移指针 + 引用计数"）即可。★ 本文不改代码，只记录 ★

**内核侧要什么**：

| 要什么 | 今天 | 代价 |
|---|---|---|
| `exec` 时**不**关闭的句柄（`FD_CLOEXEC` 的补集） | **底座已有**（exec 不动句柄表） | 零内核改动 |
| `exec` 时**关闭**标记了的句柄 | 缺 | 需要内核在 exec 提交路径上**按标记关闭句柄**。两种做法：① 内核里加一个"句柄的 close-on-exec 位"（**这是把标准里的语义搬进机制层，与 §1.4 冲突**）；② 用户态在 `exec` 前自己关、或者让 exec 带一个"要关哪些句柄"的参数（**推荐**：名字是中性的"关闭这组句柄"） |
| `fcntl(F_GETFD/F_SETFD)` / `F_GETFL/F_SETFL` | 缺 | **纯用户态** |

**归属**：`dup`/`dup2`/`fcntl` = **用户态**；`close-on-exec` 的**执行动作** =
**两者**（内核提供"exec 时关闭指定的句柄集合"，标记的语义留在用户态）。

**标准判定**：★ **标准要求（三处都是），而且其中一处今天**实现错了** ★

| 项 | 判定 | 依据与后果 |
|---|---|---|
| `dup`/`dup2` **共享文件偏移** | ★ **标准要求** ★ | ★ 这不是"某个实现的做法"：标准明确要求 `dup` 出来的两个描述符共享同一个打开文件描述（含偏移）。所以 `fd_entry.shared` 从未被分配 = **实现与标准不符**，而**不是**"我们选择了另一种语义"——文件头 `posix.c:15-17` 写的正是标准，错的是实现 ★ |
| `FD_CLOEXEC` / `fcntl(F_SETFD)` | **标准要求** | `<fcntl.h>` 的 `FD_CLOEXEC` 与 `fcntl` 都是标准接口；今天一处都没有（§6 待查第 2 条是待核实的清单） |
| "`exec` 保留未标记的句柄" | **标准要求** | `execve` 之后除 `FD_CLOEXEC` 之外的描述符必须保留（除非 `fcntl` 另有约定）。★ 我们的底座已经满足这一半（`exec` 不动句柄表，`process.h:197-199`）★ |
| `fcntl(F_GETFD/F_SETFD/F_GETFL/F_SETFL)` | **标准要求** | 纯用户态可实现（常量已在 `user/include/posix/fcntl.h`） |

★ 后果（**待办，见 §6 第 13 条**）★ `dup` 偏移不共享是一条**真缺陷**，
按"标准要求"处理：**改实现，不改注释**。★ 但它属于 `user/libposix/`，
不在本文的改动范围里（本文只写文档）★

### 2.4 信号 —— 内核侧最大的一块，且**必须分成两件事**

★ 这是全表里唯一一处"候选描述本身是对的、但需要拆得更细"的地方 ★
拆开的理由不是分类癖，而是**两者的实现代价差一个数量级**，而且**共用投递点
这件事本身是一个需要判据的决定**。

#### (a) 故障转交 = K5（设计已完成，未实现）

| 事实 | 出处 |
|---|---|
| 今天的决定点只有一行：`user_fault` 尾巴上的 `fe_thread_exit(-1)` | `kernel/arch/x86_64/idt.c:279-281` |
| 分发处的用户态分支 | `kernel/arch/x86_64/idt.c:306`（`if ((r->cs & 3) == 3 && vector < 32)`） |
| 完整设计（登记端点、三个返回值、深度 1、就地让出而非阻塞） | `docs/18-user-fault-handler.md`（§2.0 是形状，§2.6 是"IF=0 里只能有界轮询"） |
| ★ 它的 syscall 号**要顺延** ★ 文档写 `0x90/0x91`，而 `0x90` 已被 `exec` 占掉 | `18-user-fault-handler.md:681` 自己写着"若 K6 `exec` 先落地，它会占 `0x90`，K5 顺延到 `0x92/0x93`"；而 `kernel/include/fe/syscall.h:353`（`FE_SYS_EXEC = 0x90`）与 `:355`（`FE_SYS_MAX = 0x92`）**证实 `exec` 已经落地**，所以 **K5 的号是 `0x92`/`0x93`，`FE_SYS_MAX` → `0x94`** |

#### (b) 异步信号投递（`kill` / `SIGTERM` / `sigprocmask` / `sigsuspend` / `EINTR`）

**今天内核有什么（我读到的）**：

| 有什么 | 出处 | 它为什么**不是**信号 |
|---|---|---|
| `FE_SYS_TASK_TERMINATE`（`0x8C`）把**整个任务**标记为死亡 | `kernel/include/fe/syscall.h:263-281`；`kernel/include/fe/task.h:76`（`bool dying`）；`kernel/include/fe/process.h:147`（`fe_task_terminate`） | 它是**一个**动作、任务级、不可屏蔽、没有"编号"。信号的形状是"**一个编号 + 一个待决位图 + 一个处置表**"，其中**只有处置表在用户态** |
| 通知对象（可等、可取位） | `kernel/include/fe/syscall.h:52-54`（`NOTIFICATION_*`）；`kernel/include/fe/ipc.h:180-182` | 它是"**别人置位、我等位**"的对象，没有"**打断我当前正在做的事**"这一半——而这一半正是信号的定义 |
| 取消点（阻塞中的线程被唤醒并带 `FE_ERR_CANCELED` 返回） | `kernel/include/fe/syscall.h:273-277`；`kernel/include/fe/process.h:151-155`（`FE_EXEC_KILL_ROUNDS`） | ★ **这是最接近信号的东西**，但它只由"任务被终止"驱动，而且**返回之后线程就死了**（`user/include/fe_user.h:696-700`）——`EINTR` 要的是"**返回之后线程继续跑**" |

**(b) 需要什么新机制（逐项）**：

| 要什么 | 为什么用户态做不到 | 代价 |
|---|---|---|
| **一个待决位（pending）位图 + 一个"有信号待投递"标志** | 必须有地方存"信号还没被处理"这件事，而它必须在**内核**：信号的本质是"**打断一条正在内核里跑的线程**"，用户态没有这个立足点 | 小（任务上 64 位 + 一个标志）；**难点在投递时机** |
| **投递时机**：在"回用户态的路上"检查 | 这是唯一能打断用户态执行的位置，也就是**已有的闸门**（`fe_sched_maybe_switch`，`11-kernel-next.md:356` 写着它是"isr 与 syscall 两条返回路径的唯一交汇点"） | ★ **与 K5 共用还是两套——这是本节要回答的问题** ★ 见下 |
| **投递语义**：把线程的返回帧改成"跳到用户态的入口蹦床"，并把原现场推进用户栈 | 改返回帧是内核独占的能力（`15-exec.md` §6 的 `fe_exec` 用的就是同一招） | 中。要定死"蹦床地址从哪来"（用户态注册）、"原现场怎么摆"（一个 ABI 结构）、"`sigreturn` 怎么回去"（一条新 syscall） |
| **屏蔽字（`sigprocmask`）** | 屏蔽字本身可以放用户态，但"被屏蔽时**不许投递**"这条判断必须在**投递那一刻**做，而那一刻在内核里 | 小。内核要能读到一个"当前屏蔽字"——最省的做法是**随每个线程一份的镜像**，由 `sigprocmask` 那条 syscall 更新 |
| **`sigsuspend`** | 它是"原子地换屏蔽字 + 睡下"——★ **又是一次"原子地做两件事"** ★ | 中。如果 §2.8 的 futex 已经落地，它可以建在 futex 上（用户态）；否则要新一次等待登记 |
| **`EINTR` 与"系统调用自动重启"** | ★ "系统调用被信号打断"这件事只有内核知道 | ★ **需要一条纪律**：每个可阻塞的 syscall 都要能返回 `FE_ERR_INTR`（今天**没有**这个错误码，`kernel/include/fe/errno.h:19-45` 里最接近的是 `FE_ERR_CANCELED`），用户态再决定重不重启（`SA_RESTART` 的语义**留在用户态**） |

**(b) 与 K5 的关系：共用"投递点"，不共用投递格式** —— 我的建议：

| | K5（故障转交） | (b) 异步信号 |
|---|---|---|
| 触发源 | 硬件异常（`#PF`/`#GP`…），**同步**，就是当前这条线程干的 | 另一个任务/线程调 `kill`，**异步** |
| 现场从哪来 | CPU 压在栈上的 `struct fe_regs`（**现成的**） | **没有现场**——要自己**造**一个（"回到用户态之后立刻进处理者，`sigreturn` 再回来"） |
| 谁接收 | 任务的**一个端点**（`18-user-fault-handler.md` §2.1 定死了：登记在任务上，消息带 `thread_id`） | 用户态的**处置表**决定"忽略/默认/处理者"——**内核不该有处置表** |
| 能不能等 | 必须在**异常上下文**里就地让出（`18` §2.6：IF=0 里阻塞必死锁） | 可以走**闸门**（回用户态的路上），那里 IF 正常 |

**建议：共用的是"闸门"这一个投递时机，不共用消息格式与等待语义。**
理由：把 (b) 塞进 K5 的异常路径会强制它继承 K5 最贵的那条约束
（IF=0 → 只能有界轮询），而 (b) 完全可以在闸门里**直接改返回帧**（一次赋值，
没有等待）。反过来，让 K5 走闸门也做不到——异常发生在**用户态执行时**，
闸门是"从内核回用户态"的地方，那时现场已经不在手里了。

**判据（(b)，可证伪）**：① 正向：线程 A 在用户态死循环，线程 B `kill(A, n)`
→ A **在有限时间内**进入它注册的处理者，处理者 `sigreturn` 之后 A **继续**
原来那段循环（证明"被打断且能恢复"，而不是"被杀掉"）；② 反向：屏蔽掉信号
→ 处理者**不执行**，且 A 的循环**没有出现被插入的痕迹**；③ 反向：不注册处理者
+ 默认动作是终止 → A 死，**退出码是终止码而不是 0**（区分"被杀"与"自己退出"）；
④ 反向：`EINTR` —— 一条线程阻塞在 `fe_wait` 上时收到信号 → 那次调用返回
**错误**（不是"成功且退出码是 0"），重启与否由用户态决定。

**归属：内核**（待决位、投递时机、返回帧改写、屏蔽字镜像、`FE_ERR_INTR`）。

**标准判定**：★ **标准要求** ★ —— 信号（`signal`/`sigaction`/`kill`/`sigprocmask`/
`sigsuspend`/`raise`）与"异常转交的处理者"都是 POSIX 标准的内容；
★ 而**用哪个机制去投递是我们自己的实现形态**（"端点 + 闸门 + 返回帧蹦床"
不是标准规定的东西，标准只规定**可观察的语义**：处理者在被打断的线程上运行、
`sigreturn` 之后恢复）。这正是 §1.4 的分层。
★ **一条"只是某个实现的做法"、所以不做的**：Linux 的 `signalfd` 与
`SA_RESTORER` 那一套 ABI（restorer trampoline 的约定）**不是标准**——
我们要提供的是 `sigreturn` 这个**标准**行为，而不是 Linux 的 restorer 约定。
（★ 本文没有逐个核实每个信号接口的版本归属，**该清单列为待查第 14 条** ★）

### 2.5 `kill(pid, sig)` / 进程组 / 会话

★ **与候选描述不符的一条** ★ 候选说"内核**刻意没有全局 pid 表"，
并把 `docs/00-architecture.md` / `fe/task.h` 的注释列为证据。**我核实的结果是
"半个对"**——必须分开说，否则会得出错误的结论：

| 陈述 | 我读到的 | 判定 |
|---|---|---|
| 内核用**句柄**而不是 pid 表达"我能对谁做什么" | `kernel/include/fe/process.h:6-13`：spawn 返回新任务的**句柄**（能力），"父进程只能 wait 自己持有句柄的任务。Linux 的 pid 是全局可猜的整数，谁都能对别人 kill/wait；句柄不可伪造" | ✅ **对** |
| `spawn`/`wait` 只认句柄 | `kernel/include/fe/process.h:123-131`（`fe_process_spawn` 输出句柄、`fe_process_wait` 收句柄） | ✅ **对** |
| 内核里**没有任何**能按 id 找任务的东西 | ★ **不对** ★ `kernel/include/fe/task.h:102-109` 有 `fe_task_by_id(u64 id)`，`:111-113` 有 `fe_task_by_name(const char *)`；`kernel/include/fe/task.h:23` 有 `struct fe_task *next; /* 全局任务链 */`，`:116` 有 `fe_task_first()` | ❌ **不对** |
| `TASK_LIST` 给用户态一个只读快照，**含任务 id 与名字** | `kernel/include/fe/syscall.h:168-179`（`FE_SYS_TASK_LIST = 0x84`，共享 ABI 在 `:384-458`，含 `struct fe_task_info_x` 的 `id`/`name`）；`kernel/include/fe/task.h:133-142` | ✅ 对，且**这是"用户态已经能看见 id"的证据** |

**所以准确的表述是**：内核**没有 pid 命名空间**，也**没有**"句柄之外的可操作引用"
（`fe_task_by_id` 的注释 `kernel/include/fe/task.h:104-108` 明说它是给内核自己
确认 id 是否还存在用的，"用户态拿不到这个能力"）；但内核**确实有**一张全局任务链
与 id/名字查询，并且**有一条专门的 syscall 把 id 暴露出去**——
`FE_SYS_RESOURCE_GRANT_ID`（`0x88`，`kernel/include/fe/syscall.h:210-234`），
它的注释里把原因写得比我能写的更清楚：

> ★ 为什么在"用句柄不用 pid"的项目里还要一个 id 版本 ★ …但设备管理器的现实
> 处境是：**被授予硬件的驱动往往不是它拉起的**。…代价：目标 id 是**可猜的**。

→ **这是本节最重要的既成事实**：项目**已经**在"句柄之外"开过一个 id 口子，
并且**已经**把它的代价（id 可猜、必须额外加"调用者身份"与"任务必须已存在"两道
防护）写下来了。讨论"要不要再开一个"时，应该照这一条的先例，而不是从零开始。

**两条路的代价与安全差异**：

| | **A. 用户态注册表（某个服务持句柄）** | **B. 内核加"可查询的任务名/id 表"** |
|---|---|---|
| 今天能做吗 | ★ **今天就能做**（`devfs` 就是干这个的：`fe_devfs_publish`/`fe_devfs_open`，`00-architecture.md:258-269`） | 已经**部分**做了（`TASK_LIST` 是只读快照），"可操作"那半只有 `0x88` |
| 能表达什么 | "**你向我注册，我替你转交**"：注册者必须**主动**把自己的任务句柄交出来 | "**我知道你是谁就能对你做**"：查询者**不需要**对方同意 |
| 谁能被 `kill` | 只有**注册过的**（能力模型：不可伪造、不可猜） | 任何**存在**的任务（id 可猜 → 谁都能枚举） |
| 新服务挂掉的后果 | 注册表丢失 → 已有进程**失去被管理的能力**（不是失去能力本身） | 无（表在内核） |
| 一个新漏洞面 | 无（转交用的是既有的句柄传递，权限只收窄） | ★ **提权面** ★ 有了 id 就能枚举"系统里有哪些任务、都叫什么"，而**名字本身是信息**（`11-kernel-next.md` §9 那次 VBox 竞态的根因就是"谁先认领 devmgr 身份"） |
| 与终止（K2）的关系 | `fe_task_terminate` 需要 `FE_RIGHT_TERMINATE`（`kernel/include/fe/syscall.h:265-267`）——**注册表把句柄收上来的那一刻，被注册者就把"能不能杀我"交出去了**，这是**显式**的 | 同样要权限位，但"找得到"与"杀得掉"被拆开了 |
| 代价 | 一个常驻服务 + 生命周期管理（服务重启后注册表怎么恢复——`devfs` 的"发布者退出时名字自动收回"是现成的先例，`00-architecture.md:276-277`） | 内核多一张可查询表（与 `TASK_LIST` 高度重叠，**"两份我以为"的风险**：两张表的 id 集合不一致时，症状是"ps 看得见、kill 找不到"） |
| 与项目纪律的关系 | ✅ 与 `00-architecture.md` §9"学 BSD，不建注册表"**表面冲突、实际一致**：那条纪律反对的是"与 VFS 平行的**命名空间**"，而这里的注册表是**在 devfs 上的一个服务** | ⚠ 与 `10-posix-layer.md` §5 的"内核只认识句柄、端点、通知、任务"有张力：它要加的是"任务名 → 任务"的**可操作**映射 |

**推荐：A（用户态注册表）**，理由落在"用户态做不到什么"上：

1. **`kill` 真正做不到的那一半与"能不能按 pid 找到人"无关**——它是
   §2.4(b) 的**投递机制**（打断一条正在跑的线程）。把注册表放内核**并不能**
   让 `kill` 变得可能，只能让"找谁"变得方便。**先做真挡住的那一半。**
2. **B 会引入一张与 `TASK_LIST` 并行的表**，而这个项目已经为"两份我以为"
   交过学费（`10-posix-layer.md` §9 的第 3 条：fsd 与客户端各抄一份协议）。
3. **A 的形状今天已经存在**：`devfs` + 句柄传递 + `FE_RIGHT_TERMINATE`，
   三者都已完成、都有实测。要加的只是"一个把任务句柄登记起来的服务"。
4. ★ 但要如实记下 A 的一个**真缺口** ★ **`FE_RIGHT_TERMINATE` 无法"事后授予"**：
   一个进程如果**没**主动把句柄交给注册表，注册表就永远杀不掉它。
   POSIX 标准里的 `kill(pid)` 允许**有权限的**进程杀其他进程，而 A 把它变成
   "**登记过的**才能被杀"。这是**能力模型与标准语义的真实差异**，
   必须写进文档，不能被"我们推荐 A"盖过去。
   （缓解：`init` 拉起所有服务时**天然**持有它们的句柄（`fe_process_spawn`
   给父进程的就是它），所以"系统服务"这一类可以由 `init` 交给注册表；
   但**用户自己 spawn 出来的进程**不在其中。）

**判据（A，可证伪）**：① 正向：注册一个子任务之后，注册表服务能按 pid `kill`
到它；② 反向：**没有注册**的子任务，注册表**查不到**（返回明确的错误，
不是"随便杀一个"）；③ 反向：注册表服务自己重启之后，旧注册项的处置有明确
答案（要么失效要么恢复，**不能**是"有时还能杀"）。

**标准判定**：★ **混合，必须分开看** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `kill(pid, sig)` 按 **pid** 寻址 | ★ **标准要求** ★ | 标准里的 `pid` 就是一个整数标识，"发送者要能按它找到目标"是标准语义的一部分 |
| **进程组**（`setpgid`/`getpgrp`/`kill(-pgid, …)`）与**会话**（`setsid`） | ★ **标准要求** ★ | 它们是标准里的概念（作业控制的基础），不是某个实现的发明 |
| ★ **"必须有全局的、可猜的 pid 命名空间"** ★ | ⚠ **不是标准要求，是实现形态** ★ | 标准只要求"**有权限的调用者**能按 pid 送到"——它**没有**规定 pid 必须全局可枚举、也没有规定内核必须持有一张 pid 表。★ **这正是我们推荐用户态注册表（A）的依据**：把"找到谁"放在用户态注册表里，标准语义仍然可以满足（`init` 天然持有服务的句柄）；而"内核加一张可查询的 id 表"换来的是**可枚举性**，那是标准不要求的东西 ★ |
| ★ **"没登记过的进程杀不掉"这个后果** ★ | ⚠ **是 A 与标准之间的真实差异** ★ | 如实记为缺口（见上面第 4 条），**不能**用"标准没要求"把它抹掉 |

★ 一句话：**"按 pid 送到"是标准要求（要做）；"pid 全局可枚举"是实现形态
（不做，也不需要）**。★

### 2.6 `waitpid` / 僵尸

★ **与候选描述不符的一条（本节最重要的发现）** ★ 候选说"POSIX 的 `waitpid(-1)`
（等任意子进程）需要什么？用户态能不能做（父进程持有全部子进程句柄 → 需要
'多对象等待'）"——**它已经做了，而且没有用多对象等待**：

| 我读到的 | 出处 |
|---|---|
| `waitpid(pid <= 0)` 取"第一个**还没收尸**的孩子"，然后**阻塞在它身上** | `user/libposix/spawn.c:200-212`（`for` 循环找第一个 `used && !reaped`） |
| `wait(0)` 就是 `waitpid(-1, ...)` | `user/libposix/spawn.c:241-243` |
| `WNOHANG` **明确返回 `ENOSYS`** | `user/libposix/spawn.c:193-198`，注释写着"内核没有 wait(nohang) 语义，所以这一条如实不支持。假装支持（立即返回 0 = '没有孩子退出'）会让轮询循环永远转下去" |
| 子进程表是**定长 16 项** | `user/libposix/spawn.c:25`（`#define SPAWN_MAX 16`） |
| `waitpid` 会在拿到退出码之后**关掉那个任务句柄** | `user/libposix/spawn.c:231-234` |

**所以真正的缺口不是"多对象等待"，而是三件更小的事**：

| 缺口 | 症状（可观察） | 归属 |
|---|---|---|
| **"等任意一个"没有实现** | `waitpid(-1)` 挑中的是**列表里第一个未收尸的孩子**，如果它**还在跑**，即使**别的孩子已经退出**，调用者也会一直等下去。标准要求"任意一个退出就返回" | **用户态**（有 `fe_wait_any` 的内核机制可用，但它**没有用户态 ABI**——见 §2.9；也可以在用户态用**通知对象**合成：每个孩子退出时置一位，但"孩子退出"这件事要有人替它置位） |
| **`WNOHANG` 不存在** | 轮询式监督循环（`while (waitpid(-1, &st, WNOHANG) > 0)`）**直接报错** | ★ **内核侧缺口** ★ 需要"**不阻塞地问一次任务是否已结束**"。今天只有阻塞的 `FE_SYS_PROCESS_WAIT`（`kernel/include/fe/syscall.h:111`）。★ 但注意：`TASK_LIST` 快照里的 `exited` 字段（`kernel/include/fe/syscall.h:422`）**已经**能让用户态**只读地**看出"某个任务结束了"——所以 `WNOHANG` 可能在用户态就能做（拿快照比对），代价是"每轮一次全表快照" |
| **僵尸的回收** | ★ 这一条**已经解决了**，而且是有实测的：`th->reap_ok = !boot_init`（`kernel/task/process.c:305`）让非 init 进程的主线程僵尸由调度器回收；K2/K3 那一轮的教训（僵尸线程从不回收 → 每个跑完的程序都泄漏任务对象）记在 `11-kernel-next.md:361-364` | 内核（已完成） |

★ **还有一个容易漏的点** ★ `SPAWN_MAX 16` 是**用户态**的定长表
（`user/libposix/spawn.c:25`）：第 17 个子进程 spawn **失败**（`child_alloc`
返回 NULL → `EAGAIN`，`:130-134`）。标准里没有这个上限。**它不需要内核**，
但它是"内核侧补全"在用户态那一半的一个真实缺口，写在本文里免得被漏掉。

**归属**：`waitpid(-1)` 的**正确语义** = **用户态**（+ §2.9 的用户态 ABI）；
`WNOHANG` 的**事实来源** = **内核已有**（`TASK_LIST` 的 `exited`）或
一条新的"非阻塞问一次"的原语（★ **待定**，见 §3.4 的 **K15** 与 §6 待查第 3 条 ★）。

**标准判定**：★ **标准要求（每一处都是）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `waitpid(pid, &st, options)` / `wait(&st)` | **标准要求** | 都是标准接口 |
| `waitpid(-1, …)` = "**任意一个**孩子终止就返回" | ★ **标准要求** ★ | 这正是今天实现错的那一处（挑第一个未收尸的然后死等）——**不是**"我们选了另一种语义" |
| `WNOHANG` | **标准要求** | 标准定义的 `options` 位；今天如实返回 `ENOSYS` |
| 僵尸与"父进程取走退出状态" | **标准要求** | 标准明确描述了 `wait` 之前子进程的终止状态必须可取 |
| `WUNTRACED`/`WCONTINUED` | **标准要求**（可选） | 它们与作业控制绑定（§2.17 明确不做），所以今天**不实现不算缺口**，但要写明原因是"作业控制整体不做" |
| `SPAWN_MAX = 16` 这个上限 | ⚠ **我们的实现限制**（不是标准语义） | 标准没有这个上限；它纯属用户态实现，改它就是改 `user/libposix` |

### 2.7 线程：`pthread_create` / `pthread_join`

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| `fe_thread_create` 用户态可调，**返回的是线程 id（一个整数），不是句柄** | `user/libfe/libfe.c:100-104`；内核侧 `kernel/task/user.c:546`（`return th ? th->id : 0;`） |
| 内核的 `fe_thread_join` 收的是 `struct fe_thread *`——**内核对象的裸指针** | `kernel/sched/sched.c:1276-1280`（`if (!t) return FE_ERR_INVAL;`） |
| 它的等待方式是**有界自旋**：让出 + 计轮数，**上限 2000 万轮**，超时打印一行然后**放弃等待并 `thread_free(t)`** | `kernel/sched/sched.c:1306-1317`（`spins >= 20000000u` 的分支）、`:1311-1315`（打印）、`:1338`（`thread_free(t)`） |
| ★ 用户建的线程**默认由调度器收尸**，因为"内核里没有人 join 它" | `kernel/task/user.c:540-545`（`th->reap_ok = true;`） |
| 用户线程的栈由内核分配（默认 64 KiB，`FE_USER_STACK_SIZE`），每线程**一个 VMA 区间** | `kernel/task/user.c:506-518`；`kernel/include/fe/user.h:19` |
| 用户线程优先级**写死**为 `FE_PRIO_NORMAL` | `kernel/task/user.c:538-539`（`fe_thread_create_ring3(..., FE_PRIO_NORMAL, "user")`） |
| 用户态**没有** `pthread.h`、没有 `pthread_*` | `user/include/posix/` 下 12 个头（`docs/17-libcxx-build.md:1030` 记的三个数字里"文件数"那一把），**没有** `pthread.h`；全仓搜 `pthread` → 见 §6 待查第 4 条 |

**要补什么（逐项，含"为什么用户态做不到"）**：

| 要什么 | 为什么 | 代价 |
|---|---|---|
| **线程要变成一种"可等待的对象"** | `pthread_join` 要的是"**等它退出并拿退出码**"。今天用户态手里只有一个 `u64` 线程 id，**没有任何能等它的东西**（内核的 join 收内核指针） | ★ 两种形状 ★ ① 给 `fe_thread_create` 返回一个**线程句柄**（新对象类型或复用句柄表）；② 让**任务**句柄可等"它的一条具体线程"。①更贴近 `pthread_t`，代价是**对象类型 + 句柄表项 + 生命周期**（线程退出后句柄还能被 join，意味着线程对象要活到被 join 或最后一个句柄关闭——这与今天"僵尸立刻被回收"（`:540-545`）的假设冲突） |
| **退出码要能被取回** | 今天 `fe_thread_join` 返回 `t->exit_code`（`kernel/sched/sched.c:1318`），但那是**内核对内核**的路径 | 小（字段已有，`kernel/include/fe/syscall.h:435` 的线程记录里也有 `exit_code`） |
| **回收策略要重定** | 今天"用户线程一律 `reap_ok = true`"，即内核**假定没人 join**（`kernel/task/user.c:540-545`）。一旦有了 join，被 join 的线程**不能**被调度器提前回收（否则 join 拿悬空指针——`kernel/sched/sched.c:1283-1288` 把这条教训写得很清楚：曾经在循环里收尸，后果是"内核堆被破坏"） | 中。判据必须写死：**谁负责收**只有一处答案 |
| **线程创建要能指定栈与优先级** | `pthread_attr_setstacksize`/`setinheritsched` 会用到；今天 `flags` 参数**被显式忽略**（`kernel/task/user.c:501` `(void)flags;`） | 小（ABI 上已经有 5 个参数的形状，`kernel/arch/x86_64/syscall.c:116-120` 的 `flags` 今天一路透传到 `(u32)flags` 后被忽略） |
| **`pthread_detach`** | "不需要 join 的线程" | 小（一个标志） |

**判据（可证伪）**：① 正向：4 条线程各算一段，主线程 join 全部，**总和精确相等**；
② 反向：一条线程 `fe_exit(7)` 之后 join 返回 **7**（不是 0——0 会"碰巧正确"，
`10-posix-layer.md` §9 已经用过这个手法）；③ 反向：**不 join** 的线程退出之后，
它的栈/TLS/FPU 区**必须被回收**（否则那是"加了 join 就泄漏"）；
④ 反向：join 一个**已经被 join 过**的线程 → 明确的错误，不是双重释放。

**归属：内核**（可等待的线程对象 + 回收策略 + 栈/优先级参数）。

**标准判定**：★ **标准要求** ★ —— `pthread_create` / `pthread_join` /
`pthread_detach` / `pthread_attr_*` 都属于 POSIX 的线程扩展（`<pthread.h>`），
是标准的正式组成部分（不是"某个实现的做法"）。
★ 两条要分开 ★ ① **"线程可等待、能取回退出码"是标准语义**（要做）；
② **"线程必须是一种内核对象 / 必须有一个线程句柄"是实现形态**（标准没有规定，
我们选句柄是因为 §1.4 的能力模型）。**不做 ② 就做不到 ①**——这是本节
"用户态做不到什么"那一栏的全部内容。

### 2.8 ★ `futex` / 等一个用户地址（K11）★

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| 内核里**完全没有**：`fe_wait_any` 只认两类目标，`FE_WAIT_MSG`（端点）与 `FE_WAIT_BITS`（通知） | `kernel/include/fe/ipc.h:125-134`（`struct fe_wait_target` 只有 `handle`/`kind`/`mask`） |
| `fe_wait_any` **没有超时参数**（5 个参数，最后一个是 `payload_cap`） | `kernel/include/fe/ipc.h:168-170` |
| `fe_wait_any` 已有"登记与再检查在同一个关中断区间"的正确形状（K4 的设计要点） | `11-kernel-next.md:205-207`（三行设计要点，第 2 行就是这个） |
| 用户态**没有** `FE_SYS_WAIT_ANY` | `kernel/include/fe/syscall.h:38-356`（枚举里没有）；分发表 `kernel/arch/x86_64/syscall.c:1457-1611`（51 个 `case`）里也没有 |
| 今天有的替代品：`fe_yield`（让出）、`fe_sleep_ms`（睡够时间）、`fe_notification_wait`（等内核对象的位） | `user/include/fe_user.h:431-432`、`:643` |
| ★ 为什么自旋在这个内核上等于**死** ★ QEMU 默认 `-smp 1`，一个自旋的等待者占着唯一的 CPU，被等的线程永远跑不到 | `17-libcxx-build.md:216-220`（"不是'慢'，是**卡死**"）；`16-selfhost-path.md` §2.3 |
| ★ libc++ 的线程支持是**全有或全无** ★ 打开 `_LIBCPP_HAS_THREADS` 就必须提供 `__libcpp_condvar_wait` 这一族；而且**关掉线程就连带关掉单调时钟** | `17-libcxx-build.md` §7.1（`:1144-1183`，含上游 `support.h` 与 `__config` 的逐字依据） |
| ★ `docs/17` §2.6/§7.1 的两条候选出路 ★ | `17-libcxx-build.md:231-236`（A：内核加"等一个用户地址"；B：用通知对象伪装，代价是 `sizeof(pthread_cond_t)` 不再是平台无关常量）；`:1185-1191`（T1/T2/T3，其中 T3 = `LIBCXX_HAS_EXTERNAL_THREAD_API=ON` + 自写 `<__external_threading>`） |

**机制设计的两条候选与各自代价**：

| | **A. 内核等待队列挂在用户地址上**（真 futex） | **B. 通知对象 + 用户态重查**（"伪装"） |
|---|---|---|
| 形状 | 新等待目标类型 = `(地址空间, 用户地址, 期望值)`；内核在**同一个关中断区间**里"读用户内存的值 + 若不等于期望就入队睡眠" | 用户态对象里放一个**内核通知对象句柄**；等的人先重查用户内存的值，再 `fe_notification_wait` |
| 为什么用户态做不到 A | ★ **原子性**：检查与入队之间那一个窗口就是丢唤醒的来源；用户态无论怎么排都会留下窗口（这正是 `11-kernel-next.md:206` 那条设计要点在讲的事） | — |
| 丢唤醒窗口 | 由内核的关中断区间消掉（**这是 A 的全部价值**） | ★ **消不掉** ★ 必须在用户态用"置位之后再看一次值"的协议把它压小，而**压小不是消除**；判据只能是"压力测试跑 N 轮不出错"，那是**概率**不是**证明** |
| ABI 影响 | `pthread_mutex_t`/`pthread_cond_t` 可以是**平台原生长度**（用户态自己定） | ★ `sizeof(pthread_cond_t)` **不再是平台无关的常量**：它必须装下一个句柄与一个代际计数——而 libc++ 的 `<__external_threading>` / pthread 头**要求实现方自己声明这个尺寸**，于是"我们的 48 字节"就变成了一个必须写进文档的偏离 |
| 内核新代码 | 一条新的等待对象类型 + 接进 K4 的等待节点 + 唤醒时的重查 + **`(地址空间, 地址)` 作为键**（微内核有多个地址空间，**同一个虚拟地址在不同任务里是不同变量**——这一点在多任务下不是理论问题） | 零内核新代码（`fe_notification_*` 已有） |
| 唤醒的代价 | 唤醒时必须**逐个重查**（条件可能已被别人改回） | 广播式唤醒（通知对象置位唤醒全部登记者），于是**惊群**：N 个等待者醒来、N-1 个白跑 |
| 与 K11 的关系 | 就是 K11 | 也是 K11 的"另一条出路"，但它**不解决** `futex` 语义（原子地"检查 + 入队"是标准的定义，不是实现细节） |

**推荐 A，并把 B 明确记为"被否掉的备选"**，理由：

1. **B 的失败形态是"有时能跑"**，而这个项目把它反复列为最坏的一类
   （`18-user-fault-handler.md:429-431`：把"没准备好"变成"有时能跑"）。
2. **B 会把一个偏离写进 ABI**（`sizeof(pthread_cond_t)`），而 ABI 偏离
   是**最难撤回**的一类决定（`17-libcxx-build.md:1205-1210` 已经为
   "改 `_LIBCPP_ABI_*` 还是用官方的 `_LIBCPP_HAS_THREAD_API_EXTERNAL`"
   讨论过一次同类问题）。
3. ★ **A 需要的机制，K4 已经做对了一半** ★ `fe_wait_any` 的等待节点挂在
   **线程**身上、对象里只存线程指针（`11-kernel-next.md:205`），
   而且"登记与再检查在同一个关中断区间里"（`:206`）——**这正是 futex 需要
   的那条不变式**。工作量是"多一种目标类型 + 一个用户内存读"，不是从头造。

**A 必须先定死的两条边界（否则会写出一个不安全的内核接口）**：

| 边界 | 为什么 | 代价 |
|---|---|---|
| **用户地址必须连同"哪个地址空间"一起做键** | 两个任务的同一个虚拟地址是两个变量。只用地址做键 = **跨任务串唤醒**（症状：A 改自己的变量，唤醒了 B 的等待者 → B 提前醒来重查、发现条件不成立、又睡回去；**看起来只是慢**，实际是一个可被利用的信息泄漏面） | 键变成 `(space 指针, 地址)`，多一次比较 |
| **内核只能读那个地址、且读失败必须能退出** | 用户地址可能**未映射**（对端已经把那段 munmap 了）。内核读它会怎样取决于怎么读：走 HHDM 直接解引用会**内核 #PF**（而在异常上下文里那次读可能就在 IF=0 里） | 必须走"逐页校验 + 可失败"的读路径（`kernel/include/fe/user.h:4-5` 的 P4 纪律："内核**永不信任用户指针**"），并且**校验失败要有一个明确的返回码**（不是当作"值不相等"） |

**判据（可证伪）**：① 正向：4 线程 + 互斥量 + 条件变量的生产者/消费者跑 N 轮，
**总数精确相等**（`11-kernel-next.md:580` 的 ① 已经写好了这条）；② 反向：
把等待改成纯自旋版 → 在 `-smp 1` 下**必须卡死或超时**（证明这条机制真的存在且必要）；
③ 反向：**故意丢一次唤醒** → 总数必须对不上；④ ★ 新增 ★ **跨地址空间的反向**：
两个任务在**同一个虚拟地址**上各等各的，唤醒其中一个 → 另一个**不许**被唤醒
（这一条专门堵"只用地址做键"的错误实现）。

**归属：内核**（等待对象 = 用户地址 + 地址空间）。

**标准判定**：★ **标准要求（但它的名字是 `pthread_mutex_*` / `pthread_cond_*`，
不是 `futex`）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `pthread_mutex_lock/unlock`、`pthread_cond_wait/signal/broadcast`、`pthread_once` | ★ **标准要求** ★ | 它们要求"**原子地检查条件并睡下、被唤醒后重新检查**"这条语义（`pthread_cond_wait` 还要求与互斥量原子地配对），这是标准的定义，不是实现细节 |
| **`futex` 这个系统调用本身** | ⚠ **不是标准**（Linux 专有） ★ | ★ 这是本节最容易混的一处 ★ 我们**不做 `futex` 这个接口**，我们做的是"**能实现 `pthread_cond_wait` 语义的那条内核机制**"（等待对象 = 用户地址 + 地址空间）。名字与号都是我们的（§1.2.5 第 (1) 条）。**判定依据是"标准要什么语义"，不是"Linux 有什么接口"** |
| `SIGEV_THREAD` 一类建在标准接口之上的东西 | **标准要求** | 但它们建在信号（§2.4(b)）与线程（§2.7）之上，不额外要内核机制 |

### 2.9 `poll` / `select` / `epoll` + 超时

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| 内核机制 `fe_wait_any` **已完成**（4 组自检含 3 条反向） | `kernel/include/fe/ipc.h:232-234`（`fe_selftest_wait_any`）；`11-kernel-next.md` §8（`:189-275`，含双环境实测输出） |
| ★ **用户态 ABI 一直挂着** ★ D4 实测证明 virtio-blk **不需要**合流，所以"第一个真实调用者"没有出现 | `docs/12-drivers.md:115`（D7 行："⬜ **用户态 ABI 待定**……ABI 继续挂着等真实调用者"）；`docs/01-milestones.md:1401-1403`（"实测没有出现。**不要为了兑现文档里的一句话而造一个调用者**"）；`11-kernel-next.md:319-324`（同一件事的原文） |
| ★ **与候选描述不符的一点** ★ 候选说"`docs/12-drivers.md` 与 `docs/01-milestones.md` 里'第一个真实调用者实测没有出现'的记录"——**两处都有，属实**；但要补一句：**这不是"没做完"，而是一个刻意的决定**（`11-kernel-next.md:273` 的边界表第一行写着"先有调用者再定 ABI，比先定 ABI 再找调用者少一轮返工"） | 同上 |
| `fe_wait_any` 的上限：**n ∈ [1,8]**，等待者表上限 **4** | `kernel/include/fe/ipc.h:151`（`n` 必须 ≥ 1 且 ≤ 8）；`11-kernel-next.md:274`（第 5 个登记者不报错也不登记） |

**把它暴露给用户态需要什么**：

| 要什么 | 代价 |
|---|---|
| 一条新 syscall + 共享 ABI 结构（`struct fe_wait_target` 与 `fe_wait_result` 必须**逐字段镜像**到 `user/include/fe_user.h`，并用 `_Static_assert` 钉住大小） | 小到中。★ 这里有一个**真实的坑** ★ `struct fe_wait_result` 里内嵌了 `struct fe_msg_header` 与 1024 字节的 `payload`（`kernel/include/fe/ipc.h:145-148`），整个结构**超过 1 KiB**——用户态要提供一块对齐的缓冲，而"两边布局漂移"的症状是"字段莫名其妙是 0"（项目已经栽过好几次：`kernel/include/fe/syscall.h:405-409` 的 `FE_TASK_STRIDE` 事故） |
| `poll`/`select` 的**投影** | 纯用户态：`pollfd[]` → `fe_wait_target[]` 的翻译、`POLLIN`/`POLLOUT` 的语义、"超时"的表示 |
| `epoll` | ★ **可以先用 `poll` 顶上，但必须如实记下"这是模拟"** ★（`16-selfhost-path.md:185` 已经写了"epoll 可以先用 poll 顶上（如实记下'这是模拟'）"）。真正的 `epoll` 语义（一次注册、长期有效、**边沿触发**）与 `poll` 不同，模拟品会在"注册一次反复等"的程序上表现不同 |

**超时怎么表达**（这是本节要回答的问题）：`fe_wait_any` **没有**超时参数
（`kernel/include/fe/ipc.h:168-170`）。三条路：

| 路 | 代价 |
|---|---|
| **① 给 `fe_wait_any` 加超时参数** | 改的是**已经验过的机制**（K4 的 4 组自检要重跑、反向对照要重写）。而且今天 `11-kernel-next.md:275` 已经把这条写在边界表里（"**超时**：`wait_any` 没有超时参数 → 与 K7（真实时钟）一起做"）——K7 **已经完成**，所以这个前置已经清了 |
| **② 用户态做超时**：把"超时"变成**另一个等待对象**（一个通知对象，由一个定时线程在到点时置位） | 纯用户态。代价：**每个需要超时的进程都要有一条定时线程**（CPU + 一个线程的栈，而线程栈是 VMA 槽，`FE_VMA_MAX = 32`，`kernel/include/fe/mm/vma.h:65`）；而且"到点"的精度受制于定时线程被调度到的时机 |
| **③ 内核提供"定时器对象"** | 见 §2.12 的定时器一节——**这两条其实是同一个决定**，不该分开做 |

★ **建议**：把 `wait_any` 的用户态 ABI 与**定时器/超时**放在**同一刀**里定，
理由与 §2.12 一样：**"超时"是两个机制的交点**，分两次做会出现"ABI 先定死、
后来发现超时要另一种形状"的返工——而 `11-kernel-next.md:273` 那条边界的
全部意义就是"别在调用者出现之前把 ABI 钉死"。

**归属**：`fe_wait_any` 的**用户态 ABI** = **内核**（已完成的机制的暴露）；
`poll`/`select` = **用户态**。

**标准判定**：★ **混合，两半必须分开写** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `poll()` 与 `select()`（含**超时**参数） | ★ **标准要求** ★ | 两者都是标准接口，超时也是标准语义的一部分（"到点返回 0 并报告什么都没就绪"）。→ 所以 §2.9 里"超时怎么表达"**不是可选问题**，是标准要求的一部分 |
| ★ **`epoll`** ★ | ⚠ ★ **不是标准**（Linux 专有） ★ | ★ 这是本节最清楚的一处判定 ★ 标准里**没有** `epoll`。→ 按 §1.2.4：**不以"支持标准"为理由做它**；今天"用 `poll` 顶上"只能算**给程序用的兼容层**，且必须如实记下"这是模拟"（`16-selfhost-path.md:185` 已经这么写了）。★ 什么时候才做 `epoll`：出现一个**非它不可**的真实程序（`epoll` 的边沿触发语义 `poll` 表达不了）★ |
| `fe_wait_any` 的 n ≤ 8 / 等待者表 ≤ 4 | ⚠ **我们的实现限制** | 标准对 `poll` 的 `nfds` 没有这个上限；改变它是实现的事，不是标准的事 |

### 2.10 文件映射 `mmap(fd)` / `msync` / 缺页转交

> ★★ **本节最重要的一条结论（它决定文件映射的实现形态，不是一个细节）** ★★
>
> **`mmap(fd)` 不能做成"缺页时向用户态文件服务（fsd）问一页"。**
>
> 依据是一条**读代码得到的事实**：缺页解析跑在 **IF=0** 的异常上下文里
> ——`fe_user_resolve_fault` 由 `user_fault` 在同一次异常里调用
> （`kernel/arch/x86_64/idt.c:254-259`），而这条路上中断是关着的。
> `docs/18-user-fault-handler.md` **§2.6.1** 把这件事论证到三条例证：
> ① 所有 IDT 项都是**中断门**（`idt.c:16`、`idt.c:85`，中断门清 IF）；
> ② `isr_common` 里只有 `cld`、**没有 `sti`**（`isr.asm:49-69`）；
> ③ 全内核只有**两处**汇编级 `sti`（`idt.c:105-108`、`sched.c:1149-1150`），
> 而异常入口到 `user_fault` 之间**没有任何一处**放开中断。
> → 在 IF=0 里"向 fsd 发一条 IPC 并等回复"**必然死锁**（`fe_endpoint_call`
> 要阻塞，而它的唤醒源需要中断/节拍才能推进）。
>
> **出路（今天就能走）**：**"用户态预取 + 内核按需补页"**——
> 让用户态的文件服务**在缺页发生之前**把页准备好、以内存对象的形式挂到
> VMA 的 `frames` 上，然后走**今天已经存在**的第三条缺页路径
> （`frames != NULL` 的区间，判据在 `kernel/include/fe/user.h:92-109`）。
> **内核不回调用户态，用户态也不在缺页里等。**
>
> ★ **代价必须一起写**（否则就是假装 `mmap(fd)` 完整）：预取粒度是**整段**，
> 所以"读一个大文件的一小段"会白读；真正的按需（一页一次 IPC）今天做不到。 ★
> ★ 细节、另一条被否掉的出路（"缺页里挂起 + 让别的线程去取"）与判据见下面第 2 点 ★

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| `mprotect` **已完成**（三层链：页表 → VMA → syscall `0x91`，用户态 `fe_mem_protect`） | `kernel/include/fe/syscall.h:67-90`（`FE_SYS_MEM_PROTECT = 0x91` 与三段说明）；`kernel/include/fe/mm/vma.h:107-125`（`fe_vma_protect_range`）；`user/include/fe_user.h:462-476`（`fe_mem_protect` 与两个易踩点） |
| 它的边界是**两条**（范围必须落在同一个 VMA 内 + W^X），第三条"不许绕过写保护"被**撤回**（因为保护清单收的是磁盘 LBA，与虚拟地址没有交集） | `kernel/include/fe/mm/vma.h:113-119`；`11-kernel-next.md:541-561`（整段"被撤回的判据"） |
| ★ 文件后备映射今天**完全没有**，而且原因是**写下来的** | `kernel/include/fe/mm/vma.h:54-58`：`frames == NULL` → 匿名；`frames != NULL` → 来自内存对象；"**文件映射需要'缺页时去读文件'，那是另一个里程碑（要能睡眠）**" |
| `fe_mem_map` 映射的是**对象已有的帧**，不是"按需零页" | `18-user-fault-handler.md:473-479`（"今天根本走不通"那段，它同时说明了"用户态补不了页"） |
| 缺页解析只承认**三种**情况：栈紧邻下方、`ANON` 区间内、有后备帧的区间内 | `kernel/task/user.c:132-218`；`kernel/include/fe/user.h:92-109`（三情况的权威描述） |
| ★ 内核侧今天能用的数据来源是**VFS/inode**，而它给出的是**能直接给出字节的后端** | `15-exec.md` §8 第 3 条（`:390-392`）："内核的 VFS 今天没有 fd 概念，`fe_vfs_data` 只对**能直接给出字节**的后端有效（ramfs/引导模块）" |

**"文件后备映射"需要的内核机制**：

1. **VMA 要能表达"这一段的页从哪来"**：今天的 `struct fe_vma` 只有
   `flags` 与 `phys_addr_t *frames`（`kernel/include/fe/mm/vma.h:48-59`）。
   文件后备要加的是"**哪个 inode + 从哪个偏移开始 + 这一段覆盖文件的哪一部分**"。
   代价：`struct fe_vma` 变大，而它是 `FE_VMA_MAX = 32` 的定长数组
   （`kernel/include/fe/mm/vma.h:61-70`，整个结构今天 1.3 KiB），
   32 项 × 每项多几十字节 = 每个任务多 2~3 KiB。
2. ★ **"缺页时向用户态文件服务问一页"是一种新的缺页来源，而它与既有路径的关系
   必须想清楚** ★ 这正是本节最重要的一问：

   | 关系 | 我的结论（依据是"缺页路径能不能睡眠"） |
   |---|---|
   | 它能不能走 `fe_user_resolve_fault`（今天那条路）？ | ★ **不能** ★ `fe_user_resolve_fault` 在 `#PF` 的异常上下文里被调用（`kernel/arch/x86_64/idt.c:254-259`），而那条路上 **IF=0**（`18-user-fault-handler.md` §2.6.1 用三条读代码的事实论证过：所有 IDT 项都是中断门、`isr_common` 里没有 `sti`、全内核只有两处汇编级 `sti`）。**"向 fsd 发一条 IPC 并等回复"在 IF=0 里会死锁**——`fe_endpoint_call` 要阻塞，而阻塞等待的唤醒源可能正是需要节拍/中断才能推进的东西 |
   | 那 `vma.h:57` 的注释"要能睡眠"是不是就否掉了这条路？ | ★ **不一定，而且这里有一个更好的出路** ★ 缺页时内核**不需要**自己去读文件：它可以让**页在缺页发生之前就已经是"有后备帧"的**——也就是让**用户态的文件服务**把页准备好、以内存对象的形式挂到 VMA 的 `frames` 上（那条路**今天已经存在**：`frames != NULL` 的第三情况，`kernel/include/fe/user.h:92-109`）。★ **换句话说：`mmap(fd)` 可以做成"用户态预取 + 内核按需补页"，而不是"内核回调用户态"** ★ |
   | 代价 | 预取的粒度是**整段**（或者用户态自己决定的一段），所以"读一个大文件的一小段"会浪费；而真正的按需（一页一次 IPC）今天**做不到**，因为缺页上下文不能阻塞。**这一条必须写在文档里，不能假装 `mmap(fd)` 是完整的** |
   | 另一条出路（记下来，但今天不选） | **不在缺页里等，而是在缺页里"挂起 + 让别的线程去取"**：内核需要一个"缺页未决"状态 + 一个"页到了之后重新执行出错指令"的机制。它的代价是**新的线程状态 + 新的唤醒源**，而今天的闸门/取消点体系（`11-kernel-next.md:356-357`）没有为"半途停住的缺页"留位置。★ 这是一条**大**改动，等"预取版真的不够用"再说 ★ |

3. **`msync`**：今天文件写是"每次 `write` 就发一条写请求，服务端每轮刷盘"
   （`user/libposix/posix.c:466-469` 的 `fsync` 注释）。`msync` 的语义依赖
   "脏页"这个概念，而**今天没有脏页**（没有页缓存）。所以 `msync` 应当
   **如实返回 `ENOSYS`**，或者返回 0 并在文档里写明"它今天是无操作，
   因为没有任何东西被缓存"。★ **推荐前者**：`msync` 返回 0 而实际没同步
   会让调用者以为数据落盘了（这与 `10-posix-layer.md` §9 那条
   "静默的错误行为比报错难查"是同一条纪律）。

**判据（可证伪）**：① 正向：把一个文件映射进来、读到的内容与 `read()` 逐字节
相符；② 正向：**帧数不随映射长度线性增长**（证明是按需而不是"全读进来"）——
如果走预取版，这一条**必须改成"预取的粒度是 X"**并如实写出来；
③ 反向：映射一个**只读**文件然后写 → `#PF` 被拒（不是静默成功）；
④ 反向：文件被截短之后访问超出部分 → 明确的错误（不是读到零页）。

**归属：内核**（VMA 的文件后备表达 + 补页来源）**+ 用户态**（谁来取页）。

**标准判定**：★ **标准要求（但"谁来取页"不是标准规定的东西）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `mmap(fd, …)` 文件映射、`munmap`、`mprotect`、`msync` | ★ **标准要求** ★ | 都是标准接口；`msync` 的语义（把映射里的修改同步回文件）也是标准的 |
| ★ **"缺页时内核**同步地**去读文件"** ★ | ⚠ **不是标准要求，是实现形态** ★ | ★ **这正是上面那条结论的判定依据** ★ 标准只规定**可观察结果**（读那段地址能读到文件内容、写进去的能同步回文件），**没有**规定"哪一次缺页、由谁、用同步还是异步去填"。"用户态预取 + 内核按需补页"**同样满足标准语义**，所以它是**合法的实现形态**，不是缺口 ★ |
| ★ **代价要如实说：预取粒度 = 整段** ★ | ⚠ **是"我们的实现形态"带来的代价** | 它不影响**正确性**（读到的字节是对的），只影响**内存/IO 用量**。"读大文件的一小段"会多读——★ 这一点必须写在文档里，**但不能因此说 `mmap(fd)` 是缺口** ★ |
| `msync` 如实返回 `ENOSYS` | ⚠ **在"没有页缓存"这个实现形态下是诚实的回答** | 见本节第 3 点：返回 0 会让调用者以为数据落盘了 |

### 2.11 `sysconf` / `getrlimit` / `setrlimit`

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| K8 的原始判据："内存总量、CPU 数、页大小——内核知道，用户态猜不出来" | `10-posix-layer.md:78`（K8 行，代价写的是"小。一个 `fe_sysinfo` syscall 就够"） |
| ★ **今天没有**这样一个 syscall ★ | `kernel/include/fe/syscall.h:38-356` 的枚举里没有任何 `SYSINFO`/`SYSCONF` 类条目；分发表 `kernel/arch/x86_64/syscall.c:1457-1611` 的 51 个 `case` 里也没有 |
| 内核**确实知道**这些数：物理内存总量、页大小 | `kernel/include/fe/mm.h`（`FE_FRAME_SIZE`）；`user/include/fe_user.h:406-412`（`struct fe_mem_info` 里有 `u64 phys` / `page_count`，但那是**针对一个内存对象**的，不是全系统的） |
| **CPU 数**今天没有任何自述接口 | `16-selfhost-path.md:189` 自己写着"今天没有'CPU 数'的自述接口"；★ 而 K10（SMP）未实现，所以今天这个数**恒为 1**——★ **如实返回 1 与"返回一个写死的 1"是两回事** ★：前者在 SMP 落地之后自己变对，后者不会 |
| `TASK_LIST` 能告诉用户态"有多少任务/线程" | `kernel/include/fe/syscall.h:446-455`（`total_tasks` / `total_threads`） |
| 句柄上限：内核侧有一个定值 | `kernel/include/fe/object.h`（`FE_HANDLE_TABLE_SIZE`，`18-user-fault-handler.md:161` 引用为 **256**）；用户态 fd 上限是 **64**（`user/libposix/posix.c:55`） |

**要补什么**：一条只读的"系统自述"syscall（K8 的原话是 `fe_sysinfo`），
至少给：**页大小、物理内存页数/可用页数、CPU 数、句柄表容量、
内核版本/构建标识**。

**代价**：

| 项 | 代价 |
|---|---|
| 一条新 syscall + 一个共享 ABI 结构 | 小（与 `FE_SYS_CLOCK_INFO`（`0x8D`）同一形态——★ 而且**照它抄要注意一件事**：`18-user-fault-handler.md:289-290` 指出 `fe_clock_info` 的用户态那份**今天没有 `_Static_assert`**，别照它抄，要照 `fe_task_info`/`fe_thread_info` 那两行抄） |
| **"多少算 too much"** | ★ 这是本节真正的边界 ★ `sysconf(_SC_OPEN_MAX)`、`_SC_ARG_MAX`、`_SC_LINE_MAX` 之类**不是内核的事实**，是 libc 的常量（`FE_ARGV_MAX 16` / `FE_ENVP_MAX 8` / `FE_ARG_MAX 128` 是**内核的**限制，`kernel/include/fe/process.h:38-40`）。**内核只该回答它真的知道的那几个**，其余让 libposix 自己定常量 |
| 安全面 | 零（只读、无新权限）。★ 但要与 `TASK_LIST` 划清：`TASK_LIST` 已经暴露了"有哪些任务"，`sysinfo` 若再暴露"哪个任务在用多少内存"，那是**新的信息面**——今天不做 |

**判据**：① 正向：`sysconf(_SC_PAGESIZE)` 与内核实际页大小相符（**并且这个数
能被内核自检独立验证**，不是同一个常量被抄两遍）；② 反向：问一个**不存在**的
`sysconf` 名 → 明确返回 -1/`EINVAL`（不是 0——0 会被当成"这个限制是 0"）。

**归属：内核**（给出事实）**+ 用户态**（把事实翻译成 `sysconf` 的名字与
`rlimit` 的结构）。

**标准判定**：★ **标准要求（"回答哪些名字"是标准，"由谁回答"是实现形态）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `sysconf` / `getrlimit` / `setrlimit` 这几个**接口** | ★ **标准要求** ★ | 都是标准接口 |
| `sysconf(_SC_PAGESIZE)` / `_SC_PHYS_PAGES` / `_SC_NPROCESSORS_*` 这些**名字** | ★ **标准要求**（名字是标准定义的） ★ | 但**取值从哪来**是实现的事：我们的答案是"内核只回答它真的知道的"（§2.11 代价表第二行） |
| `_SC_OPEN_MAX` / `_SC_ARG_MAX` / `_SC_LINE_MAX` | **标准要求**（名字），⚠ **但值不是内核的事实** | 它们是 libc 的实现常量（`FE_ARGV_MAX`/`FE_ENVP_MAX`/`FE_ARG_MAX` 是**内核的**限制，`process.h:38-40`）。→ **不要**把它们塞进取值来自内核的那个 syscall |
| `uname()` | ★ **标准要求** ★ | ★ **本节新增的一条**：它是标准接口，而 `20` §1.2.5 第 (3) 条已经用"`sysconf`/`uname` 这一类"指过它——但上表**没有列它**。★ 今天它是**完全不存在**的（`user/include/posix/` 12 个头里没有 `sys/utsname.h`）。**列入 §6 第 15 条待查**（要不要与 K8 同一刀做）★ |

### 2.12 定时器：`clock_gettime` / `nanosleep` / `timer_create` / `setitimer` / `alarm`

**事实（我读到的）**：

| 项 | 今天 | 出处 |
|---|---|---|
| 单调时钟（TSC 制，纳秒） | ✅ 内核 `fe_time_ns()`，用户态 `fe_clock_ns()` | `user/include/fe_user.h:433-442`；`11-kernel-next.md` §11（K7 完成） |
| 时钟自述（频率/分辨率/来源） | ✅ `FE_SYS_CLOCK_INFO`（`0x8D`） | `kernel/include/fe/syscall.h:283-294`；`user/include/fe_user.h:444-452` |
| ★ `clock_gettime` **函数本身** | ★ **缺**（纯用户态包装：`CLOCK_MONOTONIC` ← `fe_clock_ns()`） | `17-libcxx-build.md:244`（"全项目搜 → 0 处"） |
| 绝对纳秒睡眠 | ✅ `FE_SYS_SLEEP`(ns) 把 ns 转成 ms；`fe_sleep_ms` | `kernel/arch/x86_64/syscall.c:122-130`（★ **注意粒度**：`ns / 1000000`，不足 1 ms 也要真的睡一次）；`user/include/fe_user.h:432` |
| `nanosleep` | **缺**，但底座在（`usleep` 已实现，**粒度 1 ms**） | `user/libposix/posix.c:750-758` |
| `sleep` | ✅ | `user/libposix/posix.c:744-748` |
| ★ 睡眠的**真实语义**是"至少 N 毫秒"（只会晚、不会早） | ✅ 这是**故意的**，而且有实测 | `11-kernel-next.md:448-464`（改绝对纳秒之后 VBox `sleep(20ms)` 从 5 ms 变 22 ms；代价写在 `:460-464`） |
| `alarm` / `setitimer` / `timer_create` / `timerfd` | ★ **完全没有** ★ | 全仓搜：见 §6 待查第 5 条（我能确认 `user/include/posix/` 12 个头里没有 `time.h`/`signal.h`，而这三个接口分别需要它们） |

**"定时器需要什么"——这是本节要回答的问题**。三个 POSIX 设施的性质**不同**，
不能一句话回答：

| 设施 | 它是什么 | 今天能不能在用户态做 | 代价 |
|---|---|---|---|
| **`nanosleep`** | "睡到某个**绝对**时刻"（标准里的 `nanosleep` 是相对的，但内核给的是绝对能力：`fe_thread_sleep_ms` 直接算 `fe_time_ns() + ms*1e6`，`11-kernel-next.md:448-450`） | ★ **能，纯用户态** ★ 包一层，把 1 ms 粒度如实暴露（或者向内核要 ns 粒度的睡眠——**那是一条小改动，但今天没有消费者**） | 极小 |
| **`setitimer` / `alarm`** | "到点**给我一个信号**" | ★ **不能** ★ 它需要 §2.4(b) 的信号投递。没有信号，`alarm` **无处投递** | 必须等 §2.4(b) |
| **`timer_create` / `timerfd`** | "到点**置位一个可等的对象**"（`timerfd` 是"到点让 fd 可读"，`timer_create` 默认投递信号但可以用 `SIGEV_THREAD`） | ★ **可以绕过信号** ★ 如果内核提供一个"**到点置位一个通知对象**"的原语，`timerfd` 那条路就是纯机制、不需要信号 | 见下 |

**所以内核侧真正需要的是**：一条"**在 T 时刻把某个通知对象的第 B 位置位**"的
机制。它的形状有两种：

| 候选 | 代价 |
|---|---|
| **A. 内核定时器对象**（新对象类型：`create(nt_handle, bits)` → `arm(handle, abs_ns, interval_ns)` → `cancel`） | 中。要新增对象类型 + 定时器队列 + 与既有睡眠队列的关系（★ 今天 `wake_sleepers(fe_time_ns())` 在节拍里跑，`11-kernel-next.md:448-450`——**新队列要不要与它合并，是一个必须先回答的问题**，否则会出现两套"到点"逻辑，而"两套"正是丢唤醒的温床） |
| **B. 用户态一条定时线程 + `fe_sleep_ms` + `fe_notification_signal`** | ★ **今天就能做** ★ 代价：每个需要定时器的进程一条线程（CPU + 一个线程栈 = 一个 VMA 槽，`FE_VMA_MAX = 32`）；精度受制于"定时线程什么时候被调度到"；而且**它会与 §2.9 的超时需求争同一块资源**——一个进程如果需要 3 个不同周期的定时器，就要 3 条线程或者一套用户态的定时器堆 |

**推荐：先用 B 把"能表达"这件事做出来，A 等出现"每进程大量定时器"的真实需求
再做**。★ 但要把 B 的代价写清 ★ 它把"定时"从内核的职责变成了"每个进程自己
养一条线程"，而线程栈是有硬上限的（`FE_VMA_MAX = 32`，
`17-libcxx-build.md` §4.1 已经把它列成会让 libc++ "编出来了但跑不对"的三个
硬开关之一）。

**判据**：① 正向：一个 20 ms 的 `timerfd` 到点之后 `poll` **立刻**返回可读，
且**时间差在 20 ms 与"N 毫秒 + 一个节拍"之间**（语义是"至少 N"，`11-kernel-next.md:460-462`）；
② 反向：`arm` 一个**过去**的时刻 → 立刻到点（不是永远不到）；
③ 反向：`cancel` 之后**不许**再置位（区分"取消"与"下一次不会再置位"）。

**归属**：`clock_gettime`/`nanosleep` = **用户态**；`alarm`/`setitimer` = 等
**内核**（§2.4(b)）；`timerfd` 类 = **两者**（内核给"到点置位通知"，
用户态给 fd 语义）。

**标准判定**：★ **混合（两半的处置完全不同）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `clock_gettime` / `nanosleep` / `alarm` / `setitimer` / `timer_create` / `timer_settime` | ★ **标准要求** ★ | 都是标准接口（`timer_create` 那一族也在标准里）。→ `nanosleep` 缺失是**缺口**，`alarm`/`setitimer` 必须等 §2.4(b) 的信号 |
| `CLOCK_REALTIME`（`clock_gettime` 的一个**必选**时钟） | ★ **标准要求** ★ | ★ 这一条把 §2.13 与本节绑在一起 ★：没有墙钟来源时，`CLOCK_REALTIME` 只能"如实说不支持"（`EINVAL`），而那**是缺口**，不是"我们选了单调时钟" |
| `CLOCK_MONOTONIC` | **标准要求**（可选时钟，但标准定义了它） | 我们**有**（K7，TSC 制） |
| ★ **`timerfd_*`** ★ | ⚠ ★ **不是标准**（Linux 专有） ★ | ★ 与 `epoll` 同类判定 ★ → **不以"支持标准"为理由做它**；但"到点置位一个通知对象"这条**内核机制**仍然值得做（K14），因为**标准的** `timer_create`+`SIGEV_THREAD`、以及 `poll` 的超时都要落在它上面。★ 做**机制**，不做那个**接口** ★ |
| 睡眠语义"至少 N 毫秒"（只会晚、不会早） | **标准允许** | 标准对 `nanosleep` 的要求是"不得早于请求的时长返回"——我们的语义方向**是符合的**（`11-kernel-next.md:460-462`）；要核实的是它的**最短分辨率**（`rem` 怎么填，§6 第 9 条） |

### 2.13 ★ 墙钟时间 `time()` / `gettimeofday` ★

★ **与候选描述不符的一条（口径混淆）** ★ 候选写的是"核实'今天没有 RTC、
`time()` 只能是常量'这条是否有据（`user/libposix/posix.c` 与 `docs/`）"。
**"没有 RTC"有据；"`time()` 只能是常量"这个说法不准确**——准确的表述是
**`time()` 这个函数今天根本不存在**，而"时间戳一律 0"说的是 **`stat`/`fstat`
结构里的三个时间字段**（另一个地方、另一件事）：

| 陈述 | 我读到的 | 出处 |
|---|---|---|
| 没有 RTC 驱动 | 内核里**没有任何** RTC/CMOS 访问：全仓搜 RTC/CMOS 只命中文档里的说明、`resource.c` 里的端口 `0x70`（那是**资源池自检用的端口区间**，不是 CMOS 驱动）、`tools/run_vbox.py:125` 的 `--rtcuseutc`（虚拟机参数）、`tools/run_qemu.py:199` 的 `-rtc clock=vm`（同样是虚拟机参数） | `grep RTC` 的全量命中列表（见 §6 待查第 6 条对"我搜了什么"的记录） |
| `user/libposix/posix.c` 里"时间戳一律 0"出现在 **`stat_common`**，不是 `time()` | `user/libposix/posix.c:498-500`：注释"时间戳一律 0：没有 RTC（见 docs/08 已知限制 #6 与 fsd 的说明）。★ 报 0 而不是编一个时间 ★"；`buf` 在 `:492` 被整块清零，`:493-497` 只填了 `mode`/`size`/`nlink`/`blksize`/`blocks`（★ **三个时间字段确实在这两段之间没有被赋值**——`:493-497` 就是那五行 ★） | ✅ |
| 同一条规矩在别处也有 | `user/include/posix/sys/stat.h:54`（"没有 RTC：一切时间戳都是 0"）；`user/servers/fsd/main.c:644-646`（"加 RTC 之后再补"）；`08-kernel-completion.md:398-399`（已知限制 #6） | ✅ |
| ★ `time()` / `gettimeofday` / `time.h` / `sys/time.h` 今天**不存在** ★ | `user/include/posix/` 实有 **12 个文件**（`dirent.h`、`errno.h`、`fcntl.h`、`spawn.h`、`stddef.h`、`stdio.h`、`stdlib.h`、`string.h`、`sys/stat.h`、`sys/types.h`、`sys/wait.h`、`unistd.h`），**没有 `time.h`、没有 `sys/time.h`**；`17-libcxx-build.md:248` 独立核实为"全项目搜 → 0 处" | ✅ |

**补它属于内核还是用户态**：★ **两者，但分界很清楚** ★

| 部分 | 归属 | 理由 |
|---|---|---|
| **"现在是什么墙钟时间"这个事实** | ★ **内核** ★ | 今天**没有任何来源**：没有 RTC 驱动、没有引导器给的启动时刻（`00-architecture.md:48-49` 写明内核只通过 Limine 请求结构拿信息，而 RTC 不在那份归一化信息里）。**用户态变不出一个不存在的时刻**——它最多能给出"自启动以来的秒数"（那是单调时钟的换算，**不是**墙钟） |
| **两种实现路径，代价不同** | — | ① **RTC/CMOS 驱动**（端口 `0x70`/`0x71`，走已有的资源池认领）：★ 但这是**设备语义**，而 P1 写着"内核不含任何设备驱动"（`00-architecture.md:13`）★ → 正确的做法是**用户态服务读 RTC**（它需要 `IOPORT_REQUEST` 认领 `0x70..0x71`，机制已有：`kernel/include/fe/syscall.h:99-104`），然后把"墙钟起点"交给需要它的程序。② **引导器给的时刻**（如果 Limine 协议里有日期时间字段——★ **我没有核实过**，见 §6 待查第 7 条） |
| **`time()` 的语义** | **用户态** | ★ 关键决定：`time()` 返回什么 ★ 没有 RTC 时**只能**返回"自启动以来的秒数"，而那个值**不是 Unix 时间**（它从 0 开始，而 1970 距今约 1.8e9 秒）。`16-selfhost-path.md:180` 把它写清楚了："没有 RTC，`time()` 只能给'自启动以来的秒数'，这一点必须**如实写下来**而不是编一个纪元" |
| **日历换算**（`localtime`/`mktime`/`strftime`） | **纯用户态** | 闰年/时区/`tzdata` 都不需要内核；`17-libcxx-build.md:434` 已经决定 `LIBCXX_ENABLE_TIME_ZONE_DATABASE=OFF` |

★ **这一条的真实后果要说清** ★ `configure`/`make` 用**文件时间戳**判断
"产物是不是比源文件新"。今天 `stat` 的三个时间字段**恒为 0**，
所以"新比旧"的比较退化：**0 与 0 无法排序**。这一退化
**已被记录但未实测**（`16-selfhost-path.md:882` 待查第 7 条："没有 RTC 时
'增量判断会怎么退化'仍未实测"）——**本文不编造它的症状**，只把它列为待查。

**判据**：① 正向：两次 `time()` 之间睡 1 秒，两个值**相差 1**（证明它在走，
而不是一个常量）；② 反向：加 RTC 之后 `time()` 与宿主机时间**相差在一个可
解释的范围内**（不是 0，也不是 1970）；③ 反向：**没有** RTC 时，
一个需要"文件新旧"的构建流程必须**明确退化**（重建全部，或者报错），
**不许**静默地"全部当成新文件"。

**归属：内核（或用户态 RTC 服务）给"墙钟起点" + 用户态给 `time()` 的语义**。

**标准判定**：★ **标准要求（全部），而且这是本次判定里最"贵"的一条** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `time()` / `gettimeofday()` / `clock_gettime(CLOCK_REALTIME)` | ★ **标准要求** ★ | 标准要求它们给的是**自纪元（Epoch）以来的时间**——不是"自启动以来"。→ "返回自启动以来的秒数"**不满足标准**，必须如实记成缺口 |
| `localtime` / `gmtime` / `mktime` / `strftime` | ★ **标准要求** ★ | 但它们是**纯用户态**的换算（闰年/时区），不需要内核 |
| ★ **"必须有一个 RTC 或等价的墙钟来源"** ★ | ★ **是标准语义**（由上面第一条**推出**的，不是额外要求） | ★ 关键区分 ★ 标准**没有**规定"墙钟必须来自 RTC 芯片、必须由内核读"（那是实现形态，P1 还说内核不含设备驱动）——它规定的是**结果**：`time()` 要给得出真实纪元时间。→ **用户态 RTC 服务 + 一个"墙钟起点"的来源**是合法实现形态；**"永远给不出"才是缺口** |
| `tzdata` / `tzset` 的环境依赖 | **标准要求**（行为可配置） | `TZ` 环境变量是标准的；`17-libcxx-build.md:434` 已决定关掉 libc++ 的 IANA tzdata——那是**数据**问题，不是机制问题 |
| ★ **Unix 纪元 1970-01-01 本身** ★ | ⚠ **是标准的取值约定，不是"照某个实现抄"** ★ | 有人会把它当成"Linux 的东西"——**不是**：纪元与"自纪元起的秒"是标准定义的（`<time.h>` 的语义）。★ 但"**必须**用 Unix 纪元"这件事要等 §6 第 7 条（Limine 有没有日期时间）与本节两种来源定下来再写死 ★ |

### 2.14 `sched_yield` / 优先级 / `sched_setscheduler`

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| `fe_thread_yield` 用户态可调 | `user/libfe/libfe.c:95-98`（`FE_SYS_THREAD_YIELD`）；`kernel/include/fe/syscall.h:41`（`0x02`） |
| ★ 让出的语义**刚被修过一次**（"唯一可运行的非空闲线程"时退化成空操作） | `11-kernel-next.md:571-635`（`sched.c:607-635` 的判据三条）；判据 `fe_selftest_yield`（`schedtest.c:436`） |
| 用户线程优先级**写死** `FE_PRIO_NORMAL` | `kernel/task/user.c:538-539` |
| **用户态设不了优先级**：`sys_thread_create` 的 5 个参数里没有优先级，`flags` 一路透传之后**被忽略** | `kernel/arch/x86_64/syscall.c:116-120`；`kernel/task/user.c:498-501`（`(void)flags;`） |
| 内核**有**优先级概念（32 级 / 时间片） | `kernel/include/fe/sched/thread.h:107`（`u32 priority`）；`kernel/include/fe/sched/thread.h:184` / `kernel/include/fe/sched/sched.h:18`（创建时带 `priority` 参数） |

**要补什么**：

| 项 | 归属 | 代价 |
|---|---|---|
| `sched_yield` | **用户态**（包一层 `fe_yield`） | 极小。★ 但要注意它的**语义**：标准里的 `sched_yield` 在只有一个可运行线程时**应当立刻返回**——而这一条**刚刚**才被修对（`sched.c:607-635`），所以今天在用户态包一层是**真的**符合标准的，这在之前不是 |
| `sched_getaffinity` / CPU 数 | **两者** | 依赖 §2.11 的 `sysinfo`（今天 CPU 数恒为 1） |
| `sched_setscheduler` / `setpriority` / `nice` | ★ **内核**（一条新 syscall）★ | 中。★ **这是本节最需要写代价的一条** ★ 让用户态**任意**设优先级 = 让任何进程能把别人饿死（今天的调度器是 32 级优先级 + 时间片，"让出"的语义刚刚才修对，见 `sched.c:571-606`）。**所以这条要带边界**：① 只能**收窄**（降低自己的优先级，或者给**自己创建/持有的**任务设）；② 需要一个"最低优先级下限"防止把自己饿死（否则一个 `setpriority` 到最低的进程会变成"看起来卡住"）；③ 判据必须包含**反向**："A 把优先级设到最低之后，B 的 CPU 时间**必须真的变多**"——否则测的是"syscall 返回了 0" |
| 实时调度（`SCHED_FIFO`/`SCHED_RR`） | **明确不做** | 它需要优先级继承/天花板协议才能安全（否则一次优先级反转就能锁死系统），而今天**没有任何调用者** |

**归属**：`sched_yield` = 用户态；优先级相关 = **内核**（带"只能收窄"的边界）。

**标准判定**：★ **混合（一条必选 + 一族可选）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `sched_yield()` | ★ **标准要求** ★ | 它是标准接口（进程调度那一族） |
| `sched_setscheduler` / `sched_getscheduler` / `sched_setparam` / `setpriority` / `nice` | ★ **标准要求**（接口在标准里） ★ | → "用户态设不了优先级"是**能力缺口** |
| `SCHED_FIFO` / `SCHED_RR`（实时策略） | ⚠ **标准里的可选特性**（Real-time 扩展，`_POSIX_PRIORITY_SCHEDULING` 那一族） | ★ 判定 = **不是必选**，可以选择不支持，**但必须如实声明**（`sysconf(_SC_SCHEDULING_...)` 或让 `sched_setscheduler` 返回 `EINVAL`）——**不许静默当成 `SCHED_OTHER` 接受** ★ |
| `sched_getaffinity` / `sched_setaffinity` | ⚠ **标准要求接口；但我们的 CPU 数今天恒为 1** | 依赖 K10（SMP，编号已占用）。今天如实返回"只有一个 CPU"是**正确的**，不是缺口 |

### 2.15 `execve` 的 `envp`

**事实（我读到的）**：

| 事实 | 出处 |
|---|---|
| `exec` 已落地（`sys_exec` + `fe_exec`，syscall `0x90`） | `kernel/include/fe/syscall.h:340-353`；`kernel/arch/x86_64/syscall.c:1158`（`sys_exec`）；`kernel/task/process.c:475`（`fe_exec`）；`user/libfe/libfe.c:306-309` |
| ★ **环境今天为空**，而且是**压了一个 NULL 终止符** ★ | `kernel/task/process.c:109`（`push8(as, &sp, 0); /* envp 终止符（环境目前为空） */`） |

| 代价已经写过一次 | `15-exec.md` §8 第 2 条（`:387-389`）："**没有 `envp`**：`build_initial_stack` 今天压一个 NULL 终止符，环境为空。加环境需要同一个'先拷进内核'的处理（那时真的需要，因为环境可能来自别处），今天不做" |

★ **精确的表述** ★ **不是"环境变量为空"，而是"环境变量无法跨 `spawn`/`exec`
传递"**：一个进程内部的 `getenv`/`setenv` 完全可用（`environ` 由 `_start` 从栈上装），
只是那个栈上的 `envp` **永远是空表**，因为**没有任何路径能往里放东西**。

**扩展 ABI 的代价**（`15-exec.md` §8 列了"需要同一个'先拷进内核'的处理"，
这里把它展开）：

| 要什么 | 代价 |
|---|---|
| syscall 参数增加 `user_envp` + `envc`（`SPAWN` 与 `EXEC` **两个都要**，而且形状必须一致——`15-exec.md:335-337` 已经把"两者形状一致"定成规矩：调用者只需要记一套） | 小到中。★ **真正的代价在"先拷进内核"** ★ 参数与环境都可能是**几百字节到几 KB**的用户内存，而内核要有一个定长缓冲（今天 `argv` 用的是 `FE_ARGV_MAX 16` / `FE_ARG_MAX 128`，`kernel/include/fe/process.h:38-40`）。环境的上限必须**同时**定死，而且超限必须返回 `FE_ERR_RANGE` 而**不是截断**——理由已经在 `argv` 那一行写好了（`:35-37`："静默截断会让人以为是程序自己的 bug"） |
| `build_initial_stack` 要摆两段字符串与两张指针数组 | 小。★ 但它有一个**已经踩过的坑**：16 字节对齐。今天的实现里有一段专门的推导（`kernel/task/process.c:103-108`："指针区一共 n + 3 个 8 字节字…… `n` 为奇数"）。★ **加了 envp 之后 `n + 3` 变成 `argc + envc + 3`**，那段对齐推导必须**一起改**——改错的症状是"某些程序在某些参数个数下 `#GP`"（`kernel/task/user.c:519-536` 记着同一族的一次真实事故：线程入口栈少减了 8 字节，"潜伏了一年的 ABI 错误，被'打开 SIMD'这件事照出来"） |
| `posix_spawn` 要把 `envp` 真的用起来 | 小（今天 `(void)envp`，`user/libposix/spawn.c:121`） |

**判据**：① 正向：父进程 `setenv("K","V")` 之后 spawn 一个 `getenv("K")`
的程序 → 打印 `V`；② 反向：**不传**环境时子进程的 `environ[0] == NULL`
（标准允许，`user/libposix/posix.c:39` 已经这么写了）；③ 反向：
参数个数**改变**（`argc+envc` 的奇偶各测一次）→ 子进程仍然正常启动
（这一条专门堵上面那个对齐坑）；④ 反向：超出上限 → `FE_ERR_RANGE`，
**子进程不存在**（不是"起来了但环境被截断"）。

**归属：内核**（初始栈里的 envp + syscall 参数）。

**标准判定**：★ **标准要求** ★ —— `execve(path, argv, envp)` 的**第三个参数就是
环境**，它是标准的接口形状（不是"某个实现多给了一个参数"）。
→ "环境传不进子进程"是**缺口**；而且它同时影响 `posix_spawn`（`spawn.c:121`
的 `(void)envp`），所以是**一处缺口、两个调用者**。
★ 一条实现形态的说明 ★ `environ` 由 `_start` 从初始栈装（`start.asm:34-38`）
是**我们的做法**；标准只要求"`getenv` 能读到 `/usr/bin/env` 那种环境"，
没规定内核要用什么形状交过去。

### 2.16 `madvise` / `mlock` / `mremap` 这类

**事实（我读到的）**：这三个**全都没有**（全仓搜：`17-libcxx-build.md:300`
核实 `madvise` → 0 处；`mmap`/`munmap` 的 POSIX 包装也没有，
`16-selfhost-path.md:212`）。★ 但"没有"分成两类，处理方式**必须不同** ★

| 接口 | 今天能不能"如实返回 `ENOSYS`" | 理由 |
|---|---|---|
| `madvise(MADV_DONTNEED)` | ★ **不能如实成功，但可以如实失败** ★ | 它是标准里程序**释放内存**的手段。今天返回 `ENOSYS` 的后果是"内存不还"——而 `heap.c` 的 arena **本来就只增不减**（`user/libposix/heap.c:22-25` 的注释自己写着"释放不还内存给内核……进程生命周期短，今天是对的"）。**所以今天返回 `ENOSYS` 是诚实的**（调用者会知道"这个提示没人理"），而**假装成功会更糟**：程序以为内存还了。★ 但必须升级成一条记录 ★ `17-libcxx-build.md` §2.9 已经把它列为"待实测"（`:308`） |
| `madvise(MADV_HUGEPAGE/MADV_SEQUENTIAL/...)` | ✅ **可以如实返回 0 或 `ENOSYS`** | 它们是**性能提示**，不影响语义（标准明文说实现可以忽略）。★ 建议返回 `ENOSYS` 并**不是**因为"不能忽略"，而是因为"我们确实什么都没做"——两者在调用者看来一样，但 `ENOSYS` 让调试者知道真相 ★ |
| `mlock` / `munlock` | ★ **需要内核，且今天是"假需求"** ★ | 它保证"这段内存**不被换出**"。★ **今天没有换页**（没有 swap、没有页回收——`kernel/include/fe/mm/vma.h` 里没有它），所以**所有内存都已经是 locked 的**。正确的做法是**如实返回 0 并写明理由**（"没有换页，所以这个保证已经成立"），而**不是** `ENOSYS`：`ENOSYS` 会让一个"用 `mlock` 来保证实时性"的程序走降级分支，而那个降级分支在这里**没有必要**。★ 但这也意味着：**等有了换页之后，`mlock` 必须真的实现**——这一条要写成"随换页一起做" ★ |
| `mremap` | ⚠ **Linux 专有，不是 POSIX** | 它不是 POSIX 接口（标准里没有 `mremap`）。**不需要以"POSIX 完整性"为理由做它**；如果将来某个程序（Qt/libc++ 的分配器）真的用它，那时按"某个具体程序要"的纪律评估。★ 这就是 §1.2.4 那条判据的第一次应用 ★ |
| `mmap`/`munmap` 的 **POSIX 包装** | ⚠ **必须做，但它是用户态** | 内核的 `fe_mem_map`/`fe_mem_unmap` 已有（`user/include/fe_user.h:453-461`），缺的是"匿名 `MAP_ANONYMOUS` 的语义"（内核侧要一个"不基于对象"的映射来源——★ **这一条要单独核实**：今天 `fe_mem_map` 收的是**内存对象句柄**，所以纯匿名 `mmap` 必须先 `mem_alloc` 一个对象。这不是"做不到"，是"每次匿名映射多一个对象"） |

**归属**：`madvise` = 用户态（如实回答）；`mlock` = **用户态如实返回 0 +
文档写明"没有换页"**；`mremap` = 不做（非 POSIX）；`mmap` 包装 = 用户态。

**标准判定**：★ **混合（这一节是 §1.2.4 判据用得最多的一节）** ★

| 项 | 判定 | 说明 |
|---|---|---|
| `madvise` / `mlock` / `munlock` / `munmap` / `mmap` 的**匿名映射**（`MAP_ANONYMOUS`） | ★ **标准要求** ★ | `madvise`/`mlock` 都在标准里；`MAP_ANONYMOUS` 也在（★ 但要核实我们这棵树里对它的支持形态——§6 第 8 条 ★） |
| ★ **`mremap`** ★ | ⚠ ★ **不是标准**（Linux 专有） ★ | **不做**，并按 §1.2.4 明写它是附加行为 |
| `madvise(MADV_HUGEPAGE)` / `MADV_FREE` 一类**建议值** | ⚠ **部分不是标准**（大页建议是各实现的扩展） | 它们本来就可以被忽略，所以"返回 0 或 `ENOSYS`"都合规；★ 判定要点是：**不要把扩展的建议值当成"标准要求的提示"** ★ |
| ★ **`mlock` 返回 0 的依据** ★ | ★ **是标准语义 + 我们的实现事实** ★ | 标准要求"锁定之后不会被换出"；**今天没有换页**，所以该保证**已经成立** → 返回 0 是**真的**。★ 一旦有了页回收，返回 0 就变成谎话（这一条已写进 §7 与 §3.2 第九步）★ |
| `mlock` 的 `RLIMIT_MEMLOCK` 上限 | **标准要求**（受 `getrlimit` 约束） | 与 §2.11 相邻：`setrlimit(RLIMIT_MEMLOCK)` 今天也没有承载体 |

### 2.17 明确不做 / 不要求（每条写理由）

**标准判定**：★ **这一节按 §1.2.4 分成两类，判定写在表里** ★
★ **"明确不做"有两种，处置完全不同** ★

- **判定 = 不是标准（某个实现的附加行为）→ 不做，而且不做不需要理由之外的辩解。**
  今天属于这一类的有：`ptrace`（Linux 专有）、`/proc` 的布局（标准没规定 procfs）。
- **判定 = 标准要求，但内核侧没有缺口 → 不是"不做"，而是"内核已经给全了"。**
  今天属于这一类的有：System V IPC、`aio`。
  ★ **这两条最容易被误读成"我们不支持标准"——必须按下面表里的措辞写清楚** ★

| 不做 | 标准判定 | 理由（每条都要能回答"什么时候会咬人"） |
|---|---|---|
| **`ptrace`** | ⚠ ★ **不是标准**（Linux 专有） ★ | 它需要内核能**停住另一个任务的任意时刻**并读写它的内存/寄存器。今天的内核**没有"暂停另一个线程"这个原语**（只有终止，`kernel/include/fe/syscall.h:263-281`），而"暂停"会引入一整套新状态（被暂停的线程在闸门/取消点上算什么）。★ 更硬的一条：**它需要 `cs`/`ss` 级别的现场篡改**，而 `18-user-fault-handler.md` §3.1 把"用户态能改内核态现场"明确列为**提权漏洞**并要求拒绝——`ptrace` 的语义与那条边界正面冲突。**没有调试器需求之前不做。** |
| **`/proc` 文件系统** | ⚠ ★ **不是标准**（标准没有规定 procfs） ★ | 它是**策略**（把内核状态投影成文件）。项目已经有 `devfs`（`00-architecture.md` §9：服务发现走 VFS，不建平行注册表）+ `TASK_LIST`（只读快照，`kernel/include/fe/syscall.h:168-179`）。★ 真要 `/proc`，它是一个**用户态服务**在 ramfs/devfs 上拼出来的（数据源是 `TASK_LIST`），**不是内核新后端**。今天不做是因为**没有 procfs 消费者**（`10-posix-layer.md:268` 已经记了"POSIX 里没有'我在哪'的接口（没 procfs）"这个后果）。 |
| **System V IPC**（`shmget`/`msgget`/`semget`） | ★ **是标准要求**（XSI 那一族）★ ★ **但内核侧没有缺口** ★ | ★ **它不是"不做"，而是"内核该给的已经给全了"** ★ 它是标准里最"重复"的一块：同一批能力在三处都有——System V、POSIX（`shm_open`/`mq_*`/`sem_*`）、以及本项目已有的"端点 + 内存对象 + 通知对象"（`00-architecture.md` §3 的机制清单第 5 条）。→ **System V IPC 完全是用户态**（建在端点/内存对象上）。★ 缺的是**用户态那一层**，而那一层不是本项目的交付物（§1.1）★ |
| **`aio`**（`io_submit`/POSIX `aio_*`） | ★ **混合**：POSIX `aio_*` 是标准；`io_submit`（Linux 的 `libaio`/`io_uring` 那套）**不是** ★ ★ **但内核侧没有缺口** ★ | 它要的是"**异步 I/O 完成通知**"，而内核已经有通知对象（可等、可置位，`kernel/include/fe/syscall.h:52-54`）。★ 真正的阻塞是**文件 I/O 服务（fsd）的协议是同步的**（一次请求一条回复，`user/libposix/posix.c:317-333`）——那是**用户态服务**要改的，不是内核。**今天不做：没有消费者。** |
| **完整信号语义里的作业控制**（`SIGTSTP`/`SIGCONT`/`SIGTTIN`/`SIGTTOU`/前台进程组） | ★ **是标准要求** ★（作业控制与 `SIGTSTP` 那一族都在标准里） | ★ 它需要三样今天**都没有**的东西 ★ ① 进程组/会话（§2.5）；② "**暂停一个任务**"的原语（同 `ptrace` 那一条：今天只有终止）；③ **控制终端**（TTY 语义：前台进程组、行规程）——而 `user/libposix/posix.c:110-113` 明确写着"今天的内核只给用户态两样标准流……真正区分它们需要 TTY 语义（行规程、作业控制），那是另一个里程碑。此刻诚实的做法是：三个标准 fd 都通向控制台，并把这一点写下来，**而不是假装有 TTY**"。**三者任一不做，作业控制都做不成。** ★ 这是本节里"标准要求但今天确实做不到"的那一类，不能混进"附加行为" ★ |
| **网络（socket/DNS/TLS）** | ★ **是标准要求** ★（socket 那一族在标准里） | 没有 TCP/IP 栈（`00-architecture.md` §4 的 `netd`/`ipd` 还只是设计），且它**不挡**"普通 C 程序"这一类（`10-posix-layer.md:154` 的原文）。★ 修它属于用户态服务（网卡驱动 + 协议栈），内核侧需要的机制（MMIO/DMA/MSI-X/中断→通知）**已全部完成**（`12-drivers.md:116` 的 D8 行）。★ |
| **动态链接（`dlopen`/`.so`）** | ★ **是标准要求** ★（`dlopen` 那一族在标准里） | 但**内核侧不需要新机制**：它是"用户态 loader + 文件格式"的事。独立项目（`10-posix-layer.md:155`）；`qtbase` 在 `-static` 下可编（`16-selfhost-path.md:187`），而"能编出来"与"能加载插件"是两条不同的要求。 |

★ 这一节的结论（一句话）★ **"明确不做"里只有 `ptrace` 与 `/proc` 的布局是
§1.2.4 意义上的"附加行为、不做"；其余五条要么是"内核已经给全、缺的是用户态"，
要么是"标准要求但今天被别的机制挡着"——三种情况的说法不能混。**

## 3. 优先级与顺序

### 3.1 排序的判据（照 `11-kernel-next.md` §3 的写法：**挡谁**）

本文的排序只用两条判据，**不用"重要性"这种形容词**：

| 判据 | 含义 |
|---|---|
| **D1 它挡多少个 POSIX 设施** | 一个机制被多少个"今天做不到"的接口共同依赖 |
| **D2 它挡不挡别人（是不是前置）** | 没有它，后面某项**一步也走不了**（而不是"做完更好"） |

### 3.2 建议顺序（每条给一句顺序理由）

```
第一步（已完成，不在本文范围）：K6 2c 收尾 + mprotect —— 见 11-kernel-next.md §3/§13
第二步：K5 用户态异常处理者（0x92/0x93）      ← 设计已完成，只等实现
        理由：它是 C1（"用户态能表达的执行模型"）的最后一项（11-kernel-next.md:590-596），
              而且它与 (b) 异步信号要共用的"投递时机"（闸门）在同一片区域
第三步：K11 "等一个用户地址"（futex 语义）      ← 挡的设施最多的一条
        理由：D1 最高（pthread_mutex/cond/once/key + std::mutex/condition_variable/
              thread/call_once + 所有建在 condvar 上的东西），
              而且它是 libc++ 线程支持的硬前置（17 §7.1 全有或全无）
第四步：K12 可等待的线程对象（pthread_join）    ← 与第三步互补，不能合成一刀
        理由：D2 —— 只有 futex 而没有 join，pthread 仍然是残缺的；
              但两者改的是不同的东西（一个加等待对象类型，一个加线程对象生命周期与回收策略），
              分开做可以让"出错时归因清楚"（11-kernel-next.md:297-301 的两刀纪律）
第五步：K13 spawn/exec 带上"初始句柄组 + envp"  ← 把 posix_spawn 补成能用的形状
        理由：D1 高（file_actions + dup2 重定向 + envp 一次性解决），
              而且它们改的是**同一个函数的两段**（build_initial_stack + 句柄安装），
              合成一刀比拆开便宜
第六步：K14 到点置位通知对象（定时器 + wait_any 超时）
        理由：★ 这两件事必须同一刀 ★（见 §2.9 与 §2.12）：
              "超时"是 wait_any 与定时器的交点，分两次做必然返工
第七步：K8 sysinfo（页大小/内存/CPU 数/句柄上限）
        理由：D1 中（sysconf + getrlimit + sched_getaffinity + idealThreadCount），
              但它是**只读**的、"便宜且无争议"，可以在任何一刀的空隙里做
第八步：K15 "非阻塞地问一次任务是否结束"（waitpid 的 WNOHANG）
        ★ 状态：待定（取决于 TASK_LIST.exited 是否够用）★
        理由：D1 低（只服务 waitpid 的一种用法），
              ★ 而且它可能**不需要内核** —— TASK_LIST 快照里的 exited 已经能读出来，
              所以这一步应该先评估"用户态拿快照够不够"，不够才加 syscall
              （**评估结论写进 §3.4 的 K15 那一行**）
第九步（等换页一起做）：mlock 的真实语义
        理由：今天所有内存都没被换出，所以 mlock 的保证"已经成立"；
              ★ 只有等有了页回收，"如实返回 0"才会变成谎言 ★
```

### 3.3 为什么这个顺序（与 `11-kernel-next.md` §4 的关系）

- **K5 排在 K11 前面**，是因为它是**已有设计的未实现项**（`18` 是完整设计：
  投递点、三个返回值、深度 1、有界轮询、七条明确不做），
  而 K11 是**设计还没定**的一条。**先把设计已经定死的做完**，
  比同时开两条"设计 + 实现"的路便宜。
- **K11 与 K12 拆成两刀**，理由是 `11-kernel-next.md:297-301` 的既成纪律：
  "2a 是让内核能安全地杀掉指定线程……**不引入任何新系统调用**；
  2b 才是 `sys_exec`。出了事归因清楚"。同理：K11 改的是**等待对象类型**，
  K12 改的是**线程对象的生命周期与回收策略**——后者会碰到
  `kernel/task/user.c:540-545` 那条"用户线程一律 `reap_ok = true`"的
  假设，而那条假设与 K11 一行关系都没有。
- **K13 排在 K11/K12 后面**，是**优先级**而不是依赖：
  `file_actions`/`envp` 不需要 futex；但它们服务的是**构建系统**（`make`/`cmake`
  用重定向），而构建系统在 S6/S7 才出现；多线程 C++ 在 S3 就出现
  （`16-selfhost-path.md` §4 的 S1–S10）。
- **K10（SMP）不在本文里** ★ 它是独立的一条线（`06-smp.md` 的 M10.0–M10.8），
  而且**编号已经被占用**。★ 但要说清一件事：**本文推荐的每一项都必须
  在 SMP 之后重新审一遍** ★ 三处最明显：① futex 的等待队列（多核需要
  per-CPU 或加锁，而今天的等待节点方案建在"关中断 = 全局互斥"上）；
  ② 信号的待决位（多核下"回用户态的路上"不再只有一个 CPU）；
  ③ `15-exec.md` §8 第 1 条的"杀其它线程"整条推理（`:383-386` 自己写着
  "**SMP 之后整条推理都不成立**……这是明确的债"）。

| 新编号 | 内容 | 为什么不占用已有号 |
|---|---|---|
| **K12** | **可等待的线程对象**（`pthread_join` 的底座：线程句柄 + 退出码 + 谁收尸） | K11 已被"等一个用户地址"占用（`11-kernel-next.md:55`、`:87`） |

② **K8（`sysinfo`）虽然排在 §3.2 的第七步，但它的编号早就有**

## 5. 代价清单（一句话版）

- **`fork`/COW：不做，并文档化为"唯一刻意偏离"。** 它需要的页表机制**内核已经
  为 `mmap`/`mprotect` 提供了**，而"复制地址空间"的结果可以用 `posix_spawn`
  表达——★ **它是"用户态做不到"的，但也是"用户态不需要"的** ★；
  真正的连锁需求（进程组/会话/信号处置/fd 继承）里有**两样今天完全没有**。
  ★ 判据是"标准里 `posix_spawn` 与 `fork` 是两个并列接口"，不是"某个实现
  也在往 `posix_spawn` 上靠"（后者只是旁证，见 §1.2.4）★
- **信号要拆成两件事，而且不能共用投递格式。** (a) 故障转交 = K5，
  现场**是现成的**（CPU 压的 `struct fe_regs`），必须在 IF=0 的异常上下文里
  **有界轮询**（`18` §2.6）；(b) 异步信号**没有现场、要自己造**，
  可以走**闸门**（回用户态的路上）。★ 共用的是"闸门"这一个时机，
  **不是**消息格式 ★ —— 把 (b) 塞进 (a) 会强制它继承 IF=0 那条最贵的约束。
- **(b) 还缺三样**：一个待决位图、一个投递时机（= 闸门）、一个"造现场 +
  `sigreturn`"的 ABI；外加一条**新的错误码 `FE_ERR_INTR`**（今天
  `kernel/include/fe/errno.h:19-45` 里**没有**它）。
- **`kill(pid)` 的真缺口不是"找到谁"，是"打断谁"。** 内核有全局任务链与
  id/名字查询（`kernel/include/fe/task.h:102-113`），`TASK_LIST` 已经把 id
  暴露给用户态（`kernel/include/fe/syscall.h:168-179`），而且项目**已经**
  为设备管理器开过一个"按 id 授予"的口子并写下了代价
  （`FE_SYS_RESOURCE_GRANT_ID`，`:210-234`）。→ 推荐的**用户态注册表**是
  `devfs` + 句柄传递 + `FE_RIGHT_TERMINATE` 的组合，代价是
  **没登记过的进程杀不掉**（这是能力模型与标准语义的真实差异）。
- **`waitpid(-1)` 已经实现了**（`user/libposix/spawn.c:200-212`），
  而且**没有用多对象等待**；真缺的是"等任意一个已退出的"语义与 `WNOHANG`
  （后者可能**不需要内核**：`TASK_LIST` 的 `exited` 已经够读）。
  ★ 另外 `SPAWN_MAX = 16` 是用户态自己的上限（`:25`）★
- **`dup`/`dup2` 已在用户态，但有一处语义与自己的注释相反**：
  `fd_entry.shared` 这个共享节点指针**只被声明、从未分配也从未被读过**
  （`user/libposix/posix.c:71` 声明，`:436`/`:456` 是整条结构体对拷）
  → **dup 出来的 fd 不共享偏移**，而文件头 `:15-17` 写的是"共享"。
  ★ 不需要内核，但必须改代码或必须改文档 ★
- **`close-on-exec` 的底座已经有了**：`exec` 不动句柄表
  （`kernel/include/fe/process.h:197-199`），缺的只是"exec 时关闭指定句柄"。
- **`pthread_join` 缺的不是实现，是原语**：`fe_thread_create` 只给一个
  **id**（`kernel/task/user.c:546`），内核的 `fe_thread_join` 收**内核裸指针**
  且是**有界自旋**（`kernel/sched/sched.c:1276-1317`，上限 2000 万轮，
  超时后**放弃并 free**）。要补的是"**可等待的线程对象**"（K12）。
- **`futex`/K11 是挡得最多的一条**，而且 K4 **已经做对了一半**：
  等待节点挂在线程身上、登记与再检查在同一个关中断区间里
  （`11-kernel-next.md:205-206`）——**那正是 futex 需要的不变式**。
  ★ 两条必须先定死的边界 ★ 键必须是 `(地址空间, 地址)`（否则跨任务串唤醒），
  读用户内存必须**可失败**（P4：内核永不信任用户指针）。
- **`wait_any` 的用户态 ABI 挂着**，而且**这不是欠债是纪律**
  （`11-kernel-next.md:273`：先有调用者再定 ABI）。★ 暴露它有一个具体代价 ★
  `struct fe_wait_result` 内嵌 1024 字节载荷（`kernel/include/fe/ipc.h:145-148`），
  超过 1 KiB；两边布局漂移的症状是"字段莫名其妙是 0"（项目栽过：
  `FE_TASK_STRIDE` 事故，`kernel/include/fe/syscall.h:405-409`）。
- **★ 超时必须与"到点置位通知对象"同一刀做 ★** 因为"超时"是
  `wait_any` 与定时器的**交点**（§2.9 与 §2.12 是同一个决定）。
- **`mmap(fd)` 不能走"缺页时向 fsd 问一页"**：缺页路径在 **IF=0** 的异常
  上下文里（`18` §2.6.1），而"发 IPC 并等回复"在那里会死锁。
  → 出路是"**用户态预取 + 内核按需补页**"，它建在**今天已经存在的**
  第三情况上（`frames != NULL`，`kernel/include/fe/user.h:92-109`）。
  ★ 代价：预取粒度是整段，所以"读大文件的一小段"会浪费——**这一点
  必须写在文档里，不能假装 `mmap(fd)` 是完整的** ★
- **`msync` 应如实返回 `ENOSYS`**：今天没有页缓存、没有脏页，
  返回 0 会让调用者以为数据落盘了。
- **`mlock` 应如实返回 0**（不是 `ENOSYS`）：今天**没有换页**，所以它的保证
  **已经成立**；`ENOSYS` 会让"用 mlock 保实时性"的程序走没必要的降级分支。
  ★ 等有了页回收，"如实返回 0"就变成谎言——这一条要随换页一起做 ★
- **`sysconf` 的边界**：内核只回答**它真的知道的**（页大小、内存页数、CPU 数、
  句柄表容量）；`_SC_OPEN_MAX`/`_SC_ARG_MAX` 之类是 libc 的常量。
  ★ CPU 数今天恒为 1（K10 未落地），但**"如实返回 1"与"写死 1"是两回事** ★
- **`time()` 不是"只能给常量"，而是"不存在"**：没有 RTC 有据
  （内核里没有任何 RTC/CMOS 访问），"时间戳一律 0"说的是
  **`stat` 结构里的三个字段**（`user/libposix/posix.c:498-500`）。
  补它**必须有一个墙钟来源**（RTC 在用户态服务里读、或引导器给的时刻），
  而"`time()` 返回什么"是一个**语义决定**：没有 RTC 时它只能给
  "自启动以来的秒数"（`16-selfhost-path.md:180`）。
- **`sysconf`/`getrlimit` 的 syscall 与"墙钟来源"今天都不存在**，
  而它们是**只读、无新权限**的——属于"便宜且无争议"的一类。
- ★ **K15 是"待定"，不是"已定"** ★（§3.4）：它是否该存在取决于
  `TASK_LIST` 的 `exited` 字段够不够表达"非阻塞问一次"（§6 第 3 条）。
  ★ **够就撤回它**——"不要为了兑现一张清单而造一个 syscall"与
  `11-kernel-next.md:324` 那条纪律是同一条 ★
- **`alarm`/`setitimer` 必须等 (b)**（它们要投递信号，而信号无处投递）；
  **`timerfd` 类不必等**（它只要"到点置位通知对象"）。
- **`sched_setscheduler` 要带"只能收窄"的边界**：让任何进程任意设优先级 =
  让任何进程能把别人饿死——而"让出"的语义**刚刚**才修对
  （`11-kernel-next.md:571-635`）。
- **实时调度（`SCHED_FIFO`/`SCHED_RR`）明确不做**：没有优先级继承/天花板协议时，
  一次优先级反转就能锁死系统。
- **`envp` 的代价在"对齐推导"上**：`build_initial_stack` 有一段 16 字节对齐的
  推导（`kernel/task/process.c:103-108`），加了 `envc` 之后 `argc + envc + 3`
  的奇偶必须一起改——★ 同一族的事故已经发生过一次（线程入口栈少减 8 字节，
  "潜伏了一年的 ABI 错误"，`kernel/task/user.c:519-536`）★
- **不做 `ptrace` 的理由与"内核态现场不许被用户态接管"是同一条**
  （`18` §3.1：那是**提权漏洞**与特性的分界线）。
- **不做 `/proc`/System V IPC/`aio` 的共同理由是"内核该给的已经给了"**：
  `/proc` 的数据源是 `TASK_LIST`；System V IPC 的三样能力（共享内存/消息/信号量）
  内核分别用内存对象/端点/通知对象提供了；`aio` 的完成通知用通知对象。
  ★ **"不在内核做"不等于"做不到"** ★
- **`mremap` 与 `/proc` 的布局不是 POSIX 要求**，是某个实现的附加行为
  （§1.2.4）——**"支持标准"不构成做它们的理由**。
  ★ 同类的还有 `epoll`、`timerfd`、`ptrace`、Linux 的 `signalfd`/`SA_RESTORER`
  ——**§2 每一节的"标准判定"里逐条列了**（§2.0 说明了三种判定的处置方式）★
- ★ **`dup` 偏移不共享是"实现错了"，不是"我们选了另一种语义"** ★
  （§2.3 的标准判定）：标准要求 `dup` 出来的两个 fd 共享同一个打开文件描述，
  文件头 `posix.c:15-17` 写的正是标准。**处置 = 改实现**（把 `fd_shared`
  真的分配出来、带引用计数），★ **但不在本轮动**：`user/` 正被 2c 占用，
  登记为 §6 第 13 条的**待办**，等 2c 落地后单独一刀 ★
- **作业控制的三个前置（进程组/会话、暂停原语、控制终端）今天一个都没有**，
  而第三样在内核里是被**明确拒绝**的（`user/libposix/posix.c:110-113`：
  "而不是假装有 TTY"）。
- **本文一行代码都不改、不跑构建、不跑虚拟机**：另一个执行体正在独占构建与
  QEMU/VBox。★ **本文没有一个实测数字**，凡是没读到的都写进了 §6 ★
