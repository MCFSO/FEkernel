# 驱动：现在的处理方式，与"跑 Linux 驱动"的路线

> 本文回答三个问题：**今天的驱动模型是什么**、**Linux 驱动能不能用**、
> **要走到那一步内核还缺什么**。最后一条是本项目的工作清单。
>
> 进度：D1/D2（§4）、D3（§5）、D3b（§6）、D7 内核侧（§8）、
> **D4（§9，virtio-blk + DMA + 共享内存批量，已在 QEMU 上达标）**。

## 1. 今天：内核里没有驱动

这是 `00-architecture.md` 的 P1（内核只放机制）最直接的落点。
实测：内核里唯一碰设备端口的代码是 `arch/x86_64/reset.c` 向 `0x64` 写 `0xFE`
（那是"让机器重启"，不是驱动）。其余 **0 行设备语义**。

```
内核提供三种硬件手段的「认领 + 检查」：
  I/O 端口  fe_ioport_request  → ① 从资源池认领（互斥）② 写本任务 TSS 位图
  MMIO      fe_mmio_map        → 从资源池认领 + 关缓存映射 + 禁止映射可用内存
  IRQ       fe_irq_register    → 从资源池认领 + 中断只投递到通知对象
驱动住在用户态（ring 3），按路径发布到 devfs 供客户端发现。
```

| 服务 | 认领的端口 | IRQ | MMIO | 发布名字 | 完成方式 |
|---|---|---|---|---|---|
| `blkd`（ATA PIO） | `0x1F0..1F7`、`0x3F6` | 14（占位） | — | `/dev/blk0` | 轮询 |
| `kbd`（PS/2） | `0x60..0x64`（共享） | 1 | — | 推送到控制台 | 阻塞等通知 |
| `mouse`（PS/2） | `0x60..0x64`（共享） | 12 | — | 推送到控制台 | 阻塞等通知 |
| `consoled` | — | — | 帧缓冲整段 | `/dev/console` | 拥有屏幕 |
| `fsd`（FAT32） | — | — | — | `/dev/fs0` | 经 blkd 读写 |

三条已经成立的性质（都有反向测试）：

- **没认领就碰硬件 = `#GP`**：`drvdeny` 故意不认领就 `in`，被 CPU 逐条指令拒绝
  （双环境实测向量 13）。这是 TSS I/O 位图的作用，不是软件检查。
- **可用内存不能被映射为 MMIO**：`sys_mmio_map` 拒绝，否则驱动能拿到
  一块可写映射直接改内核数据结构。
- **共享区间有协作锁**：PS/2 的端口物理上分不开（键盘 IRQ1、鼠标 IRQ12，
  但数据口都是 `0x60`），所以资源池能表达"中断各自独占、端口共享"。

## 2. Linux 驱动能不能用

### 二进制 `.ko`：不能

四道各自独立的墙：

| 墙 | 内容 |
|---|---|
| **执行模型** | `.ko` 是内核态代码（`module_init`、直接碰寄存器）。我们的驱动模型是用户态进程用能力认领硬件 |
| **符号面** | 一个 e1000.ko 依赖 `request_irq`/`ioremap`/`dma_alloc_coherent`/`pci_register_driver`…。要"能加载"就得先把这些**内核内部 API** 实现出来 |
| **子系统** | 网卡驱动挂在 netdev/NAPI/`sk_buff` 上，块驱动挂在 block layer（`gendisk`/`bio`）上。**这些比驱动本身大得多** |
| **内核内环境** | `vmalloc`/`spin_lock`/`workqueue`/`completion`/`jiffies`/`printk`——用户态没有这些语义 |

### 源码级移植：可行，且有成熟先例

| 项目 | 做法 |
|---|---|
| **Genode（DDE Kit）** | 提供"Linux 内核 API 的用户态实现"，让驱动源码几乎原样编译成组件 |
| **HelenOS** | 同样思路：驱动跑用户态，用 shim 映射到自己的原语 |
| **rump kernel（NetBSD）** | 极端版本：把整个驱动栈"去内核化"成用户态库 |

**共同点**：都不是"加载 `.ko`"，而是**提供一层足够像的内核 API 让驱动源码能编**。
那一层 shim 本身就是项目级的工程量（对 e1000 这种设备大约一两万行，
且要跟着 Linux 版本走）。

## 3. 目标形态：驱动宿主服务（`drvhost`）

```
内核引导 → init（按依赖拉起服务）
            └→ drvhost（驱动宿主，用户态常驻）
                 ├─ 加载驱动包（.ko/*.drv），提供 Linux 内核 API 的仿真层
                 ├─ 通过内核的资源池认领硬件（ioport / mmio / irq / dma）
                 └─ 把设备能力发布到 devfs，客户端按路径打开

内核全程不含驱动代码；驱动**在用户态**运行，但**对内提供内核态语义**。
```

★ **这不是降低目标，而是唯一同时满足两件事的形态** ★
"跑 Linux 驱动源码" + "内核不含驱动"只有这一条路：
把内核 API 仿真成用户态库。而且它带来一个额外好处——
**驱动崩溃只死宿主进程，内核不受影响**（今天 Linux 上驱动 bug 占内核崩溃的多数）。

### 许可边界（重要，且不用改项目许可）

| 部分 | 许可 | 说明 |
|---|---|---|
| 内核、libfe、服务 | **0BSD**（不变） | 铁律里"内核 0BSD"**不受影响** |
| `drvhost` 宿主服务 | 待定（建议 0BSD） | 它只是"加载器 + 仿真层"的壳 |
| **驱动包** | **GPL-2.0**（Linux 模块本来就是 2.0-only） | 与 Linux 内核链接是兼容的；放进我们自己的包里也是独立的作品 |
| 仿真层的头文件（`linux/*.h` 形态的接口声明） | 需谨慎 | ★ **不许抄 Linux 头文件的内容**：函数原型按公开文档重写，

不复制度数/宏体。这一条与项目铁律"不许抄任何现有内核"一致 ★ |

结论：**"换证书"这件事不必发生**。驱动包是独立作品、独立许可；
内核保持 0BSD。真正要守的纪律是**仿真层不抄 Linux 的代码与头文件内容**。

## 4. 内核这一侧还缺什么（本清单是本项目要做的）

不管仿真层将来多大，**内核的接口形态现在就得对**，否则将来一行都接不上。

| # | 缺什么 | 状态 |
|---|---|---|
| **D1** | **设备管理器能力**：只有被指定的那个任务能向资源池申报硬件 | ✅ 已完成（`FE_SYS_RESOURCE_POOL_ADD`） |
| **D2** | **资源授予**：把一段硬件交给指定任务（而不是"谁先跑谁拿"） | ✅ 已完成（`FE_SYS_RESOURCE_GRANT`，用**任务句柄**而非 id） |
| **D3** | **PCI 配置空间访问**：端口 `0xCF8/0xCFC` 入池，驱动可枚举总线 | ✅ 已完成（见 §5） |
| **D3b** | `pcid` 用户态枚举服务：认领端口 → 枚举总线 → 报告设备与 BAR | ✅ **本轮完成**（见 §6） |
| **D4** | **DMA 窗口**：机制已有（`fe_mem_alloc_dma` + `fe_mem_info` 给物理地址），缺的是"设备地址从哪来"（依赖 D3） | ✅ **已完成**（virtio-blk + 共享内存批量，见 §9） |
| **D5** | **中断的更多语义**：电平/边沿、共享中断线、MSI/MSI-X（Linux 驱动大量依赖 MSI） | ✅ **已完成**（D5a 共享线 + D5b 触发方式契约 + D5c MSI/MSI-X，见 `14-interrupt-semantics.md` §6–§8）。MSI-X 实测：QEMU 上 virtio-blk 在"**没有登记 INTx**"的前提下被 MSI-X 送达（伪中断 32 / 向量 97 / `addr 0xfee00000 data 0x4061`）；VBox 本机无 virtio 设备，只跑通拒绝路径。⬜ 遗留：MSI 的目的 CPU 现在固定写给 BSP，等 K10 SMP 落地后才谈 per-CPU 投递 |
| **D6** | **`drvhost` 的加载形态**：驱动包怎么进来（initramfs 模块？磁盘上的文件？）、版本与签名 | ⬜ 设计先于实现 |
| **D7** | **`wait_any`**：驱动常常要"同时等中断和等请求"，今天必须开两条线程（见 `11-kernel-next.md` K4） | ✅ **内核机制完成**（`fe_selftest_wait_any` 4 组含 3 条反向，双环境 0 失败）；⬜ **用户态 ABI 待定**——★ 实测修正：D4 的 virtio-blk 驱动**没有**成为它的第一个调用者（完成判据是 used ring 下标，同步轮询，不需要合流），所以 ABI 继续挂着等真实调用者 |

### D1/D2 的实现（本轮）

```
kernel/resource.c   设备管理器身份（fe_resource_set_devmgr / is_devmgr / clear_devmgr）
                    资源授予（fe_resource_grant，独占与共享两条路径）
                    入池校验移进**机制层**（见下）
kernel/include/fe/syscall.h   FE_SYS_RESOURCE_POOL_ADD = 0x86 / RESOURCE_GRANT = 0x87
kernel/arch/x86_64/syscall.c  两个入口：能力检查 + 参数护栏
kernel/task/task.c            任务退出时收回设备管理器身份
```

**为什么"身份"由内核指定一次、而不是一个权限位**：谁能当设备管理器是**策略**
（由引导链决定），内核只记"是它"。这与 A/B 更新器身份（`fe_protect_note_process`）
是同一条做法。任务退出时身份随之失效——否则 id 复用就是提权。

### 本轮实测（`fe_selftest_devmgr`，双环境）

```
申报 MMIO 0xfebf0000+0x1000 → 驱动认领成功
[资源] 拒绝：0x14f000+0x1000 是可用内存，不能入池为 MMIO
可用内存不能申报为 MMIO（权限不足）
范围校验（端口越界 / IRQ 越界）+ MMIO 自动页对齐: OK
资源已从 5 转给 4（所有权唯一）
非主人不能授予（凭空转移被拒）: OK
设备管理器退出后身份失效（id 复用不会继承能力）: OK
=> 设备管理器失败项: 0
```

★ 其中两条是**反向对照**，它们才是这一组的价值 ★
"能申报硬件"很容易做到（把检查删掉也能通过）；真正要证明的是
**越权路径被堵住**：不是设备管理器的任务不能申报、设备管理器也不能
把可用内存当 MMIO 申报、不是主人不能授予、身份随退出失效。

### 一个关于分层的教训（值得单记）

第一版把那道"可用内存不能当 MMIO"的护栏**只写在 syscall 入口**，
机制函数 `fe_resource_pool_add` 一点没查。自检直接调机制函数，
于是一条都没挡住——日志里明明白白打出 **"可用内存 0x14f000 竟然能被
申报为 MMIO"**。

这暴露的不是"少写一个检查"，而是**分层放错了**：

- 机制的**不变式**（池子里只有真正可交给驱动的硬件、区间互不相交、
  在合法范围内）必须由**机制自己**维持。否则每一条新调用路径
  （引导期入池、自检、将来的设备管理器、还没写的代码）都要各自
  记得再查一遍，而**漏一个就等于没有**。
- 入口层（syscall）该管的是**谁能调**（能力检查）与**报错准不准**，
  那是策略与体验。

所以同一个检查写两层是**对的**（入口层给更准的报错），
但**机制层那一层不能省**。

## 5. D3 完成：PCI 配置空间（用户态能发现设备了）

### 做了什么

```
kernel/main.c        把 PCI 配置空间端口 0xCF8..0xCFF 放进资源池
                     （**独占**，理由见下）
kernel/resource.c    fe_selftest_pci：认领、独占、真读一次、归还后再认领
```

**为什么这两个端口要入池、而不是让内核自己读**：
"总线上有什么设备"是**发现**（要处理桥、认设备类、认厂商 ID），
那是用户态设备管理器的活。内核不该长出一个 PCI 枚举器——
那正是"内核只放机制"这条线。但"谁能碰配置空间"必须由内核裁决：
配置空间不是只读的（写 BAR、启总线主控、配 MSI 都走它），
谁能改它谁就能把设备的地址窗口挪到别人头上。

**为什么是独占而不是共享**：机制 #1 的访问是**两步**——先写 `0xCF8`
指定地址，再读写 `0xCFC`。两个任务交错就会各自改到对方的窗口。
这种"两次访问构成一次操作"的寄存器对必须独占。
（对比：PS/2 的 `0x60/0x64` 是**物理上分不开**才共享，两者不是一回事。）

### 实测（QEMU + WHPX）

```
[自检] PCI 配置空间（机制 #1：0xCF8/0xCFC）:
        PCI 配置端口是独占的（第二个认领被拒: 忙）
        PCI 配置空间可读：00:00.0 厂商 0x8086 设备 0x1237
          00:00.0 厂商 0x8086 设备 0x1237 类 0x0600   ← 主机桥（i440FX）
          00:01.0 厂商 0x8086 设备 0x7000 类 0x0601   ← PIIX3 ISA 桥
          00:02.0 厂商 0x1234 设备 0x1111 类 0x0300   ← 标准 VGA
          00:03.0 厂商 0x8086 设备 0x100e 类 0x0200   ← e1000 网卡
        释放后可被另一个任务认领（独占是暂时的，不是永久占用）: OK
        => PCI 配置空间失败项: 0
```

★ 这一段虽然只有几十行，但它是**整条"跑 Linux 驱动"路线的第一块地基** ★
从这一刻起，"内核硬编码设备地址"变成了"用户态可以发现设备"。
而这份设备清单同时是**环境指纹**：QEMU 与 VirtualBox 列出来的设备不同，
日志里一眼就能看出这份证据来自哪个环境。

### 断言写错一次（记下来，因为它是"测试的错不是机制的错"）

`fe_resource_claim(..., owner_id = 0)` 被拒——因为 `owner_id == 0` 是
**共享条目的保留值**（共享条目的 owner 恒为 0）。机制是对的，
我的断言用了一个非法的持有者 id。改成用一个真实任务 id 之后通过。
这类"断言比机制更严格"或"断言用法不对"的失败，症状与真 bug 一样，
区分办法只有一个：**把机制的真实契约写清楚**，再回头对断言。

## 6. D3b 完成：用户态枚举服务 `pcid`

### 它做什么、不做什么

**做**：认领配置空间端口 → 枚举总线 → 读出每个功能的厂商/设备 ID、
类代码、BAR、中断线 → 打印 + 发布到 devfs。

**不做**：不让设备工作、不碰设备寄存器、不分配 BAR。
真正让设备动起来要走的链是"设备管理器把 BAR/IRQ 申报给内核 →
授予某个驱动 → 驱动认领"，那条链还没接（D4）。

★ **按名字打开 `/dev/pci/00:03.0` 得到的是"能问 pcid 关于这个设备的信息"，
不是"能操作这个设备"** ★ 这个区别必须写清楚，否则客户端会以为
打开它就能读写设备寄存器——而在微内核里"设备"不是一个内核对象，
它是一段只能由内核资源池裁决归属的硬件。

### 实测（QEMU + WHPX，`pcid` 退出码 0）

### 三条边界（写清楚，不是遗漏）

| 边界 | 为什么现在这样 | 何时该改 |
|---|---|---|
| **只枚举总线 0** | 完整枚举要跟着 PCI-to-PCI 桥递归下级总线、处理 CardBus 与热插拔。而 QEMU 与 VBox 的设备**都在总线 0**，桥下面没有东西可验证——按项目一贯做法，不写"以后可能需要"的机制 | 真机上出现桥下设备时 |
| **打印 BAR 只挑 4 类设备** | 几十个设备的 BAR 会把日志淹掉。但**发布**不筛——"这个设备有没有驱动"是消费者的判断 | 永不：枚举者不该替消费者筛选 |
| **跑完就退出** | 它今天是一次性工具。要常驻得先有事件来源（热插拔），而"谁产生热插拔事件"（ACPI 注意按钮 / PCIe 存在检测）是个新问题，不该现在猜 | 做热插拔时 |

### 这一轮的分层收获（D3/D3b）

`pool_add_common` 里的"可用内存不能当 MMIO"护栏本来只写在 syscall 入口，
机制函数一点没查——自检直接调机制函数就全部漏过。已移进机制层。
**同一类错误的第二次出现**是断言的错，不是机制的错（`owner_id = 0`
被拒，因为 0 是共享条目的保留值）。区分两者的办法只有一个：
**把机制的真实契约写清楚，再回头对断言**。

## 7. 建议的第一步：virtio-blk，而不是移植 Linux 驱动
理由：

1. **它解决最痛的问题**：磁盘 0.18 MB/s（目标 200 MB/s）。根因是
   blkd 走 PIO 轮询 + 每次 2 扇区，**不是驱动能力问题**——内核的批量搬运
   能力已经证明过（1 MiB / 2000 us）。
2. **它有公开规范**（OASIS Virtio 1.x），**自己写不涉及抄任何内核代码**。
3. **内核侧 DMA 机制已经在**，只差"设备地址从哪来"（D3）。

顺序：**D3（PCI 枚举）→ blkd 走 virtio-blk + DMA + 共享内存批量传输**。
这条链走通之后，"驱动宿主 + Linux 驱动包"才有落脚点——
因为到那时内核已经能表达"发现设备 / 授予硬件 / DMA 窗口"这三件事。

## 8. D7 的内核侧已完成：`wait_any`（本轮）

驱动主循环的形态是"**等设备中断 + 等客户端请求**"的合流。没有 `wait_any` 时
只有两条写法，都别扭：

| 写法 | 代价 |
|---|---|
| 两条线程（一条等通知、一条等端点）+ 自写的唤醒逻辑 | 每个驱动作者都要把"丢唤醒"重踩一遍，而这类 bug 只在负载下偶发 |
| 单线程轮询两个对象 | 烧 CPU，或者引入延迟（轮询间隔直接变成响应延迟的下限） |

内核侧的 `fe_wait_any` 已经实现并验证（`kernel/ipc/ipc.c` +
`fe_selftest_wait_any`，4 组自检含 3 条反向对照；设计与实测见
`11-kernel-next.md` §8）。**但它今天只有内核 API，没有用户态入口**。

★ **为什么故意不急着定 ABI** ★

用户态 ABI 要一次定死三件事：等待目标数组怎么跨 syscall 边界传
（用户指针 + 内核校验）、`struct fe_wait_result`（含 1024 字节载荷）怎么回写、
以及"消息顺带收下"这件事在**有多个线程共享同一端点**时的语义。
这三条现在都只能靠猜——而猜测的代价是 ABI 兼容包袱。

**第一个真实调用者就是 D4 的 virtio-blk 驱动**（它要同时等 virtqueue 中断通知
与客户端请求端点）。让调用者先出现、再定 ABI，比先定 ABI 再找调用者少一轮返工。
这也是本项目一贯的做法：**机制先在内核里被自检证明，再让第一个真实用户把它顶出 ABI。**

## 9. D4 已完成：块设备走 DMA + 共享内存批量（本轮）

目标是一个量级：**0.18 MB/s → 200 MB/s**。结论先说：**达到了，而且超出一个量级**
（下表）。但这一轮真正花时间的不是 virtio 本身，而是"**证据本身是不是真的**"——
下面按"做了什么 / 为什么这样做 / 代价是什么 / 查出来的错"分开写。

### 9.1 为什么落到 virtio-blk 上

D4 原本打算让 `blkd` 用 ATA 总线主控（BMDMA）做 DMA。**这条路在 QEMU 上不存在**：

- `IDENTIFY` 的 w88 = `0x203F` —— UDMA 与多字 DMA 的支持位**全是 0**；
- `SET FEATURES` 被拒，在状态寄存器上留下粘住的 ERR 位（要软复位才能清）；
- 多扇区 PIO 读出 `状态 0x50 = DRDY|DSC`（**没有 DRQ**），
  而"一条命令一个扇区"完全正常。这个现象在 lba=2064/67584、
  2/8/256 扇区、有/无软复位这几种组合下一致 ⇒ 与位置、长度、复位都无关。

所以不是"慢"，是**这台机器上的 IDE 没有那条路**。virtio-blk 的数据通路本身就是
DMA（virtqueue 的每个缓冲区都以物理地址交给设备），于是它是唯一能验证
"DMA + 共享内存批量"的后端。**注意这里换的是被测对象，不是判据**——
判据仍然是"每 KiB 搬多少成本"，见 9.5。

### 9.2 一个后端契约的补充：`phys_only`

内联读（数据过 IPC 载荷）需要一个**虚拟地址落点**。而"能不能写虚拟地址"是
**传输方式**的性质，不是设备的性质：

| 后端 | 数据往哪落 | 能写虚拟地址吗 |
|---|---|---|
| ATA + PIO | CPU 从端口搬进内存 | 能 |
| ATA + BMDMA | 设备自己搬 | 不能（但它有 PIO 可退，所以整体算能） |
| virtio-blk | 设备自己搬 | **不能** |

于是 `struct blk_backend` 多了一位 `phys_only`。**为什么用声明而不是
运行期判断"是不是 virtio"**：这是关于传输方式的事实，写在后端的定义里
才和责任方一致；散在调用点的 `if (g_be == &g_vio_backend)` 会在加第三个
后端时被漏掉。

**代价**：只认物理地址的后端在内联读那条路上要垫一块自己的 DMA 缓冲，
每次多一次 1 KiB 拷贝（常量 `STAGE_BYTES`，常驻一个 4 KiB DMA 页）。
这次拷贝**不该被藏起来**——内联读之所以慢，正是因为数据必须经过服务进程。

★ 顺带修掉的一个真 bug ★ 改之前，virtio 的内联读会把
`(u64)(usize)buf`（一个**虚拟**地址）当作设备视角地址交给设备。
那不是在"效率差一点"，是**让设备往那个数字对应的物理页上写**——
也就是写进别的任务的内存。它只在"有 DMA 的机器上走内联读"时才显形，
而在这之前没有任何调用者走过那条路。现在 `phys_only` 让这条路径改走垫脚缓冲。

### 9.3 一个真正的竞态：init 可能在"内核知道它是谁"之前就跑起来

VirtualBox 上**每次**复现，QEMU 上**从不**出现：

```
[devmgr] 设备管理器：认领设备管理器身份
[资源] 拒绝：任务 init(14) 不能认领设备管理器（只有引导者 init 能，且只能一次）
[用户态异常] 线程 init 触发 通用保护错误 (#GP)
[init] /slot_a/init 已启动（任务 14, 主线程 15）—— 内核到此交棒
```

日志顺序就是答案：**新任务的那两行在"已启动"之前**。根因是
`fe_thread_create_ring3` 在返回前就把线程挂上了就绪队列（`rq_push`），
而 `fe_resource_note_init(t->id)` 原来写在 `fe_process_create` **返回之后**——
只要那一刻发生一次抢占，新任务就会在 `g_init_task == 0` 的时候去认领身份，
被拒，接着去读还没认领的 PCI 配置空间端口 → #GP → **整个用户态没起来**，
而内核自己的自检全部通过（"内核好的、用户态全灭"这种形状最容易误判）。

修法：把"这是不是引导者"作为参数传进 `fe_process_create`，
在内核**创建线程之前**记下它（和那里设 `%fs` 是同一条理由：
这是唯一能确定"接下来跑的就是它、而且它还没开始跑"的时刻）；
失败路径上撤回记下的 id，不让"引导者"指向一个马上要被销毁的任务。

**这一条的教训比 bug 本身重要**：内核里凡是"某任务将要运行"与
"内核为该任务准备好的状态"之间存在间隙的地方，都要按竞态对待——
即使在一个虚拟化平台上看它永远是对的。

### 9.4 五处错都不在被测对象身上（比被测对象错更难发现）

**(a) 一条断言假装有一道不存在的护栏。** `blkbench` 原来断言
"声明长度大于对象真实大小必须被拒"，依据是驱动里一句注释说会拒。
而实现并不拒，**而且不该拒**：驱动从不写超过 `sectors*512` 的字节，
而那个长度是被独立核对过 `<= 对象真实大小` 的；声明里多出来的部分
驱动根本不看。于是一个**正确**的驱动被判成红的。
改法是把两个方向分开验，而且都验在真正的护栏上：

- `buf_len < want`（客户端自己算错了，驱动不替它猜）→ 拒；
- `want > 对象真实大小`（**内存安全**那一条：只信声明的实现会写越界）→ 拒。

那句注释一并改掉了。**注释承诺一个不存在的护栏，比没有注释更糟**——
它会让后来的人以为那道墙在那儿。

**(b) 测试代码自己手搓协议、还搓错了。** "拿普通内存冒充 DMA 缓冲"那条反向对照
自己拼了一遍消息，只传了 1 个句柄；而这条协议的 `handle[0]` 是回复端点、
`handle[1]` 才是数据缓冲。驱动于是把那个普通内存对象当成了回复端点，
状态码回进一个不是端点的地方，客户端什么都没收到——那一版的"失败"
说明的是**测试自己的 bug**。改成调用**同一条**请求函数、只换缓冲对象，
唯一变量才是被测的那一个。

**(c) 驱动里一个把程序挂死的错。** 越界 LBA 那一支把应答回在了 `reply` 上，
而 `reply` 是内核在 `call` 路径给的回复能力；批量读走的是 `send`
（它才能带句柄），这条路上 `reply` **根本无效**。于是越界请求的应答
被扔进一个不是端点的地方，客户端在它自己建的回复端点上永远等不到——
症状是"越界读把整个程序挂住"，而不是"越界读被拒"。
这个 bug 只在反向对照里显形：正向路径每一支用的都是 `client_reply`，
所以怎么测吞吐都是好的。

**(d) 计时器分辨率不够。** 第一次测出来两个数字是 `5000 us` 和 `5000 us`——
**都正好**落在一个时钟刻度上。那个时钟粒度是毫秒级，而被测代码本身只有几毫秒，
于是"测出来的主要是时钟"。这和 `simdtest` 踩过的是同一个坑（那里两个数字都成了 0）。
改成：测量用 `rdtsc`（周期），`fe_clock_ns` 只用来在 ≥20 ms 窗口上标定
TSC 频率；预热一轮 + 取 8 轮里最快的一轮；报告里同时给"周期/KiB"，
那个数字**不依赖任何频率假设**。

**(e) 一条反向对照把设备写死在代码里。** 原来有一条断言是
"认领 `0x1F0` 必须拿到忙"——因为当时这个程序只对着系统盘跑。
而 `blkbench` 现在可以对着任何一台设备跑（`--dev`），对 virtio 盘来说
`0x1F0` 与它**无关**（那个端口归 IDE 那个实例）。于是"认领成功"是个
**正确**的结果，而断言把它记成失败：**测试绑死在一个设备上，换设备就报假失败。**
改成按驱动报出来的后端类型选判据（ATA → 端口，virtio → MMIO），
而判据本身一字未改：那段硬件窗口必须已经被驱动独占。

### 9.5 实测（QEMU + WHPX，`blkbench` 退出码 0）

同一台设备（virtio-blk，131072 扇区）、同一段数据、两条协议：

| 路径 | 每次搬多少 | 数据经过谁 | 周期/KiB | 折算 |
|---|---|---|---|---|
| 内联读（旧协议） | 2 扇区 = 1 KiB | 设备 → 驱动垫脚缓冲 → 驱动拷贝 → IPC 载荷 → 内核拷贝 → 客户端 | 130416 | 21 MiB/s |
| 批量读（新协议） | 256 扇区 = 128 KiB | 设备 → **客户端内存**（一次拷贝都没有） | 1266 | 2253 MiB/s |

**每 KiB 成本降到 1/103**（这条是断言，不是描述：低于 4 倍就是失败项）。
倍数用周期/KiB 而不是 MiB/s，是因为前者与主频、与标定无关，换平台照样能比。

"走了 DMA"这件事有独立证据，不靠吞吐数字：

- **毒值差分**：把缓冲填 `0x5A` 读一次、填 `0xA5` 读同一段，
  两次结果**逐字节相同** ⇒ 每个字节都被设备写过（没写到的字节会留下不同的毒值）。
  这一条覆盖"只搬了前几个扇区""描述符链少挂一段"。
- **跨路径对照**：同一段开头用旧的内联路径再读一遍，两者逐字节一致
  ⇒ 搬的**是这一段**（LBA 偏移错了在毒值差分下看起来完全正常）。
- **反向**：无关任务认领驱动的 virtio MMIO 窗口必须失败；
  普通内存冒充 DMA 缓冲必须被拒（状态 4）；越界 LBA、长度两个方向都必须被拒（状态 3）。

**VirtualBox 7.2 上没有 virtio-blk 设备**，于是这一轮的两条结论在那边**不成立**，
而且这件事在日志里是**明说**的（见 9.6），不是悄悄少几行。

### 9.6 边界（写清楚，不是遗漏）

1. **"这台机器上没有那样硬件"是一个独立的类别。** `struct unit` 多了 `needs`
   字段。三种"没启动"必须分开，否则 `失败项 N` 这条汇总在不同机器上含义不同：
   依赖没就绪（算失败）、负向测试的预期跳过（是**测试结论**）、
   硬件前提不成立（**既不是缺陷也不是测试**）。
   判据顺序也有讲究：硬件前提要在依赖检查**之前**判——否则报出来的是
   由它派生的假原因（"某个服务没起来"），而**报错指向错误的原因是排查里最贵的一种浪费**。
   实测：VBox 上 `vblkd`/`blkbench` 两行明说"硬件前提不成立，不算失败"。
2. **同一个驱动跑两个实例，而不是一个实例管两块盘。** "哪个盘是系统盘"
   只对引导链有意义；让一个实例管两块就得在协议里加"设备号"，
   那是把**多设备块层**这个上层概念塞进驱动，而今天没有消费者需要它。
   两个实例 + 两个名字（`/dev/blk0`、`/dev/vblk0`）是当前需求下最小且不撒谎的形态。
3. **块协议的 ABI 没有变。** 内联读（`BLK_OP_READ`）与批量读（`BLK_OP_READ_BULK`）
   的请求/应答形状一字未改，`struct blk_info` 只**追加**了字段
   （`mmio`/`mmio_len`/`backend`），老客户端读前缀仍然有效。
   换后端对客户端是不可见的——`blkread`、`fsd` 一行没动。
4. **中断只是通知源，不是完成判据。** 完成靠 used ring 下标（同步、不受投递限流影响）；
   VBox 的中断投递实测只有 49~169 Hz，把判据建在它上面会把每次请求拖到 6~20 ms。
5. **`wait_any` 仍然没有用户态 ABI。** virtio 的完成路径是同步轮询 used ring，
   所以 D7 那个"第一个真实调用者"还没有出现（见 §8）。
6. **块设备命令集仍然很小**：没有写批量（批量路径只读）、没有 discard/写零、
   没有多队列。这些都要等有消费者再定。
