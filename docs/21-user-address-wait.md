# K11「等一个用户地址」：设计

> **★ 这份文档的名字为什么不叫 `futex` ★**
> 它要做的机制在 Linux 里叫 `futex`，而 `20-posix-kernel-requirements.md` §2.8
> 逐字写着：**"我们不做 `futex` 这个接口，我们做的是'能实现 `pthread_cond_wait`
> 语义的那条内核机制'"**，判定依据是 §1.2.4（**标准要求 vs 某个实现的附加行为**）
> 与 §1.2.5（**syscall 号与名字都是我们自己的**）。
> 拿 Linux 的接口名当文件名，等于把"我们做的是哪个接口"这件事从一开始就搞混
> ——而这一条混淆正是 §2.8 花了一整张表去澄清的那一处。
> `futex` 这个词仍然在本文里出现（凡是需要与 Linux 对照的地方都写明了），
> 所以 `grep -i futex docs/` 照样找得到本文。

> **本文的地位**：`docs/20` §2.8 已经把"要不要做、两条候选、两条边界"定了；
> 本文**不重复**它已核实的事实（那一段的 `文件:行号` 我复核过，见附录 A），
> 只做它**没有**做的那几件事：**机制形状的第三条候选**、**与既有五处等待登记的
> 逐处审计**、**逐条语义与返回值**、**超时归谁**、**分刀与判据**。
>
> 读法：§1 是"为什么非有它不可"，§2/§3 是机制（**§3.4 是本文最重要的一节**），
> §4/§5 是 ABI 与超时，§6 是 K10 之后会破的假设，§7 是判据，§9 是代价。

## 1. 问题：为什么非有它不可

### 1.1 谁在等它（挡住的设施）

按 `docs/20` §3.2 的说法，K11 是**挡得最多的一条**（D1 最高）。落成清单：

| 设施 | 它要的语义 | 今天为什么不行 |
|---|---|---|
| `pthread_mutex_lock/unlock` | 在一个用户态字上**原子地**"试一次、不成就睡" | 内核没有"睡在一个用户地址上"这件事 |
| `pthread_cond_wait/signal/broadcast` | 与互斥量**原子地**配对：放锁 + 睡下，且"放下锁之后、真正睡下之前"到达的 `signal` 不许丢 | 同上，且多一条"丢唤醒"要求 |
| `pthread_once` | "恰好一次"的串行化 | 建在 mutex 上 |
| `sem_wait/post`（POSIX 信号量） | 计数 + 睡 | 建在同一机制上 |
| `std::mutex` / `std::condition_variable` / `std::thread` / `std::call_once` | 上面这些的 C++ 投影 | 同上 |
| libc++ 的线程支持 | ★ **全有或全无**：打开 `_LIBCPP_HAS_THREADS` 就必须提供 `__libcpp_condvar_wait` 这一族 | `17-libcxx-build.md` §7.1（`:1144-1183`），三条结论里的第 1、3 条 |

★ **为什么不能"先随便写个自旋版"** ★ `tools/run_qemu.py` 默认 `-smp 1`
（`20` §2.8 已核实；`17` §2.6 复核为真）：单核上自旋的等待者**占着唯一的 CPU**，
被等的线程永远跑不到。症状不是"慢"，是**卡死**（`17:218-219`）。
这一条把"自旋能顶一阵子"整条路否掉了——所以 K11 不是优化，是**前置**。

### 1.2 为什么用户态**做不到**（内核介入的全部理由）

只有一条，但它是硬的：

> **"检查用户内存里的值"与"把自己挂到等待队列上"必须是同一个不可分割的步骤。**

分开做就有窗口：调用者读到"值还没变"→ 另一个线程把值改了并执行 `wake`
（此时队列上没人）→ 调用者这才挂上去并睡下 → **没人再叫它**。
中间那个窗口无论怎么排都在（用户态没有"关中断"），只能靠协议压小，
而"压小"的判据只能是"压力测试跑 N 轮没出错"——那是**概率**，不是**证明**。
`20` §2.8 的表格把这一点写成 A 的"全部价值"，本文同意。

**第二条理由（更少被提到，但同样硬）**：用户态**看不见"谁在等这个地址"**，
所以"唤醒"只能做成"置一个位／发一条消息"，于是要么惊群（所有等待者醒来重查），
要么需要内核替它挑一个。内核知道队列上有谁，所以"唤醒 1 个"是**免费**的
——而 `pthread_cond_signal`（唤醒 1 个）与 `broadcast`（唤醒全部）是两个
**语义不同**的操作，用户态伪装版把前者退化成后者。

### 1.3 标准判定（照 `20` §1.2.4 逐条执行）

| 项 | 判定 | 说明 |
|---|---|---|
| `pthread_mutex_*` / `pthread_cond_*` / `pthread_once` / `sem_*` | ★ **标准要求** ★ | 标准正文定义的就是"原子地检查条件并睡下、被唤醒后重新检查" |
| `pthread_cond_timedwait` / `sem_timedwait` / `pthread_mutex_timedlock` | ★ **标准要求** ★ | 超时是这些接口**签名的一部分**——这直接把 §5 的问题变成必答题 |
| **Linux 的 `futex(2)` 接口本身**（`FUTEX_WAIT`/`FUTEX_WAKE` 这套号与形状） | ⚠ **不是标准** ★ | 号与名字都是我们自己的；本文的 `FE_SYS_*` 号与"一次等一个 **u32**"的形状是**我们的**决定，不是抄它的 |
| `FUTEX_LOCK_PI` / `FUTEX_WAIT_REQUEUE_PI` / `FUTEX_CMP_REQUEUE` / robust list / `FUTEX_WAIT_BITSET` / `FUTEX_FD` | ⚠ **全是 Linux 的附加行为** ★ | **不做**（§4.3 逐条写为什么，以及"什么时候才值得回头做"） |

## 2. 机制的形状：三条候选

`20` §2.8 给了两条（A 真 futex、B 通知对象伪装）。本文补**第三条**，
而这条恰恰是"要不要新增一处等待登记"的答案（§3）。

### 2.1 候选 A：等待队列挂在 **(地址空间, 用户地址)** 上

| 维度 | 内容 |
|---|---|
| 键 | `(struct fe_address_space *, u64 addr)`。★ 地址空间必须进键 ★ 两个任务的同一个虚拟地址是**两个变量**（微内核里没有共享地址空间，除非将来有 fork/CLONE_VM） |
| 值 | 一条等待者链，元素是**线程** |
| 等待者 | 内核在**同一个关中断区间**里：读用户内存 → 与期望值比 → 不等就挂上链、置"已登记"、置 `BLOCKED` |
| 唤醒 | `wake(addr, n)`：找到桶，逐个比键，唤醒至多 n 个（n = 0 表示全部） |
| 唤醒后 | 等待者**必须重查**（内核不保证"为什么醒"）——这是 futex 的契约，也是"伪唤醒"自动变成正确行为的地方 |

**代价**：
1. 桶表是**新的全局状态**（哈希表 + 键比较），要处理"表满/碰撞/回收"；
2. 内核**要读用户内存**，而用户地址随时可能被 `munmap`（§4.4 的读路径与返回码）；
3. 唤醒侧要**比键**，不能"地址相同就唤醒"（§7.1 的 W4 就是堵这个）。

**它买到的东西**：丢唤醒窗口由内核的关中断区间消掉——**这是 A 的全部价值**。

### 2.2 候选 B：通知对象 + 用户态重查（**否掉**）

用户态对象里放一个内核通知对象句柄，等的人先重查用户内存再
`fe_notification_wait`。`20` §2.8 已经列了它的代价，本文只补两条它没写的：

| 本文补的代价 | 为什么它比 `20` §2.8 写的两条更致命 |
|---|---|
| ★ **它把"唤醒 1 个"变成"唤醒全部"** ★ | `pthread_cond_signal` 与 `broadcast` 在标准里是**两个**语义。用"置位唤醒全部"实现，`signal` 会变成 `broadcast`：N 个等待者醒来、N-1 个白跑（惊群），而在**单核**上"白跑"意味着"真正该跑的那个排在后面"——延迟直接从"一次调度"变成"N 次调度" |
| ★ **它的失败形态是"有时能跑"** ★ | 丢唤醒窗口只能压小。`18-user-fault-handler.md:429-431` 把"有时能跑"列为最坏的一类症状，本文沿用同一条判定 |

`20` §2.8 还写了第三条代价（`sizeof(pthread_cond_t)` 不再是平台无关常量）——
本文同意，且认为它单独就足以否掉 B。

### 2.3 候选 C：**不新开一处登记**，而是给第 1 处登记加一种键

`wait_any` 的等待节点机制（`kernel/ipc/ipc.c:538-769`）今天已经具备
A 需要的大部分形状：

- 节点**放在调用者的栈上**，线程身上只挂一个 `void *wait_node` 指针
  （`kernel/include/fe/sched/thread.h:130`）——**唤醒方不碰别人的数据结构**；
- "已登记"由 `threading->waiting` 表达（`thread.h:133`），
  ★ 指针的有效性全靠"**全在关中断区间内操作 + `waiting` 标志**"（`thread.h:126-129`）★
- 摘除路径已经存在（`wait_unregister`，`ipc.c:660`），
  而且**取消路径已经覆盖它**（`fe_thread_cancel` 路径 1，`ipc.c:811`）。

于是"地址等待"可以做成**第 1 处登记的一种新键**（`FE_WAIT_ADDR`），
而不是第六处登记。**这是本文对 §3 那个问题的正面回答**，
代价与边界在 §3.3/§3.4 写清。

### 2.4 决定

> **采用 A，实现方式是 C**（机制复用第 1 处登记的记账；暴露面是**两条专用 syscall**，
> 不是 `wait_any` 的用户态 ABI）。

★ **为什么暴露面要专用，而不是"把 `FE_WAIT_ADDR` 加进 `wait_any` 的 ABI"** ★
`wait_any` 的用户态 ABI **今天根本不存在**（`20` §2.9 已核实：没有
`FE_SYS_WAIT_ANY`），而且 `20` §3.5 第 1 条把"先有调用者再定 ABI"列为纪律。
K11 的调用者是**明确的**（`pthread_*` 那一族），而它只需要**一个**地址：
把 `wait_any` 的多目标 ABI 一起定死，等于在一个还没有调用者的接口上
顺带做第二个决定——那正是纪律要防的。所以：

| | K11 暴露什么 | 谁定 |
|---|---|---|
| 单个用户地址的等 / 醒 | `FE_SYS_WAIT_ADDR` / `FE_SYS_WAKE_ADDR`（本文 §4） | K11 |
| `wait_any` 的多目标用户 ABI + `poll` 超时 | 不动 | **K14**（`20` §3.2 第六步） |

## 3. ★ 与既有五处等待登记的关系 ★（问题 2）

### 3.1 逐处审计

**这五处的清单**来自 `fe_thread_cancel` 的五条路径（`ipc.c:803-882`）——
它是这个项目里"等待登记"的**权威清单**，因为每一处都对应一条摘除路径。

| # | 登记 | 键 | 登记字段 | 唤醒方 | 取消路径 | "检查 + 登记"同一区间？ | "登记 → 置 BLOCKED"窗口？ |
|---|---|---|---|---|---|---|---|
| 1 | `wait_any` 节点 | 内核对象句柄 | `thread->wait_node` + `obj->waiters[]` | `fe_ipc_wake_object_waiters`（`ipc.c:569`） | 路径 1（`ipc.c:811`） | ★ **否** ★ 检查在 `ipc.c:718-724`，关中断区间从 `:737` 才开始 | **有**（`:759` → `:761`） |
| 2 | 端点接收 | 端点 | `ep->receiver` 单槽（`ipc.c:457`） | `wake_receiver`（`ipc.c:150`） | 路径 2（句柄表扫描，`ipc.c:830`） | 是（空队列的判据 `endpoint_pop` `:410` 与登记 `:457` 同在 `:409` 开的区间里） | **有**（`:458` → `:459`） |
| 3 | 通知等待 | 通知对象 | `nt->waiter` + `wait_mask`（`ipc.c:1006-1007`） | `fe_notification_signal_obj` | 路径 3（`ipc.c:845`） | 是（`:996` 起） | **有**（`:1008` → `:1009`） |
| 4 | 共享区间控制器锁 | 资源池条目 | `e->lock_waiter`（`resource.c:657`） | `fe_resource_unlock`（`resource.c:680`） | 路径 4（`resource.c:405`） | 是（`resource.c:646-658`） | **有**（`:658` → `:659`） |
| 5 | 目标任务 | 任务 | `child->waiter`（`process.c:424`） | `fe_process_on_thread_exit` | 路径 5（`process.c`，`fe_task_clear_waiter`） | 是（`process.c:415-425`） | **有**（`:425` → `:426`） |

**两列读出来的结论**：

1. **"检查 + 登记在同一区间"**：四处做到了，**第 1 处（`wait_any`）没有**。
   这是一个**一致性缺口**，不是风格差异——`ipc.c:726-736` 的注释逐字写着
   "登记与'再次检查'必须在同一个关中断区间里"，而代码里的"再次检查"
   有两个：一个在区间**外**（`:718-724`），一个在**循环顶部**（`:763-766`）。
   区间只包住了第二个。
2. **"登记 → 置 BLOCKED"窗口五处都有**：登记在 `fe_irq_restore()` 之后
   才 `fe_sched_block_current()`（`sched.c:880-889` 无条件置 `BLOCKED`）。
   而 `fe_sched_wake` **只接受 `BLOCKED` 与 `SLEEPING`**（`sched.c:925`/`:928`），
   其它状态走诊断分支（`sched.c:955-962`）。也就是说：落在这个窗口里的唤醒
   **被丢弃**，而且会打一行 `**fe_sched_wake 收到状态不对的线程**`。

### 3.2 这两处窗口是真的吗（**证据与它的边界**）

★ 诚实写清"读代码得出的"与"实测到的"是两件事 ★

| 判据 | 结果 |
|---|---|
| 窗口 2 会发生什么（读代码） | 唤醒被丢弃 → 等待者随后 `state = BLOCKED` + 让出 → **没人再叫它**。有粘性位的对象（通知）也救不了：位还在对象里，但**没有人再检查它** |
| 窗口 2 有没有被实测命中过 | ★ **没有** ★ `build/serial.log`、`build/vbox-serial.log`、`build/serial-ref.txt` 三份里那条诊断 **0 处**。窗口只有几条指令宽，所以"没命中"是预期的，**但它不是零** |
| 窗口 1 的宽度 | 宽得多：`wait_target_ready` 要查句柄表、在 `FE_WAIT_MSG` 分支里还可能 `memcpy` 最多 1024 字节（`ipc.c:588-654`）。★ 但它今天**打不到任何人**：`fe_wait_any` 的调用者只有内核自检（`ipc/ipctest.c`、`task/exectest.c`），**没有用户态 ABI**（`20` §2.9）★ |
| `wait_satisfied` 这个字段 | ★ **被写、从来没有被读** ★ 写点两处：`ipc.c:580`（唤醒方）与 `ipc.c:757`（等待方清零）；全仓**没有一个读者**。也就是说"处理'提前被唤醒'"这个意图**没有落地**，只留下一个字段 |

### 3.3 结论：K11 **不加第六处登记**，但要新增一把桶

| 决定 | 代价 |
|---|---|
| 地址等待是**第 1 处登记的一种新键**（`FE_WAIT_ADDR`），复用 `waiting` / `wait_node` / 栈上节点 | 取消失效的路径只有一条：如果 `wait_unregister` 学不会"按键摘除"，那么它**看起来还能跑**（大多数情况下 `waiting` 清掉就够了），只在"另一个线程/任务来唤醒"时出错。→ §7.1 的 W7 专门判它 |
| ★ 因此**取消路径仍然是五条** ★ `fe_thread_cancel` 路径 1 原样覆盖新键 | 代价是**路径 1 的语义变复杂**：它现在要能按三种东西摘除（句柄、位掩码、地址键）。缓解：`wait_unregister` 里"按 `node->tgt[i].kind` 分派"已经存在（`:668-687`），加一支即可 |
| 新增一把**哈希桶**（键 = `(space, addr)`，值 = 等待者链） | ★ 这是真正的新状态 ★ 桶里的链是**侵入式**的（线程上加 `addr_prev/addr_next` 两个指针），于是**没有容量上限**、**摘除是 O(1)**；代价是每个线程多 16 字节，以及"链的完整性"变成一条新的不变式 |

★ **为什么不用 `obj->waiters[FE_WAITERS_MAX]` 那种定长表（4 项）** ★
`ipc.h:41` 的 `FE_WAITERS_MAX = 4`，而 `waiters_add`（`ipc.c:545-561`）
在表满时**静默不登记**（`:558-560` 的注释明说"不报错"）。
对内核对象那样做有它的道理（多目标等待里少登记一个只是少一条唤醒路径），
**但对 futex 语义是致命的**：`pthread_cond_wait` 的等待者**必须**真的睡下，
"没登记就睡"= **永久睡死**。所以地址队列要么给足容量，要么**登记失败必须报错**。
本文选前者（侵入式链，无上限），并把后者写成一条**不变式**：
`fe_wait_addr` 只有两条出路——**"值已变，立即返回"** 或 **"已在链上"**，
不存在"没登记就睡"这第三种状态。

### 3.4 ★ 窗口必须堵：K11 的一部分就是修第 1 处登记的循环形状 ★

地址等待**必须**有原子性（§1.2），所以 K11 不能"绕过"窗口 1 —— 它自己就要
"读值 + 挂链"在同一个区间里。既然要改，就**一次改对**（`20` §3.5 第 2 条：
"机制层的不变式必须由机制自己维持"）：

| 改动 | 内容 | 为什么这样改就够 |
|---|---|---|
| **① 检查进区间** | 把"先看有没有已就绪的"这一遍挪进 `fe_irq_save()` 之后（对三种键一起改） | 区间内不可能有中断，于是"检查 → 挂链"之间没有第三方能改状态 |
| **② 置 `BLOCKED` 也进区间** | 在同一个区间里写 `self->state = FE_THREAD_BLOCKED`，最后才 `fe_irq_restore()` | 于是"已登记"与"能被唤醒"**同时**成立，窗口 2 消失 |
| **③ `fe_sched_block_current` 变成幂等** | `if (t->state == FE_THREAD_RUNNING) t->state = FE_THREAD_BLOCKED;` | 如果唤醒已经把它置成 `READY`（那说明"我早就该醒了"），这里**不许**再压回 `BLOCKED`——否则那次唤醒又被吃掉 |

★ **为什么②不会变成"自己把自己挂起来"** ★ 置 `BLOCKED` 之后线程**仍在跑**
（它还要 `fe_irq_restore` + 让出）。这中间若来中断，`fe_sched_maybe_switch`
看到当前线程是 `BLOCKED` 就会切走——**这正是期望行为**（它逻辑上确实在睡），
而且它已经在链上，唤醒方找得到它。
反过来（先让出、再置 `BLOCKED`）才是错的：那会有一个"还在就绪队列里、
却以为自己睡了"的窗口。

★ **③ 的判据是"唤醒不许丢"，不是"状态对不对"** ★ `fe_sched_wake` 对
`READY` 的线程不做任何事（它已经在就绪队列里）——所以③之后即使
"唤醒发生在让出之前"，那次唤醒仍然**有效**：线程不会睡，循环会回到顶部重查。

★★ **这一条必须先红再改** ★★ 铁律"先证明缺陷存在再修"在这里的具体形态：
`wait_addrtest` 里的 **W2**（§7.1）用一支**只给自检用**的钩子，
把"检查"与"挂链"之间的那一刻**确定性地**变成可注入点（照 K5 的
`fe_fault_set_wait_hook` 的先例，`kernel/task/fault.c:78`）：
钩子在那一刻改掉用户内存的值、并执行一次 `wake`。
**改之前**这条必须红（等待者漏醒、睡到超时），**改之后**必须绿。
跑不出红就不许动 `fe_wait_any` 的循环形状。

★ **这条改动顺带修好了第 1 处的窗口 1 与窗口 2**，所以 K4 的四组自检
（`fe_selftest_wait_any`）**必须重跑且零退化**——它们今天全绿，改完也得全绿。

## 4. 语义与 ABI（问题 3）

### 4.1 两个号

`kernel/include/fe/syscall.h:363` 今天 `FE_SYS_MAX = 0x94`（K5 用完 `0x92`/`0x93`）。
所以：

```c
#define FE_SYS_WAIT_ADDR  0x94   /* (uaddr, expected, deadline_ns) —— 等一个用户地址 */
#define FE_SYS_WAKE_ADDR  0x95   /* (uaddr, count)                  —— 唤醒链上的 n 个 */
/* FE_SYS_MAX → 0x96 */
```

★ 与 `20` §3.4 ① 同一条纪律：**号先查再用，不猜也不顺延**。★

### 4.2 逐条语义

| 调用 | 参数 | 返回值（`rax` 直接承载负错误码） |
|---|---|---|
| `FE_SYS_WAIT_ADDR` | `uaddr`：本地址空间里的用户地址，**必须 4 字节对齐**；`expected`：期望的 u32 值；`deadline_ns`：**绝对**单调纳秒（K7 时钟），**0 = 无限等** | `0` 被唤醒（**必须重查**，内核不保证为什么醒）；`-5 FE_ERR_AGAIN` 值**不等于**期望（这就是 futex 的 `EAGAIN`，**没有睡过**）；`-12 FE_ERR_TIMEOUT` 到点；`-7 FE_ERR_FAULT` 地址读不了；`-21 FE_ERR_CANCELED` 线程被取消/任务被终止；`-1 FE_ERR_INVAL` 对齐或参数非法 |
| `FE_SYS_WAKE_ADDR` | `uaddr`；`count`：唤醒至多几个，**0 = 全部** | `>= 0` 实际唤醒的个数；`-1` 对齐/参数非法。★ 唤醒一个**没人等**的地址不是错误，返回 `0` ★ |

**三条必须写死的语义**：

1. **唤醒是"点名"，不是"投递"**：内核只把线程置 `READY`，**不告诉它为什么**。
   等待者返回 `0` 之后**必须自己重查**用户内存。这条契约让"伪唤醒"
   （超时、被 `broadcast` 波及、取消）自动变成正确行为——用户态的循环
   写成 `while (!条件) wait_addr(...)` 就对了。
2. **键是 `(地址空间, 地址)`**：唤醒方只能唤醒**自己地址空间**里等在这个地址上的
   线程。别的任务在同一个虚拟地址上等，**一个都不许被唤醒**（§7.1 W4）。
3. **`EINTR` 怎么表达**：★ 今天**没有**信号（`20` §2.4(b) 未做）★
   所以 K11 **不发明** `EINTR` 路径，它复用已有的取消返回值
   `FE_ERR_CANCELED`——语义上正是"这次等待被外部打断了，重试或退出"。
   将来信号落地时，`EINTR` 的映射（含"待决信号要在返回用户态前检查"）
   是 **libposix 那一层**的事：**内核不认识 `EINTR`，也不认识 `errno`**
   （`20` §1.4 的硬规则）。★ 这条边界现在写下来，是为了避免将来
   "为了让 `EINTR` 好写"把信号位塞进 `wait_addr` ★

**为什么是 32 位（三条理由，每条都能核对）**：

1. **标准那一侧要等的就是一个 32 位字**：`pthread_mutex_t` 的锁字、
   `pthread_cond_t` 的代际号（sequence）都是它；
2. **对齐的 u32 恰好落在一页内**，于是"校验 + 读"是一次页校验加一次对齐读
   （§4.4）；64 位要求 8 字节对齐，跨页的概率更高，而跨页就意味着
   "第二页可能没映射"这条额外的失败模式；
3. **POSIX 里没有"等一个 64 位量"的对应物**：`sem_t`、`once_flag` 也都是
   （或有能力退化成）一个 32 位字。

**代价写在明处**：将来若有人要"等一个 64 位变量"，得等两次（这不是缺陷，
是"先有调用者再定 ABI"那条纪律的正常结果）。

### 4.3 ★ 明确不做 ★（每条给理由与"什么时候才回头做"）

| 不做 | 理由（照 `20` §1.2.4） | 什么时候才值得回头 |
|---|---|---|
| `FUTEX_LOCK_PI` / `PI`（优先级继承） | 附加行为。而且**本内核的优先级是静态 32 级**，没有"动态提升"这回事——做 PI 要先有可变的优先级，那是另一条线 | 出现一个**实时**调用者，并且优先级反转被实测成问题 |
| `FUTEX_CMP_REQUEUE` / `WAIT_REQUEUE_PI` | 附加行为。它服务的是"`cond_signal` 时把等待者从 condvar 队列搬到 mutex 队列"这种**性能**优化 | ★ 实测证明"两次唤醒"是瓶颈 ★（今天单核，先有正确性） |
| robust list（持有者死掉自动放锁） | 附加行为，而且它假设"进程可以带着锁死掉" | 有真实程序依赖它 |
| `FUTEX_WAIT_BITSET` / `FUTEX_WAKE_BITSET` | 附加行为（"按位选等待者"） | 同上 |
| `FUTEX_FD` | **已被 Linux 自己废弃**（`futex` 的 fd 形式） | 永不 |
| `FUTEX_CLOCK_REALTIME` | 附加行为：我们**只有单调时钟**（K7），墙钟是 `20` §2.13 的事 | 墙钟机制落地之后，若确有调用者 |
| 共享地址空间上的跨任务等待（`CLONE_VM`/fork 语义） | 今天**没有**共享地址空间（`fe_process_spawn` 建新空间） | `20` §2.1 的 fork/COW 那一项落地时——★ 那时 §6 的键比较要重新审 ★（★ 这里刻意写"`20` §2.1 那一项"而不是写 K 号：`20` §3.4 自己记着 **K 编号有两套**，写号容易指错 ★） |

### 4.4 参数校验与读路径（★ 这一节决定"内核对不对得起来" ★）

| 校验 | 判据 | 为什么 |
|---|---|---|
| 4 字节对齐 | `uaddr & 3` → `FE_ERR_INVAL` | 保证那次读**不跨页**，于是它是一次普通的对齐 32 位读（也才谈得上"一次读"） |
| 可读 | `fe_user_range_ok(space, uaddr, 4, false)`（`kernel/mm/uaccess.c:18`）→ 否则 `FE_ERR_FAULT` | ★ 内核**永不信任用户指针**（`20` §2.8 的第二条边界）★ 直接解引用会**内核 #PF**，而这次读发生在**关中断区间里** |
| 读 | 校验通过后一次 `memcpy`（`fe_copy_from_user` 的形状，`uaccess.c:50`） | 校验失败必须是**明确的返回码**，**不许**被当成"值不相等"——后者会让"地址早就 munmap 了"表现为"条件不满足"，用户态于是永远自旋重试 |
| 谁的空间 | `fe_task_current()->space` | 今天的等待者与唤醒者都是"自己空间里的地址"；★ 这条也是"内核不做跨空间唤醒"的实现方式 ★ |

★ **"校验通过之后到 `memcpy` 之间"的那一瞬** ★ 校验与实际读之间，PTE
不会变（单核 + 关中断），所以这段是安全的。**K10 之后不安全**（另一个核可以
`munmap` 并 `TLB shootdown`）——见 §6 第 3 条。

## 5. 超时：自己带，还是等 K14（问题 4）

### 5.1 判断

> **K11 自己带超时参数（绝对 deadline），顺序不变，K14 的范围因此收窄。**

### 5.2 为什么 K14 不是 K11 的前置（三条论证）

1. **标准把超时写在签名里**（§1.3）：`pthread_cond_timedwait` /
   `sem_timedwait` / `pthread_mutex_timedlock` 都是标准要求。
   "先做没有超时的 K11、超时留给 K14"等于要**两次**动同一个 ABI。
2. ★ **用 K14 表达超时反而更贵** ★ K14 的形状是"到点置位**一个通知对象**"
   （`20` §2.12/§3.4）。要让"等地址"用上它，等待者就必须**同时等两样东西**
   （地址 + 通知）——那是 `wait_any` 的**多目标**路径，而它的用户态 ABI
   今天**不存在**（§2.4）。也就是说：走 K14 等于把 K14 **和** `wait_any` 的
   ABI 一起提前，比一个 deadline 参数大得多。
3. **K11 的超时不需要 K14 的任何新机制**：它需要的是**睡眠链**
   （`fe_sched_sleep_until`，`kernel/sched/sched.c:795`；到点由
   `wake_sleepers` 处理，`:832`），而那是 **K7 已经做完的**东西
   （`fe_time_ns` + 节拍/LAPIC 周期模式）。
   ★ 换句话说：K14 的前置（"到点"这件事）**已经在了**，K14 缺的是
   "把到点接到一个**对象**上"，而 K11 不需要对象。★

### 5.3 代价：一个等待出现在**两条链**上（★ 这是本节最重要的代价 ★）

带 deadline 的地址等待，线程同时在：

- **地址桶的链**上（键 = `(space, addr)`）；
- **睡眠链**上（键 = 到点时刻，`thread->sleep_next` / `wake_ns`，`thread.h:57-58`）。

两条链的**摘除责任**必须只有一处答案，否则就是我们付过学费的那类缺陷
（"第五处登记的教训"，`ipc.c:864-875`）。今天的设计里有三处细节会咬人：

| 咬人的地方 | 事实（读代码） | 本文的对策 |
|---|---|---|
| `wake_sleepers` 只处理 `state == SLEEPING` 的线程 | `sched.c:836`：`if (t->state == FE_THREAD_SLEEPING)`。带 deadline 的等待者状态是 `BLOCKED`（它在等地址，不是在睡），于是**到点了它会被跳过而留在链上** | ★ "到点"这条路径必须知道"它还在等一个地址" ★：睡眠链由 `sched.c` 自己摘，**地址链**由等待模块摘——两边通过一个**回调**（`on_deadline(t)`，只有等待模块认识那把桶）接起来。★ 回调只能做"摘地址链 + 置 `wait_satisfied`"，**不许**自己去改线程状态（状态与就绪队列归调度器）★ |
| `fe_sched_wake` 对 `SLEEPING` 会**先摘睡眠链再唤醒**（`sched.c:952-954`） | 这是 D3 修好的行为，但它只在"唤醒时状态是 `SLEEPING`"时生效。状态是 `BLOCKED` 时**不摘睡眠链** | 对策同上：`BLOCKED` 且 `wake_ns != 0` 时也要摘睡眠链。★ 判据：`sleep_list_unlink` 的返回值（`sched.c:862` 已经返回 `bool`）要能被断言 ★ |
| `sleep_list_unlink` 是 `static`（`sched.c:862`） | 桶那一侧（`ipc.c`）看不见它 | 二选一：把摘链做成 `sched.c` 内的一致性（推荐：**"谁改状态谁负责摘链"**，即所有唤醒路径都经过一个 `fe_sched_wake_with_unlink(t)`），或者把 `sleep_list_unlink` 提升为公开函数。★ 前者更好：它把不变式收回调度器，符合 `20` §3.5 第 2 条 ★ |

★ **本文倾向的最终形状（一句话）**：把"线程在睡/在等/两样都在"这件事
**收进调度器的一处**：`sched.c` 提供
`fe_sched_block_current_deadline(deadline_ns)`，由它负责"挂睡眠链 + 置
`BLOCKED` + 在关中断区间里完成"，等待模块只负责"挂地址链"，
摘除则由**唤醒路径统一**做（回调只用来问"你还有别的链要摘吗"）。

**超时的精度（★ 两个环境差 12 倍，这是实测的不是估的 ★）**：
deadline 的判据用 K7 的 **TSC 时钟**（真实纳秒），而"到点"是被**节拍**发现并
唤醒的（`wake_sleepers`，`sched.c:832`）。所以：

> **"超时返回时刻 ≥ deadline" 成立；"恰好等于"不成立。
> 超出的量级 = 一个节拍的**真实**长度，而它在两个环境里差一个数量级。**

| 环境 | 节拍源 | 实测节拍率 | 一个节拍 | 出处 |
|---|---|---|---|---|
| QEMU + WHPX | LAPIC 周期模式 | **998 Hz**（另一次运行 999 Hz） | ≈ 1 ms | `build/serial.log`："50 个节拍 / 50065523 ns → 998 Hz（编程值 1000 Hz）" |
| VirtualBox 7.2 | **8254** | ★ **79 Hz** ★ | ★ **≈ 12.6 ms** ★ | `build/vbox-serial.log`："4 个节拍 / 50000088 ns → 79 Hz（编程值 1000 Hz，节拍源 8254）" |

★ 后果直接落在判据上（§7.2 的 C 模式）★：`--timeout` 只能断言
**"不早于 deadline 返回"**，**不许**断言"误差在 1 ms 内"——后者在 QEMU 上过、
在 VirtualBox 上必红。★ 同一份日志里还有一条更早的既成事实：VBox 上
"长窗口对照：时钟量到 51 ms，节拍量到 240 ms（请求 50 ms）"，也就是
**节拍制的时间在 VBox 上比真实时间快约 5 倍**（K7 自检对此判 0 失败项，
因为 K7 的结论本来就是"要信 TSC，不要信节拍"）。K11 的 deadline 走 TSC，
所以不受那条影响；**但任何"睡 N 个节拍"的写法都会**。★

## 6. SMP（K10）之后哪些假设会破

`20` §3.3 要求"本文推荐的每一项都必须在 SMP 之后重新审一遍"。
K11 有**四条**假设依赖单核，逐条写清：

| # | 今天的假设 | 它靠什么成立 | K10 之后要补什么 |
|---|---|---|---|
| 1 | **关中断 = 全局互斥** | 只有一个 CPU，`fe_irq_save` 之后没有任何东西能并发改桶 | 桶要**加锁**（或每 CPU 分片 + 一把保护键表的锁）。⚠ 桶锁与关中断的顺序要有唯一答案（先关中断再拿锁），否则就是经典死锁 |
| 2 | **唤醒方与被唤醒方在同一个执行体里排队** | `fe_sched_wake` 只改状态 + 入本地就绪队列 | 跨核唤醒要**发 IPI**（reschedule IPI），而且"入队"要对**目标核**的队列做（本地队列改成 per-CPU 之后） |
| 3 | **"校验用户页 → 读"之间 PTE 不会变** | 单核 + 关中断（§4.4） | munmap + TLB shootdown 会插进来。要么在"读用户内存"这段持页表锁，要么给内核一个"用户内存读失败就把当前线程杀掉/返回 FAULT"的**修复路径**（内核态 #PF 的 fixup 表） |
| 4 | **用户态的值改动对内核可见** | 唤醒方与等待者在同一个 CPU 上先后跑，程序序就够了 | ★ 需要真的内存序 ★：`wake` 之前的那次用户态 store 必须对**另一个核**上正在读它的内核可见。x86-64 是 TSO，加上"唤醒路径里有带 `lock` 前缀的操作 / IPI 投递本身有序"，实际上够用；但**这一条必须写进 K10 的检查表**，而不是靠"x86 不会乱序"这句话 |

★ **还有一条不是假设，是容量**：`FE_WAITERS_MAX = 4`（`ipc.h:41`）
那种定长表在单核下"表满"已经很难命中，多核下更容易；本文的地址队列用
侵入式链正是为了不给这个问题留活口（§3.3）。

## 7. 判据（问题 5）

原则照 `11-kernel-next.md:446`：**内核自检（含反向对照）+ 一个走真实路径的客户端**；
**每条正向都配一条会失败的反向**。

### 7.1 内核自检 `fe_selftest_wait_addr()`（新文件 `kernel/ipc/waitaddrtest.c`）

宿主形态照 K5 的探针（`kernel/task/faulttest.c`：造一个**真的用户任务** +
一页**真的映射可写**的用户页 + 临时切 CR3），因为 `fe_wait_addr` 读的是
**当前任务的用户内存**。★ 这份探针装置要**复用**（K5 那份是 `static`，
要么抽成公共的 `kernel/task/probe.c`，要么复制——实现那一刀再定，
本文只记下"不要写第二份不一样的探针"）。

| # | 正向断言 | 反向对照（必须失败/必须不变） |
|---|---|---|
| **W1** | 值没变就睡、值变了就醒：探针线程在 `expected` 上等，自检线程改成别的值再 `wake` → 等待者返回 `0`，且**它确实睡过**（判据用等待轮数/让出计数，不用墙钟） | 值**一开始就不等于** `expected` → 立刻返回 `-5 EAGAIN`，且**一次都没有睡**（让出计数 = 0）。★ 这条证明"没变就睡"不是"没检查就睡" ★ |
| **W2** | ★ **丢唤醒窗口**（§3.4）★ 钩子**确定性地**在"检查之后、挂链之前"把值改掉并 `wake` → 等待者**不许睡**（或立刻醒），且它看到的是**新值** | 钩子改成"只改值不 `wake`" → 等待者**必须**睡下去（否则说明钩子根本没落在窗口里，这条就变成了假绿）。★ 两个方向缺一不可 ★ |
| **W3** | 唤醒一个**别的地址**（同一个地址空间里的另一个字）→ 等待者**仍在等**，`wake` 返回 `0` | 唤醒**正确的地址** → 它醒，`wake` 返回 `1`。★ 证明 W3 的"没醒"是地址不对造成的，不是没人叫 ★ |
| **W4** | ★ **跨地址空间**（`20` §2.8 ④）★ 两个探针任务在**同一个虚拟地址**上各等各的，唤醒其中一个 → 另一个**不许**被唤醒，`wake` 返回 `1` | 把键退化成"只用地址"（红测试：临时去掉 space 比较）→ 两个都被唤醒 / `wake` 返回 `2`。★ 这条专门堵 `20` §2.8 点名的那个错误实现 ★ |
| **W5** | 未映射/不可读的地址 → `-7 FE_ERR_FAULT`（**不是** `EAGAIN`） | 同一地址**映射之后** → 正常等/醒。★ 证明 W5 的失败是"读不了"造成的 ★ |

★ 自检**不能**做的事（写下来，免得实现时走捷径）★ 它手工构造"等待/唤醒"的
调用序列，所以它**证明不了**"从 `pthread_cond_wait` 的语义到这条机制"那一段

### 7.2 真实客户端 `user/bin/waitaddrtest`

一个程序、四种模式（照 `killtest`/`faulttest` 的做法，**屏幕上的字一律 ASCII**）：

| 模式 | 做什么 | 判据 |
|---|---|---|
| **A 条件变量**（`--cond`） | 用 `WAIT_ADDR`/`WAKE_ADDR` **手写**一个互斥量 + 条件变量（**不引 pthread**，因为 pthread 层还没有），3 条工作线程 + 1 条消费者，生产者/消费者跑 N 轮 | **总数精确相等**（不是"没崩"）；`signal` 与 `broadcast` 各验一次 |
| **B 反向：纯自旋**（`--spin`） | **同一条逻辑**用自旋 + `yield` 写，带**有界**放弃（照 `17` §2.4 的写法：`fe_thread_yield` + 计数上限） | ★ 必须**打印超时并以确定的非零码退出** ★ —— 在 `-smp 1` 上它**永远跑不完**。这一条是"机制真的必要"的唯一直接证据（`20` §2.8 ②） |
| **C 超时**（`--timeout`） | 在一个没人唤醒的地址上等一个 **50 ms** 的 deadline | 必须在 **≥ 50 ms**（TSC 量）之后返回 `-12`，且**进程不卡死**。★ **不许断言上界** ★：到点由节拍发现，而 VBox 的节拍是 79 Hz（§5.3），50 ms 的 deadline 在那里可能 60+ ms 才回来。**把量到的毫秒数原样打印出来**（这是"如实写测量值"那条铁律的具体形态），init 侧只校验退出码 |
| **D 反向：丢一次唤醒**（`--drop`） | 故意**不**执行最后一次 `wake`，只用超时兜底 | ★ 总数必须**对不上** ★（`20` §2.8 ③ 的"故意丢一次唤醒 → 总数必须对不上"）。这一条保证前面的"精确相等"不是假绿 |

★ **客户端做不到、只能自检做的一条**：跨地址空间的 W4。
理由是**前提在本内核上不成立**：`fe_process_spawn` 建的是**新地址空间**，
而"同一个虚拟地址"在一个任务里由内核选址，用户态**无法保证**两个任务拿到
同一个 VA（K5 那一刀的同类教训：`exectest` 的"父改页子写"也不成立）。
→ 用户态只做"同空间、不同地址"（W3 的客户端版），跨空间归自检。

## 9. 代价清单与"什么时候会咬人"

| 代价 | 什么时候会咬人 |
|---|---|
| 一份新的全局状态（哈希桶 + 侵入式链，每线程 +16 字节） | 桶的**回收**：地址被 `munmap` 之后桶仍在表里（只是空的）。要么定期清理，要么**按需分配 + 空桶立即回收**——实现那一刀必须给出唯一答案，否则就是一条缓慢泄漏 |
| 内核要**读用户内存**（§4.4） | 首次写 `pthread_cond_wait` 的人会踩："我 `munmap` 了那块内存，等待者却报 `-7 EFAULT`"。正确写法是把等待对象放在**不会被回收**的内存里（与 K5 那条"处理者的缓冲区必须预先映射好"同类） |
| 唤醒是"点名"，等待者必须重查 | 用 `if (wait_addr(...) == 0) 就认为条件成立` 的写法**必然是错的**。★ 这是 futex 语义里最容易写错的一处，客户端 A 模式要用注释点明 ★ |
| 一次只等一个 u32 | 想等 64 位变量的人要等两次 |
| 超时精度 = **一个节拍的真实长度**（QEMU ≈ 1 ms；★ VirtualBox ≈ 12.6 ms ★，实测 79 Hz） | `pthread_cond_timedwait` 的调用者若期望"1 ms 内返回"，在 VBox 上必然失望。★ 写文档与写判据时都要按**最差的那个环境**写，不许按 QEMU 写 ★ |
| 一个等待同时在两条链上（§5.3） | ★ 这是本设计**最容易出悬空指针**的地方 ★：漏摘一次，`wake_sleepers` 或 `wake` 就会去碰已回收的线程。W8 就是钉它的判据 |
| 唤醒方不需要任何句柄/权限 | 同一个任务里的任意线程都能唤醒别人（线程之间本来就互信）。★ 将来若出现**共享地址空间**，这条就变成"另一个进程能唤醒你的等待者"，那时必须重新审 §4.3 最后一行 ★ |
