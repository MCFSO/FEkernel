# A/B 无缝更新（Android 式）设计

> 本文把 Android 的 A/B 方案映射到 FEKernel 的磁盘布局与启动流程。
> 它**取代** `04-write-protection.md` 里"签名更新包"那条思路——
> 那条思路是用错了工具，见第 5 节。

## 1. A/B 到底是什么

容易被记成"系统存两份"，但真正起作用的是三件事：

| 要点 | 含义 |
|---|---|
| **更新写另一份** | 系统在 A 上跑着，更新往 B 写。**运行中的系统全程不被碰** |
| **切换是原子的** | 只有一个很小的"引导控制块"决定下次启动哪一份。改它是一次写，不存在"改到一半" |
| **失败能回滚** | 新槽启动失败（尝试若干次仍未自报成功）→ 自动切回旧槽 |

第四条容易被忽略但同样重要：**用户数据不参与 A/B**。
`/home` 只有一份，两份系统共享它——否则每次更新都要搬用户数据，
"无缝"就无从谈起。

## 2. 映射到我们的磁盘

```
ESP（一个 FAT32 分区，固件只会看到它）
├── /EFI/BOOT/BOOTX64.EFI    Limine 自己 —— **不属于 A/B**，更新引导器是另一回事
├── /limine.conf             **引导控制块**：里面 default_entry 决定启动哪个槽
├── /slot_a/                 槽 A 的完整系统
│     ├── init  boot/kernel.elf  bin/*  sbin/*
├── /slot_b/                 槽 B 的完整系统（同样的结构）
└── /home/                   用户数据，**两份系统共享，不参与 A/B**

misc（FAT32 分区内的**保留扇区**，文件系统永远不会分配它们）
└── 槽状态记录 ×2（各带 CRC32，交替写入）
```

两处布局选择值得说明：

**槽是"路径前缀"，不是"分区"。** 因为固件只会去找 `EFI/BOOT/BOOTX64.EFI`，
它选的是**分区**而不是我们自定义的元数据。如果 A/B 做成两个分区，
切换就得靠改固件的 NVRAM 启动项——那是我们控制不了也不该碰的东西。
放在同一个 ESP 里用路径区分，切换就落到 Limine 的配置文件上，
而那个文件我们说了算。

**misc 用 FAT32 的保留扇区，而不是一个分区、也不是一个文件。**
- 不用文件：文件的内容归文件系统管，一旦 FS 状态不一致就跟着坏；
  "下次启动哪一份系统"这种东西不该依赖文件系统的正确性。
- 不用分区：多一个分区就要改分区表，而分区表一动，
  两个槽的相对位置、保留扇区号全都要跟着算——收益不抵复杂度。
- FAT32 的 `reserved_secs` 本来就是"文件系统不会碰的区域"，
  把它从 32 扩到 64，多出来的 32 个扇区正好放槽状态。

## 3. 槽状态记录

```c
struct slot_state {
    u32 magic;          /* 'FESL' */
    u32 seq;            /* 单调递增；两份记录取 seq 大的那个有效的 */
    u8  active;         /* 0 = A, 1 = B：下次启动用哪个 */
    u8  successful;     /* 活动槽是否已自报启动成功 */
    u8  boot_attempts;  /* 活动槽已尝试启动的次数 */
    u8  _pad;
    u32 crc32;          /* 覆盖前面所有字段 */
};
```

两份交替写、各带 CRC：**坏掉的写入不会让系统失去"下次启动哪一份"这个信息**，
因为另一份还在。这是 Android `bootloader_control` 的同一套做法。

## 4. 启动与回滚的流程

```
UEFI → Limine → 读 limine.conf 的 default_entry → 启动对应槽的 kernel.elf
     → 内核解析 cmdline 里的 slot=a|b → 交给 init
     → init：
        1. 从 misc 读出槽状态，校验 CRC，取 seq 大的那份
        2. **先登记写保护**：把"正在运行的这个槽"的区间设为禁止写入
           （另一个槽**不保护**——那是更新的目标）
        3. attempts++，写回状态（这一步在任何服务起来之前完成）
        4. 按依赖表拉起服务、跑自检
        5. 一切正常 → successful=1, attempts=0，写回
```

**回滚判定**（在步骤 1 之后）：

```
if (active 槽 !successful && attempts >= 3) {
    切到另一个槽（改状态 + 改 limine.conf 的 default_entry）
    重启
}
```

**诚实的边界**：回滚逻辑在 init 里，所以它只能救"内核起来了、init 跑到了"的情况。
如果新槽的内核自己就崩了，init 根本没机会执行——这时只能**人工干预**：
Limine 的菜单里两个槽都是可选项，手动选另一个即可。
Android 把这段逻辑放在引导器里，我们放不了（Limine 不认我们的元数据）。

这不是不能解决，而是**要么改引导器、要么接受这个边界**。
目前选后者，并把它写在文档里——比假装自动回滚总是有效要好。

## 5. 它怎么取代"签名更新包"

`04-write-protection.md` 里原本的困境是：

> 保护是单调的（没有 remove）→ 那怎么合法地更新系统？

当时的答案是"签名更新包 + 解除保护的能力"。**那是用错了工具**：
为了更新一次系统而开一个"解除保护"的口子，这个口子本身就是最大的风险。

A/B 给出的答案是：

> **永远不需要解除保护。** 更新的目标是**另一个槽**，它在本次启动里
> 本来就不受保护。切换发生在上次系统已经停掉之后。

于是：

- `fe_protect_add` **保持单调**（只能加不能减）——这一点不用动，
  它带来的"不需要判断谁可信"的好处也就保住了；
- 内核里**一行密码学都不需要**——这也正合你"不要搞密钥文件、
  密码学用现成软件包解决"的要求；
- 保护范围从"所有系统文件"变成"**正在运行的那个槽**"，
  语义反而更清楚了。

## 6. A/B 不提供什么

**它不提供真实性。** A/B 保证的是"运行中的系统不被改"和"改坏了能退回去"，
它**不保证**你启动的是官方构建的系统。谁都能把 `/slot_b` 写成自己的东西，
然后改 `default_entry` 指过去。

Android 的真实性靠 AVB / dm-verity（签名 + 哈希树）。那是**另一件事**，
而且按你的决定，真要做得由用户态服务链现成密码库来做，不是内核里手写。

在补上那一层之前，A/B 的正确描述是：
**可用性与原子性的保证，不是完整性的保证。**

## 7. 与现有实现的关系

| 已有 | 在 A/B 下的位置 |
|---|---|
| `kernel/protect.c`（受保护区间表，单调） | **保留**，只是登记的范围从"全部系统文件"变成"运行中槽的区间" |
| `fe_protect_check_write` | **保留**，blkd 在每次写之前调用 |
| blkd 的写路径 | **待做**，它是 A/B 更新的执行者 |
| `mkfat.py` | 要改：生成两个槽的目录树、扩保留扇区、写初始槽状态、按槽标注保护区间 |
| `tools/build.py` | 要改：把用户程序同时放进两个槽 |
| `init` | 要改：读槽状态、按槽登记保护、尝试计数与回滚、自报成功 |
| Limine 配置 | 两个条目（Slot A / Slot B），`default_entry` 由状态决定 |
| `/home` | 新增，两份系统共享，不保护 |

## 8. 访问矩阵（含"另一个槽连读都不行"）

**决定**：正在运行的槽只读；**另一个槽对用户态连读都不允许**。

| 区域 | 读 | 写 | 理由 |
|---|---|---|---|
| **运行中的槽** | 允许 | **拒绝** | 运行中的系统不许被改 |
| **另一个槽** | **拒绝**（更新器除外） | **拒绝**（更新器除外） | 见下 |
| misc（槽状态，保留扇区） | 允许 | 允许 | 内容极小且带 CRC，改它等于投票"下次启动谁" |
| bootsel 字节（limbo 配置里的一个数字） | 允许 | 允许 | 切换控制块；改错的最坏后果是启动另一个槽 |
| `/home` | 允许 | 允许 | 用户数据，不属于任何槽 |

### 为什么另一个槽必须**不可读**

直觉上"读又不会破坏什么"，但把它放进访问矩阵会毁掉 A/B 的意义：

1. **另一个槽是"下次要运行的一整份系统"**——一个完整的可执行映像。
   允许随意读，等于把一份可以随时被分析、比对、提取的完整系统摆在任何人面前。
2. **读+写都自由 = 它不是受控通道，而是公共草稿纸**。
   更新通道要成立，就必须是**窄的**：只有更新器能碰。
   一旦任何进程都能读写另一个槽，"更新"这件事就不再有任何边界可言——
   谁都可以把任意内容写进去，而"更新"和"破坏"在机制上就分不出来了。
3. 关掉读之后，更新路径上只剩下一个受控的参与者，**审计面缩小到一个人**。

### 实现它需要一个现在还没有的原语

blkd 要判断"这次请求该不该放行"，就必须知道**是谁在请求**。
现在做不到——它只看到一条消息，看不到发送方。

所以要加的是：**IPC 消息头里带上发送方任务 id，由内核填写**。

```c
struct fe_msg_header {
    u32 protocol, opcode, payload_len, handle_count;
    u64 request_id;
    u64 sender_task;      /* ← 内核在投递时填写；发送方写什么都不算数 */
};
```

这不是为 A/B 特设的东西：**任何需要"按客户端做策略"的服务都需要它**。
没有它，微内核里的服务只能做"全局策略"，做不了"per-client 策略"。
（这也是为什么它该在消息头里、由内核填——放在载荷里就是可伪造的。）

于是访问矩阵落到两个检查上：

```c
/* blkd 在每次读写前调用，把发送方（内核给的，不可伪造）一起带上 */
fe_status_t fe_protect_check_read (u64 lba, u64 count, u64 requester_task);
fe_status_t fe_protect_check_write(u64 lba, u64 count, u64 requester_task);
```

保护表里的每条区间带一个 `exempt_task`：只有它能在该区间上突破模式限制。
运行中的槽 `exempt_task = 0`（谁都不例外）；另一个槽 `exempt_task = 更新器`。

### 两次启动的完整切换（实测，QEMU + WHPX）

第一次运行（`--ab-update`，启动槽 A）：

```
[引导] 命令行: slot=a fek.update=1
[AB] 命令行里有 fek.update=1 → **本次启动执行更新**
[AB] 记录份 0: magic OK, CRC OK, seq=1, active=A, successful=1, attempts=0
[AB] 记录份 1: magic OK, CRC OK, seq=1, active=A, successful=1, attempts=0
[AB] 记录与现状一致（active=A, successful=1, attempts=0）→ 不写盘
[AB] → 拉起更新器
[保护] 更新器已指定: 任务 15（/slot_a/bin/abupdate）—— 只有它能碰另一个槽
    OK   运行中的槽：读放行
    OK   运行中的槽：写被拒绝
    OK   另一个槽：读**放行**（我是被指定的更新器，这正是豁免的意义）
  [2] 预扫描（只读比较两个槽）
         扫描 2717 扇区，其中不同的 7 个          ← 两个槽出厂就不一样，所以有东西可更
  [3] 逐段拷贝到另一个槽
         拷贝结束：2720 扇区，用时 7655 ms
  [4] 刷写缓存（提交前的屏障）
    OK   写缓存已刷到盘上（屏障成立）
  [5] 回读核对
         核对 2720 扇区，不一致 0 处
    OK   目标槽与源槽逐字节一致
  [6] 提交（翻转引导控制块）
         控制块现在是 '2'（下次启动槽 B）
    OK   回读确认控制块已生效
=== A/B 更新器结束，失败项 0 ===
[AB] 已写入第 1 份: seq=2, active=B, successful=0, attempts=0
[AB] 更新已提交：下次启动槽 B，状态为试用
[AB] 重启以进入新槽……
[复位] 请求系统复位（0xCF9）
```

第二次运行（`--keep-image`，**同一块盘**，控制块是上一次写下去的）：

```
[引导] 命令行: slot=b                                   ← Limine 读了盘上的 default_entry
[保护] A/B 清单已应用: 引导槽 b → 登记 46 段受保护区间  ← 保护范围跟着槽翻转了
[init] 槽前缀 = "/slot_b"
[AB] 记录份 1: magic OK, CRC OK, seq=3, active=B, successful=0, attempts=1
[AB] 本槽处于试用启动，失败次数累计为 1（上限 3，超过即回滚）
[AB] 已写入第 0 份: seq=4, active=B, successful=1, attempts=0
[AB] 本槽自报启动成功 ✓（successful=1, attempts=0）
=== init 结束，失败项 0 ===
```

三件事同时被证明了，而且**缺一不可**：

- 切换真的发生了：第二次启动进的是槽 B，而它不是靠任何命令行参数指定的——
  是更新器写进盘里的那个字节决定的；
- 状态机认得出"这是新槽的第一次启动"：记录里 `successful=0` → 试用 → 计数；
- 试用能转正：整个系统（14 个单元、全部自检）跑通之后才写
  `successful=1, attempts=0`。这一条如果不成立，一个**好**的更新会在三次
  启动之后被自己回滚掉。

### 回滚路径的实测（用 `tools/abtool.py` 种入"已经失败 3 次"的历史）

回滚的触发条件是"试用启动连续失败 3 次"。要自然造出它，得先让一个槽真的坏掉、
再启动它 4 次（4 轮完整启动）。而那个条件在盘上**就是几个字节**，所以更诚实的
做法是：把历史种进去，让**真正的状态机**去判断。

```powershell
python tools/mkfat.py build/disk.img build/esp --label FEKERNEL
python tools/abtool.py bootsel b                              # 控制块指向槽 B
python tools/abtool.py seed --active b --successful 0 --attempts 3
python tools/run_qemu.py --headless 30 --keep-image
```

```
[引导] 命令行: slot=b
[AB] 记录份 0: magic OK, CRC OK, seq=2, active=B, successful=0, attempts=3
[AB] → 采用第 0 份（seq 较大且 CRC 有效）
[AB] **回滚**：槽 B 连续 3 次没能自报启动成功（阈值 3）
[AB] 引导控制块已写成 '1'（下次启动槽 A）
[AB] 已写入第 1 份: seq=3, active=A, successful=1, attempts=0
[AB] 已切回槽 A 并标记为已成功（它执行更新时正处于该状态）
[AB] 重启以进入该槽……
```

再启动一次（仍是 `--keep-image`）：

```
[引导] 命令行: slot=a
[AB] 记录份 0: magic OK, CRC OK, seq=2, active=B, successful=0, attempts=3
[AB] 记录份 1: magic OK, CRC OK, seq=3, active=A, successful=1, attempts=0
[AB] → 采用第 1 份（seq 较大且 CRC 有效）
[AB] 记录与现状一致（active=A, successful=1, attempts=0）→ 不写盘
=== init 结束，失败项 0 ===
```

★ **两次 `abtool.py show` 之后的盘面本身就说明了双份记录的意义** ★
回滚写的是**第 1 份**，所以失败的那段历史（第 0 份，seq=2）还在：

```
  记录份 0: magic OK, CRC OK, seq=2, active=B, successful=0, attempts=3   ← 失败历史，保留
  记录份 1: magic OK, CRC OK, seq=3, active=A, successful=1, attempts=0   ← 回滚结果，生效
```

如果每次两份都写，这段历史在回滚的瞬间就没了——而"为什么回滚了"恰恰是
事后最需要回答的问题。

`tools/abtool.py` 是主机侧工具（离盘查看/修改 A/B 状态）。它存在的两个理由都
不是"方便"：**系统起不来的时候只能把盘拿下来看**；以及**只有把状态和判断分开，
才能单独测判断**——`seed` 只写盘点状态，一行判断逻辑都没有。

### 访问矩阵在两个身份下的两种结果

同一个操作（读另一个槽），在更新器里**必须放行**，在 protcheck 里**必须被拒**：

```
protcheck（普通进程）:  [保护] （落在受保护区间 3654 + 1，模式 禁读禁写）
                        OK   另一个槽：**读被拒绝**
abupdate（更新器）:     OK   另一个槽：读**放行**（我是被指定的更新器，这正是豁免的意义）
```

我第一版把更新器的这条断言写成了"读被拒绝"——那是把 protcheck 的期望
照抄到了更新器身上。**同一个动作在两个身份下期望相反**，这恰恰是豁免机制
存在的意义；把"和另一个程序一样"当成不变量，测试就会把正确行为报成失败。
（症状：更新器退出码 2，`[AB] 更新未完成 → 不切槽`，看起来像权限出了问题。）

### protcheck 的访问矩阵实测（QEMU 与 VirtualBox 均通过）

```
[保护] A/B 清单已应用: 引导槽 a → 登记 46 段受保护区间

=== 扇区访问矩阵测试（M8：A/B + 写保护）===
    [2] 内核里的受保护区间: 46 段
        正在运行的槽: LBA 3653（禁写）
        另一个槽:     LBA 3654（禁读禁写）
      OK   运行中的槽：**读允许**
[保护] **拒绝写入** LBA 3653 + 1（调用者 blkd）
      OK   运行中的槽：**写被拒绝**
      OK   内核记下了一次违规（计数 +1）
           读回来与原来不一致的字节数: 0
      OK   磁盘内容**逐字节未变**（写确实没落到盘上）
[保护]   （落在受保护区间 3654 + 1，模式 禁读禁写）
      OK   另一个槽：**读被拒绝**
      OK   读违规也被记下（计数 +1）
      OK   另一个槽：**写被拒绝**
      OK   写违规也被记下
    [3] 正向对照：往不受保护的扇区写
      OK   区间之外：**写成功**（证明写路径本身是好的）
=== 访问矩阵测试结束，失败项 0 ===
```

四点值得指出：

- **`调用者 blkd`** —— 内核记录的是执行者；而"为谁执行"由 `hdr.sender_task` 带给它。
  这两个身份分开是这套设计的关键：内核知道**谁在问**，blkd 知道**替谁问**。
- **两个方向的证据缺一不可**：磁盘内容逐字节未变（证明写没落盘）+ 内核违规计数 +1
  （证明这次拒绝是被**判定**出来的，而不是碰巧写失败）。
- **正向对照**同样不可少：没有它，"写被拒绝"和"写功能整个是坏的"看不出区别。
- **测试从内核取区间表**，不把布局硬编码——布局是 mkfat.py 每次建镜像时算出来的，
  硬编码的测试只能验证"我以为的布局"。

## 10. 本轮踩到的坑

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | 内核说"登记 40 段"，用户态查却是 **0 段** | `fe_selftest_protect()` 结尾调 `fe_protect_init()` 把**真实表**清空了（连违规计数一起） | 自检改为**保存/恢复**。用保存/恢复而不是"靠调用顺序避开"：顺序是不可靠的约定，谁把自检挪前面就静默失效 |
| 2 | `mkfat` 抛 `RuntimeError: 簇链断裂` | `/bin` 的目录内容超出它分配的簇。加进 `protcheck` 后 `/bin` 有 10 个条目、每个都要长名 → 20×32 = 640 字节 > 512 | 目录内容超出时**自动扩容**。"能装下"以前一直是巧合，现在才是保证 |
| 3 | 连读三次**旧日志**，还据此下了两次错误结论 | 建镜像那一步失败（`Select-Object -First 3` 把 traceback 吞了），脚本中止，而旧串口日志还留在原地 | 启动脚本改成**先删旧日志再干任何可能失败的事**。失败于是只剩"没有日志"一种表现，不会伪装成成功 |
| 4 | 自检报 2 项失败，我先只看了 QEMU 的一栏就说"全绿" | `got == 16` 把"环形缓冲有 16 格"当成了"一定填满"（实际只产生 10 次违规）；`task_id == 0` 把内核任务 id 猜成了 0（实际是 1） | 断言改成真正的不变量：`got == min(总数, 格数)`；`task_id == fe_task_current()->id` |
| 5 | `parse_u64` 与别处同名函数冲突 | 内核里已有一个 `parse_u64` | 改名 `mparse_u64` |
| 6 | 清单明明解析了 46 段，槽状态机却说"没有 A/B 布局" | `fe_selftest_protect()` 的保存/恢复漏了 `g_ab`——清空它的时候还没有人用，所以"保存/恢复"看起来是完整的 | 保存/恢复改成**对齐 `fe_protect_init()` 清掉的每一样**，并加一条断言专门盯 `flags`。教训不是"这次记得加上"，而是"清什么就存什么" |
| 7 | 自检报"另一个槽"那类断言失败 2 项 | 断言写的是 `mode == FE_PROT_DENY_ALL`，而 mode 里还装着 `FE_PROT_EXEMPT_UPDATER` 位 → 相等判永远不成立 | 改成按**位**判（`(mode & DENY_ALL) == DENY_ALL`）。语义是"禁止集合里有没有读和写"，不是"模式字面量等于几" |
| 8 | 更新"成功"、控制块回读是 `'1'`、镜像里也确实是 `default_entry: 1`，可**每次启动还是槽 A** | Limine 的 `default_entry` 是 **1 起算**的：`0` 越界后落到第一个条目，`1` 也是第一个条目 → 翻了个寂寞 | 约定改成 `'1'` = 槽 A、`'2'` = 槽 B，并在 `fe_user.h` 里给它名字（`FE_AB_BOOTSEL_A/B`）。**只有真重启一次看进哪个槽才能发现它** |
| 9 | 更新器退出码 2，报"另一个槽：读被拒绝" | 把 protcheck 的期望照抄给了更新器——更新器本来就该被豁免 | 更新器的正向对照改成"读**放行**"，并在注释里写明同一动作在两个身份下期望相反 |
| 10 | 2720 个扇区的拷贝用了 **14.3 秒**，看起来像卡死 | 驱动在**每个扇区**后面都发 FLUSH CACHE。每次 FLUSH 就是一次真实落盘屏障（虚拟化下 = 一次 fsync） | 把刷新做成**独立操作**（`BLK_OP_FLUSH`），由调用方在**提交点之前**发起一次：14.3 s → 7.6 s。屏障的粒度属于调用方，不属于驱动 |
| 11 | 拷贝里"大于 1 个扇区的区间全失败、1 个扇区的全成功" | 写请求载荷是"头 16 字节 + 数据"，而内联载荷上限 1024 → 一次只能写 1 个扇区（读是 2 个） | 上限拆成 `FE_BLK_MAX_READ` / `FE_BLK_MAX_WRITE` 两个名字，写在 `fe_blk.h` 里。差别在接口上，不靠人记 |
| 12 | 装了新槽之后，`fs` 报"子目录 bin 可列出且非空"失败，而日志只显示"共 0 项" | 两件事：fsd 把"读被拒"和"目录到末尾"一起 `break` 了（错误被吞成"空目录"）；而拒绝本身是块级拷贝的后果（见 §11） | fsd 分开处理 I/O 错误并向上报错；`fs` 把"明确的拒绝"与"真的空目录"分开——前者是已解释的边界，后者仍是失败 |

第 1 条和第 3 条是同一个教训的两面，而且**这一轮里各自又犯了一次**：

- 第 1 条是"自检污染真实状态"——我在资源池上踩过，这次换了个形式（清空区间表）复现；
- 第 3 条是"看着旧产物下结论"——我在这轮第 3 次栽在它上面（前两次分别是 `run_qemu.py` 的完整性检查指错路径、`--no-rebuild` 复用旧镜像）。

第 4 条也值得记：**断言写在"我猜的值"上，而不是"不变量"上**。
`got == 16` 和 `task_id == 0` 都是猜的，而且都猜错了；
改成 `min(总数, 格数)` 和 `fe_task_current()->id` 之后，它们在什么环境下都成立。

第 6 条是第 1 条**第三次**以新的形式出现（资源池 → 区间表 → `g_ab`），
第 7 条和第 8 条则是同一类错误的两种面孔：**把"我以为的编码"当成了事实**
（模式字面量等于几、条目编号从几开始）。它们共同的特征是——
代码逻辑全对，只有一条先验是错的，而且错的那条**不会报错，只会静默走偏**。

## 11. 块级拷贝在一个文件系统内部不自洽 ★ 本轮最重要的发现 ★

装上槽 B 之后，`fs` 客户端列 `/slot_b/bin` 被拒。原因不是随机故障：

```
  ls /slot_b/bin
[保护]   （落在受保护区间 12023 + 1，模式 禁读禁写）
    失败 子目录 bin 可列出且非空
```

**FAT32 的目录项里放的是绝对簇号**（`first_cluster` 字段），而我们的两个槽
是**同一个文件系统里的两棵子树**。把槽 A 的扇区原样拷到槽 B 之后：

- 槽 B 的目录簇里现在是 A 的目录项，而 A 的目录项写的是 **A 的簇号**；
- 于是 `/slot_b/bin` 解析出来指向 `12023`，那落在**槽 A 的区间**里；
- 而"另一个槽连读都不行"——运行槽 B 时槽 A 就是"另一个槽"，读被拒。

三点补充，缺一条都会让人得出错误结论：

1. **系统本身照常启动、照常运行。** 内核与所有程序都是引导器按 `module_path`
   当作**模块**加载进 ramfs 的，运行期不碰 FAT。所以"装上新槽之后系统
   跑得好好的"并不构成"拷贝是自洽的"——它只说明这条依赖当前没被用上。
2. **A/B 的可用性保证没有因此失效。** 切换、试用、自报成功、回滚判定全都在
   块级照常工作（见 §9 的实测）。
3. **但这是"槽做成同一文件系统里的子树"这个选择的直接代价**，不是实现瑕疵。
   Android 的 A/B 槽是**独立分区**，分区内部所有引用都以分区为基准，
   所以整分区对拷天然自洽。我们把槽做成路径前缀，就丢掉了这个性质。

### 两条正确的修法

| 修法 | 做法 | 代价 |
|---|---|---|
| **槽独立成分区**（推荐） | 两个 FAT32 分区各放一份完整系统；Limine 用分区选择读另一个槽的 `kernel.elf` | 要把 `mkfat.py`、`limine.conf`、`build.py` 的槽布局全改成多分区；`slot_*` 前缀随之消失，"我在哪个槽"要改从 cmdline 拿 |
| **只拷文件数据**（文件级更新） | 目录项与 FAT **一个字节都不动**，只把每个文件的数据簇按"源簇 → 目标簇"搬过去 | 需要一张"路径 → 两边的簇"映射表。mkfat 建镜像时**已经知道**每个文件的簇（`alloc_log`），把它写进清单即可让更新器零 FAT 知识；真正的难点是升级包里文件集变化时的映射来源 |

两条路都**不引入密码学**，也都保持保护表单调。短期保留现状，
因为系统运行不依赖它，而 `fs`/`fsd` 现在是诊断程序而非关键路径——
但**下一件该做的事就是换成分区**：`fsd` 的写路径一做出来，
这条边界立刻会从"诊断程序的抱怨"变成"系统读不了自己的文件"。

## 12. 重启（复位）路径与它在 QEMU 下的行为

A/B 的生效点就是重启，所以"让机器重启"必须是系统的一等能力，而不是调试接口：

- 内核新增 `FE_SYS_REBOOT`，实现是三条路径依次尝试（`kernel/arch/x86_64/reset.c`）：
  1. **PCI 复位控制寄存器 0xCF9**（QEMU/VBox 都实现，且能表达"这是系统复位"）；
  2. **8042 的 RESET 线**（向 0x64 写 0xFE）——最老、最通用；
  3. **三重故障**（`lidt` 一个空 IDT 再 `int3`）——必然复位，但看起来像一次崩溃，
     所以排在最后。
  三条都失败时**停机而不是返回**：返回去会让调用者以为"重启完成了"。
- init 在两个地方调用它：更新提交之后、回滚判定之后。
  另加一条 `fek.reboot=1` 的启动请求，用来**单独**验证复位路径
  （不必先跑完一次 7.6 秒的拷贝 + 一整轮启动）。

**QEMU + WHPX 下的实测**（`-d cpu_reset` 计数）：

| 场景 | CPU Reset 次数 | 串口 |
|---|---|---|
| 普通启动 | 2 | 正常 |
| init 请求复位（0xCF9） | **3** | 复位之后**没有新输出**，进程 99% CPU 空转 |
| init 请求复位（8042） | — | 同样没有新输出 |
| **QEMU monitor 的 `system_reset`** | — | **同样没有新输出** |
| VirtualBox 7.2 下 init 请求复位（8042） | — | 同样没有新输出 |

最后一行是关键：连 QEMU **自己**的复位命令也叫不回固件。也就是说
"复位之后固件不回来"是这台环境（QEMU + WHPX + OVMF）的性质，
不是内核写错了端口——内核那两次至少让 CPU Reset 计数从 2 变成 3，
证明请求确实被处理了。

我一开始的推理顺序是反的：先怀疑自己的 0xCF9 序列（RST_CPU 位会把 CPU
扣在复位态），改成了 8042 优先。改完症状不变，才想到去用 monitor 做对照——
**对照实验比继续猜测便宜得多**，而且它把"我的代码有问题"和"环境做不到"
这两件事彻底分开了。复位顺序仍然保留 8042 优先（副作用最小），
但理由从"我猜 0xCF9 有问题"变成了"首选应当是副作用最小的那条"。

所以在 QEMU 演示里，"第二次启动"是用**下一次运行**完成的
（`--keep-image` 复用盘上的引导控制块，见 §9 的实测）。
这一条不能含糊：在能正常重新初始化固件的环境里，这个复位应当直接生效；
QEMU 下 A/B 的"无缝"体验会退化成"需要再跑一次"。
