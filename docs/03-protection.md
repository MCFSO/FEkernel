# 系统文件保护：移植 WRP / WFP

> 决策：**Windows 资源保护（WRP）及其前身 Windows 文件保护（WFP）两代机制一起移植。**
> 更新走「专用更新能力 + 签名更新包」；受保护文件**全部放磁盘 FAT32**。

## 一、先把两代机制的事实说准

### WFP（Windows 2000 / XP / 2003）

| 项 | 内容 |
|---|---|
| 组件 | `sfc.sys`（内核态）+ `sfcfiles.dll`（受保护文件名清单，**由内核加载**）+ `%SystemRoot%\System32\dllcache`（原始副本缓存） |
| 行为 | **不阻止修改**。安装程序写系统文件照样成功 |
| 兜底 | 事后发现哈希不符 → 从 `dllcache` **静默还原** → 记事件日志 |
| 再兜底 | `dllcache` 也坏了 → 弹窗要安装光盘 |

**WFP 的"保护"= 最终状态正确，不是"碰不到"。** 这一点很多人记反了。

### WRP（Vista 及以后）

| 项 | 内容 |
|---|---|
| 机制 | 换成**事前阻止**：所有者 = `TrustedInstaller`，Administrators 只有读权限 → 删除直接"拒绝访问" |
| 存储 | 组件存储 `WinSxS` + 硬链接（`System32` 和 `WinSxS` 里的名字指向同一份数据） |
| 修复 | `TrustedInstaller` 服务按需修复 |
| 覆盖 | 文件、目录、注册表键 |
| 绕法 | 管理员启用 `SeTakeOwnershipPrivilege` 夺取所有权 → 改 ACL → 删 |

### 为什么要两代一起抄

| 机制 | 阻止正常路径 | 修复异常路径 |
|---|---|---|
| WFP | ✗ | ✓ |
| WRP | ✓ | — |

**WRP 管正常路径，WFP 管异常路径。** 只抄 WRP，遇到物理接触/恶意驱动就没了；
只抄 WFP，正常路径上谁都能删（虽然会被还原），体验和语义都不对。

## 二、映射到我们的能力模型

| Windows 概念 | FEKernel 对应物 |
|---|---|
| `sfcfiles.dll`（内核里的受保护清单） | **签名清单**：放磁盘，公钥编进内核，内核验证签名后才采信 |
| 所有者 `TrustedInstaller` | 保护记录的 owner 字段 + `FE_RIGHT_PROTECT` 能力 |
| Administrators 只有读权限 | 除持有对应 owner 能力者外，所有任务对受保护对象**只有读权限** |
| `SeTakeOwnershipPrivilege` 夺取所有权 | **不存在这条路**：能力不可伪造、且不落在磁盘上——没有"先补一个特权位、再改规则"的路径 |
| `dllcache` / `WinSxS` | 磁盘上的**组件存储区**（FAT32 保留簇区，块层写白名单保护） |
| `TrustedInstaller` 服务 | **更新服务**：持有更新能力，且该能力只能由**签名更新包**触发释放 |
| 事件日志 | 保护违规日志（内核环形缓冲 + 落盘） |
| 弹窗要安装光盘 | 组件存储也损坏时 → 拒绝加载受保护组件，报告**需要安装介质** |

## 三、信任根：内核里只放一把公钥

编进内核镜像的东西**只有一样**：**Ed25519 公钥（32 字节）**。

- 清单放磁盘（满足"全部放磁盘"的要求），但**签名由内核用内置公钥验证**。
- 改清单 → 签名验不过 → 内核拒绝采信该清单 → 系统进入"受保护组件不可用"状态，
  **不静默降级**（静默降级正是 WFP 最被诟病的地方）。
- 更新系统文件 = 用私钥签一个新包。**私钥不进仓库**；`tools/sign_pkg.py` 只把公钥注入构建。
- 这是 Windows 的 catalog / 签名模型，比"哈希清单编进内核"更好：更新不必重编内核，
  而信任根只有 32 字节。

## 四、四个执行点（按从外到里）

1. **访问检查（WRP 层）**：受保护路径的写 / 删 / 改名 / 改属性 → `FE_ERR_PERM`，
   除非任务持有该记录 owner 对应的能力。**默认拒绝，不是检查后拒绝。**
2. **块层写白名单（WRP 层）**：文件系统服务拿到的写能力**不含**组件存储区 →
   即使 FS 服务被整个替换成恶意版本，它也写不动那些扇区。
3. **内容校验（WFP 层）**：内核在加载受保护组件前按清单哈希校验；不符 → 从组件存储还原 → 记日志。
4. **组件存储自校验（WFP 层）**：存储区里的副本也要过哈希；坏了 → 报告需要安装介质。

## 五、诚实的两条边界

1. 磁盘驱动若持有原生端口 / MMIO 访问权，可以自己发 DMA 写任意 LBA，**绕过第 2 层**。
   这时靠第 3、4 层检测并还原——**这正是 WFP 存在的理由**。
   （注意 IOMMU 堵不住这件事：它限制的是"能写哪块内存"，不是"能写哪个 LBA"。）
2. 攻击者若**同时**改文件内容和组件存储，我们只能拒绝加载并索要安装介质。
   Windows 在这里也一样，没有更神的办法。

## 六、接口与里程碑

| 组件 | 归属 | 状态 |
|---|---|---|
| 能力授予路径（`fe_ioport_request` / `fe_mmio_map` / `fe_irq_register`） | 内核 | **M5 已完成** |
| 硬件资源池（互斥认领 + 归还） | 内核 | **M5 已完成** |
| `FE_RIGHT_PROTECT` 权限位 | 内核句柄表 | M6 待加 |
| 块设备层 + 扇区写白名单 | 内核 | M8 |
| FAT32 + 保护路径检查（执行点 1） | 内核 VFS | M8 |
| 清单解析 + Ed25519 验签 | 内核 | M9 |
| 组件存储 + 还原（执行点 3、4） | 内核 / 更新服务 | M9 |
| `tools/sign_pkg.py`、`tools/mkmanifest.py` | 构建工具 | M9 |
| 保护违规日志 | 内核 | M9 |
| 安装介质恢复流程 | 安装器 | M10 |

## 七、已定决策

- **保护强度**：WRP + WFP 两代机制合体（事前阻止 + 事后修复）
- **更新**：专用更新能力，只能由签名更新包触发
- **位置**：全部放磁盘 FAT32（签名清单 + 组件存储区都在磁盘上）
- **信任根**：Ed25519 公钥编进内核，私钥不进仓库
