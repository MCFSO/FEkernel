# 句柄传递与批量 IPC：把能力模型补成可用

> 本文记录三件事的设计与代价：**句柄传递的 ABI 入口**（①）、
> **随消息传内存对象的批量 IPC**（②）、以及**两个已经声明却没实现的系统调用**
> （`FE_SYS_MEM_UNMAP` / `FE_SYS_HANDLE_DUP`，③）。
> 它们是同一件事的三面：**内核里的能力模型早就写好了，用户态够不着它**。

## 1. 问题：能力模型在用户态是残的

内核的 `build_message()` 早就会把发送方给的句柄查出来（带 `FE_RIGHT_TRANSFER`
权限检查）放进 `m->transferred[]`，接收方 `fe_endpoint_recv(..., out_transferred)`
也会把它安装进自己的句柄表，引用计数一路都对。**但是用户态用不了**：

```c
/* kernel/arch/x86_64/syscall.c（改之前） */
return fe_endpoint_send(t, (fe_handle_t)ep, &hdr, payload, NULL);   /* ← 永远是 NULL */
```

ABI 里根本没有传句柄的通道，`fe_endpoint_recv` 的 `out_transferred` 也没人接。
于是用户态服务之间只有三种办法交换数据：

1. 内联载荷（**上限 `FE_MSG_MAX_PAYLOAD` = 1024 字节**）；
2. devfs 路径找服务（这是"找到对方"，不是"传东西给对方"）；
3. 全局名字（本项目刻意不做的东西）。

后果是具体的、可测量的：**块设备一次最多 2 个扇区**——不是 ATA PIO 的能力限制，
是 1024 字节载荷减去 16 字节请求头之后只够 2×512。fAT 每次读写都要拆包，
而"拆包的边界处理"（半扇区、重试、跨簇拼接）是纯粹的额外复杂度。

所以 ① 不是"再加一个功能"，而是**把已经写好的机制接到用户态**。
没有它，② 无从谈起（批量传输的正解就是"随消息传一个内存对象句柄"）。

## 2. ① 句柄传递的 ABI

### 新签名

```
0x11 FE_SYS_ENDPOINT_SEND(ep, hdr, payload, hcount, harr)
0x12 FE_SYS_ENDPOINT_RECV(ep, hdr, payload, cap, hbuf, nbuf) -> reply_ep
```

`harr` 是用户态的 `u32[hcount]`；`hbuf` 是用户态的 `u32[FE_MSG_MAX_HANDLES]`
（不足项填 0 = `FE_HANDLE_INVALID`），`nbuf` 接收实际安装了几个。

### 六个决定，以及为什么

**1. `hcount` 必须由参数给出，而且必须与 `hdr.handle_count` 一致。**
两个来源（头里的字段、参数）不一致时，内核**拒绝**（`FE_ERR_INVAL`）而不是
"以某一边为准"。理由：`hdr.handle_count` 决定内核要查几个句柄，
参数决定内核要从用户内存拷几个字节；允许它们不一致，
就是允许"内核按 A 读、用户按 B 理解"——那类不一致的症状是
"有时传过去的句柄是垃圾"，而根因在几千行之外。

**2. 只能在 `SEND` 上传，不在 `CALL` 上传。**
`CALL` 的请求载荷是裸字节（没有消息头），它的头由内核构造。
给它加句柄通道意味着要再造一套参数，而**今天的真实需求（服务端把大块内存交给
客户端）发生在回复方向**——回复走的是 `fe_endpoint_send(reply_ep, ...)`。
所以 `CALL` 保持原样：这不失去任何能力，`CALL` 的请求本来就可以拆成
`SEND` + `RECV` 两步走。

**3. 接收侧的 `hbuf`/`nbuf` 先校验、后接收。**
`fe_endpoint_recv` 是**阻塞**的，而且成功时已经在接收方句柄表里装好了新句柄。
如果那句柄数组最后拷不回去，用户态就拿到了一堆**自己不知道句柄号的已安装句柄**
——泄漏，而且是不可回收的泄漏。所以两个用户指针在进入 IPC 之前就用
`fe_user_range_ok()` 校验（未映射 → `FE_ERR_FAULT`，不消耗任何消息）。

**4. 接收方拿到的权限 = 发送方的权限减去 TRANSFER。**
这是能力模型的核心约束的落点：**能力只能收窄，不能放大**。
"减 TRANSFER"这一条尤其重要：不加它，A 把端点交给 B 之后 B 就能自己
无限转发，一条能力会像病毒一样扩散，而"谁持有这个端点"这个问题就再也答不出来了。
（可以给需要转发的场景加 opt-in，但那是**需求出现时**的事，不是现在。）

**5. 权限不足的错误必须能区分。**
发送方句柄没有 `FE_RIGHT_TRANSFER` → `FE_ERR_ACCESS`（不是 `BADHANDLE`）；
句柄号根本不存在 → `FE_ERR_BADHANDLE`。两者混在一起，
调用者分不清"我没这个能力"和"我传错了句柄号"。

**6. `handle_count` 超过 `FE_MSG_MAX_HANDLES`（4）→ 明确拒绝。**
不截断。截断会让发送方以为 5 个都过去了，
而接收方只看到 4 个——这类"少了一个"的 bug 极难定位。

## 3. ② 批量 IPC：内核完全不碰数据

有了 ①，"搬 1 MiB"变成了三步，**内核一次都不参与数据搬运**：

```
客户端                                 服务端
fe_mem_alloc(1 MiB) -> h
fe_mem_map(h)       -> p     ← 客户端拿到可读写的虚拟地址
fe_endpoint_send(ep, {handle_count=1}, payload, 1, &h)
                                        fe_endpoint_recv(..., hbuf, &n)
                                        h2 = hbuf[0]
                                        q = fe_mem_map(h2)  ← 同一个物理内存
                                        memcpy(q, data, size)
fe_endpoint_recv(reply_ep)   ← 拿到"写完了"的应答（载荷只有几十字节）
读 p 校验内容
```

关键性质：**同一条消息的内联载荷仍然只有几十字节**，
1 MiB 走的是页表映射。于是吞吐由内存带宽决定（本项目实测 memcpy 52 GB/s），
而不是由 `FE_MSG_MAX_PAYLOAD` 决定。1024 字节的上限从此只约束"控制面"，
不约束"数据面"。

### 这条路径上必须验证的三件事

1. **接收方真的能映射它收到的句柄**——`fe_memory_map_user` 要求句柄带
   `FE_RIGHT_WRITE` 才能可写映射，而接收侧的权限是收窄过的。
   权限位给错的话，症状是"映射成功但写进去客户端看不见"（映射成了只读）。
2. **两个地址真的指向同一份物理内存**——不是"两个进程各有一块内容相同的副本"。
   用一个只有服务端知道的模式去校验：服务端写、客户端读，
   客户端再改、服务端回读。单向校验发现不了"两份副本"。
3. **大块（1 MiB）与小块走的是同一条路径**——只有小块过、大块不过，
   说明某处按页数或按大小分了支。

### 反向对照（这条比正向测试重要）

只测"该过的过了"永远为真也可能毫无意义。所以同时测：

| 场景 | 期望 | 为什么必须有 |
|---|---|---|
| 没有 `FE_RIGHT_TRANSFER` 的句柄被发送 | `FE_ERR_ACCESS` | 证明权限检查真的在跑，而不是"看起来在跑" |
| 不存在的句柄号被发送 | `FE_ERR_BADHANDLE` | 证明错误码有区分度 |
| `hcount` 与头里的 `handle_count` 不一致 | `FE_ERR_INVAL` | 证明两个来源真的在互相校验 |
| 句柄数组指针未映射 | `FE_ERR_FAULT`，且**消息没有到达** | 证明"先校验后接收"这条约束成立（否则接收方会拿到无法回收的句柄） |
| 接收方拿到的句柄再转发 | `FE_ERR_ACCESS` | 证明 TRANSFER 位真的被减掉了（能力不能自我复制） |

## 4. ③ 两个缺失的系统调用

### 4.1 `FE_SYS_MEM_UNMAP`（0x22）

```
0x22 FE_SYS_MEM_UNMAP(addr, size) -> 0
```

**它不释放物理帧**，因为帧的所有者是内存对象，不是映射。
映射只是"在页表里指一下"；对象还在（可能还被别的任务映射着、
可能还被句柄持有），帧就必须还在。想释放内存的正确做法是
**关掉最后一个句柄**，那是对象生命周期的事。

这条分界必须写清楚，否则会有人想让 `MEM_UNMAP` "顺手把内存还回去"——
那样就会释放一块另一个任务正在用的内存，症状是对方数据随机损坏。

约束：**只允许撤销 mmap 区（`FE_USER_MMAP_BASE..END`）内的映射**。
程序映像与栈也在这个地址空间里，但它们不是 `MEM_MAP` 建立的；
允许撤销它们等于提供一个"把自己的代码页拆掉"的接口——
那不是机制，是陷阱。范围外返回 `FE_ERR_INVAL`。

### 4.2 `FE_SYS_HANDLE_DUP`（0x31）

```
0x31 FE_SYS_HANDLE_DUP(handle, new_rights) -> handle
```

内核的 `fe_handle_dup()` 早就实现了（含"权限只能收窄"的检查），
缺的只是分发 case 与用户态包装。`new_rights == 0` 表示"沿用原权限"。

它解决的具体问题：**同一个能力给同一个任务的另一个线程用**。
今天的替代方案是把句柄号写进共享变量——而句柄号是**进程内索引**，
两个线程共用一个号没有任何保护（一个线程 close 掉，另一个线程的号就指向别的东西
或变成无效）。dup 出来的两个句柄各自独立关闭，引用计数保证对象活到最后一个关闭。

## 5. 代价与边界（诚实记账）

| 项 | 代价 | 说明 |
|---|---|---|
| 每次 `SEND` | 多一次 `fe_copy_from_user`（≤16 字节）| 只在 `hcount > 0` 时发生；`hcount == 0` 走原路径，零额外开销 |
| 每次 `RECV` | 多两次范围校验 + 一次 `fe_copy_to_user`（≤16 字节）| 同上 |
| `struct fe_message` | 多 16 字节（4 项权限数组）| 消息池 64 条 → 1 KiB |
| 接收侧安装失败 | 该槽位留 0，**不使整次接收失败** | 句柄表满时"消息收到了但句柄没装上"，返回 0 而不是让整条消息丢失——消息里的数据仍然有效 |
| 本次**不做** | `CALL` 上的句柄通道、跨任务句柄的 `DUP`、句柄数组长度 > 4 | 见 §2 决定 2/6；都是"需求出现再加"，不是"以后再说" |

**没有做的事要有硬理由**：`FE_MSG_MAX_HANDLES = 4` 保持不变，
是因为它直接决定 `struct fe_message` 的大小（64 条消息池），
而现在**没有任何一个真实协议需要一次传 5 个以上能力**。
把它提到 16 会让消息池多占 3 KiB 而收益为零。

## 6. 验证方式

三层，缺一不可（沿用项目既有做法）：

1. **内核自检**（`fe_selftest_ipc` + `fe_selftest_vmm_unmap`）：
   句柄传递（含上表 5 条反向对照）、句柄复制（收窄/放大/无 DUP 权限）、
   内存对象跨线程可见性、撤销映射（页表项已清 / 撤销后重映射看不到旧内容 /
   撤销不还帧 / 帧计数复元）；
2. **用户态端到端** `user/bin/hxtest`：走**真实 IPC 路径**，
   在**两个真实任务**之间传内存对象（1 MiB 双向 + 4 KiB + 只读负向对照）；
3. **双环境**（QEMU+WHPX 与 VirtualBox）实测，串口日志里的失败项数为 0。

## 7. 实现过程中撞出来的 6 个问题（每一个都是证据，不是推测）

这一轮的收尾方式与前几轮一致：**先把机制做出来，再用端到端测试把它逼到墙角**。
下面 6 条里有 2 条是内核的真 bug（已修），4 条是"我按习惯用接口、而接口的定义不是那样"。

| # | 症状 | 根因 | 性质 |
|---|---|---|---|
| 1 | 一个真实存在的程序 `spawn` 报 `EFAULT` | `sys_process_spawn` 用**定长 256 字节**从用户指针拷路径。字符串本身有效，但它落在映射区末尾时，往后读 256 字节跨进未映射页 | **内核真 bug**。修法：`fe_copy_str_from_user()` 逐页校验、遇 `'\0'` 即停，**从不读越过终止符的字节**。devfs 的 publish/open 也走同一条路 |
| 2 | 服务端"只能收"的收件端点，任何按名字打开的人都能**发**（甚至能收） | `fe_devfs_open` 一律安装 `SEND\|RECV\|DUP\|TRANSFER`，**不保留发布时的权限** → "发布时收窄"是装饰 | **内核真 bug（能力泄漏）**。修法：`devfs_entry` 记住发布方当时持有的权限，打开时取交集。反向对照进了 `fe_selftest_devfs`：只给 RECV 发布 → 客户端打开后 `SEND` 必须返回 `FE_ERR_ACCESS` |
| 3 | 服务端拿到 `argv[1]` 里的句柄号，用它接收**成功返回 0 但收不到消息** | **句柄号是进程内索引，不能跨任务**。父进程把"3"写给子进程，子进程表里的 3 是另一个对象 | 用法错误。修法：改用项目自己的机制——收件端点发布到 devfs（名字跨任务），状态页句柄**随消息**交过去。引导问题不该用"传号码"绕过 |
| 4 | 握手明明成功，客户端却判它失败 | `fe_endpoint_recv` 的**返回值不是错误码**：`>= 0` 就是收到了，0 只表示"发送方没给回复能力" | 用法错误。接口的返回值含义必须按定义读 |
| 5 | 服务端"回复"了，客户端永远等不到 | 请求是用 `fe_endpoint_send` 发的，**没有回复端点**，服务端的 `reply` 是 0，应答被丢进黑洞 | 用法错误。修法：`fe_endpoint_call` 就是为此存在的——它建临时回复端点、随请求交出去、在它上面等应答 |
| 6 | 服务端报告"校验和为 0（没有真的读）"，而它明明读完了 1 MiB | 我的聚合方式写成了 `sum ^= checksum_of(chunk)`：16 个 64 KiB 块内容完全相同，XOR 起来正好是 0 | 测试自身的缺陷。修法：改成加法累加。**聚合方式选错会把一次正确的读判成失败** |

★ 第 3/4/5 条是同一类：**我按习惯猜接口语义** ★
它们全都表现为"IPC 不通"，而根因分别是"号码不是能力"、"返回值不是错误码"、
"发送不等于请求-应答"。定位它们的唯一有效手段是**看内核侧的追踪**
（谁在哪个端点上收到/发出了什么），而不是盯着用户态的报错猜——
用户态能看到的只有"没收到"，而"没收到"至少有五种原因。

## 8. 与其他机制的关系（这一轮之后哪些东西解锁了）

| 机制 | 之前 | 现在 |
|---|---|---|
| 服务间传内存对象 | 做不到（ABI 没有通道） | `fe_endpoint_send(..., handles, n)` |
| 块设备批量传输 | 一次 ≤ 2 扇区（1024 字节载荷上限） | 随消息传内存对象，**内核不碰数据**；QEMU 实测 1 MiB 往返 2000 us |
| 同一能力的多线程使用 | 只能共用句柄号（一方 close 就废） | `fe_handle_dup`，两个句柄各自独立关闭 |
| 撤销映射 | 没有 syscall（映射进内存对象就还不回去） | `fe_mem_unmap`，幂等、只接受 mmap 区 |
| 发布时收窄权限 | 只是发布方那边的装饰 | 打开方拿到的权限以发布方权限为上界 |

### 已知边界（写在这里而不是含糊过去）

- **`CALL` 上没有句柄通道**（见 §2 决定 2）：`CALL` 的请求是裸字节、头由内核构造。
  需要"请求带能力"时，用 `fe_endpoint_call` 的**扩展形式**：
  像 `hxtest` 那样把内存对象句柄与回复端点一起用 `fe_endpoint_send` 交出去
  （回复端点是最后一个句柄，这是 `fe_endpoint_call` 的语义决定的）。
  这条约定值得在未来提升成 ABI 的一部分。
- **句柄数组上限 4**（见 §5）：它决定消息池大小，没有真实协议需要更多。
- **跨任务 `DUP`**：句柄复制只在**自己**的句柄表里做。跨任务复制没有意义
  ——那正是句柄传递（TRANSFER）的用途。


### 计时这件事本身也要有证据（本轮最后补上的一条）

`hxtest` 报"1 MiB 往返耗时"时换过三次写法，每一次都是被一个环境的读数逼出来的：

| 写法 | QEMU | VBox | 问题 |
|---|---|---|---|
| 毫秒 | 3 ms | **0 ms** | 看不出快慢，容易被读成"没测" |
| 微秒 | 1000~2000 us | **0 us** | 同上，而且更像"极快" |
| 微秒 + 刻度自证 + 分辨率说明 | 2000 us | 小于一个节拍 | 读者知道这个数字能不能用 |

根因是**内核的单调时钟是按节拍算的**（`fe_time_ms()` = 节拍数 / 每毫秒节拍数），
而节拍间隔在 QEMU 是 1 ms、在 VBox 是 6~20 ms（VBox 对中断投递限流，见
`08-kernel-completion.md` §6 第 5 条与 `01-milestones.md` 的实测记录）。
往返不足一个节拍时，两次读数一模一样，差值必然是 0。

所以工具现在先做一次**刻度自证**（睡 50 ms 再量它，QEMU 与 VBox 都是 100%），
再按**能分辨的量**报耗时；分辨不出来时明确写"小于一个时钟节拍"。

★ 这一条不是吹毛求疵 ★ 它和本项目前几次误判是同一个根：
**证据本身要先被证明可用，再去用它下结论。** 一个"0 us"看起来很漂亮，
而它真实的含义是"这个尺子量不了这么短的东西"。
`fe_clock_ns()` 走的是节拍而不是 TSC，这一条本身也值得将来改
（`time.c` 的注释里写着"凡是时间都应以 TSC 为准"）——
那是内核侧的一件事，不在本轮范围。
