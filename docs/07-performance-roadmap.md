# 性能路线图：按"每次操作省下多少绝对时间"排序

> 目标：**性能要优**，不是"够用就行"。
> 本文把系统里所有已知的性能问题放在**同一把尺子**上量，排出执行顺序。
> 结论先说：这不是一个 3 倍的问题，而是**三个不同数量级的问题叠在一起**，
> 而且**多核不是最大的那个**。

## 1. 实测 vs 可达

| # | 路径 | 实测（今天） | 可达 | 倍数 | 靠什么 |
|---|---|---|---|---|---|
| 1 | **块设备每扇区** | **2.81 ms**（= 182 KB/s） | 1 ~ 5 µs（200 MB/s ~ 2 GB/s） | **~1000×** | 总线主控 DMA（AHCI / virtio-blk） |
| 2 | **批量传输每次 RPC** | 512 B / 1024 B | 64 KiB ~ 1 MiB | **128 ~ 2000×** | 共享内存批量 IPC（今天被 1024 B 内联载荷卡死） |
| 3 | **A/B 拷贝 1.36 MiB** | **7.6 s** | ~10 ms | **~700×** | 1 + 2 叠加 |
| 4 | IPC 往返 | 5836 ~ 6002 周期 | ≤ 2000 | **3×** | 同核 direct switch + 去掉全局池 + 复用回复端点 |
| 5 | 上下文切换 | 2134 ~ 2375 周期 | ≤ 600 | **3.5×** | 直接栈切换（不再绕完整中断帧路径） |
| 6 | 文件系统元数据（`ls`/`stat`） | 每次若干次磁盘读（≈10 ms 级） | µs 级 | **1000×** | fsd 里的块/目录缓存 |
| 7 | **用户态 SIMD** | **完全不可用**（`-mno-sse`，CR4 无 OSFXSR） | AVX2 可用 | **解锁一整类工作** | CR4.OSFXSR/OSXSAVE + XSAVE 上下文 |
| 8 | memcpy | ~40 GB/s（纯整数） | 60 ~ 100 GB/s | 1.5 ~ 2.5× | 向量化 + 非临时存储 |
| 9 | 系统调用 | 118 ~ 129 周期 | 80 ~ 100 | 1.3× | 已经很好；只求别被锁吃掉 |
| 10 | 多核扩展（4 核） | 1×（不可用） | ≥ 3.5× | — | 热路径不共享（见 `06-smp.md`） |

## 2. 排序的算术（为什么磁盘排第一）

排优先级不能按"架构上是否优雅"，只能按
**每次操作省下的绝对时间 × 该操作的频率**：

| 优化 | 单次省下 | 频率量级 | 每秒收益 |
|---|---|---|---|
| 磁盘 DMA | **2.8 ms / 扇区** | 有 I/O 时就是瓶颈 | 一次 1.36 MiB 拷贝省 **7.6 秒** |
| 批量 IPC | 1228 次 RPC → 1 次（省 2.4 ms） | 每次大数据传输 | 同上量级 |
| IPC fastpath | **~1.3 µs / 次** | ~500k 次/秒 | 吞吐 ×3 |
| 上下文切换 | ~0.5 µs / 次（RPC 内含 2 次） | 同上 | 每次 RPC 再省 1 µs |
| 多核 | 把**每核吞吐**乘 3.5 | 全局 | 3.5× |

★ **磁盘与 IPC 差三个数量级，而多核只差 3.5 倍** ★
这不是偏好，是算术：**在 182 KB/s 的磁盘上做多核，等于给一辆轮胎没气的车换更大马力的发动机。**

但三条主线**都要做**，因为它们覆盖不同的工作形态：

- **做 I/O 时**（启动加载、A/B 更新、将来任何文件操作）→ 磁盘路径决定一切；
- **服务间通信密集时** → IPC 与上下文切换；
- **并行计算 / 多客户端时** → 多核。

### 一条必须说清楚的诚实边界

2.81 ms/扇区 里**有很大一部分是虚拟化的放大**：WHPX 下每一次端口 I/O 都是一次 VM 退出，
而 PIO 传一个扇区要 256 次 `outw` 加若干次状态轮询——上千次 VM 退出。
真机上 PIO 大约是 4 ~ 20 MB/s，仍然比 DMA 慢两个数量级，但**不会有 1000 倍这么多**。

所以：
- "PIO 必须换成 DMA" 这个结论**在任何环境下都成立**（真机上也是几十倍）；
- "1000×" 这个数字**只在虚拟化下成立**，引用时必须带上环境。

## 3. 主线 A：磁盘路径（1000× 级）

```
今天：客户端 ──IPC(512B/次)──▶ fsd ──IPC(512B/次)──▶ blkd ──PIO(256 outw/扇区)──▶ ATA
      1.36 MiB = 2720 扇区 → 2720 次 PIO + ~5400 次 RPC = 7.6 秒
```

四步，每一步都独立有效，**顺序不能反**：

1. **PIO → 总线主控 DMA**（AHCI 或 virtio-blk）。
   一次命令搬 64 KiB～128 KiB，CPU 只写几次寄存器，然后等中断。
   预计 **2.81 ms → 2~5 µs/扇区**。
2. **单扇区 RPC → 批量共享内存 IPC**。
   把一块内存对象随消息交给服务，服务直接写进去——内核完全不碰数据。
   预计 RPC 次数 **5400 → ~20**。
   这一步同时把"每次最多 2 个扇区"（`FE_BLK_MAX_READ`）这个上限从
   "协议约束"变成"没有约束"：今天那个上限**不是驱动能力决定的，是内联载荷决定的**。
3. **零拷贝**：磁盘 DMA 直接落到客户端持有的页，中间不经任何 bounce buffer。
   这需要 §5 的共享内存 IPC 与"服务端写客户端页"的权限模型（能力已经够用：
   内存对象 + 句柄权限）。
4. **fsd 加块缓存 / 目录缓存**：元数据操作（`ls`、`stat`、路径解析）
   从"每次若干次磁盘读"变成内存查表。**这一条与 DMA 独立**，即使不换 DMA 也该做。

做完 1+2，A/B 拷贝 7.6 s → **~10 ms**。这是那种"用户能直接感觉到"的差别。

## 4. 主线 B：IPC 与上下文切换（3~10× 级）

微内核的税就在这里，所以它必须被压到最低。

| 项 | 现状 | 目标 | 做法 |
|---|---|---|---|
| 每次 RPC 的固定成本 | 5836 ~ 6002 周期 | ≤ 2000 | 同核 direct switch（客户端阻塞时直接把 CPU 交给服务线程，不经过调度器排队） |
| 全局空闲链 | 每次 RPC 动 2 条（消息池 64 + 端点池） | 0 | 每 CPU 消息缓存 + 回复端点复用（端点是**对象**，可以直接挂在端点上循环用） |
| 上下文切换 | 2134 周期（走完整中断帧） | ≤ 600 | 直接栈切换：`switch_to(prev, next)` 只保存被调用者保存寄存器 + 换栈，不再构造/解析中断帧 |
| 数据搬运 | 内联 ≤ 1024 B | 批量零拷贝 | 共享内存对象（与主线 A 第 2 步同一件事） |
| 小消息 | ≤ 64 B 走寄存器直传 | 保持 | 已经做了，别退回去 |

★ **direct switch 是这里唯一"用并行度换延迟"的地方** ★
它要求客户端与服务在同一个核上（见 `06-smp.md` §11）。性能优先的用法是：
**把服务线程钉在收它中断的核上**，让"同核"成为常态，跨核才走常规排队。
这样同时拿到"中断不打核"和"IPC 走 fastpath"两份收益。

## 5. 主线 C：多核（3.5× 级，且是唯一能叠加的东西）

多核本身不解决上面任何一条，但它把上面每一条的**每核吞吐**乘起来。
性能优先的多核设计与"先上大锁跑通"的保守设计有几处**关键差别**
（完整设计见 `06-smp.md`）：

| 项 | 保守做法 | **性能优先做法** |
|---|---|---|
| 锁策略 | 先 BKL，再逐步拆 | ★ **热路径从第一天就不共享** ★：per-CPU 运行队列 / slab / 消息缓存 / 页帧批次 → 公共路径上**一把锁都不拿** |
| 冷子系统 | 以后再说 | 各自一把锁即可（VFS、protect、资源池），它们本来就不在热路径上 |
| 中断定向 | 先全 BSP | 直接定向到"处理它的那个核"（省一次跨核唤醒 + 缓存局部性） |
| IPC | 常规排队 | direct switch 是**目标**而不是"以后再说" |
| 地址空间切换 | 不做 PCID | PCID **值得做**（exec/spawn 频繁，免全刷 TLB） |
| 空闲 | 每核照常打节拍 | **tickless 空闲**：没活干就关掉本地定时器，减少 VM 退出与干扰 |
| 共享数据 | 用锁保护 | ★ 优先**消除共享**，而不是保护共享 ★ |

★ **为什么可以跳过 BKL** ★
BKL 存在的理由是"我还不知道哪些数据是共享的"。而这个理由在这里**不成立**：
`06-smp.md` §2 已经把 9 处共享逐条定位了。既然知道，就直接建对的结构——
而且**分阶段依然安全**：per-CPU 数据结构可以在**单核**下先建好并验证
（此刻它只是"一个 CPU 的结构"，行为不变、自检全绿），再启动 AP。
这样既不经过 BKL，又保留了"每步可验证"的好处。

**一条硬规则**（可静态检查）：**热路径（syscall 入口/出口、调度切换、IPC 收发、
时钟中断）上不允许获取全局锁。** 调试构建里把全局锁标出来，任何从这些路径
进入全局锁的行为直接报错。这条规则把"性能"从愿望变成约束。

## 6. 主线 D：FPU / SIMD —— 从"不可用"到"可用"（✅ 已完成）

**之前的状态：用户态不能执行任何 SSE/AVX 指令。** 两个原因叠加：

- `USER_CFLAGS` 里有 `-mno-sse -mno-sse2 -mno-avx -mgeneral-regs-only`；
- 内核**从不设置 CR4**：没有 `OSFXSR`、没有 `OSXMMEXCPT`、没有 `OSXSAVE`/`XCR0`。

所以这不只是"慢"，是**一整类工作根本做不了**：向量化的 memcpy/memset、
图像与音频处理、数值计算、以及——★ **任何真正的密码学库** ★。
（OpenSSL / BoringSSL 要求 SSE2/AVX，所以"密码学放用户态服务链现成库"
这个计划在 SIMD 打开之前一步都执行不了。）

### 做完之后（实测，QEMU + WHPX，`-cpu host`）

```
[FPU] XSAVEOPT（跳过未修改部件）：CR0.EM=0 MP=1 TS=0，CR4.OSFXSR=1 OSXMMEXCPT=1 OSXSAVE=1
      XCR0=0x7（x87 1 SSE 1 AVX 1），每线程状态 832 字节，区大小 1024 字节
      内核仍为 -mgeneral-regs-only：中断与系统调用**不保存向量寄存器**
```

| 项 | 之前 | 现在 | 证据 |
|---|---|---|---|
| 用户态 SSE2 | 不可用（`-mno-sse`） | **可用** | `simdtest` 写/读 xmm0 一致 |
| 用户态 AVX | 不可用 | **可用** | VEX 指令 `vmovdqu` 成功执行（= CR4.OSXSAVE + XCR0[2] 都对了） |
| 状态跨切换保存 | — | **有** | 5 次 yield 后 xmm0 仍是自己的值 |
| 跨线程隔离 | — | **双向成立** | 另一个线程写满它的 xmm0，两边都读到自己的值 |
| memcpy（缓存内 256 KiB） | 5.3 GB/s（逐字节） | **36 GB/s** | **6 倍**，`simdtest` 同口径对照 |
| memcpy（25 MB，bench） | 42957 MB/s | **53797 ~ 56169 MB/s** | 带宽受 DRAM 限制，所以只有 +25~31%（数字必须带条件） |
| 密码学库 | 链不进来 | **可以链了** | 前置条件已满足 |

**双环境一致**（QEMU+WHPX 与 VirtualBox 7.2）：

| | QEMU + WHPX | VirtualBox |
|---|---|---|
| 模式 | XSAVEOPT | XSAVEOPT |
| XCR0 | 0x7 | 0x7 |
| AVX 指令 | 可执行 | 可执行 |
| SSE2 / 整数 拷贝 | 36244 / 5344 MB/s（6 倍） | 36244 / 5344 MB/s（6 倍） |
| bench 25 MB 拷贝 | 53797 MB/s | 56169 MB/s |
| 全部自检 | 0 失败 | 0 失败 |

（有意思的是 `simdtest` 那一栏两个环境**数字完全相同**——256 KiB 的拷贝完全在缓存内，
与虚拟机的中断/IO 开销无关。这正好说明"选对测量对象"的重要性：
bench 的 25 MB 拷贝跨环境差 4%，因为那个数字包含内存带宽而不是 CPU 行为。）

每线程状态区 1024 字节（AVX 实际需要 832）。取 1024 不是随手取整：
内核堆的尺寸等级是 16/32/…/2048，**1024 这一级的对象天然 64 字节对齐**
（对象基址 = 页 + 64，步长 1024），而 XSAVE 要求 64 字节对齐。
这条依赖是隐式的，所以 `fe_fpu_area_alloc()` 里**显式验证**对齐，
不满足就报错并放弃——否则会在"切换线程的那一刻"收一个 #GP，
现场离原因非常远。

### 四个必须记住的设计点

1. ★ **内核继续 `-mgeneral-regs-only`** ★ 这不是保守，是性能：
   内核一行向量寄存器都不碰 ⇒ **中断与系统调用不需要保存 FPU 状态**。
   一旦有人"顺手用 SIMD 优化内核里的 memcpy"，中断延迟就要多付保存/恢复的代价。
   测试里那条"VEX 可执行"同时也证明了边界：用户态能用，内核没沾。
2. **急切保存，不做惰性**（CR0.TS + #NM）：XSAVEOPT 会跳过未修改的部件，
   从没用过 FPU 的线程只写一个头部，代价可预测、没有异常抖动。
3. **每个线程都有状态区，内核线程也不例外**：内核线程不用 FPU，
   但如果没有自己的区，切进它时会"继承"上一个线程留在寄存器里的数据——
   那是信息泄漏。创建失败时用静态的"干净状态区"兜底，隔离性不依赖分配成功。
4. **基线停在 SSE2，AVX2 走运行期分派**：AVX2 不是 x86_64 的保证项，
   编进每一个二进制意味着"在不支持 AVX2 的机器上连 init 都起不来"。
   正确做法是启动时查 CPUID 再把热点函数指针指到 AVX2 版本（后续独立项）。

无论磁盘多快都会被这一条卡住。

## 8. bench 要跟着改

今天的 bench 只测延迟（单次操作多少周期）。性能优先需要的是**吞吐与扩展**：

- `--throughput`：固定时间内完成多少次操作（RPC、syscall、切换）；
- `--bulk N`：一次搬 N KiB，报告每字节周期数；
- `--smp N`：N 个线程并行，报告**墙钟加速比**；
- ★ **负向对照** ★：同样 N 个线程但亲和性全设成 CPU 0 → 加速比必须回落 ≈1。
  没有这一条，"加速比 3.8"无法区分"真的并行"和"计时写错了"。
- 报告里同时给 **p50 与 p99**：平均好而尾部差，对"性能优"是不合格的。

## 9. 顺序（与里程碑对应）

| 顺序 | 做什么 | 归属 | 为什么在这个位置 |
|---|---|---|---|
| 1 | **批量共享内存 IPC**（协议 + 内核支持） | M9 前半 | 它是主线 A 第 2 步与主线 B 第 4 步**共同的**前置；做完它，磁盘与 IPC 两条线同时受益 |
| 2 | **AHCI / virtio-blk + DMA** | M9 前半 | 1000×，且做完 1 之后立刻吃满收益 |
| 3 | fsd 块/目录缓存 | M9 | 元数据 1000×，与 DMA 独立，随时可做 |
| 4 | **Per-CPU 数据结构**（仍单核运行） | M10.1 | 多核的地基；单核下可验证 |
| 5 | **AP 上线**（无 BKL，热路径已不共享） | M10.2 | 此时热路径已经是 per-CPU，直接就是快的 |
| 6 | IPC direct switch + 直接栈切换 | M10.3 | 3× 级，依赖"服务钉核"策略 |
| 7 | 中断定向 + 亲和性 + tickless | M10.4 | 让 5 与 6 的收益落地 |
| 8 | TLB（惰性 → IPI）+ PCID | M10.5 | exec/spawn 频繁时明显 |
| 9 | ~~**FPU / SIMD 打开**~~ | **✅ 已完成** | 解锁了一整类工作；密码学服务的前置条件已满足（§6） |
| 10 | 争用驱动的细粒度化 | M10.7 | 用计数器说话，不猜 |

★ 前三条（1~3）**都不需要多核**，但它们占了本文里 1000× 级收益的全部 ★
如果只能做一件事，做第 1 条；如果能做两件，加第 2 条。
多核（4~8）是**放大器**，不是发动机。

## 10. 明确还不要碰的

| 不做 | 理由 |
|---|---|
| 无锁数据结构（除引用计数/原子所有权） | 在前面几条做完之前，锁不是瓶颈；无锁会带来内存回收难题 |
| NUMA、CPU 热插拔、AVX-512 | 没有目标硬件/场景 |
| 内核里用 FPU | 会让中断路径必须保存 FPU 状态，代价远大于收益（SIMD 只给用户态） |
| 手工汇编优化 memcpy | 让编译器用 AVX2 就够了；先打开 SIMD 再说 |
| 换文件系统（FAT32 → 别的） | 文件系统的性能问题在今天排在"没有缓存"和"没有 DMA"后面 |

## 11. 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| **顺序做反**（先多核，磁盘仍是 182 KB/s） | 投入很大，用户感觉不到任何变化 | 本文的算术；§7 的目标里磁盘类指标排最前 |
| 虚拟化掩盖真机特性 | 拿 WHPX 的 1000× 去承诺真机，落空 | 每个性能结论都标环境；PIO 异常慢这件事单独说明（§2） |
| 批量 IPC 破坏隔离 | 共享内存 = 服务能写客户端页，权限模型出错就是内存破坏 | 走既有的能力模型（内存对象 + 句柄权限），服务端只拿到**被显式授予**的那一段 |
| 打开 SIMD 后内核被污染 | 中断路径被迫保存 FPU → 全局变慢 | 内核坚持 `-mgeneral-regs-only`，并在文档里写明这条边界（§6 第 1 点） |
| 优化了没人用的路径 | 白干 | §8 的 bench 先测出"每种操作占多少时间"，再优化占比最高的 |

## 12. 本轮 SIMD 落地时踩到的坑（都值得记）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 日志显示 `[FPU] 仅 SSE（FXSAVE）`，用户态 CPUID 报 `AVX=无` | **不是内核的问题**：QEMU `-machine pc` 默认给 **qemu64** CPU 型号，它**没有 XSAVE、没有 AVX** | 改用 `-cpu host`（WHPX）。内核本来就是运行期探测的，所以什么都没改就自动升级到 XSAVEOPT + AVX。★ 环境限制伪装成实现缺陷——这已经是本项目第二次踩（前一次是复位路径） |
| 2 | 打开 `-cpu host` 后**一个节拍都不投递**（实测 0 Hz），启动卡在调度器自检 | CPUID 里出现了 TSC-deadline，内核于是切到那条路径——而那条路在本项目里**从未被走到过**（老 CPU 型号没有这个特性位），在 WHPX 下不工作 | 本轮先用 `-cpu host,-tsc-deadline` 绕开，并把"TSC-deadline 在 WHPX 下不投递中断"作为**未解决的独立问题**记录（不假装不存在）。掩掉特性是权宜之计，所以必须写在明处 |
| 3 | AVX 测试失败，但线程**没有**被 #UD 杀掉 | 值被改掉了，说明指令执行了；真正的原因是**测试方法错了**：xmm 是**调用者保存**寄存器，写与读之间夹了一次 C 函数调用，编译器把 xmm0 挪作他用了 | 把"写 → 系统调用 → 读"整段放进**同一块内联汇编**，编译器无法插入任何东西。★ 教训：**测试跨切换的寄存器状态时，中间不能有编译器能插手的地方**——否则测的是编译器 |
| 4 | 拷贝带宽测出"SSE 版比逐字节整数版**慢 6 倍**" | 第一次拷贝把**冷缓冲区**的代价（BSS 首次写入的 RFO）算进了 SSE 那一栏，而整数那栏跑在热缓冲区上 | 先各跑一轮预热、再各跑 5 轮取最快（与 bench 同口径）。★ 微基准里"第一轮"往往测的是缓存与页错误，不是被测对象 |
| 5 | 用 `fe_clock_ns()` 测 256 KiB 拷贝，两个数字都是 0 µs，算出 "250000000 MB/s" | 计时器粒度**粗于**被测对象 | 换 `rdtsc`。★ 微基准的计时器必须远细于被测对象 |
| 6 | 测试线程 return 之后，日志里多一条 RIP=0x0 的 #PF | 线程入口的返回地址是 0（初始栈帧被清零），return 就跳到地址 0 | 线程入口**必须显式 `fe_exit()`**。★ 这种"测试全绿但日志很脏"的输出比失败更危险——它会被当成正常现象 |
| 7 | 内联汇编报 `invalid operand for instruction` | 用了位置编号 `%1/%2`，而"输出在前"的编号规则让 `movl %reg64, %eax` 这种非法组合混了进来 | 改用具名操作数 `%[name]`。数位置编号的收益是零，风险是编译错误或更糟的静默语义错 |
