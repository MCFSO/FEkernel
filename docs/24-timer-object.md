# 到点置位通知对象（K14：定时器对象）

> K14 在 `20-posix-kernel-requirements.md` §3.4 的登记是"**到点置位通知对象**
> （定时器；并且是 `wait_any` 超时的表达方式）"。
>
> ★ 但 `21-user-address-wait.md` 附录 B 第 2 条把它**收窄**了 ★
> （`docs/21-user-address-wait.md:545-548`）：K11 的**单地址等待自带绝对
> deadline**（§5.1/§5.2，`:316-335`），所以"超时"这件事不再全部落在 K14 上。
> 收窄后的 K14 = **定时器对象 + 多目标合流的超时**。
> 本文核实了那句话，**结论：收窄成立**（依据见 §3.1）。
>
> 本文只写设计，不改任何代码。所有代码事实都复核过并给出 `文件:行号`；
> 数字要么引实测出处，要么写"未实测"。

## 1. 判据与今天的缺口

### 1.1 标准判定（照 `20` §1.2 的三分法逐条执行）

| 设施 | 判定 | 依据 / 后果 |
|---|---|---|
| `timer_create` / `timer_settime` / `timer_gettime` / `timer_delete` | ★ **标准要求** ★ | POSIX.1-2001 的定时器接口族（`docs/20-posix-kernel-requirements.md:923` 已判） |
| `poll` / `select` / `ppoll` / `pselect` 的**超时参数** | ★ **标准要求** ★ | 同上；它们要的是"等 N 个目标，到点也算一次返回"——那正是本文的**多目标合流** |
| `clock_nanosleep` | ★ **标准要求** ★ | `docs/20:923`（它今天已有等价物，见 §1.2） |
| `sem_timedwait` / `pthread_cond_timedwait` / `pthread_mutex_timedlock` | ★ **标准要求** ★ | `docs/21-user-address-wait.md:322-324` 逐条点过；它们的超时由 **K11 的 deadline** 承担（§3） |
| `timerfd_create` / `timerfd_settime` / `timerfd_gettime` | ⚠ **不是标准**（Linux 专有） | `docs/20:926`：**做机制，不做那个接口**。本文按这条办——§4 明写不做 `timerfd_*` |
| `alarm` / `setitimer` | ★ **标准要求，但今天做不了** ★ | `docs/20:893`：它们要的是"到点**给我一个信号**"，而信号投递（`docs/20` §2.4(b)）今天不存在。K14 **不负责**把它们做出来 |
| `CLOCK_REALTIME` 上的定时器 | ★ **标准要求，但今天只能如实拒绝** ★ | `docs/20:924`：没有墙钟来源（`docs/20` §2.13，`:929-940` 有"没有 RTC"的逐条取证），所以 `CLOCK_REALTIME` 只能返回 `EINVAL`。**这是缺口，不是"我们选了单调时钟"** |

### 1.2 今天有什么、缺什么（复核过的代码事实）

**有的**：

- **"到点"这件事本身已经在了**：`fe_sched_sleep_until(u64 wake_ns)`
  （`kernel/sched/sched.c:827`）按**绝对纳秒**把线程挂上睡眠链，
  `wake_sleepers(now_ns)`（`sched.c:863`）在节拍里把到点的摘下来唤醒。
  K7 之后时间走 **TSC**（`kernel/time/time.c:288` `fe_time_ns`），
  节拍只作**调度单位**（`docs/11-kernel-next.md:50`）。
- **K11 又加了一条"给一个已经 BLOCKED 的线程装 deadline"**：
  `fe_sched_sleep_arm(u64 wake_ns)`（`sched.c:854`），注释里写明它是
  "两条链、一个状态"那个形状的一半（引 `docs/21` §5.3）。
- **通知对象已经能被等待、也能被 `wait_any` 合流**：
  `struct fe_notification`（`kernel/include/fe/ipc.h:62-69`）有 `bits` /
  `waiter` / `wait_mask` / `waiters[FE_WAITERS_MAX]`；
  `fe_notification_wait`（`kernel/ipc/ipc.c:1273`）、
  `fe_wait_any`（`ipc.c:884`）、`FE_WAIT_BITS`（`ipc.h:145`）。

**缺的**（这就是 K14 要补的口子）：

| # | 缺口 | 事实（`文件:行号`） | 后果 |
|---|---|---|---|
| 1 | 通知对象的 `bits` **只能被软件置位** | 唯一的置位点是 `fe_notification_signal_obj`（`ipc.c:1245-1252` 的 `nt->bits \|= bits;`）；全仓没有第二个写入者 | "到点"没有任何路径能落到一个**对象**上——只能落到一个**线程**上（睡眠链） |
| 2 | `fe_notification_wait` **没有超时** | `ipc.c:1273` 的签名只有 `(nt_h, mask, out_bits)` | 一个"只等着看有没有"的调用者没有退路，只能再开一条线程去睡 |
| 3 | `fe_wait_any` **没有超时**，而且它的**用户态 ABI 根本不存在** | `ipc.c:884` 的签名没有 deadline；全仓搜不到 `FE_SYS_WAIT_ANY` 之类的号；`docs/12-drivers.md:115` 明确记着"内核机制完成、**用户态 ABI 待定**"（因为 D4 的 virtio-blk 驱动最终没用上它） | `poll`/`select` 的语义今天**无法表达**：不是"慢"，是"没有这个形状" |
| 4 | 睡眠链的键是**线程**，不是**对象** | `sched.c:827/863`；节点是 `thread->sleep_next` / `wake_ns`（`kernel/include/fe/sched/thread.h:56-59`） | 想要"到点置位一个**共享的**对象"，睡眠链帮不上忙：它一次只叫醒一个线程，而定时器要叫醒**所有等这个对象的人** |
| 5 | 一个对象上的等待者**上限是 4** | `ipc.h:41` `#define FE_WAITERS_MAX 4` | 一个被很多线程等待的定时器会撞到这个上限——§8 待查第 1 条 |

★ 一句话概括缺口 ★ **今天"到点"只能叫醒一个线程，不能置位一个对象；
而"等 N 个目标里任意一个 + 到点也算"这条标准语义，两个条件都不满足。**

## 2. 设计：两条候选与取舍

### 2.1 候选 A：新对象 `FE_OBJ_TIMER`

```c
/* 新的对象类型（加进 fe/object.h 的 enum fe_object_type） */
FE_OBJ_TIMER,

/* 形状（三个调用，全部走句柄表 —— 与端点/通知/内存对象同一套） */
timer_create(clock_id, nt_handle, bits, out_timer_handle);
timer_arm(timer_handle, abs_ns, interval_ns);   /* interval_ns = 0 → 一次性 */
timer_cancel(timer_handle);
```

- 定时器的**效果**就是"到点对 `nt_handle` 那个通知对象的 `bits` 置位"，
  也就是复用 `fe_notification_signal_obj`（`ipc.c:1245`）这一个既有入口——
  **不新增第二套"置位"逻辑**。
- 定时器自己**不是**等待对象：它不需要 `waiters[]`，因为它不阻塞任何人。
  想等它的人等的是那个**通知对象**（今天就能等，`ipc.c:1273`/`884`）。

### 2.2 候选 B：给通知对象加"定时置位"（不引入新对象类型）

```c
/* 通知对象上多两个字段 */
struct fe_notification {
    u64 timer_deadline_ns;    /* 0 = 没有定时置位 */
    u64 timer_bits;           /* 到点置哪几位 */
    ...                       /* 其余不变 */
};
```

- 少一个对象类型、少一组生命周期代码；`fe_notification_destroy`
  （`ipc.c` 里已有）顺手把定时器一起撤掉。
- ★ 代价是**信息被压平** ★ `bits` 是 64 位**共享位图**：软件 `signal`
  和定时器到点写的是**同一个字段**，于是"这一位是软件置的还是定时器置的"
  再也答不出来。今天 `bits` 的读者很多（中断投递用伪中断号作下标，
  `kernel/include/fe/syscall.h:332-333` 记着"MSI 没有 ISA 中断号，
  通知对象只有 64 位，所以要有一个下标"），压平之后**排查会退化**。

### 2.3 逐项对比

| 维度 | A：新 `FE_OBJ_TIMER` | B：通知对象加字段 |
|---|---|---|
| 一次性 vs 周期 | 自然：`interval_ns` 一个参数 | 要再想"周期时 `bits` 每次置位还是只置一次" |
| 多个定时器 | 一个定时器一个句柄，各自 `abs_ns`/`interval` | **一个通知对象只能有一个 deadline** ⇒ 想在同一对象上挂两个不同周期的定时器**做不到** |
| 与 `wait_any` 合流 | 复用既有的"等通知对象"路径（`ipc.h:145` 的 `FE_WAIT_BITS`），**一个字都不用改** | 同样复用，但等待者分不清来源 |
| 取消语义 | `timer_cancel` 是一个独立动词，能断言"它再也不会响" | 取消 = 把 `timer_deadline_ns` 清 0，与"通知本身"耦合 |
| 时钟源 | `clock_id` 是参数，将来能拒绝 `CLOCK_REALTIME`（`EINVAL`）而不是假装支持 | 也要一个 `clock_id`，但字段挤在通知对象上 |
| 对象生命周期 | 要新增 `FE_OBJ_TIMER` 的 `destroy` 分支 + 引用计数路径 | 随通知对象走，**这条是 B 的真优势** |
| 任务销毁时的撤销 | 走句柄表（关句柄即撤销），与端点/内存对象完全同构 | 自动（通知销毁即撤销） |
| 精度 | 见 §2.4，两条候选**完全一样** | 同左 |

### 2.4 两条候选都躲不掉的三件事

**（a）时钟源：单调，不是实时。**

时间来源只有单调的 `fe_time_ns()`（`time.c:288`，TSC 制）。
所以第一版 `clock_id` **只接受 `CLOCK_MONOTONIC`**，其余（`CLOCK_REALTIME`
以及 `CLOCK_PROCESS_CPUTIME_ID` 之类）返回 `EINVAL`——按 `docs/20:924` 的口径，
那是**如实说不支持**，不是"我们选了单调"。

**（b）精度：上界是"一个真实的节拍"，而它在两个环境里差一个数量级。**

"到点"由节拍发现（`wake_sleepers`，`sched.c:863`）。实测节拍率
（★ 引 `docs/21-user-address-wait.md:366-369`，不是本文量的 ★）：

| 环境 | 节拍源 | 实测节拍率 | 一个节拍 |
|---|---|---|---|
| QEMU + WHPX | LAPIC 周期模式 | 998 Hz（另一次 999 Hz） | ≈ 1 ms |
| VirtualBox 7.2 | 8254 | 79 Hz | ≈ 12.6 ms |

所以判据只能是"**不早于** `abs_ns` 返回"，**不许**写"误差在 1 ms 内"
（那在 QEMU 上过、在 VBox 上必红，`docs/21:371-372` 已经把这条写死）。

**（c）队列：★ 绝不能让"到点"出现第二套逻辑 ★**

`docs/20:901` 在候选 A 那一行就警告过："新队列要不要与
`wake_sleepers` 合并，是一个必须先回答的问题——否则会出现两套'到点'逻辑，
而'两套'正是丢唤醒的温床。"

本文的回答（**这是 K14 实现上最硬的一条约束**）：
- 定时器链**是**一条独立的链（键是 `abs_ns` + 一个"对谁置位"的描述，
  而睡眠链的键是**线程**，两者不能同构——见 §1.2 缺口 4）；
- 但**推进它的地方只能有一处**：`fe_sched_tick`（`sched.c`）里那一次
  "按 now 扫到期项"的动作，必须**同时**处理睡眠链与定时器链，
  并且共用同一个 `now`。**不许**在别处（例如某个驱动的回调、或
  `wait_any` 的循环里）再写一次"现在几点、有没有到点"。

## 3. 与 K11 的边界

### 3.1 那句话我核实了：**收窄成立**

`docs/21-user-address-wait.md:316-335`（§5.1/§5.2）的判断是
"K11 自己带超时参数（绝对 deadline）"，并给了三条论证；代码里
`fe_sched_sleep_arm`（`sched.c:854`）就是它的落点——**把 deadline 装到一个
已经 BLOCKED 的线程上**，全程不涉及任何对象。

于是两者**不重复**，各解决各的：

| | K11 的 deadline | K14 的定时器对象 |
|---|---|---|
| 键 | **线程**（`thread->wake_ns` + 地址桶，`docs/21` §5.3） | **对象 + 位**（"到点置位谁"） |
| 到点做什么 | 叫醒**那一个**等待者 | 置位一个**共享的**通知对象（所有等它的人一起醒） |
| 服务谁 | `pthread_cond_timedwait` / `sem_timedwait` 那一族单点等待 | `poll`/`select` 的**多目标**合流；`timer_create` 那一族 |
| 需要新对象吗 | 不需要 | 需要（或候选 B 的字段） |

### 3.2 但两条有**同一个代价形状**，K14 必须沿用 K11 立下的规矩

带 deadline 的等待会同时出现在**两条链**上，而"摘除责任"必须只有一处答案
（`docs/21:337-351` 用一整节讲这件事，结论是
★ **"谁改状态谁负责摘链"，不变式收回调度器** ★，`docs/21:351`）。

K14 的同构代价是：一个定时器到点时，**可能**有人正在 `wait_any` 上等它
（那人的状态是 `BLOCKED`，不是 `SLEEPING`），所以：
- 定时器的到期扫描**只许做一件事**：`fe_notification_signal_obj(nt, bits)`；
- ★ **不许**自己去改任何线程的 `state`、也不许自己碰就绪队列 ★
  ——状态与队列归调度器，这是 K11 已经定下的分工，K14 照抄不重新讨论。

### 3.3 与 `docs/21` 的一处**编号**提示（不是冲突，是接力）

`docs/21` §4.1（`:238-249`）为 K11 预留了 `0x94`/`0x95` 并把
`FE_SYS_MAX` 推到 `0x96`。今天头文件里是 `FE_SYS_MAX = 0x94`
（`kernel/include/fe/syscall.h:363`），即 K11 的两个号**尚未落进头文件**。
**K14 的号必须从 `0x96` 起**，并且在写进 `syscall.h` 之前**先查一遍**
`FE_SYS_MAX`（`docs/20` §3.4 ① 那条"号先查再用，不猜也不顺延"的纪律）。
★ 我没有改 `docs/21`，只在这里指出接力关系。★

## 4. 明确不做（每条给理由与"什么时候才回头做"）

| 不做 | 理由 | 什么时候回头 |
|---|---|---|
| `timerfd_*` 那套**接口** | **不是标准**（`docs/20:926`，与 `epoll` 同类判定） | 有真实 Linux 程序依赖它时，作为"兼容层"单独评估——**不以"支持标准"为理由** |
| `alarm` / `setitimer` | 它们要**信号投递**（`docs/20:893`），今天没有 | 信号（`docs/20` §2.4(b)）落地之后 |
| `SIGEV_THREAD`（到点起一条线程） | 它是"信号 + 线程回调"的组合，前两者都不在 | 同上 |
| `CLOCK_REALTIME` 上的定时器 | 没有墙钟来源（`docs/20` §2.13，`:929-940`） | 有 RTC/墙钟来源之后；今天**如实返回 `EINVAL`** |
| CPU 时间时钟（`CLOCK_PROCESS_CPUTIME_ID` / `THREAD_CPUTIME_ID`） | 今天没有"每任务 CPU 时间"的记账（有 `cpu_ticks`，但那是**节拍**，粒度=一个节拍，且是诊断字段不是 ABI） | 有微秒级 CPU 记账需求时 |
| `timer_getoverrun`（超限次数） | 只有周期定时器 + 信号语义才需要它 | 与信号一起 |
| 微秒级/亚节拍**保证** | 见 §2.4(b)：到点由节拍发现，**给不出比一个节拍更细的上界** | 换成 TSC-deadline 或 LAPIC 单次触发（§8 待查第 3 条） |

## 5. 判据（可证伪 + 反向对照）

写法照本项目的规矩：**每条正向断言配一条会失败的反向对照**；
"死了/没响"这类结论必须能区分"真的没有"与"恰好没被观察到"。

宿主：内核自检 `fe_selftest_timer()`（新文件 `kernel/task/timertest.c`，
挂 `main.c`）；真实客户端留给 `poll`/`select` 那一刀（§6）。

| # | 正向断言 | 反向对照（必须失败 / 必须不变） |
|---|---|---|
| 1 | `arm(abs = now + 20 ms)` 之后，**等那个通知对象**的线程在 200 ms 内返回，且拿到的位正好是约定的那几位 | ① **不 arm** 时，同一个等待在同一个窗口里**必须没返回**（证明"返回"来自这次 arm）；② 拿到的位**不等于**别的定时器的位（证明位没串） |
| 2 | 返回时刻用 `fe_time_ns()` 量出来 **≥ `abs_ns`**（不早于） | ★ **不许**断言"误差 ≤ 1 ms"★：节拍是 998 Hz（QEMU）与 79 Hz（VBox）两种，`docs/21:366-369` 有实测。写成反向对照即："同一份自检在 QEMU 与 VBox 上都只能断言不早于" |
| 3 | ★ **取消后绝不能再响** ★ `cancel` 之后等 `3 × interval`：通知位**仍然是 0**，等待者**没有**被唤醒 | **同一程序里第二个未取消的定时器必须照样响**（证明"没响"是取消造成的，不是对象坏了/节拍停了） |
| 4 | 周期：`interval > 0` 时连续两次到点各置位一次（用 `signal_total` 或取位次数观测） | `interval == 0` 的**一次性**定时器在同样长的窗口里**只响一次**（证明周期是参数说了算，不是"到点就自动重挂"） |
| 5 | 重复 `arm` 覆盖旧 deadline：先 `arm(T1)` 再 `arm(T2)`，**T1 那次不许响**，只有 T2 响 | 反向：完全不重新 arm 时，T1 **必须**照常响（证明"T1 没响"是覆盖造成的） |
| 6 | 删除/关闭定时器句柄之后再 `arm` → `BADHANDLE`（不是崩、不是静默成功） | 反向：同一个句柄**关之前** `arm` 必须成功（证明拒绝的是"句柄没了"，不是"这个调用不支持"） |
| 7 | 定时器随**任务销毁**一起撤销：探针任务退出后，原来那个通知对象**再也不会**被它的定时器置位 | 反向：另一个任务的定时器在同一窗口里必须照常响（证明撤销只作用于目标任务） |
| 8 | 与 `wait_any` 合流（K14 的另一半）：同一次 `wait_any` 里等"端点消息"与"定时器通知"，**只有定时器**到点时它返回且 `index` 指向定时器那一项 | 反向：端点先来消息时，`index` 指向端点那一项（证明"哪个目标先就绪"这件事没被写死成定时器） |
| 9 | 时钟源：`clock_id = CLOCK_MONOTONIC` 成功；`CLOCK_REALTIME` → `EINVAL` | 反向：同一时刻 `CLOCK_MONOTONIC` 必须成功（证明拒绝的是"那个时钟源"，不是"这个调用"） |

★ 第 3 与第 5 条是这一组里最值钱的两条 ★ 它们验的不是"能响"，
而是"**说了不响就真的不响**"——那是定时器最容易错、也最难在事后发现的一面
（一个还会响的定时器，会在几百万条指令之后置位一个别人正在用的位）。

## 6. 分刀（照 5a/5b 的纪律：一刀一个可证伪的结论）

| 刀 | 内容 | 为什么这么切 |
|---|---|---|
| **K14-1** | **定时器对象本体**：`FE_OBJ_TIMER` + `timer_create/arm/cancel` + 与睡眠链**同一处**推进的到期扫描 + §5 的 1–7 条自检 | 它自己有完整、可证伪的判据（"到点置位一个对象 / 取消后不再响"），**且不引入任何新 ABI 号**——只在句柄表上加一种对象 |
| **K14-2** | **`wait_any` 的用户态 ABI + 超时**：把 `wait_any` 的号与参数（含 deadline）**一次定死**，并让 §5 的第 8、9 条就位 | `docs/20:734-735` 那条"**'超时'是两个机制的交点，分两次做必然返工**"说的正是这里：ABI 只能定一次 |

★ 顺序是硬的 ★ K14-1 先落地，K14-2 才有一个**已经被验证过的**"到点会置位
一个可等的对象"可以依赖；反过来（先定 ABI 再补机制）会把 ABI 押在
尚未验证的语义上。

## 7. 代价清单（一句话版，以及"什么时候会咬人"）

- 一种新对象类型：`enum` 一个值 + 一条 `destroy` 分支 + 句柄表路径（与端点/通知/内存对象同构，没有新概念）；
- 节拍路径上多扫一条链（定时器数量级是"每进程几个"，线性扫描与睡眠链同级）；
- **精度上界 = 一个真实节拍**：QEMU ≈1 ms、VBox ≈12.6 ms（`docs/21:366-369`）。★ 咬人处：任何"每 1 ms 触发一次"的用法在 VBox 上根本表达不出来，而且**它不是错误，是环境**——所以判据只能写"不早于"；
- **只有单调时钟**：`CLOCK_REALTIME` 的定时器返回 `EINVAL`（`docs/20:924` 已判为缺口，不是设计选择）；
- 一个对象上的等待者上限仍是 `FE_WAITERS_MAX = 4`（`ipc.h:41`）：定时器本身不占这个额度（它不是等待对象），但**它置位的那个通知对象**会——见 §8 第 1 条；
- **SMP 债**：到期扫描与"置位"今天靠"只有一个核、且在节拍里做"这套推理成立；多核之后它与 `docs/21` §6 是同一批要重审的假设（`docs/20` §3.3 要求每一项都在 SMP 之后重审）。

## 8. 待查清单

1. **`FE_WAITERS_MAX = 4`（`ipc.h:41`）够不够**：一个被"一个定时器 + 若干
   客户端"共同等待的通知对象，`wait_any` 的登记者是定长 4 项。K11 已经因为
   同一条理由把 `waiters[4]` 判成"对 futex 语义不成立"
   （`docs/21:541-543`），定时器这边要不要同样处理——**先量真实形态再决定**，
   不凭猜。
2. **到期扫描放在节拍里够不够**：`wake_sleepers` 今天就是这么跑的
   （`sched.c:863`，被 `fe_sched_tick` 调用）。要问的是"如果一个进程装了
   20 个定时器，线性扫描的代价是否可接受"——**没有实测数据，写"未实测"**。
3. **能不能换成 TSC-deadline / LAPIC 单次触发**（把精度从"一个节拍"
   提到"更细"）：`tools/run_qemu.py:124-132` 记着一条既成事实——
   启用 `-cpu host` 之后内核会切到 TSC-deadline 路径，然后**一个节拍都不投递**
   （0 Hz，实测），于是那一轮把该特性显式掩掉了，并记为**未解决的独立问题**。
   ★ 所以"提高定时精度"这件事的前置是先把那条查清楚，不是直接换源。★
4. **`timer_create` 的 `sigevent` 形状**：标准允许"到点通知"的几种形式，
   我们今天只能表达"置位一个通知对象"。客户端要用的那一种要先确认
   （`SIGEV_NONE` 那种"只查询"的形态不需要任何投递，成本最低）。
5. **与 `docs/12` 的 `wait_any` ABI 谁先动**：`docs/12:115` 记着
   "等真实调用者"。K14-2 会把那个 ABI 定死，所以要先确认**驱动侧**
   （`blkd`/`fsd`/`consoled`）到底有没有合流需求，别再一次"ABI 先定死、
   调用者不来"。
