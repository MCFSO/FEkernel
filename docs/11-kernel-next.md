## 1. 判据：内核"够用"的标准是什么

不是"功能多"，而是这三条：

| # | 判据 | 为什么是它 |
|---|---|---|
| **C1** | 用户态能表达的**执行模型**完整：创建/替换映像、终止、等待、多路等待、异常处理者 | 缺任一条，用户态就得靠"约定"绕（今天我们就在绕：没有 kill，服务只能靠协议自杀） |
| **C2** | **内存模型**完整：按需分页、栈增长、区间属性变更、映射撤销 | 缺任一条，用户态只能"预留+全映射"，把物理内存当虚拟内存用 |
| **C3** | **时间与可见性**：真实时钟、任务/线程枚举、诊断 | 缺任一条，用户态没法做超时、`ps`、性能归因 |

这三条都可测，且**不涉及任何一节用户态语义**。

## 6. K1 完成：按需分页与栈自动增长

### 机制

```
kernel/mm/vma.c           区间表：用户地址空间的"意图"（哪儿允许有映射、什么权限、能否增长）
kernel/include/fe/mm/vma.h
kernel/task/user.c        fe_user_resolve_fault：#PF 的解析路径
                          fe_user_map_stack：栈区间 + 只预映射顶部 4 页
kernel/arch/x86_64/idt.c  user_fault 里加"缺页的第一条出路"
kernel/ld/elf.c           映像段登记为区间（**故意不标 ANON**：它们没有后备存储，
                          缺页必须仍然是错误，不能被"补一页零"掩盖）
kernel/include/fe/task.h  任务持有区间表 + stack_low（已映射到的最低页）
```

**VMA 与页表的分工**（这条不能混）：
VMA 是**意图**（这段地址属于什么、允许什么），页表是**事实**（这一页现在有没有帧）。
"区间里只有一部分页有映射"是按需分页的**正常状态**；
反过来"页表里有映射而 VMA 里没有"才是非法状态。

**栈的模型**：区间 `base` = **已映射到哪儿**（缺页时向下移动），`end` = 栈顶。
保留下界由 `stack_low` 的下移与"撞上邻居必须被拒"共同约束。
（第一版把区间建成整个保留范围，于是"要增长的那一页本来就在区间里"——
增长分支永远轮不到、两个条件互相矛盾。见 §7 第 2 条。）

### 实测（双环境）

内核自检 `fe_selftest_demand_paging` + `fe_selftest_vma`：

```
正向：紧邻栈下方一页被补上（零填充、可写、NX、stack_low 前移）: OK
正向：连续三页按需增长（r2=1 r3=1 stack_low=0x7ffeffff9000）: OK
反向：跳过保留区一大段**不**补页: OK
反向：区间外**不**补页: OK
反向：栈上方越界**不**补页（栈只向下长）: OK
反向：只读区间写被拒、读被补（同一区间的正反对照）: OK
反向：不可执行区间取指被拒（NX 不是摆设）: OK
反向：无后备也无 ANON 的区间不补页（不掩盖不一致）: OK
反向：栈增长撞上相邻区间被拒: OK
区间表：插入/查找、重叠被拒（4 种形式）、相邻共存、裁剪（切尾/整段/挖洞/全包含）、
        栈式增长（4 项）、表满 NOSPC —— 全部 OK
=> 按需分页失败项: 0    => 区间表失败项: 0
```

**端到端证据**（`user/bin/posixprobe`，一个普通 C 程序递归到栈的深处）：

```
[posixprobe]   递归 700 层（每层约 96 字节栈）……
[posixprobe]   递归完成，内核解析缺页 5 次（栈是**长**出来的，不是预映射的）
[init] posixprobe 退出码 = 0  期望 0  —— 相符
```

★ 为什么必须有这一条，而不是只看"没崩" ★
"栈能长"有两种实现：(a) 真的按需补页；(b) 干脆一开始把整个保留区映射好。
**从用户态看，这两者行为完全一样**——程序都不崩。
只有 `fe_pf_resolved_count()`（新增 syscall `FE_SYS_PF_STAT`）能把它们分开：
`>0` 才说明走的是 (a)。这正是本项目一贯的原则：
**一个断言必须能被证伪，"没崩"什么都证明不了。**

## 7. K1 期间撞出来的三个 bug（每一个都是"看起来在工作"）

| # | 症状 | 根因 | 性质 |
|---|---|---|---|
| 1 | **一次成功的缺页解析被当成致命异常，系统 panic** | `fe_isr_dispatch` 里调用 `user_fault(r)` 之后**缺 `return`**。`user_fault` 现在有两种正常结局：消化掉缺页后**正常返回**、或无法消化时 `fe_thread_exit`。第一版它是 `FE_NORETURN`，所以当时不需要这个 return；加了按需分页之后，"成功"这条路径直接落到下面的 `exception_fatal` | **真 bug，且症状极具误导性**：panic 打印的是**用户态**现场（CS=0023、RIP 在用户代码、CR2 是刚补上的那一页），看起来像"用户程序把内核弄崩了" |
| 2 | 栈"能按需补页"却**永远长不动**（`stack_low` 不更新、增长分支从不执行） | 两个条件互相矛盾：① 栈区间建成**整个保留范围**，于是要增长的地址**本来就在区间里**，`fe_vma_find` 命中它 → 走"区间内补页"分支；② 就算走到增长分支，`fe_vma_grow_down` 也会因"new_base 落在区间内部"判非法 | **设计缺陷**。修法：区间只覆盖**已映射**段，缺页时向下扩 |
| 3 | 删中间一段后，前半段**整段消失** | `fe_vma_remove_range` 的两个锚点写成 `base > v->base`（切头）与 `end < v->end`（切尾）——后者在"移除范围完全落在区间内部"时也成立，于是走进挖洞分支；而在"移除范围从区间内部开始、到区间末尾结束"时，`end == v->end` 让切尾为假、切头为真，于是**把头整个砍掉**。正确判据是"区间在移除范围左侧/右侧有没有剩" | **真 bug**（锚点选错） |

**另外两个附带发现也修了**：

- **`exception_fatal` 会因读用户栈而二次异常**：它直接解引用 `r->rsp`，
  而用户栈越界时 `r->rsp` 就是那个**未映射的用户指针** → 内核态 `#PF` →
  再进 `exception_fatal` → 递归到栈耗尽。也就是说**任何用户程序的栈溢出
  都能把内核带崩**。修法：只在内核栈范围内才 dump，否则明确打印"不可读"。
  （诊断代码也必须遵守"异常处理是终点、不能自己再出异常"这条纪律。）
- **区间表指针会被插入失效**：`fe_vma_add` 会 memmove 数组元素，
  于是先前拿到的 `struct fe_vma *` 指向别的区间。实测踩到：测试里拿旧指针
  继续用，"撞邻居"该报 NOSPC 却报成 NOTSUP（读到的是邻居的 flags）。
  修法：加 `fe_vma_find_index`/`fe_vma_at`，**跨插入/删除一律用下标**。


## 8. K4 完成：多对象等待（`fe_wait_any`）

### 机制

```
kernel/include/fe/sched/thread.h  线程身上挂"等待节点"指针 + waiting/wait_satisfied
kernel/include/fe/ipc.h           等待目标/结果结构；FE_WAIT_MSG / FE_WAIT_BITS
kernel/ipc/ipc.c                  fe_wait_any；waiters_add / wait_unregister；
                                  fe_ipc_wake_object_waiters（send / signal / call 三处调用）
kernel/ipc/ipctest.c              fe_selftest_wait_any（4 组，其中 3 条反向）
```

**设计要点（三条都不能省）**：

| 要点 | 为什么 |
|---|---|
| 节点挂在线程身上，对象里只存线程指针 | 一个线程等 N 个对象，若用"每对象一条等待队列"，插入是 N 次分配、唤醒要从 N 个队列摘；指针方案里对象只需 `fe_sched_wake`，摘除由被唤醒者自己做 |
| 登记与"再检查一次"在**同一个关中断区间**里 | 否则丢唤醒：检查完发现没就绪、刚要登记，对方在这一刻置位并发现"没人等"，于是睡下去没人叫 |
| 唤醒**全部**登记者，被唤醒者**重新检查全部目标** | 唤醒方只知道"这个对象动了"，不知道是第几项满足；让唤醒方去读别人栈上的节点等于"持有别人栈指针"。重查让伪唤醒自动变成正确行为 |

**契约（写清楚，免得再对错断言）**：`FE_WAIT_BITS` 的 `mask == 0` 表示 `~0`
（等所有位）；`fe_notification_wait` 的 `mask == 0` 同样是 `~0` ——
**"等 0 个位"不是"立刻返回"，而是"等任意一位"，位不来的话它会一直阻塞**。

### 实测（双环境，同一份内核与镜像）

QEMU + WHPX **与** VirtualBox 7.2 的输出**逐字一致**（下面这一份两处都成立）：

```
[自检] 多对象等待（wait_any：等 N 个对象中任意一个就绪）:
        已就绪的目标立刻返回（下标 1，消息顺带收到）: OK
        被通知唤醒（下标 1，取到位 0x4，取出即清除）: OK
        反向：位已被取走（对象 bits 归零），同一个掩码不再就绪
        被消息唤醒（下标 0，消息顺带收到）: OK
        反向：类型不匹配 / 坏句柄 / n 越界 全部被拒: OK
        => 多对象等待失败项: 0
```

两个环境整机自检都以 `M5 里程碑自检全部通过` 结束（`g_selftest_failures == 0`），
日志里没有 `失败项` 非 0、没有 `不符`。
VBox 日志里的环境指纹（`80ee:beef` VBox 显卡、`VBOX HARDDISK`、节拍 49 Hz）
与 QEMU 的（`1234:1111`、`QEMU HARDDISK`、999 Hz）不同，
**说明这两份证据确实来自两个不同的虚拟机**，而不是同一份日志被读了两次。

三条反向对照各自堵一条错误实现：

| 反向 | 它抓住的错法 |
|---|---|
| 第 1 组：就绪项在**中间**（下标 1） | 返回值写死 0 / 总报第一项 / 总报最后一项 |
| 第 2 组：等 [端点0, 通知1]，只动通知 → 必须报 1 | 同上，而且与第 3 组的期望**互相矛盾**，两条一起才有约束力 |
| 第 3 组：同样两个目标，只动端点 → 必须报 0 | 同上；顺带证明消息被**收下**而不是只报"可读" |
| 第 2 组附加：取走位之后对象 `bits` 必须归零 | "只报结果不消费" → 调用方会拿到一次永远重复的就绪 |
| 第 4 组：类型不匹配 / 坏句柄 / n ∈ {0,9} | 把非法参数当"没就绪"，让调用方**永远等一个永远不会来的事件** |

### ★ 本轮**没有**改任何内核机制代码 —— 记下来因为这本身是教训 ★

`fe_wait_any` 的机制代码自上一轮就已完整，问题是**自检夹具写错**：
第 2 组的反向对照调了 `fe_notification_wait(g_wa_nt, 0, &left)`
去验证"位已经被取走"，而按契约 `mask == 0` 是 `~0`——
位确实已经被取走、再没有人会置位，于是这次调用**永久阻塞**。

症状是：日志停在第二组的 OK 之后，**第三组一行都没有**。
于是上一轮把它归因成"第三组的消息唤醒没实现 / helper 时序有问题"，
还顺带去怀疑 `fe_thread_sleep_ms(2)` 的相对时序——**整个方向都是错的**。

★ 定位手法（值得复用到别处）：**在调用点与 callee 各打一个探针。** ★
探针一是"主线程即将进入 wait_any"（在 `test_wait_any_by_msg` 里）、
探针二是"阻塞结束、被唤醒"（在 `fe_wait_any` 里）。
日志里**两个都在、但都不在第三组**——三次 `wait_any 循环顶部` 全部来自前两组，
第三组的调用点探针一次都没打。**只打一边必然误判**：
只打 callee 会把"卡在别人体内"看成"卡在这次调用"，只打调用点则分不清
"没进去"和"进去了没出来"。

第二个教训与坑清单第 7 条同源，但这次是**反向对照自己犯的**：
**自检里绝不能用"本该阻塞"的接口去验证它没立刻返回。**
"没返回"与"永远不返回"在日志上长得一模一样。
正确做法是把问题变成**状态查询**：读通知对象的 `bits` 是否为 0，
既准确又没有任何时序问题。原来那句还带一个 `&left` 是**没被用过的输出**——
它连"打印出来对照"都做不到，因为它永远不返回。

### 边界（写清楚，不是遗漏）

| 边界 | 现状 | 何时该做 |
|---|---|---|
| **用户态 ABI** | 只有内核 API 与自检；`user/` 下没有 `FE_SYS_WAIT_ANY` | **D4 之前**：virtio-blk 驱动要"等中断 + 等请求"合流，那才是它的第一个真实调用者。先有调用者再定 ABI，比先定 ABI 再找调用者少一轮返工 |
| **等待者表上限 4** | 第 5 个登记者**不报错也不登记**：它仍能被同一个节点上的其它对象唤醒，醒来后重查全部目标 | 有真实需求（>4 个线程等同一对象）时；在那之前"把 N 个来源合成一个通知位图"是更好的形态 |
| **超时** | `wait_any` 没有超时参数 | 与 K7（真实时钟）一起做：节拍制的超时在 VBox 上量不出亚节拍间隔（实测 0 us） |

## 9. D4 期间改到的内核部分（只有一处，且是被实测逼出来的）

D4 的主体在 `user/`（`libdrv/virtio.c`、`servers/blkd`）与 `init`，
内核这一侧只动了一处：**任务创建的顺序**。

**竞态**：`fe_resource_note_init(t->id)` 原来写在 `fe_process_create`
返回之后，而新线程在 `fe_process_create` **返回之前**就已经在就绪队列上
（`fe_thread_create_ring3` 里的 `rq_push`）。于是"内核还没记下 init 是谁、
init 已经跑起来并去认领设备管理器身份"这个窗口是真实存在的。
**QEMU 上从不出现，VirtualBox 上每次出现**，症状是认领被拒 → 读未认领的
PCI 配置空间端口 → #GP → 整个用户态没起来，而内核自检全部通过。

**修法**：`fe_process_create` 多一个 `bool boot_init` 参数，
内核在**创建线程之前**记下它；失败路径上撤回。
设计与实测详见 `12-drivers.md` §9.3。

**代价**：一个参数、一处调用点语义变化；`fe_process_spawn` 与三处自检传 `false`。
**为什么值得单独记**：这是"内核里凡是'任务将要运行'与'内核为该任务准备好的状态'
之间存在间隙的地方都要按竞态对待"的第一个实例——即使在一个虚拟化平台上
看它永远是对的。

## 10. K2 + K3 完成：终止与枚举（本轮）

完整的设计、代价、边界与实测见 `docs/13-tasks-and-kill.md`。这里只记
**这一轮真正改到内核的部分**，以及它照出来的东西。

| 项 | 内容 | 为什么必须在内核 |
|---|---|---|
| K3 快照 | `FE_SYS_TASK_LIST` = 0x84；`fe_task_snapshot_build`（`kernel/task/tasklist.c`）拼表，`sys_task_list` 只做"校验用户指针 + 一次拷贝" | 全系统状态只有内核知道；而它是**只读快照**，所以不产生任何新权限 |
| K2 终止 | `FE_SYS_TASK_TERMINATE` = 0x8C；`FE_RIGHT_TERMINATE`（bit 9）；`task->dying` | "谁能杀"必须是不可伪造的能力；判据只能是句柄 + 权限位 |
| 闸门 | `fe_sched_maybe_switch` 里检查 `dying` —— 这是 **isr 与 syscall 两条返回路径的唯一交汇点** | 放在每个 syscall 里各写一遍，漏一处就是一个"已经杀了却还能跑"的洞 |
| 取消点 | `fe_endpoint_recv` / `fe_notification_wait` / `fe_wait_any` 三个重试循环顶部返回 `FE_ERR_CANCELED`；`fe_thread_cancel` 负责摘登记 + 唤醒 | 阻塞中的线程走不到闸门；而**不能就地拔掉它**（它在对象的等待表上留着指针） |

### 这一轮照出来的两个内核缺陷（都是"第一次被执行"）

1. **僵尸线程从不回收** → 每个跑完的程序都泄漏任务对象，连同端口 / MMIO /
   IRQ / devfs 名字 / 地址空间一起。`fe_sched_reap()` 写了却没有调用者。
   这个泄漏一直在，**第一次被看见是因为 K3 让"枚举任务"成立了**。
   修法：空闲线程收尸 + 线程加一个 `reap_ok` 位区分"谁负责收"。
2. **销毁地址空间会把借来的内存还给 PMM**：内存对象映射的帧归对象所有、
   MMIO 根本不是 RAM，而销毁时一律归还。实测症状是"销毁一个刚跑完的程序，
   另一个正在跑的进程在自己的代码上取指 #PF"。修法：新增软件位
   `FE_PTE_NOFREE`，把"拥有"记进页表；并让损坏不扩散（遇到
   "present 但地址为 0"的中间层项只报告、不释放）。

★ 共同形状 ★ 它们都在**从来没被执行过的代码**里。K2 的价值不只是"能杀进程"，
更是让"进程会死"这条路径第一次真的走通——**写好了却从没跑过的代码，
与没写的区别只是"看起来像有"**。这与 §2 里 K3 的步长错误是同一族。

## 11. K7 完成：真实时钟（TSC 制）

### 机制

节拍与时钟**分成两件事**：节拍是调度单位（时间片、睡眠，1 ms），
而"现在多久了"建在 TSC 上。

| 接口 | 作用 |
|---|---|
| `fe_time_ns()` | 自启动以来的纳秒（TSC 制；没有 TSC 频率时退回节拍） |
| `fe_time_clock_is_tsc()` / `fe_time_clock_hz()` | 时基自述 |
| `FE_SYS_CLOCK_MONOTONIC`（0x2E） | 用户态的 `fe_clock_ns()`，**现在返回 TSC 制的纳秒** |
| `FE_SYS_CLOCK_INFO`（0x8D） | 时钟自述：频率、**分辨率**、来源 |

★ 为什么要专门一个"问精度"的 syscall ★ D4 那次的教训：`fe_clock_ns()`
实际返回的是"毫秒 × 1e6"，被测代码只有几毫秒，于是两次**独立**的吞吐
测量都得到**正好 5000 us**——测出来的是时钟的粒度，**而断言看起来是
通过的**。与其在文档里承诺"时钟够细"，不如让调用者当场问出来，
据此决定用不用它。**一个不知道自己精度的时钟比一个慢时钟更危险。**

### 代价与边界

1. **每次读时钟是 `rdtsc` + 两次除法**（约 40~60 周期）。没有做
   "倒数乘法"优化：今天没有需要亚微秒精度的热路径，而倒数乘法会引入
   一套需要单独验证的取整误差。有消费者时再做。
2. **不能用 128 位除法**：`(u128)delta * 1e9 / hz` 会引出 `__udivti3`，
   而内核是 freestanding 链接的，那个符号不存在（实测链接失败）。
   拆成两段 64 位（`(delta/hz)*1e9 + ((delta%hz)*1e9)/hz`）精度不损，
   且要求 TSC 频率 < 18.4 GHz。
3. **绝对时间可能有百分之几的偏差**：频率取自引导器声明（实测声明
   2996 MHz，而用 8254 这个独立时基交叉校验得到 3169 MHz，差 5.8%）。
   **间隔测量是自洽的**（两条路用同一个频率），但"开机多久了"这种
   绝对值会带着这个偏差。要修得用一个独立时基去校准频率——那件事没做。
4. **回退路径如实报出**：引导器没给 TSC 频率时退回节拍制（1 ms），
   并且 `fe_clock_info` 会把 `FE_CLOCK_FLAG_TSC` 清掉。

### 实测（QEMU + WHPX，内核自检与客户端都失败项 0）

```
[时间] 时钟：TSC 制，2996 MHz（分辨率约 0.3 ns；节拍只作调度单位）
[自检] 真实时钟（K7）：短忙等（2000 × pause）读到 71934 ns，小于一个节拍 1000000 ns
[自检]               长窗口对照: 时钟量到 49 ms，节拍量到 50 ms
[自检]               自述分辨率 1 ns，两次连读差 19 ns → 相符
[clocktest] 短循环（20000 次累加）读到 5816 ns   ← 节拍制时钟在这里只能给 0
[clocktest] 两次连读相差 66 ns
[clocktest] 同一段 10 ms：内核时钟量到 9084 us，客户端自己读 TSC 量到 9084 us
```

最后一条是**交叉验证**：客户端自己读 TSC、按内核自述的频率换算，
与内核的 `fe_clock_ns()` 比——两条独立路径给出同一个数。

★ 这条交叉验证证明了什么、没证明什么 ★ 它证明**内核时钟确实建在 TSC 上**
（如果其实建在节拍上，两条路会差三个数量级）；它**不证明频率准确**，
因为两边用的是同一个 `hz`。后者由边界 3 负责说清楚。

### 顺带修掉的一个正确性问题：睡眠按"节拍个数"计时

做 K7 的自检时，双环境跑出了**互相矛盾的两个数**（同一个启动、同一个 8254 源）：

| 测量 | 结果 |
|---|---|
| 被动地在一个 50 ms 窗口里数节拍 | **5 个**（≈99 Hz） |
| `sleep(50 ms)`（= 50 个节拍）实际用了多久 | **14 ms**（≈3571 Hz） |

同一个节拍源不可能既 99 Hz 又 3571 Hz——**中断是突发投递的**。
于是"睡 N 个节拍"这个写法的问题暴露出来：**它根本不是时间的度量**，
100 个节拍在 VBox 上可以是 30 ms 也可以是 450 ms。

而方向是致命的：睡眠**提前** 3~4 倍返回，意味着**超时提前触发**。
既有测试其实一直看得见这个症状，只是把它当成了"虚拟化限流"的**报告**：
`hxtest` 的"时钟刻度自证：睡 50 ms，时钟量到 13934 us → **刻度 27%**"、
`bench` 的"sleep(10ms) 实测约 3 ms"。**限流只会让睡眠偏长，偏短是错误。**

改法：睡眠的到期时刻改成**绝对纳秒**（`fe_thread_sleep_ms` 直接算
`fe_time_ns() + ms*1e6`，不再经过节拍），节拍只负责"过一会儿来看一眼"
（`wake_sleepers(fe_time_ns())`）。

| | 改之前 | 改之后 |
|---|---|---|
| VBox `sleep(20 ms)` 实测 | 5 ms | **22 ms** |
| VBox `hxtest` 刻度自证 | **27%** | **114%** |
| VBox `bench` sleep(10ms) | 3 ms | 10~17 ms |
| QEMU `sleep(100 节拍)` | 100 节拍 / 100 ms | 100 节拍 / 100 ms（不变） |
| QEMU `hxtest` 刻度自证 | 100% | **118%** |

**代价写在明处**：醒来时机受限于节拍（加上被重新调度到的延迟），
所以实测**偏晚**（QEMU 上 50 ms 睡成 59 ms）。语义变成
**"至少 N 毫秒"**——**只会晚、不会早**，而这正是超时需要的方向。
想同时做到"不早也不晚"需要一个更细的唤醒源（比如用 TSC-deadline
按每个睡眠者重新武装定时器），今天没有消费者需要那个精度。

★ 这一条与 K7 的关系 ★ 时钟本身**没有**修好睡眠——是"有一个可信的
时间基准"这件事让**错误的判据暴露出来**：原来那个"睡够 N 个节拍"的
判据只有在节拍均匀到达时才等价于时间。**K7 的价值不只是多了一个
精确时钟，更是让"用节拍当时间"这类错误再也藏不住。**

## 12. 2a 排障记录：四处队列卫生缺陷 + 一条"让出饥饿"（**都已修**）

K6 的 2a 落地之后，"闸门能杀线程"这条路的第一次真实执行照出了五件事。
前四件是**调度器队列维护**上的既有缺陷（与 `exec` 无关，是这次被杀线程
把它们踩出来的）；第五件是"让出被当成时间片轮转"。**五件都已修**：
前四件在 2a 那一刀里，第五件独立成一刀（commit `f12e39b`，2026-10-01）。

| # | 症状（实测） | 根因 | 修法 |
|---|---|---|---|
| 1 | `异常: 页错误 (#PF)`，`RIP = fe_sched_maybe_switch+0x231`（`movl 0x1060(%rax), %edi`，即读 `next->task->iopb_slot`）、`CR2 = 0xffffffffa00a4060`；`next` 指向**已销毁的任务** | 闸门判死一个**已经在就绪队列里**的线程（`sched.c:1036-1037` 的说明：它可能在时间片用尽时被抢占、进了队列），却只置 `state = DEAD`、**没摘队列**；随后空闲线程把僵尸 `free` 掉，队列上留下一根指向已释放内存的指针，下一次 `rq_pick` 选中它 | `thread_mark_dead` 里 `rq_remove(t)`（`kernel/sched/sched.c:1063`，不变式与实测症状写在 `:1032-1062`）。★ 摘在这里而不是 `rq_pick` 里判状态：`rq_pick` 信任"队列里都是可运行的线程"这条不变式，把判断塞进消费者一侧等于把不变式扩散到每个调用者 |
| 2 | 同一形状的第二次：线程活得比任务久（内核线程僵尸 `reap_ok=false`，永不回收、它对任务的引用永不释放），任务照样被销毁 ⇒ 线程的 `task` 字段悬空 | 任务销毁时**没有**把还指着它的线程摘干净 | 新增 `fe_task_detach_threads()`（`sched.c:1308-1329`），在任务销毁时把所有 `t->task == 该任务` 的线程置成 `NULL`，并在 `fe_kfree(t)` **之前**调用（`kernel/task/task.c:52-58`）。这是"第二道闸"：即使某个僵尸被别的路径又排进队列，也只会被当成内核线程处理（`next->task ? ...->iopb_slot : -1`） |
| 3 | 被释放的线程仍留在队列上 | 与第 1 条同一条不变式的**另一个落点**："死了不在队列里"之外还要"**被释放了也不在队列里**"（中间隔着"回收"这一步，僵尸是可能被重新排进队列的） | `thread_free` 里也 `rq_remove(t)`（`sched.c:1152`，说明在 `:1145-1151`） |
| 4 | `fe_sched_wake` 唤醒一个已经死掉的线程，**静默什么都不做** ⇒ 症状延后到别处才显形 | 静默 return 正是这类 bug 活下来的原因 | `fe_sched_wake` 改成**点名但不静默**（`sched.c:863-918`）：先按 `g_all` 注册表判"在不在册"——**不在册就一个字节都不碰**（传进来的指针可能指向已 unmap 的页，读 `t->state` 就是一次 #PF，实测 `CR2 = 任务地址 + 0x1060`），只打指针值与调用者；在册但状态不是 `BLOCKED` 的按状态点名。★ 其中 `SLEEPING` 那一支**只点名、不动手**：叫醒睡眠是 §6.3（2）/D3 的修复范围，这一步顺手做掉会让"D 组如实变红"这条判据失去意义 |
| 5 | **一条 prio=16 的内核线程在 `yield` 循环里每 100 个节拍只拿到约 10 个**（10:90；"让出 2000 次用了 20002 个节拍 = 10.00 节拍/次"） | **已查清**：`rq_pick()` 无条件把当前线程从就绪队列摘下来——当前线程是它那一级**唯一**的线程时，让出仍然走完整条切换路径 ⇒ 切到 idle ⇒ **等 idle 跑满一整个时间片（10 个节拍，正是默认时间片）**才轮回来。所以"让出"被解释成了"把自己降级给空闲线程"。★ 顺带否证了最初的怀疑："就绪位图与队列不同步"**不成立**（逐级对照 `位与队一致=1`，反向探针一次都没触发）★ | **已修（commit `f12e39b`）**：① 让出时先看候选，"除自己以外只有 idle 可跑"时把候选放回队尾、让出退化成**空操作**（三条判据缺一不可，`sched.c:585-614`）；② `next == prev` 早退**必须补一次时间片**（`sched.c:651-656`，漏了它这个线程再也没有被抢占的机会）；③ `fe_thread_join` 顺手收尸 + 轮数上限 200 万 → 2000 万（让出快了 60 倍，旧上限会提前放弃并 `thread_free` 一个没死透的线程 = use-after-free，`sched.c:1232-1233`）。判据：`fe_selftest_yield()`（`schedtest.c:436`，挂 `main.c:617`）——让出 2000 次 ≤ 8000 节拍；修前 **20002（红）** → 修后 **0（绿）**。★ 公平性只用计数器、不带打印 ★ 见下面那段与 `08-kernel-completion.md` 的"测量的中立性"一节 |

★ 这一节值钱的地方不是这四处修复，而是**它们只在"线程会被杀"之后才出现** ★
前四处都属于同一族：**队列里躺着一个不该在的节点**（或者反过来：一个该被摘的
指针没摘）。K2 那一轮已经因为"僵尸线程从不回收"交过一次学费
（`13-tasks-and-kill.md` §5.1），这一次是同一族缺陷在**另一条路径**上的重演——
区别只在于这次的触发者是 `exec` 的"杀别的线程"。

★★ 一条被撤回的判据：**"`mprotect` 不许绕过写保护"——它的前提是错的** ★★

这条判据**由提出者在 `mprotect` 的验收要求里写下**，实现时核实发现**前提不成立**：

- `kernel/protect.c` 的保护清单收的是**磁盘 LBA**（`fe_protect_add(lba, count, …)`，
  `protect.c:17/88/152`），管的是"哪几个扇区不许被某个任务写"；
- 而 `mprotect` 改的是**虚拟地址**的权限（`fe_vma_protect_range`）。
- 这两者是**两个地址空间**：今天**不存在**"内存地址 ∈ 保护清单"这种对应关系，
  所以那条判据**没有可判的交集**——它不是"没通过"，而是**根本无处落地**。
- 处理：**撤回该判据**。真正该挡的边界写成了两条，落在 `kernel/mm/vma.c:242-284`
  （并在 `:256-264` 明确记下"第三条边界不存在"这件事，免得下一个人再查一遍）：
  ① 范围必须**完全落在同一个 VMA 内**（跨区间/部分覆盖一律拒绝，不做隐式扩展）；
  ② **W^X**（一次调用同时给 W 与 X 直接拒绝）。
  再加上 VMA 的归属，真正被保证的性质是：
  **用户态只能改"自己地址空间里、自己 VMA 内"的页。**
- ★ 若将来真的要有"某段**内存**受保护"，那需要**另立机制**（保护对象是物理帧或
  虚拟区间，而不是 LBA），今天没有，也不该由 `mprotect` 顺手发明一条——
  那会变成第二个会漂的判据。★
- ★ 为什么值得单记 ★ 错的前提**不会被任何断言抓到**：实现与判据"看起来都对"
  （都通过了、都合理），只有去核实"它指的两个东西是不是在同一个空间里"才会露出来。
  这与 `08-kernel-completion.md` 里那条"判据可能建立在错前提上"是同一件事。
