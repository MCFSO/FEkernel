# FEKernel 性能实测与优化

> 测试时间：2026-09-24 · 环境：VirtualBox 7.2 / UEFI / 单 vCPU / 512 MiB · TSC 3.0 GHz
> （TSC 频率已用 8254 独立时基交叉校验：2850~3069 MHz vs 引导器声明 2999~3003 MHz，误差 <3%）
>
> 测试程序：`user/bench/main.c`，**在 ring 3 里测**。这样每条路径都包含完整代价
> （syscall 进出、换栈、用户指针校验、调度器参与），而不是内核内部某个函数的热身数据。

---

## 一、结果总览

| 项目 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 系统调用往返 | 130 周期 / 43 ns | **118 ~ 129 周期 / 39 ~ 43 ns** | 约 5~10% |
| 线程让出（含完整上下文切换） | 2191 周期 / 730 ns | **2134 ~ 2375 周期 / 711 ~ 792 ns** | 约 3% |
| IPC 往返（同步 RPC） | 13852 周期 / 4.6 µs | **5836 ~ 6002 周期 / 1.95 ~ 2.0 µs** | **2.3 倍** |
| 内存拷贝带宽 | 6877 MB/s | **40073 ~ 41236 MB/s** | **约 6 倍** |
| 内存对象 4 KiB 分配+释放 | 4369 周期 / 1.46 µs | **3985 ~ 3989 周期 / 1.33 µs** | 约 9% |

换算吞吐量：**同步 RPC 约 50 万次/秒**（单核，16 字节载荷），比优化前的 21.6 万次/秒翻了一倍多。

## 二、测量方法（为什么数字可信）

**在噪声环境里单轮测量没有意义。** 本机 VirtualBox 与 Hyper-V 共存，vCPU 调度不稳，
同一项测试不同轮次能差 2~3 倍（实测 IPC 一轮 5997、另一轮 16158 周期）。
干扰只会让测量值**变大**，因此每项都跑 5 轮取**最小值**作为该路径固有代价的估计，
并把最慢一轮一并打印出来，让抖动可见：

```
  系统调用往返 (fe_clock_ns): 最快 118 周期/次  (最慢 148)   [5 轮取最快]
  线程让出 (fe_yield，含完整切换): 最快 2134 周期/次  (最慢 2949)   [5 轮取最快]
  IPC 往返 (call+reply): 最快 6002 周期/次  (最慢 7630)   [5 轮取最快]
  内存拷贝带宽: 41236 MB/s  (25600 KiB，最快一轮)
  内存对象 4KiB 分配+释放: 最快 3985 周期/次  (最慢 4401)   [5 轮取最快]
```

`rdtsc` 本身在 VirtualBox 下可能触发 VM exit，但每项测试只在整段循环前后各读一次 TSC，
这点成本摊到上万次迭代后可以忽略。

## 三、做了什么优化

### 1. libfe 的 memcpy/memset 改为按字长拷贝 —— 带宽 6 倍

原实现是逐字节循环（约 2.3 字节/周期，6.9 GB/s）。改成：先把目的地址对齐到 8 字节，
主体按 8 字节步进搬，再收拾尾部零头。**实测 6.9 → 41 GB/s（约 13 字节/周期）**。
用户态编译选项是 `-mgeneral-regs-only`（内核不保存 FPU 状态，因此禁止编译期生成 SIMD），
所以字长对齐拷贝基本就是这个方向的上限。

### 2. IPC 消息池 —— RPC 快 41%

原先每条消息都要 `fe_kzalloc` + `fe_kfree` 一次。改成用一个空闲链复用消息结构体
（容量上限 64，超过就还给堆），并且只清必要字段而不是整块 memset。

**这一项的贡献做过干净的 A/B**（同一套测量方法，只改池容量常量）：

| 配置 | IPC 往返 |
|------|----------|
| 池容量 = 0（每条消息一次堆分配） | 10256 周期 |
| 池容量 = 64（复用） | 6002 周期 |

**即消息池单独省掉 4254 周期/次，占未池化成本的 41%。**

### 3. 节拍换算去掉 64 位除法

`fe_time_ms()` 原先是 `ticks * 1000 / hz`，除数 `hz` 是变量，编译器只能生成一次 64 位除法
（约 20~40 周期）——而系统调用总耗时只有 ~130 周期。既然默认 `hz == 1000`，
此时 ticks 本身就是毫秒，直接返回即可；其他频率预存 `ticks_per_ms`。

### 4. 睡眠链表插入走头部快速路径

原先每次睡眠都从头遍历链表找插入位置。绝大多数情况新线程的唤醒时刻晚于表头，
因此先试头部插入。遍历仍保留环检测（链表被破坏时要明确报错，而不是静默挂死——
这是 M4 踩过的坑）。

## 四、怎么看待这些数字（诚实版）

**系统调用 39~43 ns 与 Linux 同级甚至更快，但这不是"超越 Linux"，而是复杂度差异的正常结果。**
Linux 的 `getpid` 在现代 x86 上约 50~100 ns（含 KPTI、Spectre 缓解、审计与 seccomp 钩子）。
我们的路径上这些全都没有——没有 KPTI、没有缓解措施、没有安全钩子，只有换栈 + 分发 + 返回。
**该对比的意义是证明这条最热的路径没有写歪**，而不是性能优越。

**上下文切换 711~792 ns 属于合理区间**（Linux 通常 1~3 µs 量级），但我们的切换走的是
完整中断路径（`int 0x30` → ISR 保存 22 个寄存器 → 调度决策 → 从目标栈弹出 → `iretq`），
而不是直接的栈切换，因此仍有明显余量。

**41 GB/s 的拷贝带宽已经接近这个做法的上限**：13 字节/周期意味着每周期约 1.6 个 8 字节存取，
在禁用 SIMD 的前提下属于正常水平。

## 五、还没测的东西

| 未测项 | 原因 | 何时能测 |
|--------|------|----------|
| SMP 扩展性 / 锁竞争 | 目前只有 BSP 单核在工作 | M10 |
| 缺页 / 按需分页 | 尚未实现（内存全部预映射） | 后续里程碑 |
| 文件系统 / 网络路径 | 尚未实现 | M8 / M9 |
| 大消息 IPC | 目前内联载荷上限 256 字节 | 引入共享内存传递后 |
| 高负载下的调度公平性 | 需要几十个线程持续竞争才有意义 | M6 服务全部跑起来之后 |

### 中断延迟与抖动：已复核，结论修正

原先记的是「VirtualBox 把定时器中断投递限流到 ~130~190 Hz，属虚拟化层限流而非内核缺陷」。
**这个结论一半对一半错**，接入 QEMU(WHPX) 后复核定案：

| 环境 | 节拍投递速率 | 归属 |
|---|---|---|
| VirtualBox 7.2 | 49~169 Hz（声明 1000 Hz） | **确实是 VirtualBox 的中断投递限流**——同一份内核在 QEMU 下是 999 Hz |
| QEMU 11.1 + WHPX | **999 Hz** | 与声明值一致 |

但复核过程中发现，原先那个「自检测出 99 Hz」的数字里**混进了内核自己的 bug**：
调度器自检为了诊断直接操作 LAPIC 寄存器测计数速率，窗口算错 10 倍
（`tsc_freq/10` 是 100 ms 不是 10 ms），并且**测完不恢复**——把系统节拍源按错值重编，
在已经退到 8254 的 VBox 上还会让两个节拍源同时跑。
所以当时日志里「投递 49 Hz」与「睡眠 100 节拍花 1000 ms」两个测量是互相矛盾的，
而我把它整体归给了虚拟化层。**这个归因是错的**：矛盾的那部分内核有责。

修复后（自检不再碰 LAPIC 寄存器，改由时间子系统提供
`fe_time_restart_tick()` / `fe_time_measure_lapic_rate()`）：

```
QEMU   : 启动校验 999 Hz / LAPIC 计数速率 12520 与校准值 12519 吻合 / 投递 999 Hz
VBox   : 投递 49 Hz，睡眠 100 节拍实测 1450 ms —— 两个数字终于自洽
```

**因此本文档里所有以「节拍」为单位的结论不受影响**（调度算法、睡眠语义、时间片都以节拍验证），
但所有**换算成毫秒或赫兹**的结论必须标明环境：VirtualBox 下 1 节拍 ≈ 20 ms，QEMU 下 ≈ 1 ms。

另外纠正一个早先报过的可疑数据：内核里那项"ISR 平均耗时 135k 周期（45 µs）"**不可信** ——
该测量本身在 ISR 里调用了两次 `rdtsc`，而 VirtualBox 下 `rdtsc` 很可能触发 VM exit
（每次数十微秒），把测量成本算进了被测对象。QEMU 下同类数据是
「中断服务 167 次, 平均 1719 周期, 最大 36522 周期」——相差近 80 倍，
印证了 VirtualBox 的 `rdtsc` 开销确实是主因。

## 六、磁盘路径：两个被误判成"卡死"的数字

A/B 更新第一次跑起来时，2720 个扇区（1.36 MiB）的拷贝用了 **14.3 秒**，
而且日志停在"逐段拷贝到另一个槽"那一行不动。第一反应是死锁——
实际是两个**性能**问题叠在一起，而且量级都足以伪装成挂起：

| 现象 | 根因 | 改法 | 结果 |
|---|---|---|---|
| 拷贝 14.3 s | 驱动在**每个扇区**后面都发 FLUSH CACHE。每次 FLUSH 是一次真实的落盘屏障，虚拟化下就是一次 fsync | 把刷新做成独立操作 `BLK_OP_FLUSH`，由调用方在**提交点之前**发起一次 | **7.6 s** |
| 剩下的 7.6 s（≈2.8 ms/扇区） | ATA PIO 的一个扇区 = 256 次 `outw`，而 WHPX 下**每次端口 I/O 都是一次 VM 退出**，再加上等 DRQ/BSY 的状态轮询（每次轮询也是一次 VM 退出） | 未做；正确的方向是**别用 PIO**：总线主控 DMA 让一次传输只花几次端口写 | 待 M9（AHCI / virtio-blk） |

两点方法论上的收获：

- **"慢"和"卡住"在只有串口日志的时候长得一模一样。** 判据是：给它加**进度输出**
  （每 512 扇区打一行 + 耗时）。加上之后 14.3 秒这件事从"疑似死锁"变成了
  一个有具体数字的性能问题——顺带还留下了吞吐量这个有用的数字。
- **性能问题会伪装成正确性问题。** 如果当时按死锁去改（加超时、改重试），
  就会在一个健康的路径上叠一层没必要的机制。

## 七、还可以做什么（按预期收益排序）

1. **IPC 去掉每次调用的临时回复端点** —— 现在每次 `call` 都要创建/销毁一个端点对象
   并做两次句柄操作。改成从端点池取用，预计能再砍掉可观的一部分。
2. **上下文切换改走直接栈切换**，不再绕完整中断路径 —— 预计 711 ns 可降到 200 ns 量级。
3. **小消息走寄存器直传**（设计文档里已写，当前实现仍是"分配 + 拷贝"）。
4. **IPC 大载荷改走共享内存对象传递**，避免大块拷贝。
5. **调度器 tick 处理避免每次遍历睡眠链表**（当前只优化了插入侧）。
