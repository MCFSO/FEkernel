# 任务可见性与终止（K3 / K2）

> 本文回答两个问题：**"谁在跑"要怎么能看见**（K3），
> 以及 **"怎么让一个跑飞的服务停下来"**（K2）。
>
> 写作顺序说明：K3 的实现（`FE_SYS_TASK_LIST`）早在 D4 那一轮就落地了，
> 但**没有一个调用者**，也没有自检——本文补上设计说明，同时记下
> "没有调用者的 ABI"实际付出了什么代价（见 §2）。K2 是本文之后才实现的。

---

## 1. K3：为什么是"只读快照"，而不是"一个任务表句柄"

`TASK_LIST` 要回答的是**全系统的状态**（`ps`、诊断、以及设备管理器
"按名字找到驱动现在是什么 id"）。把它做成句柄就必须回答"谁有权持有它"，
而在能力模型里那个答案会一路膨胀：持有任务表的进程等于能看见**并且**
（只要再给一个写口）干预所有进程。

只读快照满足"看得见"，且**不产生任何新权限**。
一句更短的表述：**看不见的能力也就无法被滥用。**

反过来，这也定死了它**不能**用来杀进程：快照里只有 id，没有句柄。
而"杀"必须是能力——见 §3。

### 快照的形状：表头 + 定长任务记录 + 紧凑线程记录

内核必须能在**不知道用户态结构体布局**的前提下填这张表，否则两边任何一次
填充差异都会表现成"某个字段莫名其妙是 0"。所以：

- 记录是**定长**的（步长写成宏 `FE_TASK_STRIDE` / `FE_THREAD_STRIDE`）；
- 内核按**字节偏移常量**填，不做结构体强转；
- 线程记录是紧凑数组，任务记录里用 `thread_base` 指向自己的第一段。

★ 为什么不是"结构体数组"★ 结构体数组要求两边对 `sizeof` 与填充规则
完全一致，而那正是最容易在两台编译器之间漂移的东西。

### 截断要能看出来

`task_cap` / `thread_cap` 是调用者给的容量。表头里另给
`total_tasks` / `total_threads`（**真实总数**）。调用者据此判断自己看到的
是不是全部——而不是"填了 32 条就以为系统里只有 32 个任务"。

## 2. 没有调用者的 ABI 付出了什么代价（实测）

D4 那一轮把 `TASK_LIST` 的内核侧写完了，从那一轮到现在：
**没有任何程序调用过它，也没有任何自检覆盖它。**

实测后果：两个步长宏都写成了 `48`，而两个记录结构体都是 **64** 字节。
（`fe_thread_info` 的注释里那行算式 `4+4+8+8+8+4+4+4+4 = 48`
把末尾的 `name[16]` 漏掉了，步长宏正是照着那行错误算式写的。）

于是：

| 现象 | 后果 |
|---|---|
| 内核把 `name` 写在记录偏移 +48（也就是**下一条记录的头上**） | 后一条任务的 `id`/`parent_id` 被前一条的 `name` 覆盖 |
| 用户态按 48 步长读 `name` | 读到的其实是下一条记录的头 16 字节 |
| `switches` 字段被写死 0 | `ps` 会显示所有线程"一次都没被调度过"，与"刚创建"不可分 |

这三处**都不会让任何东西报错**：构建通过、启动通过、自检全部通过
（因为没有自检覆盖它）。

★ 这一条比 bug 本身重要 ★

1. **没有调用者的 ABI 等于没有验过的 ABI。** 写实现的那一刻它看起来
   "完成了"，而它真正的状态是"一个从未被执行过的猜测"。
   K3 之所以值得补自检与客户端，不是因为那张表重要，
   而是因为**它已经被写出来了**——写出来而没验，比没写更危险：
   文档与 syscall 表里都会记着"已完成"。
2. **"宏而不是 sizeof"这条规则原来只对了一半。** 它的本意是
   "不要用某一个编译器的 `sizeof` 去**定义** ABI"——这对。
   但它漏了后半句：宏一旦与结构体对不上，**就再没有别的东西会报错**。
   现在两边都用 `_Static_assert` 把宏钉在自己的结构体上：
   数字仍然是**契约**，"契约与本编译器的布局是否一致"由编译器判。
   规则改成：**契约用数字写，一致性用断言守。**

## 3. K2：终止为什么需要一个原语

今天的处境（`08-os-completion.md` 的限制清单里记着）：除"自己退出"与
"异常打死"之外，没有任何办法终止一个任务。于是：

- 跑飞的服务只能等它自己退；
- 测试里表现为"服务端只能靠协议让它自己退"（`hxtest` 就是这么收尾的）。

### 3.1 能力：`FE_RIGHT_TERMINATE`，不是 pid 也不是名字

"杀"是**破坏性**操作，所以它必须是不可伪造的能力。名字可以改、id 会复用
（`05-ab-update.md` 里"身份随退出失效"要防的就是这件事），
所以判据只能是**句柄 + 权限位**：

```
FE_RIGHT_TERMINATE  (1u << 9)
```

**谁天然拥有它**：`fe_process_spawn` 装进父进程句柄表时带上
`READ | WAIT | DUP | TRANSFER | TERMINATE`。也就是**拉起者可以终止它拉起的东西**
——这正是"系统自管"需要的形状：init 拉起服务，服务跑飞了，init 终止它。
权限可以经 `TRANSFER` 转交（那是一条正常的授权），但**不能凭空获得**。

### 3.2 难在哪：不能"就地拔掉"一个线程

一个线程可能正卡在内核里：阻塞在某个端点/通知的等待表上、或者已经登记进
`wait_any` 的节点里。**就地把它标记为死亡是不行的**：

- 它还在对象的 `waiters[]` 表里，指针留在那儿；
- 唤醒方（`fe_ipc_wake_object_waiters`）会解引用那个线程指针；
- 而僵尸被回收（`fe_sched_reap`）之后，那就是一次 use-after-free。

所以终止必须是**协作式**的：线程只在**取消点**上死。这不是妥协，
是"内核状态必须有机会自行收拾"这一条的必然结果——POSIX 有取消点，
也是同一个理由。

### 3.3 设计：一个标志 + 一个总闸门 + 若干取消点

**（a）总闸门：`fe_sched_maybe_switch`**

这是**唯一**的"回到用户态"的必经之路——`isr.asm` 与 `syscall.asm`
都在弹出寄存器之前调它（一个是 `iretq`，一个是 `sysret`）。
于是"一个任务的线程再也不能回到用户态"这件事只需要在一个地方表达：

```
任务 dying ⇒ 当前线程不返回用户态，就地变成僵尸，然后切到下一个线程
```

放在这里而不是每个 syscall 里各写一遍：漏一处就是一个"已经被杀了却还能
继续跑"的洞，而那种洞只在特定调用序列下出现。

它同时利用了已有的退出路径：僵尸登记与 `fe_process_on_thread_exit`
本来就是 `exit_isr` 做的事，抽成 `thread_mark_dead()` 给两边共用——
**所有线程死亡的必经之路仍然只有一条**。

**（b）取消点：阻塞循环的重新检查点**

一个阻塞中的线程根本走不到闸门（它没在跑）。所以终止方还必须把它**叫醒**：

1. 把它从正在等待的对象上摘下来（否则就是 §3.2 说的悬空指针）；
2. `fe_sched_wake` 它；
3. 它从 `fe_sched_block_current()` 返回，回到**重试循环**顶部；
4. 重试循环检查 `task->dying`，返回 `FE_ERR_INTR`；
5. 它带着这个错误返回用户态的途中经过闸门 → 在那里死掉。

第 3~4 步之所以成立，是因为**每个阻塞调用本来就必须是重试循环**
（伪唤醒是允许的，见 `fe_wait_any` 的说明）。取消点不是新加的机制，
是"重新检查条件"这个既有动作顺带得到的能力。

> ★ **下面这两句已被 §6.3 证伪（2026-09-26），原文保留是为了留下"当时以为只有两条"这个事实。** ★
> 按读到的代码，等待登记实际上是**五处**：线程的 `wait_node`、端点的 `receiver`、
> 通知对象的 `waiter`、控制器锁的 `lock_holder`/`lock_waiter`、目标任务的 `waiter`。
> —— 这正应了本表最后一行那句"漏加的症状是那个线程杀不掉，而不是崩溃"：
> 它当时只是一句提醒，后来真的发生了（`fe_process_wait` 与 `fe_resource_lock`
> 两处至今没有取消点，通知 `waiter` 至今没有摘除路径）。**以 §6.3 为准。**

**当时以为只有两类等待登记**，所以取消路径也只有两条：

| 等待形态 | 登记在哪 | 怎么摘 |
|---|---|---|
| `fe_wait_any`（等 N 个对象） | 线程的 `wait_node` + 各对象的 `waiters[]` | `wait_unregister`（复用既有的摘除路径） |
| `fe_endpoint_recv`（收消息） | 端点的 `receiver` 单槽 | 遍历该任务句柄表里的端点，清掉 `receiver == 目标线程` 的那一个 |

第二条为什么靠遍历句柄表而不是"给端点加一条链"：**正在收消息的线程
必然持有那个端点的句柄**（否则它没法收）。所以"谁在等这个端点"
可以从两个方向回答，而句柄表那个方向不需要任何新状态。

### 3.4 语义契约（写清楚，因为它们决定了怎么用）

1. **终止是异步的。** `TASK_TERMINATE` 返回时只保证"目标的所有线程都
   已被标记"，不保证它们已经死透。想要"确定没了"就 `WAIT` 那个任务句柄
   ——这正是 `WAIT` 已有的语义。
2. **被终止的任务不会再回到用户态。** 这是硬保证（闸门保证的）。
   它可能在核心里把当前这个系统调用走完，但不会执行用户态的下一条指令。
3. **可以终止自己。** 一个工作线程想让**整个任务**结束时用它；
   返回值无法观察（它在返回用户态之前就死了），这是语义的一部分，不是缺陷。
   只想结束当前线程请用 `THREAD_EXIT`。
4. **不能终止内核任务**（`FE_ERR_ACCESS`）。内核任务没有句柄表，
   也不该有"被杀"这个状态。
5. **资源回收时机不变**：任务对象在最后一个引用消失时销毁，
   那里已经在归还端口/MMIO/IRQ/devfs 名字/地址空间（见 `fe_object_destroy`）。
   终止只是让"最后一个引用消失"这件事发生得更早。

### 3.5 代价与边界

| 项 | 代价 / 边界 |
|---|---|
| `task->dying` 一个字段 + 闸门一次判断 | 每次返回用户态多一次字段读取（`g_current->task->dying`）。**没有**为它加锁：单核、且写它的路径在关中断区间里 |
| 取消点只有两类 ⚠ **已被 §6.3 证伪：实际是五处登记** | 将来若有第三种等待登记（例如"等一个内存对象可写"），必须同时加取消路径——**漏加的症状是"那个线程杀不掉"，而不是崩溃**，所以列在这里。★ 这一行当时的预言**已经应验**：`fe_process_wait`（等子进程）与 `fe_resource_lock`（等协作锁）今天就没有取消点，通知对象的 `waiter` 今天也没有摘除路径。见 §6.3 的处理决定表 |
| `FE_ERR_CANCELED` 会成为可见错误 | 被终止任务的线程可能把这个错误（`-21`）带回用户态（如果它恰好在终止前返回）。用户态应当把它当作"这次调用没做完"，而不是"参数错" |
| 不终止**正在被别的任务等**的东西 | 终止释放资源的方式是"任务销毁"，因此等待者会看到端点/名字消失——那是既有语义（`devfs` 名字回收），不是新引入的 |
| 没有信号 / 没有"杀它的理由" | 被终止任务的退出码固定为 `FE_ERR_KILLED`（`-22`）。今天没有消费者需要"为什么被杀"——需要时再加 |
| 最多一个 waiter | `task->waiter` 是单槽（既有设计）。多个任务同时 `WAIT` 同一个任务时，后登记者覆盖先登记者——**这是既有边界**，K2 不改变它，但列在这里免得被当成新问题 |

## 4. 验收口径与实测

### K3

- **内核自检** `fe_selftest_tasklist`（`kernel/task/tasktest.c`）：表头自洽 /
  每条记录回到内核对象上核对（名字、线程数、state、priority、主线程位、
  index）/ 线程归属 / `switches` 非零 / 容量只给 1 时如实报出**真实总数**。
  反向对照 4 条：`buf_len` 差一个字节 → NOSPC、`task_cap = 0` → INVAL、
  超过硬上限 → INVAL、`buf == NULL` → INVAL。
- **真实客户端** `user/bin/ps`：走完整 syscall 路径取快照并打印；
  反向对照 5 条（NOSPC / INVAL×2 / **未映射缓冲 → FAULT** / 截断如实报总数）。
  实测（QEMU 与 VBox 均失败项 0）：14 个任务 / 6 个线程，
  当前主线程的 `switches` 在两次快照之间从 1 涨到 9。
  判据用"孩子的 id 比第一张快照里任何一个都大"，而不是"任务总数变多了"——
  后者在回收链走通之后**不再成立**（见 §5.1）。

### K2

- **内核自检** `fe_selftest_kill`（`kernel/task/killtest.c`），四条路径各验一次：
  1. **忙等中的线程** → 走闸门。判据是它自己的 `cpu_ticks`：
     终止前必须增长，终止后 30 ms 内必须**不再增长**
     （"状态是 DEAD 却还在跑"的线程会在这里露出来）。
  2. **阻塞在收消息上** → 走取消点（端点的 `receiver` 槽），
     那次 recv 必须返回 `FE_ERR_CANCELED`。
  3. **阻塞在 `wait_any` 上** → 走取消点（`wait_node`），返回 `-21`，
     而且登记必须摘干净（`waiting == 0 && wait_node == NULL`）。
  4. **自我终止** → 整个任务结束、父进程方向的 `exited` 置位。
  反向对照：没有 `TERMINATE` 权限的句柄查不到；终止一个没有线程的任务
  安全且可重复。
- **真实客户端** `user/bin/killtest`：同一个可执行文件分饰两角
  （`--spin` / `--pub` / `--recv`）。实测（QEMU 与 VBox 均失败项 0）：
  - 忙等的孩子被终止 → 退出码 **-22**、`wait` 返回、**关掉句柄之后**才从任务表消失；
  - 阻塞在 recv 上的孩子先被确认为 `blocked`（从 K3 的表里读出来，
    不是"睡一会儿假定它阻塞了"），再被终止 → 也以 -22 结束；
  - 它发布过的 `/dev/killme0`：**杀之前打得开**（反向对照的前提），
    关句柄之后**打不开**（devfs 名字随任务销毁回收）；
  - 反向：坏句柄 → BADHANDLE；不含 TERMINATE 的句柄 → **ACCESS**。

★ 一条值得写下来的 ABI 细节 ★ 权限判据在**类型判据之前**：拿一个端点句柄
去调 `fe_task_terminate`，得到的是 `FE_ERR_ACCESS`（它没有 `TERMINATE` 这一位），
而不是 `INVAL`（"这不是任务"）。第一版的断言写成了 INVAL，于是它必然失败——
**那说明的是断言错了，不是内核错了。**

### 两处"计数类断言"的教训（K2/K3 期间各踩一次）

两次红都不是机制错，而是**断言没有等到计数有时间变化**：

1. 内核自检里"让出 2000 次，要求探针的 `cpu_ticks` 变大"——那个循环在
   一毫秒内跑完，1000 Hz 的节拍根本来不及跳，于是 `t1 == t0`。
2. 更隐蔽的一次：探针写成 `for(;;) fe_thread_yield();`，**它的 `cpu_ticks`
   永远是 0**——让出会把 CPU 交给空闲线程，而节拍记在"当时在跑的那个线程"
   头上，于是节拍全记到了 idle 账上，探针被记成"从没跑过"。
   改成纯忙等之后立刻正常，而且**纯忙等才是"跑飞的服务"该有的样子**。

教训：`t1 > t0` 这种断言必须配一个"等到它该变"的机制（睡够一个节拍、
或者有界轮询），否则测的是"循环够不够慢"。而"用哪个计数器"同样要选对——
**计数记在谁头上，取决于谁在那一刻是 RUNNING**。

## 5. 收尾时查出来的两个内核缺陷（都是"第一次被执行"暴露的）

K2 让"任务真的会死"，于是**任务的销毁路径第一次被执行**。
它一直是死代码——僵尸线程不被回收、对任务的引用永远不放，
`fe_object_destroy` 的任务分支从来没跑过。第一次跑就掉出两个问题。

### 5.1 僵尸线程从不回收 → 每个跑完的程序都泄漏

`fe_sched_reap()` 写好了却**没有任何调用者**；`fe_thread_join` 只释放它自己
等的那一个。于是每个退出线程的僵尸都留在链上，而僵尸**持有任务的引用**——
任务对象因此永不销毁，挂在销毁路径上的端口 / MMIO / IRQ / devfs 名字 /
地址空间 / 区间表全部泄漏。

这个泄漏一直都在。**它第一次被看见，是因为 K3 让"枚举任务"这件事成立了**：
第一次跑 `ps`，表里躺着二十多个"已退出"的任务。

修法：空闲线程里调 `fe_sched_reap()`；线程多一个 `reap_ok` 位区分
"由调度器收尸"（进程主线程：父进程用 `fe_process_wait` 拿退出码，不 join 线程）
与"有人在 join，不许碰"（引导线程 join 的 init 主线程）。
默认是**不回收**：漏一个僵尸是可见可查的，use-after-free 不是。
另外 `fe_thread_join` 原来只把线程从全局链摘掉、**没摘僵尸链**，
留下了一根已释放的指针——回收器一开工那就是 use-after-free，一并修掉。

修完之后最终任务表里只剩下真正的常驻服务（9 个）与内核自己的探测线程，
那二十多个"已退出"消失了。

### 5.2 销毁地址空间会把**借来的**内存还给 PMM

`fe_vmm_space_destroy` 遍历用户半区、把叶子项背后的帧一律还给 PMM。
但并不是每个叶子项背后的帧都属于这个地址空间：

| 映射来源 | 帧归谁 | 一律归还的后果 |
|---|---|---|
| ELF / 栈 / 匿名缺页 | 本地址空间 | 正确 |
| **MEM_MAP（内存对象）** | 那个对象（可能多个任务在映射它） | 把别人的内存还给池子 |
| **MMIO_MAP** | 根本不是 RAM，是设备寄存器 | 把设备寄存器变成可分页内存 |

实测症状：**销毁一个刚跑完的程序，另一个正在跑的进程（fsd）在自己的代码上
取指 #PF**——它的页帧被错误回收并重新分配了出去。紧随其后是
`fe_pmm_free_frames 参数非法: base=0x0` 的 panic：页表被写坏之后，
销毁遍历把"present 但地址为 0"的中间层项当成真表去走，
`pt_from_phys(0)` 指向**物理 0**，于是把低端内存当页表念了一遍，又释放一大片。

修法是两层，各自解决一个方向：

1. **让"拥有"记在页表里**：新增软件位 `FE_PTE_NOFREE`（bit 9，硬件不用），
   `MEM_MAP` 与 `MMIO_MAP` 都置它；销毁时只还**没有这一位**的帧
   （PCD 也一并挡住，作为第二道保险）。代价：将来任何"映射非独占内存"的
   新路径都要记得置它——**漏置的症状是"那次销毁多还了别人的帧"**，
   所以两处都写了互相指认的注释。
2. **让损坏不扩散**：遍历遇到"present 但地址为 0"的中间层项时
   **只报告、不释放**。一次"表被写坏"不该变成"到处崩"，留着根因还能被查。

顺带修掉的还有两处"分配失败被伪装成别的东西"：
`fe_vmm_space_create` 的**第二个**帧分配失败时 `pt_from_phys(0)` 不是 NULL，
于是那句 `if (!as)` 永远不成立，返回一个指向物理 0 的"合法"指针，
最后在销毁时变成 `fe_pmm_free_frame(0)` 的 panic——**内存不足被伪装成内核崩溃**。
另外 `fe_sched_maybe_switch` 在切到内核线程时**不换 CR3**，于是空闲线程
带着上一个用户任务的页表在跑；它一旦释放那个地址空间，CR3 就指着已被
回收的帧。现在两个任务各自的地址空间不同就切，内核线程一律切回内核空间。

### 5.3 共同形状

这两个缺陷都在**从来没被执行过的代码**里。K2 的价值不只是"能杀进程"，
更是**让"进程会死"这条路径第一次真的走通**——写好了却从没跑过的代码，
与没写的区别只是"看起来像有"。
这与 §2 的 K3 布局错误是同一族：**没有被执行过的路径，在文档和
syscall 表里都会被记成"已完成"。**

## 6. 闸门从任务级扩到线程级（为 exec 做准备）

> `15-exec.md` 原来把"多线程进程不能 `exec`"写成一条限制（§8 第 1 条），
> 并把它归到"终止的闸门是任务级的一位，表达不了'只死别人、不死我自己'"。
> **这条限制不保留了**：`exec` 按 POSIX 的语义来——**先杀掉调用者之外的
> 其它线程，再换映像**。本节写清这件事的形状、代价、边界，以及
> **它今天还没有成立的部分**。
>
> ★ 与 §3 的关系 ★ §3.3"总闸门"那一段的**判据**（`task->dying` 一位）
> 被 §6.1 取代；其余一个字不改：为什么不能就地拔掉线程（§3.2）、
> 取消点为什么必须存在、`thread_mark_dead` 为什么是唯一的登记处（§3.3），
> 全部照旧。§4/§5 记的是 K2/K3 那一轮的实测与缺陷，也不动。
>
> ★ 行号的读法 ★ 本节的行号取自写作当时读到的文件内容。`exec` 这一轮
> 正在改 `kernel/task/process.c` 与 `kernel/task/user.c`（`15-exec.md` §9
> 的清单），这两处的行号会漂；**以函数名为准**（每个引用后面都写了
> 是哪个函数里的哪一段）。

### 6.1 新机制的形状：每线程一票 + 判据只有一份

**（a）新字段：`kill_pending`**

```c
/* kernel/include/fe/sched/thread.h，加在 reap_ok（thread.h:83）之后 */
bool kill_pending;      /* 非 0 = 这个线程已被判定"必须死" */
```

语义三条，缺一条就会有人用错：

1. **它只说"这个线程不许再回到用户态"**，不说"任务怎么了"。任务可以继续
   活着、继续持有句柄表、devfs 名字、资源认领、任务 id——`exec` 要的正是
   这个：映像换掉，身份一个字节都不动（`15-exec.md` §2）。
2. **它只有置位、没有清除**。置它的只有"别的执行体"（§6.2 那个函数），
   线程自己从不置、从不清；线程 `state == FE_THREAD_DEAD` 之后这一位
   不再有意义（回收时不必清）。
3. **它不改变退出码**：走到闸门时仍然是 `FE_ERR_KILLED`（`sched.c:353`），
   与任务级终止一致。僵尸线程的退出码今天没有任何观察者：线程不是
   主线程时 `fe_process_on_thread_exit` 直接返回（`process.c:415`），
   而用户态的 `join` 语义今天不存在（`user.c:540-542` 的注释）。

**（b）判据只有一份：一个函数**

```c
/* kernel/sched/sched.c（挨着闸门），声明进 fe/sched/thread.h */
bool fe_thread_should_die(const struct fe_thread *t)
{
    return t && (t->kill_pending || (t->task && t->task->dying));
}
```

★ 为什么是一个函数，而不是"闸门与三个取消点各写一遍或运算" ★
`FE_TASK_STRIDE` 在两个头文件里各写一遍、两处还不一致的教训就在本文 §2。
这两份判据漂移的症状是**闸门放行了、取消点没放行**（或反过来）：
它只在一部分调用序列上出现，表现成"有时杀得掉、有时杀不掉"——
比崩掉难查得多。

**（c）闸门（`sched.c:352`）**

```c
-    if (g_current && g_current->task && g_current->task->dying) {
+    if (g_current && fe_thread_should_die(g_current)) {
         thread_mark_dead(g_current, FE_ERR_KILLED);
         g_need_resched = true;
     }
```

位置不动：仍然**必须在 `g_need_resched` 的早退之前**（`sched.c:344-347`），
否则"被杀的任务只要连着做几次不需要重调度的系统调用就能继续跑"这个洞
会原样回来——只是这次换成"被杀的线程"。

★ 顺带一条已经存在的性质，这里要用到它 ★
新线程的初始栈被伪造成"刚被中断的现场"（`sched.c:9-11`），所以线程**第一次
启动**也走 `isr_common` 的返回路径（`isr.asm:76-78`）——闸门对它同样成立。
一个"刚创建、还没跑过一条指令"的线程，如果所属任务在终止、或自己被标记，
它会死在启动路径上，而不是先跑一段用户代码。

**（d）为什么不能复用 `task->dying`**：三个理由，每个都能单独否掉它

| # | 理由 | 引用 |
|---|---|---|
| 1 | `dying` 表达的是"**整个任务**完蛋"（"本任务正在被终止"），而 `exec` 之后这个任务**还要继续活着跑新映像**——名字、句柄表、资源认领、任务 id 全都要留着 | `task.h:66-75`、`process.c:438-441` |
| 2 | `dying` 会顺带把"进程结束"这件事做掉：闸门死亡走的是 `thread_mark_dead` → `fe_process_on_thread_exit`，而它只在**主线程**退出时置 `exited`、唤醒父进程的 `wait` | `sched.c:596-607`、`process.c:407-425` |
| 3 | ★ 最硬的一条 ★ 闸门判据对**当前线程**同样成立。用 `dying` 表达"只死别人"，等于让 `exec` 的调用者自己在提交之后、返回用户态的途中死在闸门（`sched.c:352-354`）——新映像连第一条指令都没机会跑 | 同上 |

理由 2 反过来是一条要保住的性质：**"杀掉其它线程"不能让父进程的 `WAIT`
提前返回**。它成立的前提是"调用者不是主线程的死法不触发 `exited`"
（`process.c:413-417`），也正是 §6.2 里"调用者必须被排除"的另一半。

**代价**：一个 `bool`（`struct fe_thread` 已有 4 个布尔/小整数字段，
不改变缓存行数量级）；每次回用户态多一次判据——而它本来就是那个 `if`，
只是从"读一个字段"变成"读两个字段的或"。**没有为它加锁**，理由与 K2 相同
（单核；置位路径在关中断区间里，见 §6.2）。症状性的代价是：这一位
**没有"是谁要求的"这个信息**——诊断时只能看到"它被标记了"，看不到
"因为 `exec` 还是因为任务终止"。今天够用（同一时刻只可能有一个 `exec`
在做，而任务级终止会把所有线程一起带走）。

### 6.2 谁来叫它们死：一个函数，调用者必须在名单之外

```c
/* kernel/task/process.c（导出到 fe/process.h），挨着 fe_task_terminate */
u32 fe_task_kill_other_threads(struct fe_task *task, struct fe_thread *keep);
```

它做三件事，然后立刻返回（**异步**，与 `fe_task_terminate` 同一套语义）：

1. 遍历本任务的线程（`fe_task_thread_first` / `fe_thread_next_of`，
   `sched.c:833-854`），**跳过 `keep`**，对每一个依次做三件事：
   `kill_pending = true` → `fe_resource_forget_thread_locks(t)`（§6.3（3））
   → 它若是 `BLOCKED` / `SLEEPING` 就调既有的 `fe_thread_cancel`（`ipc.c:733`）
   ——它们自己走不到闸门，必须被摘下来 + 叫醒；
2. ★ **放锁是"杀"这一步的一部分，不是死后的补救** ★ 顺序钉死为
   "先放掉它握着的控制器锁，再让它去死"。事后补救（等它变成僵尸之后再清
   `lock_holder`）等于承认中间有一个窗口：锁被一个**再也不会 unlock** 的线程
   握着，而别人可能已经卡进去了——那个窗口里的等待者没有任何东西会唤醒它。
   整个过程在同一个关中断区间里（见下面第一条细节），所以这个顺序不靠时序巧合。
3. 返回被标记的线程数（就是 `process.c:459` 那个 `killed_threads` 累加的
   东西，复用即可；`task.h:77-78` 的注释要跟着改成"被叫停的线程数"）。

实现上有三条不能省的细节，每条都有理由：

- **遍历与"置位 + 摘登记 + 唤醒"要在同一个关中断区间里做完。**
  今天的 `fe_task_terminate` 是 `restore → 调 fe_thread_cancel → save`
  （`process.c:459-462`），也就是循环中途把中断放开。那在这类循环里是一个
  真实的窗口：被 `fe_sched_wake` 叫醒的受害者一旦被抢占，就可能跑到闸门、
  变成僵尸、被空闲线程回收（`sched.c:934` → `728`），而循环手里还握着它的
  指针（`fe_thread_next_of(t)` 要读 `t->all_next`）——use-after-free。
  今天撞不上，因为系统调用期间 IF 一直是 0（§6.4 有引用），而
  `fe_task_terminate` 的调用者目前只有 syscall 与自检。**新函数会被
  `exec` 之外的地方调用，不能靠这个巧合。**
- **只对阻塞/睡眠的线程调 `fe_thread_cancel`**，就绪（在队列里或在跑）的
  什么都不用做：它们下次回用户态时会被闸门拦下（`process.c:463-468` 已经
  写明了这条，照抄）。
- **不要在这里等**。等待是另一个函数的事（§6.4），因为等待会让出 CPU，
  让出的那一刻起"遍历期间的原子性"就没了。

★ 为什么调用者自己必须被排除 ★

- 它**正在执行 `exec`**：把它标记了，它下一次经过闸门就死了（闸门对谁都
  成立，见 §6.1(d) 理由 3），而它正是"换完映像之后接着跑"的那个线程；
- `exec` 的**提交**要在**它自己的返回帧**上写新入口（`15-exec.md` §3），
  帧没了就无所谓提交了。

★ 主线程被排除与普通线程被排除，语义不一样 ★

| 谁是 `keep` | 会发生什么 | 今天可能吗 |
|---|---|---|
| **主线程**（`task->main_thread`，`task.h:61`） | 进程语义完好：主线程活着 → `exited` 不置位 → 父进程的 `WAIT` 继续等**新映像**的退出码 | ✅ 唯一允许的形态（`15-exec.md` §7 的 `INVAL`：调用者不是主线程就拒绝） |
| **普通工作线程** | 那么"杀掉其它线程"就会把**主线程**一起杀掉 → `fe_process_on_thread_exit` 置 `exited`、唤醒父进程（`process.c:418-424`）→ 父进程拿着 `FE_ERR_KILLED`（-22）认为**进程已经结束**，而这个任务还在跑新映像 | ❌ 今天被那条 `INVAL` 挡住 |

第二行说明"`exec` 只能由主线程发起"**不是一条随意的限制**：它正是
"杀掉其它线程"这件事安全的前提。将来若要让工作线程也能 `exec`，
必须先把"进程结束"的判据从"主线程死了"改成"**所有线程都死了**"——
那是一次语义改动，不是放开一个判断。

★ 因此这是一条**约束**（已定，写进 §6 而不是留给实现时自由发挥）★
`fe_task_kill_other_threads` 的 `keep` 必须是**本任务的主线程**
（`task->main_thread`，`task.h:61`）。今天它由 `15-exec.md` §7 的
`FE_ERR_INVAL`（"调用者不是本任务的主线程"）保证；**要不要放宽这条限制，
取决于"主线程退出即进程结束"这条语义要不要动**——两条是同一件事的两面
（`process.c:413-417`）。在此之前，任何"让工作线程也能 exec"的改动都是
先把下面那个语义漏洞打开，再谈功能。

### 6.3 取消点：判据换成同一个函数；以及今天**遗漏**的等待登记

三个取消点都是"重试循环顶部那一个检查"，三处都改成
`fe_thread_should_die(fe_thread_current())`。

★ 一个必须写下来的坑：这三处的局部变量 `t` 是**任务**，不是线程 ★
`fe_endpoint_recv(struct fe_task *t, ...)`（`ipc.c:320`）、
`fe_wait_any(struct fe_task *t, ...)`（`ipc.c:631`）、

"杀了别的线程再换映像"会在最常见的形态上直接卡到超时（等子进程的服务线程、
共享端口上等锁的驱动线程、睡很久的工作线程）。

**（1）等待登记不止两类，是五处。** §3.3 的表格与 `ipc.c:724` 的注释都写着
"今天只有两类等待登记"，按读到的代码是五处：线程的 `wait_node`
（`thread.h:109-112`）、端点的 `receiver` 单槽（`ipc.h:51`）、通知的
`waiter` 单槽（`ipc.h:65`）、共享区间控制器锁的 `lock_holder`/`lock_waiter`
（`resource.c:569/578`）、目标任务上的 `waiter` 单槽（`task.h:62`）。

| # | 登记 | 有取消点吗 | 摘除路径 | 后果 |
|---|---|---|---|---|
| 3 | 通知的 `waiter`（`ipc.c:878-879`） | ✅ `ipc.c:865` | ❌ 只在有匹配位被置位时清（`ipc.c:829-833`） | 线程带着 `CANCELED` 走到闸门 → 死 → 僵尸（`reap_ok=true`，`user.c:543-545` / `process.c:302`）被空闲线程回收 → `nt->waiter` 成为**悬空指针**。以后再有人 `signal` 这个通知，`fe_notification_signal_obj` 会把已释放的内存当线程去唤醒（`ipc.c:838-840` → `fe_sched_wake` 读 `t->state`）。**修法**：把 `fe_thread_cancel` 的句柄表扫描扩到通知对象（与端点那条完全对称：正在等这个通知的线程必然持有它的句柄），清零 `waiter`/`wait_mask`。 |
| 4 | 共享区间的控制器锁（`resource.c:578`） | ❌ **没有** | ❌ | `fe_resource_lock` 的重试循环只看"锁在不在"（`resource.c:566-581`），不看取消判据 → 被叫醒之后**重新登记再睡**，于是这个线程**杀不掉**，直到持锁者放锁；而持锁者可能正是同一个任务里另一个同样杀不掉的线程。**修法**：循环顶加同一个判据，返回 `FE_ERR_CANCELED`；`fe_thread_cancel` 顺手清 `lock_waiter`（否则僵尸回收后同样悬空）。 |
| 5 | 目标任务的 `waiter`（`process.c:401`） | ❌ **没有** | ❌ | `fe_process_wait` 的重试循环只查 `child->exited`（`process.c:391-404`）→ 同样"杀不掉"，直到孩子退出。而这是**最常见**的形态：任何"拉起子进程再等它"的服务线程都长这样。**修法**：循环顶加同一个判据，返回 `FE_ERR_CANCELED`。 |

**（2）睡眠中的线程根本没有被叫醒。** `fe_task_terminate` 把 `SLEEPING`
归进"阻塞/睡眠中的线程自己走不到闸门，必须把它们叫醒"那一支
（`process.c:457-462`），但 `fe_sched_wake` 只认 `FE_THREAD_BLOCKED`
（`sched.c:546`）——对 `SLEEPING` 是**空操作**。于是睡眠线程不会被提前唤醒，
它要睡到点（`wake_sleepers`，`sched.c:520-531`）才醒、才走到闸门。
而 `FE_SYS_SLEEP`（`syscall.h:43` → `syscall.c:121-129`）的入参是纳秒：
一个"睡 30 天"的工作线程能把 `exec` 拖到超时。**修法**：给睡眠链加一条
摘链路径（单向链，只能 O(n) 扫，`sched.c:502-512` 已有同样的扫描 + 成环保护），
让叫醒也能处理 `SLEEPING`。

**（3）死在持锁状态 → 锁永远卡住。** `lock_forget_owner`（`resource.c:367-377`）
只在**任务销毁**（`resource.c:524`）与资源转交（`resource.c:467`）时跑。
`exec` 之后任务还活着，所以被杀的线程握着的那把锁**再也不会被放掉**：
后来者会在 `resource.c:566-581` 一直等；而僵尸被回收后 `lock_holder`
还是悬空的，`lock_forget_owner` 会读 `e->lock_holder->task->id`。
**修法**：新增 `fe_resource_forget_thread_locks(struct fe_thread *t)`
（按**线程**匹配，不能按 `owner_id`——那会顺手放掉调用者自己握着的锁），
并在 §6.2 那个循环里、**置位与唤醒之前**对每个受害者调一次（"先放锁、再让它死"，
理由见 §6.2 第 2 条）。

**（4）IPC 的 `call` 路径与 `join` 的等待者不用改。** 前者阻塞在
`fe_endpoint_recv` 里（`ipc.c:463`），取消点与摘除都走同一条；后者是
"让出型"循环（`sched.c:749-757`，每轮 `fe_thread_yield`），而让出同样经过
闸门，所以它天然可被取消——代价是它有一个 2,000,000 次让出的上限
（`sched.c:752`），超过就打印一行 `[join] 等待线程 ... 超时` 后放弃。

**（5）"纯计算死循环不受闸门保护"这句话与代码不符**（`killtest.c:114-118`
把它写进了注释）。按代码：用户态（IF=1）的纯计算循环每个节拍都会被定时器
打断，而中断门（`idt.c:85` 的 `GATE_INTERRUPT`）→ `isr_common`
（`isr.asm:49-78`）→ **正是闸门所在的那条路**，所以它会被杀。
真正"不经过闸门"的只有一种执行流：**在系统调用里、IF=0、又不让出**的那种
（§6.4 有 IF 的来源），而它同时让整个 CPU 连节拍都不跳——那时"杀不掉"与
"系统已经不可调度"是同一件事。单核上结论不变，但**理由**要改，
否则 SMP 那一轮会按错误的理由做判断（见 §6.5）。

**（6）只改注释与文档的两处（不动行为）**：上面（5）那条注释
（`killtest.c:114-118`），以及"登记只有两类"的说法（`ipc.c:724` 的注释、
本文 §3.3 的表格与 §3.5 的边界行）。
★ 本文 §3.3/§3.5 我**没有**直接改 ★——本轮的授权是"在末尾新增 §6"，
而 §3.3/§3.5 记的是 K2 当时的判断。这里留一句：
**§3.3/§3.5 里"等待登记只有两类"与"取消点只有两类"按读到的代码是错的，
以 §6.3 为准**；要把那两句改掉，说一声即可。

### 6.4 ★ 什么时候才算"死透了" ★

`exec` 要在杀完之后**换掉整个地址空间**，所以必须回答：是"标记为 `DEAD`
就够"，还是"必须等到 `fe_sched_reap` 真的回收（`thread_free`）"？

**结论：`state == FE_THREAD_DEAD` 就够；但"只置 `kill_pending`"远远不够。**
依据是 `thread_free` 实际碰的东西——逐项列出来：

| `thread_free` 释放/触碰 | 在哪个地址空间 | 引用 |
|---|---|---|
| 内核栈 `stack_base` | **内核堆**（创建时 `fe_kzalloc`） | `sched.c:682-685` ← `239`（ring3）/ `297`（内核线程） |
| TLS 块 `user_tls`（并清 `user_fs_base`） | **内核堆**（`thread.h:142-145` 明写"用户态**从不直接访问**它的虚拟地址"） | `sched.c:688-693` ← `202` |
| FPU 状态区 `fpu_area` | **内核堆** | `sched.c:694-695` ← `fpu.c:218` |
| 线程对象自己 | 内核堆 | `sched.c:697` ← `232`/`293` |
| 对任务的一次引用（可能触发任务销毁） | —— | `sched.c:698-700` |

**`thread_free` 一个字节都不碰用户地址空间。** 用户线程栈是**任务**级的：
`fe_user_map_stack` 只往**传进来的** `as` 里建映射、把栈区间登记进**传进来的**
`vmas`，`stack_low` 由调用点写回（`user.c:433-435`、`492-494`；调用点
`user.c:515` 传的正是 `t->space` / `t->vmas` / `&t->stack_low`）。
它归 `fe_vmm_space_destroy` 管，而那条路只在**任务**销毁时走
（`task.c:70-73`）。所以"必须等回收完才能换地址空间"**不成立**——
这一条与直觉相反，写死在这里。

★ 反过来，"只设标志"为什么不够 ★ 受害者此刻可能正卡在内核里：它可能刚被
叫醒、正在把当前这个系统调用走完（§3.4 第 2 条已经承认了这个语义：
"它可能在核心里把当前这个系统调用走完"），而那段内核代码用的是**旧映像的
用户指针**。`exec` 一旦换了 CR3，同一个指针在新映像里指向别的东西——
一次"受害者在新映像里乱写"。所以判据是 **`state == FE_THREAD_DEAD`**：
`thread_mark_dead`（`sched.c:596-607`）只有两个调用点——`exit_isr`
（`sched.c:618`）与闸门（`sched.c:353`）——走到闸门就意味着"它已经不在
用户态，而且再也回不去"。

★ 为什么"读到 `DEAD`"这一刻是可信的（不会读到"正在死"的中间态）★
`thread_mark_dead` 之后，同一个线程还要在 `fe_sched_maybe_switch` 里走
几步（挑下一个、存 rsp、切 CR3，`sched.c:362-452`）才真的让出 CPU。
这段不可能与观察者交错，因为：单核；闸门只在 ISR/syscall 尾部的**关中断**
区间里跑（`sched.c:382` 的注释把这条写明了）；而系统调用期间 IF 一直是 0
（`syscall.asm:127-131` 的 `SFMASK` 清 IF/DF/TF，入口桩不再开中断，
全内核只有 `idt.c:105-108` 与 `sched.c:937` 两处 `sti`）。
**能读到 `state == DEAD` 时，那个线程已经彻底不在任何 CPU 上了。**

**怎么等**（判据用现成的枚举，不新增计数器）：

```c
/* 让出轮数：与 fe_thread_join 的 2,000,000（sched.c:752）同族的保守值，
 * 但小一个数量级——exec 是一次系统调用，不能像 join 那样"等到天荒地老"。
 * 1000 Hz 节拍下，200000 次让出至少覆盖数十秒的墙钟时间。 */
#define FE_EXEC_KILL_ROUNDS 200000u

for (u32 i = 0; i < FE_EXEC_KILL_ROUNDS; i++) {
    if (fe_task_thread_count(task) <= 1) {
        return FE_OK;                   /* 死透了 */
    }
    fe_thread_yield();                  /* 给别人一次机会：去闸门 / 去收尸 */
}
/* 超时：先打一行能直接指认凶手的日志，再返回 */
fe_exec_dump_stuck_threads(task, keep);
return FE_ERR_TIMEOUT;
```

**超时日志**（`fe_exec_dump_stuck_threads`，只在这个路径上跑）：对每个
**仍然活着且不是调用者**的线程打一行，内容必须能直接指认凶手——
`name` / `id` / `state` / **它登记的等待点**。格式串用 ASCII
（屏幕字符串只用 ASCII 是这个项目的铁律）：

```c
"[exec] kill timeout: %u thread(s) still alive\n"
"[exec]   stuck: name=%s id=%llu state=%u wait=%s\n"
"[exec]   the process is now INCOMPLETE (marked must-die, no rollback)\n"
```

- `state` 是 `t->state` 的**数值**，不是 `fe_thread_state_name()`
  （`sched.c:867-878`）——那个函数返回的是中文（"就绪"/"运行"…），
  用它就违反了上面那条铁律。日志另配一张 ASCII 标签表。
- `wait=%s` 由 `fe_thread_wait_site(t)` 给出短标签：
  `wait_any` / `endpoint_recv` / `notification` / `reslock_hold` /
  `reslock_wait` / `task_wait` / `sleep` / `runqueue` / `unknown`。
  ★ 它需要三个**只读**访问器，今天一个都没有 ★ 见 §6.7 的最后一小节——
  其中 `fe_resource_lock_holder` 还是 D4 断言的**必需品**
  （`g_pool` 是 `resource.c` 的 static，没有它就只能间接推断）。
- **最后一行那句话是这段日志存在的理由**：返回 `FE_ERR_TIMEOUT` 之后，
  进程已经**残缺**，调用者不能再把它当完整的用（线程数少了一部分，
  而且被标记的那些会在下一次经过闸门时接着死）。

- **为什么不用"我手里那个线程指针的 state"**：受害者的 `reap_ok` 是 `true`
  （用户建的线程：`user.c:543-545`；除 init 外的主线程：`process.c:302`），
  空闲线程会在任意一次让出之后把它 `free`（`sched.c:934` → `728`），
  裸指针立刻悬空。`killtest` 里能一直读 `th->cpu_ticks`，是因为那些探针是
  **内核**线程、`reap_ok` 默认 `false`（`sched.c:258`、`killtest.c:229-233`）
  ——用户线程没有这个待遇。
- **为什么每轮从链头重新扫**：`fe_task_thread_count` 每次从 `g_all` 头开始走
  （`sched.c:856-865`），DEAD 的被跳过、已回收的被摘链（`sched.c:721-727`）。
  只要不在两轮之间持有指针，就没有 use-after-free。这正是 `killtest`
  等"任务不再有存活线程"用的判据（`killtest.c:420-424`）。
- **在系统调用上下文里等，没有特殊问题**：让出就是"把 CPU 交出去一次"。
  受害者会被选中 → 走到取消点/闸门 → 死；空闲线程也会被选中 → 顺手收尸
  （`sched.c:934`），它 `sti; hlt`（`sched.c:937-938`）之后节拍才会跳，
  于是睡着的受害者也有机会到点（§6.3（2）；修好那一条之后它们会被直接叫醒）。
- **等不到怎么办**：打上面那三行日志，然后返回 `FE_ERR_TIMEOUT`
  （`-12`，`errno.h:32`），**绝不 panic**。这条路径用户态可触发
  （只要有一个线程卡在没有取消点的等待上，或者睡在一个很长的 `SLEEP` 上），
  内核 panic 等于把它变成 DoS。
  ★ 代价必须说清：**`kill_pending` 不撤回** ★ 已经发出的"必须死"标记
  没有回滚接口——撤回它需要"别的核上已经有人在往闸门走"这种事不存在，
  而那在 SMP 上根本不成立（§6.5），单核上撤回也只会制造
  "有些线程死了、有些没死、而且没死的以后也不会死"的不确定状态。
  所以：**`15-exec.md` §4 那条"失败时原程序完好"在杀这一步之后不再成立**，
  进程会带着"少了一部分线程"继续跑（被标记的线程下一次经过闸门时死掉）。
  这是本轮唯一的语义让步，写在 `15-exec.md` §8 第 1 条里。

**顺序**：杀 + 等必须在**准备全部成功之后**、**提交的第 6 步（换 CR3）之前**。
准备失败时不能已经杀过人；而一旦换了 CR3，还在内核里的受害者就会拿旧指针
写新映像。

### 6.5 单核与 SMP：今天为什么成立，SMP 之后为什么不够（未来债）

今天"别的线程没有在跑"是**免费**的，靠三件事叠在一起：

1. 只有一个 CPU（`06-smp.md` §1 的路线图把 K10 排在第八步，
   `11-kernel-next.md:252`）；
2. 杀的那一段跑在系统调用里，**IF=0**（§6.4 的引用），重调度只能由显式的
   `int`（让出/阻塞/退出）触发；
3. 于是"置标志"与"它再也回不到用户态"之间没有竞争者：置完之后唯一的
   推进方式是我们自己让出，而每一次让出都仍在"我们说了算"的顺序里。

**SMP 落地之后这三条全不成立**，`kill_pending` 会退化成**一个请求**而不是
一个结果：

- 别的核上的线程**正在跑**（用户态死循环、或内核里一段长拷贝），置标志对它
  **没有延迟上限**。单核上闸门够用，是因为"闸门在每条回用户态的路上"；
  多核上"每条路"变成"每个核上的每条路"，要靠 **IPI** 才能把别的核推进 ISR，
  而 ISR 的返回路径才会经过闸门（`06-smp.md:56` 已有 `fe_lapic_send_ipi`，
  §7 给了 IPI 向量，`06-smp.md:261-263`）。
- IPI 只送达"请求"，**不等于已经停**：`exec` 仍要等到每个受害者
  `state == DEAD`（§6.4 的判据不变），而那个读必须是跨核可见的——今天
  这些标志位没有任何原子语义，`06-smp.md:196` 计划把 `g_need_resched`
  一类状态改成每 CPU。
- 还要一条**线程创建闸门**：多核上"某个受害者在我们扫完之后又
  `THREAD_CREATE`（`syscall.h:42`）了一个线程"是可能的，新线程会带着旧映像
  的入口跑进新地址空间。单核上不可能（§6.6）。
- 换 CR3 之后还要 TLB 一致：别的核 TLB 里可能还留着旧空间的表项，而旧空间
  随后会被释放、帧会被复用（`06-smp.md:43` 与 §8；M10.5 在
  `06-smp.md:427`）。

★ 记成债，不要假装今天解决了 ★ 今天的实现**只在单核上正确**。SMP 那一轮
必须把上面四条一起做完——缺哪一条的症状分别是"某个线程还在跑"、
"旧线程写坏新映像"、"新线程带着野入口"、"别人写进刚回收的帧"。
这与 §3.5 里"取消点只有两类"是同一类债：**漏加的症状是"杀不掉 /
杀不干净"，而不是崩溃。**

### 6.6 失败与边界

| 边界 | 今天的事实 | 会发生什么 |
|---|---|---|
| 调用者自己 | 永远在 `keep` 名单之外（§6.2） | 它自己绝不会被标记；误标它的后果见 §6.1(d) 理由 3 |
| **没有取消点的等待** | `fe_process_wait`（`process.c:391-404`）与 `fe_resource_lock`（`resource.c:566-581`） | 受害者**杀不掉** → 等到 `FE_ERR_TIMEOUT`（§6.4）。这是今天最现实的边界：它不需要任何恶意，只需要一个"等子进程"的服务线程 |
| 长睡眠 | `FE_SYS_SLEEP` 是纳秒（`syscall.h:43`），而 `fe_sched_wake` 不叫醒 `SLEEPING`（`sched.c:546`） | 同上：等到它睡到点，可能超时 |
| 纯计算的用户态线程 | 每个节拍被定时器打断，返回路径经过闸门 | 会死（§6.3（5）修正了 `killtest.c:114-118` 的理由）；SMP 之后才变成"另一个核上的死循环"（§6.5） |
| **被杀线程再创建线程** | **不可能**：创建线程要走 `THREAD_CREATE`，而受害者已被禁止回到用户态（闸门是唯一出口）；单核上也没有第二个执行流能在我们扫描期间跑 | 今天不需要额外机制。SMP 之后必须有线程创建闸门（§6.5） |
| **属于本任务的线程包含内核线程** | 判据是 `t->task == task`（`sched.c:836`），它不区分 ring3；内核线程的 `reap_ok` 默认 `false`（`sched.c:258`） | 用户任务今天**不会**拥有内核线程（只有自检用"临时换 `cur->task`"的手法造，`killtest.c:155-174`）。真出现时，被杀的内核线程会变成**永不回收**的僵尸，它对任务的引用让任务永不销毁——写判据时要意识到 `reap_ok` 也得跟着处理 |
| 失败后不可回滚 | §6.4 | `exec` 返回 `TIMEOUT` 时进程已经不是原来的线程集 |
| 回收越界 | 受害者被回收时 `thread_free` 会对任务 `unref`（`sched.c:698-700`） | 不会把任务拆掉：调用者自己持有一次引用（`sched.c:261`），所以"最后一个引用消失"不可能发生在 `exec` 中途 |

### 6.7 可证伪的自检（两组：E 组验机制，D 组先证缺陷存在）

★ 规矩：**自检要先能照出问题，再谈修复** ★ 这个项目已经为此付过两次学费
（§2 的 K3 布局错误、§5 的两个缺陷）——它们都在"从来没被执行过的代码"里，
而"没被执行过"与"没有 bug"在文档上长得一模一样。所以这一轮的自检分两组：

- **E 组（E1–E5）**：验**新机制**（闸门扩到线程级）对不对。它们要等机制

  ★ 一条在今天的代码上会通过的 D 断言没有价值 ★——它要么测的不是那个缺陷，

★ 今天怎么复现（D 组必须真的能跑出"红"来）★
今天**还没有** `fe_task_kill_other_threads`，唯一的取消触发者是
`fe_task_terminate(task)`（`process.c:447`，置 `task->dying` + 叫醒阻塞者）。
所以 D1–D3 的"今天"用后者复现，但有三条**构造上的硬要求**，否则断言会以
错误的方式变红（读已销毁对象、或根本观察不到）：

1. **观察物必须活得比被终止的任务久。** D1 的通知对象在断言时必须**还在**：
   它由探针任务的句柄表持有一个引用，而探针任务本身由自检持有创建者引用
   （`fe_task_create_kernel` → `fe_object_init` 的 1 次，`killtest.c` 的写法
   就是测试期间一直持有、最后才 `unref`）。这两条缺任何一条，通知对象都会
   先被销毁（任务销毁会清句柄表，`task.c:52`）——那时读到的是"对象没了"，
   而不是"槽里有悬空指针"。稳妥做法：让**自检自己的任务**也持有一个通知
   句柄当第三方持有者，这样即使探针任务被回收，断言读的仍是同一个对象。
2. **"没被杀的兄弟线程"必须属于另一个任务。** `fe_task_terminate` 会把
   整个任务的线程一起带走，所以 D2 的反向对照 C、D3 的 L 与 L2、
   D4 的对照② 在"今天"这个复现里都得放在**另一个任务的线程**上；
   它们的状态在整个窗口里必须不变。（2a 之后有了 `fe_task_kill_other_threads`，
   它们就回到**同任务**里——那才是与 `exec` 一致的形态，也正是用户
   期望的"没被杀的同任务线程"。）
3. **D4 今天的复现路径不是"杀"，而是"持锁线程自己退出"**：让持锁线程调
   `fe_thread_exit(0)`（`sched.c:628`）——**任务还活着**，于是
   `fe_resource_release_owner`（`resource.c:524`）不会跑，状态与
   `exec` 杀线程之后**完全一样**（锁卡住 + `lock_holder` 指向已回收的线程）。
   如果走 `fe_task_terminate`，整个任务会被销毁、锁会被
   `fe_resource_release_owner` 顺带放掉——那样断言会**假绿**。
   2a 落地之后，D1–D4 都要改用 `fe_task_kill_other_threads` 再验一遍
   （那才是 `exec` 真正走的路）。

**D3 那个 100 ms 是怎么来的（不许编数字，所以写清楚）**：它**不是**
实测值，而是沿用 killtest 已经在用的等待尺度——"`5 ms` × 20 轮"的
有界轮询（`killtest.c:206-209`）与 `fe_thread_sleep_ms(30)` 的观察窗口
（`killtest.c:234-236`）。探针睡的是 **60 s**，比它大三个数量级，所以
"今天必失败"没有歧义；修好之后受害者只需"被叫醒 + 走到闸门"，
量级是几次调度，100 ms 是极宽松的上界。

★ 只读访问器：今天没有，D4 与超时日志都要用 ★
（"只看不写"是关键——能当**判据**的必须是可读的事实，不是"跑起来没崩"。）

### 6.8 落地节奏：两刀，不要并成一刀

| 刀 | 内容 | 为什么这么切 |
|---|---|---|
