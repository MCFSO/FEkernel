# FEKernel 里程碑

每个里程碑的验收标准都是「能在 QEMU 里实际跑起来并看到可验证的输出」，不接受「代码写完就算完成」。

| # | 里程碑 | 内容 | 验收标准 |
|---|--------|------|----------|
| M0 | **工具链 + 引导 + 串口** | 便携 clang/lld、NASM、Python 构建编排；Limine 请求；GDT/IDT/TSS；异常处理；16550 串口；`kprintf`；`panic` 带寄存器回溯 | QEMU 启动后串口打印内核横幅、内存映射摘要、帧缓冲信息；故意触发 `#PF` 能打印 RIP/错误码并停机 |
| M1 | **物理内存 + 虚拟内存 + 内核堆** | Limine memmap → PMM 位图；HHDM；自建页表（替换 Limine 的）；`kmalloc/kfree` slab | 串口打印可用内存总量/分配测试自检（分配 N 帧→全部可写→释放→计数归零） |
| M2 | **抢占式调度 + 定时器** | LAPIC/IOAPIC 初始化；内核线程；上下文切换；优先级 + 时间片；`sleep` | 多个内核线程交替打印，时间片轮转可观测；`sleep` 精度打印 |
| M3 | **IPC + 对象/句柄** | 端点消息传递、通知、共享内存对象、句柄表、能力校验 | 两个内核线程互发 10000 条消息并校验内容；句柄越权访问被拒绝 |
| M4 | **用户态 + 自定义 syscall ABI** | ring 3 切换、syscall/sysret 入口、ELF64 加载器、`libfe` 运行库 | 用户态 `hello` 程序通过 syscall 打印字符串后 `exit(0)`；内核打印其退出码 |
| M5 | **驱动能力 ABI + 硬件资源池** | 每任务 I/O 权限位图（TSS 槽位）、`fe_ioport_request`/`fe_mmio_map`/`fe_irq_register`/`fe_mem_info`、资源池互斥认领、中断投递到通知对象 | ring 3 驱动**认领前**执行 `in` 被 #GP 精确拦下，**认领后**同一条指令跑通；可用内存不可被映射为 MMIO |
| M6 | **第一批驱动服务** | `init`、PS/2 键鼠两个用户态服务、帧缓冲控制台（自研点阵字体） | 屏幕上出现图形控制台输出，键盘输入能回显 |
| M7 | **devfs 服务发现 + 块设备** | `devfs`（BSD 式：命名空间即文件系统）；`blkd`（ATA PIO）发布 `/dev/blk0` | 客户端只用路径 `/dev/blk0` 就能找到服务，读回扇区并解析出 MBR / FAT32 BPB |
| M8 | **FAT32 + 保护层** | `fsd` FAT32 服务（只读）；**A/B 无缝更新 + 扇区保护 + 槽状态机**（见 `05-ab-update.md`）；`pcid` PCI 枚举 | ✅ 只读、保护层/更新、**以及文件系统写路径**均完成并实测（双环境）——写路径见 `08-kernel-completion.md` §9（S2 第一步：屏幕上的一次完整验证）；⬜ 槽改分区 |
| M9 | **网络栈** | `netd`（e1000 + virtio-net）+ `ipd`（ARP/IPv4/ICMP/UDP/TCP） | 从 QEMU 用户网络里 DHCP 或静态配置后 `ping` 通网关，TCP echo 成功 |
| M10 | **SMP** | AP 启动（Limine MP）、每 CPU 结构、自旋锁、IPI、TLB、负载均衡；设计见 `06-smp.md` | **可测量的指标**：N=2 加速比 ≥1.7、N=4 ≥3.0；一个核做 I/O 时另一个核的 RPC p99 退化 <10%；`--smp 1` 不退化超过 5% |
| M11 | **真机 + 双虚拟机验证** | U 盘镜像；VirtualBox 与 QEMU(WHPX) 双跑；文档 | 真机从 U 盘启动进入图形控制台；VBox 中同样可启动 |
| M12 | **按需分页 + 栈自动增长**（K1） | VMA 区间表 + `#PF` 解析；页表是事实、区间是意图 | 正反向各 9 项自检（`fe_selftest_demand_paging` 8 + `fe_selftest_vma` 9）+ `posixprobe` 递归 700 层实测「内核解析缺页 5 次」——证明栈是**长**出来的，不是预映射的 |
| M13 | **多对象等待（`fe_wait_any`，K4）** | 一个线程同时等 N 个端点/通知（驱动的常态：等中断 + 等请求合流） | 4 组内核自检（已就绪立刻返回 / 被通知唤醒 / 被消息唤醒 / 非法参数被拒），其中 **3 条反向对照**；双环境实测失败项 0 |
| M14 | **磁盘 DMA + 共享内存批量（D4）** | virtio-blk 后端（四类结构按 PCI capability 定位）+ 客户端交缓冲的批量读（数据零拷贝直入客户端内存） | **可测量的指标：每 KiB 成本降到 1/100 量级**。QEMU+WHPX 实测 130416 → 1266 周期/KiB（21 → 2253 MiB/s，**103 倍**），且该倍数本身是一条会失败的断言（<4 倍即失败项）；4 条反向对照（MMIO 窗口被独占 / 普通内存冒充 DMA 缓冲被拒 / 越界 LBA 被拒 / 长度两个方向被拒）+ 毒值差分与跨路径对照各一条 |
| M15 | **任务枚举与进程终止（K3 + K2）** | `TASK_LIST` 只读快照（`ps`）；`TASK_TERMINATE` + `FE_RIGHT_TERMINATE`；终止的硬保证靠**唯一闸门** + 阻塞线程的**取消点** | 内核自检 2 组（K3 表头/记录/归属/`switches`/截断 + 4 条反向；K2 四条死亡路径 + 2 条反向）、真实客户端 2 个（`ps`、`killtest`——后者同一个可执行文件分饰监督者与被杀者）。**双环境失败项 0**。★ 这一轮真正值钱的是它照出的**两个从未被执行过的内核路径**（僵尸线程从不回收 → 每个跑完的程序都泄漏资源；销毁地址空间把借来的内存还给 PMM → 另一个进程取指 #PF）：见 `13-tasks-and-kill.md` §5 |
| M16 | **真实时钟（K7）+ 睡眠按时间到期** | 节拍（调度单位）与时钟（读时间）分成两件事；时钟建在 TSC 上；新增 `CLOCK_INFO` 让调用者能**问出精度**；**睡眠的到期时刻改成绝对纳秒** | **可测量的指标：能分辨亚毫秒。** 内核自检实测短忙等 2000×pause 读到 **71934 ns**（节拍制只能给 0）；客户端实测 20000 次累加的短循环读到 **5816 ns**、两次连读相差 66 ns；并做**交叉验证**（客户端自读 TSC 换算 9084 us == 内核时钟 9084 us）。双环境失败项 0。★ K7 顺带照出一个**正确性问题**：睡眠原来按"节拍个数"计时，而 VBox 的节拍是**突发投递**的（同一个 8254 源：被动 50 ms 窗口数到 5 个节拍，睡眠期间却以 ~3.5 kHz 前进），于是 `sleep(20ms)` 只用 **5 ms** 就返回——**超时提前触发**，既有测试把它当"限流"报告（`hxtest` 刻度 **27%**）放过了。改成按时间到期后：VBox `sleep(20ms)` → **22 ms**、刻度 **114%**；代价是唤醒受节拍粒度限制，语义变成"**至少 N 毫秒**"（QEMU 上 50 ms 睡成 59 ms）——只会晚不会早。见 `11-kernel-next.md` §11 |
| M17 | **中断共享与触发方式契约（D5a + D5b）** | 一根**电平**中断线可被最多 4 个任务登记（边沿线**拒绝**共享：A 处理期间 B 的边沿没有第二次跳变可检测，那一次永久丢失）；投递置位**所有**登记者（线不携带"是哪台设备"，驱动必须接受伪唤醒）；电平线**屏蔽到所有需要确认的人都确认**；新增"只认物理"之外的两种声明：触发方式要求（D5b，声明错就**拒绝登记**）与 `FE_IRQ_F_NO_MASK`（纯轮询驱动声明"不要为我屏蔽"） | 内核自检 40+ 条断言（**失败报行号**）+ 真实客户端 `irqtest`：同一台真实设备（virtio-blk 的 IRQ11，电平）被**两个任务**同时登记，**两者都收到真实设备中断并确认**，且"所有中断收完之后磁盘仍然可用"（线没被卡住）。双环境失败项 0（VBox 无 virtio 设备，irqtest 按 `needs` 如实跳过）。★ 照出**两个内核缺陷**：`pending` 欠账必须逐家记（"已确认的人退出"不能再减，否则线被提前放行 → 风暴）；**`pool_merge()` 会吃掉共享标记**（把相邻的 `[11,1)shared` 与 `[12,1)` 并成 `[11,2)flags=0`，于是第二个驱动拿 BUSY 而池子里写着"共享"）。见 `14-interrupt-semantics.md` |
| M18 | **MSI/MSI-X（D5c）** | 消息信号中断：设备不再拉一根物理线，而是**往 LAPIC 写一条消息**。内核把这件事压成三个动作——认领（设备位置 `bus/dev/fn` + 能力偏移）、拿到一条**伪 IRQ 号**（32..63，与 GSI 不共用编号空间）、把 MSI-X 表项**由内核写**（映射 BAR 里的那一小段 MMIO，写 addr/data/vector control，再置 MSI-X Enable 并清 Function Mask） | **可测量的指标：同一次读请求，在"没有 INTx 登记"的前提下被 MSI-X 送达。** QEMU 实测 `[blkd] MSI-X 中断**已到达**（辅助线程被那一位唤醒；读请求成功）—— 这条路上**没有登记 INTx**，所以只可能是 MSI-X 送来的`（关掉 MSI-X 后同一台设备在 `irqtest` 里又走 INTx 共享线，两条路都实测过），中断投递失败项 0、`irqtest` 共享测试失败项 0、`init` 失败项 0；反向对照含"偏移处不是 MSI/MSI-X 能力 → 拒绝"（两个环境都真跑到：QEMU `00:04.0 的偏移 0x40 上是能力 0x9`，VBox `00:04.0 的偏移 0x40 上是能力 0x0`、`1f:1f.7 的偏移 0x98 上是能力 0xff`）、"非 MSI-X 索引越界 → 拒绝"、"MSI 号用尽 → 拒绝"。★ 设备侧**两个开关**缺一不可：MSI-X 表写对了、Enable 也置了，中断仍然不来——virtio 的 `queue_msix_vector` 默认 **0xFFFF = 用 INTx**，必须由驱动把它改成 0（`VIRTIO_COMMON_MSIX`/`Q_SELECT`/`Q_MSIX`）。VBox 无 virtio 设备，MSI-X 实体路径按 `needs` 跳过（只有拒绝路径可测）。见 `14-interrupt-semantics.md` §8 |
| M19 | **`exec` 的每线程闸门 + 四项等待登记缺陷修复 + `mprotect`**（K6 的 2a/2b + C2 收口） | ① 终止闸门从任务级（`task->dying`）扩成**每线程一票**（`thread->kill_pending` + 判据 `fe_thread_should_die`），新增 `fe_task_kill_other_threads` / `fe_task_wait_others_dead`；② **四项等待登记缺陷**修复：通知 `waiter` 悬空（`fe_thread_cancel` 扩到通知对象）、`fe_resource_lock` 与 `fe_process_wait` 各加取消点、`fe_sched_wake` 能叫醒 `SLEEPING`、持锁而死 → 杀之前调 `fe_resource_forget_thread_locks`；③ `sys_exec` + `fe_exec`（syscall `0x90`）；④ `mprotect` 三层链 `fe_vmm_protect`（页表层，改 `W`/`NX` 位并**无条件 `invlpg`**）→ `fe_vma_protect_range`（机制层）→ `sys_mem_protect`（syscall **0x91**，`FE_SYS_MAX` → `0x92`），用户态 `fe_mem_protect` | ★ **红/绿各一对，都是先红后绿** ★ ① D1–D4 的断言**修前如实红、修后全绿**，且 **D-off 基线全绿 + D-on 全绿、连跑 3 次逐项一致**（证据在一次性空提交 `24fc079`；四刀为 D1 `47f5630`、D3 `eac825f`、D2 `0a0fc83`、D4 `7ca3965`）；② `mprotect`：把 `fe_vmm_protect` 临时改成提前返回（= "只改 VMA、不改 PTE"的缺陷版）→ `区间保护失败项: 7`，恢复 → `0`（新自检组 `fe_selftest_protect_range`：正向 5 项 + **四条反向对照**）；③ E1–E5 随 2b 落地（汇总行 `替换映像 失败项: 0`）；④ 既有判据**零退化**：**24 条汇总行全 0**（原 23 + 新增"区间保护"）、`panic=0`、`=> 用户态失败项: 0`、`M5 里程碑自检全部通过`、`init 结束，失败项 0`。★ **双环境待 2c 补齐**：2c = 用户态 `exectest` 三种模式（0x5A/0x5B/0x5C）+ mprotect 的 ring-3 探针 + QEMU/VBox 两跑（见 `15-exec.md` §10.2/§10.3）★。★ 顺带如实记一条**被撤回**的判据：原要求"`mprotect` 不许绕过写保护"**前提是错的**——保护清单收的是**磁盘 LBA**、与虚拟地址是两个地址空间，没有可判的交集；改为"用户态只能改自己地址空间里、自己 VMA 内的页"（`vma.c:242-284`），见 `11-kernel-next.md` §12 ★ |
| M20 | **用户态异常处理者（K5）** | 任务级登记（`fault_depth` / `fault_owner` / `fault_seq`）+ 每线程回复槽与 `last_fault_rip` / `last_fault_cr2`；`kernel/task/fault.c` 的 `fe_fault_set_handler` / `clear` / `release` / `reply` / `apply_regs` / `deliver`；`struct fe_fault_regs` **25×8 = 200 字节**（两条 `FE_STATIC_ASSERT`：自己的布局 + "必须包含整份现场"，`kernel/include/fe/regs.h:68-75`）；syscall **`0x92` / `0x93`**（`FE_SYS_MAX → 0x94`）。★ **四个出口的顺序**（顺序本身是判据）★：① 内核态异常**永不**交给用户态；② **先按需分页**（`fe_user_resolve_fault` 成功就 return，这条路保持在最前）；③ 投递处理者（**IF=0 里只能就地让出 + 有界轮询**，不新增等待登记）；④ 否则照旧杀线程（`kernel/arch/x86_64/idt.c:299-405`） | 内核自检 `fe_selftest_fault`（`kernel/task/faulttest.c`，挂 `main.c:696`）**九组全绿、每条正向配一条会失败的反向**（F1–F6、**F8–F10**；★ 文件里**没有 F7**，实测如此 ★），汇总行 `=> 异常处理者失败项: 0`；真实客户端 `user/bin/faulttest` **六模式**（期望值写在 `user/bin/init/main.c:821-831`）：`--segv` / `--ud` / `--de` / `--all` 退出 **0**、`--nohandler` 退出 **-1**（"没登记处理者的任务仍然被杀"，与 `drvdeny` 同一口径）、`--recursive` 退出 **0x77 = 119**（处理者自己被深度判据杀）；**双环境逐字一致**；单元表 **31 → 37**（`tools/check_init.py` 与参考日志已同步，`=> 核对通过`）；**25 条汇总行全 0**（原 24 + "异常处理者"）。★ 与 `exec` 的交互已验：**成功换映像**之后查询处理者返回 **`FE_ERR_NOENT`**（提交阶段 `fe_fault_release_handler`，`process.c:571-582`；自检 `process.c:1049` 断言 NOENT）★。★ **它挖出的两个真问题**：**(a)** `cr2` 的 ABI 在实现里本来不成立——两侧注释都写"只有 `#PF` 有意义、其余为 0"，而 `idt.c` 原先**无条件读 CR2** ⇒ `#UD` / `#DE` 报回**上一次缺页的地址**（实测 `--ud` / `--de` 打出 `cr2=0x51000000`，正是同进程 `--segv` 的越界地址；加断言后 exit **181** / **197** 真红），改成按向量取值才回到 0（`idt.c:307-313`）；**(b)** 设计文档里**七处判据不成立**（"红测试其实不经过 `user_fault`"、模式 E 的"三次 `cr2` 互不相同"不可能、`exectest` **模式 B** 之后 `NOENT` 不成立……）——逐条记在 `18-user-fault-handler.md` §7。来源提交：内核机制与自检 `e54db3e`、用户 ABI 与客户端 `ed8612c` |

> **M12/M13 的编号说明**：里程碑表原先只到 M11，而 `11-kernel-next.md` 的
> K 清单（K1 按需分页、K4 多路等待…）已经先跑起来了。为了不再出现"文档里
> 有两套编号"的情况，从这一轮起**每完成一个 K 项就补一个 M 编号**，
> 编号与 K 项的对应关系写在上表的"内容"列里。
>
> **M14/M18 的适用范围要说清**：它们的指标在 QEMU 上达标；**VirtualBox 上没有
> virtio-blk 设备**，所以那两条结论在 VBox 上不成立——而这一点在日志里是
> 明说的（`[init] 跳过 vblkd：本机没有 virtio-blk 设备 —— 硬件前提不成立，
> 不算失败`），不是悄悄少几行。这与 M12/M13 的"双环境都过"不是同一类证据，
> 不要混着引用。M18 在 VBox 上仍然留下了自己的证据：MSI 能力的**拒绝路径**
> 两个环境都真跑到了（VBox 报 `00:04.0 的偏移 0x40 上是能力 0x0`、
> `1f:1f.7 的偏移 0x98 上是能力 0xff`），而"MSI-X 送达"这一条只有 QEMU 有。

> **编号说明**：原先表里 M5 是「第一批驱动服务」、M6 是「PCI 总线服务」。铺底座时发现
> 「驱动怎么合法地碰到硬件」这件事没有先解决，驱动服务写出来也是假的（每个驱动都能
> 随便 `in`/`out`/摸任意物理内存），因此把**驱动能力 ABI + 硬件资源池**独立成 M5，
> 其后的里程碑顺延一位。

### M2 交付内容

```
kernel/acpi/acpi.c        ACPI 表解析：RSDP → RSDT/XSDT → MADT（CPU/IOAPIC/中断源覆盖）
kernel/arch/x86_64/lapic.c LAPIC：MMIO 映射、SVR/TPR/EOI、定时器校准、TSC-deadline 模式、IPI
kernel/arch/x86_64/ioapic.c IOAPIC：重定向表、按 ACPI 极性/触发方式路由 GSI
kernel/sched/sched.c      线程对象、32 级优先队列、时间片轮转、睡眠队列、统一切换路径
kernel/sched/schedtest.c  调度器自检（不含 yield 的抢占验证、睡眠语义、唤醒延迟）
kernel/time/time.c        节拍源：TSC-deadline 优先 → LAPIC 周期 → 8254，含运行时自愈
```

**核心设计：所有上下文切换都走同一条路径。** 中断发生时寄存器现场压在当前线程的栈上；
需要切换时调度器只把当前 rsp 存进线程对象、把下一个线程的 rsp 交给 `isr_common`，
后者在该栈上继续「弹寄存器 + iretq」。新建线程的初始栈被**伪造成一个刚被中断的现场**，
因此「抢占、主动让出、线程退出、线程首次启动」四种情形共用一套代码，没有特例分支。

| # | 现象 | 根因 | 修法 |

| 1 | PMM 初始化时页错误，错误码 `0xb`（保留位违例），地址在位图范围内 | 位图被放在**内核映像之后的「引导器可回收」内存**里，而 Limine 正把自己的页表放在那里。`memset` 清位图时把**活着的页表**覆盖掉了 | 位图改为从引导器标为「**可用**」的内存里取——那里不可能有引导器结构 |

| 4 | 切到 8254 后一个节拍都没有 | **有 IOAPIC 时 ISA IRQ0 走的是 IOAPIC 的 GSI 2，根本不经过 8259** | 按 ACPI 中断源覆盖给出的 GSI/极性/触发方式经 IOAPIC 路由 |

| 6 | 内核堆自检报「释放后未回到基线」 | 调度器在堆自检之前就已分配常驻对象，基线不该假定为 0 | 基线改为「自检开始前的快照」 |

```

kernel/arch/x86_64/syscall.c    MSR 初始化与 13 个系统调用的实现
```

**设计要点**：
- **进入内核后立刻把用户现场伪造成与中断完全一致的栈帧**，因此「系统调用返回」与「中断返回」共用同一套寄存器弹出序列，线程切换对两者透明；
- 返回路径按帧里的**伪向量号 0x80** 区分：来自 syscall 的用 `sysret` 快速返回，其余（线程首次启动、被抢占后恢复）用 `iretq`；
- 每个线程有独立内核栈，`TSS.rsp0`（ring 3 中断用）与 `gs:8`（syscall 用）在每次线程切换时同步更新；
- **用户态异常只终止该线程**，内核继续运行——保护模式的意义就在这里。

### M4 期间踩到的坑（第 6 条是最贵的教训）

| 1 | 用户程序打印第一行后 #GP，错误码 0x10（段选择子非法） | `wrmsr` 写入的是 **EDX:EAX 拼接的 64 位值**，而我把 64 位立即数只放进 RAX 并清零 EDX → **STAR 被写成 0** → `sysret` 加载出 CS=0x13/SS=0x0b | 显式把立即数拆成高 32 位（EDX）与低 32 位（EAX） |

| 3 | 链接报 duplicate symbol | `syscall.c` 与 `syscall.asm` 基名相同 → 目标文件路径都是 `syscall.o`，链接时同一文件被传两次 | 目标文件名保留原扩展名（`syscall.c.o` / `syscall.asm.o`） |

### M8 前半：fsd —— FAT32 只读文件系统服务

#### 分层

```
客户端程序 ──IPC──▶ fsd ──IPC──▶ blkd ──端口 I/O──▶ ATA
            (路径/文件)    (扇区/LBA)
```

fsd 完全不碰端口，也不知道 ATA 是什么；blkd 完全不知道什么叫文件。
中间是一条 IPC 协议。**四层每一层都只做自己那一层的事**，
而且每一层的连接都是"按 devfs 路径找服务"，没有一处是人手塞句柄。

#### ★ 本轮只做读，这是刻意的 ★

写路径和保护层是**同一件事**：一旦能写，就必须同时决定"谁能写哪些扇区"——
那正是 `03-protection.md` 里的块层写白名单。把写和强制点分两步做，
结果一定是先落地一个**没有任何约束的写路径**，然后再去补；那时候
所有依赖"先能写"的代码都已经写完了，补强制点的代价会大得多。
只读的 fsd 让这个问题保持敞开，而不是用一个假的安全感把它盖住。

#### 实测

**QEMU 与 VirtualBox 结果完全一致：**

```
[init] 解析出启动顺序: hello → drvtest → drvdeny → bench → blkd → blkread → fsd → fs → kbd → mouse → flaky → depmissing
[fsd] 卷标 "FEKERNEL   "，OEM "FEKERNEL"
[fsd] 每簇 1 扇区，96736 簇（48368 KiB），根目录簇 2
[fsd] 根目录可列出 6 项

=== 文件系统客户端（M8：devfs + IPC + FAT32）===
      OK   通过 devfs 按路径找到文件系统服务
      OK   IPC 取得文件系统信息
           卷标 "FEKERNEL   "，OEM "FEKERNEL"，FAT32，49152 KiB，96736 簇 × 512 字节
    ls /
      [目录] bin / boot / EFI / sbin
             init                          53856 字节
             limine.conf                   785 字节
      OK   根目录可列出且非空          共 6 项
    ls /bin
      [目录] . / ..
             bench / blkread / depmissing / drvdeny / drvtest / fs / hello
      OK   子目录 /bin 可列出且非空    共 9 项
    cat /limine.conf
  ---- 文件内容开始 ----
  # 本文件由 tools/build.py 自动生成，请勿手工修改
  timeout: 3
  interface_branding: FEKernel Bootloader
  ...
      module_path: boot():/sbin/mouse
  /FEKernel (串口调试)
      protocol: limine
      cmdline: debug verbose
  ---- 文件内容结束 ----
      OK   读出一个已知文本文件
      OK   内容包含构建时写入的字符串 "FEKernel"
      OK   内容包含 "protocol: limine"
=== 文件系统客户端结束，失败项 0 ===
```

几点值得指出：

- **启动顺序是算出来的，不是排的**。单元表里 `fs` 声明在**最前面**，
  最终却排到第 8 位——因为它 require `/dev/fs0`，而 `/dev/fs0` 由 fsd 提供，
  fsd 又 require `/dev/blk0`。**三级依赖链由拓扑排序自动解开**。
- **`. ` 和 `..` 被真实列出**（FAT 的子目录里确实存在这两个目录项），
  不是靠代码伪造的——说明目录遍历读的是磁盘上的原始数据。
- **内容做了交叉验证**：只核对"读到了多少字节"是不够的（字节数对、内容错也可能），
  所以核对构建镜像时确实写进去的字符串。

#### 实现要点

| 部分 | 说明 |
|---|---|
| 挂载 | 自己解析 MBR → 分区表 → BPB。**分区表属于文件系统层**，块设备驱动不该知道什么叫分区 |
| FAT 类型判定 | 按**簇数**（<4085 FAT12 / <65525 FAT16 / 否则 FAT32），不是信分区类型字节——那个是"声称"，簇数才是"实际" |
| 簇链 | `fat_next()` 读 4 字节 FAT 项，可能跨扇区，统一按"读两个扇区"处理 |
| 目录 | 按 32 字节目录项遍历；`0x00` = 结束，`0xE5` = 已删除，`0x08` 属性 = 卷标（跳过） |
| 长文件名 | VFAT LFN：`0x0F` 属性的项是分片，按**倒序**出现，按下标回填；UTF-16 → ASCII，非 ASCII 一律 `?`（宁可难看也不假装支持没实现的编码转换） |
| 路径解析 | 逐级分量比对，大小写不敏感，同时比对长名与短名 |

#### 踩到的坑

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | 目录遍历只读了簇的**第一个扇区** | 本镜像每簇恰好 1 扇区，所以没暴露；换个簇大小的卷就会漏掉目录项 | 按 `sec_per_clus` 逐扇区遍历 |
| 2 | 文件读取里写了 `if (sec_per_clus != 1) 报错退出` | 把"我的测试镜像恰好如此"当成了实现的边界 | 改成在簇内按扇区定位（`in_clus / 512`），对大簇也成立 |
| 3 | `fsd` 编译报未声明的 `fs_reply` | 前向声明被我放在了使用它的函数**后面** | 声明提到文件头部 |

第 1、2 条是同一类：**测试数据的形状悄悄变成了实现的假设**。
本镜像每簇 1 扇区是 mkfat.py 为了满足 FAT32 最小簇数而选的，
和 FAT32 规范没有关系；把实现写成依赖这个巧合，换个盘就崩。

#### 交付内容

```
user/servers/fsd/main.c   FAT32 只读服务：MBR/BPB 解析、簇链、目录 + LFN、路径、文件读
user/bin/fs/main.c        客户端：fs ls / fs cat / 无参数时跑固定完整验证
user/servers/blkd/main.c  支持多扇区读（单次上限由 IPC 载荷决定，2 个扇区）
user/bin/init/main.c      单元表加 argv 支持；fsd 声明 require /dev/blk0
```

**IPC 载荷上限 1024 字节是当前的硬边界**：blkd 单次最多回 2 个扇区，
大簇的卷要多次往返。真正的解法是「随消息传一个内存对象、由服务端直接写进去」，
让内核完全不碰数据——那件事和 DMA 一起做，现在够用是因为本卷每簇 1 扇区。

### M7 续：init 的依赖声明服务表（学 BSD 的 rc.d / rcorder）

原先是硬编码数组：

```c
static const char *const g_services[] = { "/sbin/kbd", "/sbin/mouse", "/sbin/blkd" };
```

服务一多就是人肉依赖注入——顺序靠人排，漏一次就是偶发启动失败，
而失败现场（某服务打开某个名字失败）离真正的原因（它被排到了提供者前面）隔着好几层。

改成 BSD 的样子：**每个单元声明 PROVIDE 与 REQUIRE，顺序由 init 算出来**。

```c
struct unit {
    const char *name, *path;
    const char *provides;   /* 就绪标志：devfs 上出现这个名字就算起来了 */
    int daemon;             /* 常驻服务 vs 一次性程序 */
    const char *require[MAX_DEPS];  /* 硬依赖：没就绪 → 跳过本单位 */
    const char *want[MAX_DEPS];     /* 软依赖：没就绪 → 只告警 */
    int expect_skip, expect_unready;/* 负向测试的预期 */
};
```

init 的四步：**静态检查依赖完整性 → 拓扑排序（Kahn）→ 依次启动 → 等依赖方
真的 publish 成功才启动下游**。

#### 实测：声明顺序 ≠ 启动顺序

单元表**故意打乱**声明顺序（`blkread` 排第 0、`blkd` 排第 6、`depmissing` 排第 1），
所以日志里两者不同本身就是排序生效的证据：

```
[init] 单元表: 声明 10 个
        0. blkread  require /dev/blk0
        1. depmissing  require /dev/flaky0
        6. blkd  提供 /dev/blk0  [常驻]
        9. flaky  提供 /dev/flaky0  [常驻]
[init] 解析出启动顺序: hello → drvtest → drvdeny → bench → blkd → blkread → kbd → mouse → flaky → depmissing
[init] 注：启动顺序与声明顺序**不同**，依赖排序起了作用
```

`blkread` 被排到了 `blkd` 后面（满足硬依赖），`depmissing` 被排到最后
（它依赖 `flaky` 提供的名字）。**两个环境跑出完全相同的顺序**。

#### 负向测试：失败路径才是容易写错的那条

依赖机制**最容易错的就是失败路径**——正常路径（依赖都在）随便写写也能跑通，
而"依赖没就绪"这条路上很容易退化成"照跑不误，然后在内部莫名其妙地失败"。
所以专门造了两个夹具：

| 夹具 | 作用 |
|---|---|
| `/sbin/flaky` | 被拉起但**永不发布名字**，模拟"服务启动就挂" |
| `/bin/depmissing` | 硬依赖 `flaky` 提供的名字 → **必须被跳过**；真跑起来就大声报错并返回 99 |

```
[flaky] 我是负向测试夹具：不发布名字，用来验证依赖未就绪时的跳过逻辑
[init] flaky **未就绪**（/dev/flaky0 未出现）
[init] （这是负向测试夹具的**预期结果**，它靠这个构造「依赖未就绪」场景）
[init] 跳过 depmissing：依赖 /dev/flaky0 未就绪（提供者 flaky 没能发布它）
[init] （这是负向测试的**预期结果**）
=== init 结束，失败项 0 ===
```

那句 "!!! depmissing 竟然被运行了 —— 依赖机制失效 !!!" **从未出现**。

顺带一个设计上的修正：我第一版把负向测试写成「依赖一个**没有提供者**的名字」，
那是错的——`preflight` 会在启动任何东西之前就把它当**静态配置错误**报出来，
走的是另一条代码路径，根本测不到"提供者存在但没就绪"这个运行期场景。
所以才有 `flaky` 这个夹具。**测失败路径时，要确保构造的确实是那条路径。**

#### 交付内容

```
user/bin/init/main.c        单元表 + preflight + 拓扑排序 + 就绪等待 + 跳过逻辑
user/bin/depmissing/main.c  负向测试：必须被跳过
user/servers/flaky/main.c   负向测试夹具：起来但永不发布
```

`provides` 用 devfs 名字而不是自造标识符：**就绪的定义就是"它在 /dev 上出现了"**，
不需要再发明一套"服务健康状态"的表示。这也是 devfs 作为命名空间的附带好处——
它同时充当了就绪信号。

### M7：devfs 服务发现 + 块设备（ATA PIO）

**决策回顾**：服务发现问过「内核注册表 / 命名服务进程 / init 分发句柄」三选一，
答复是**「学 BSD」**。BSD 的答案是现成的——**不建注册表**：命名空间就是文件系统
（FreeBSD 的 devfs 把设备暴露成 `/dev` 下的节点，Unix 的服务发布成命名套接字）。

所以做法是：**devfs 是 VFS 的一个后端**（和 ramfs 并列），挂在 `/dev`。
服务把自己的端点发布到一个名字，客户端按路径打开。

```c
long fe_devfs_publish("/dev/blk0", endpoint_handle);   /* 服务侧 */
long fe_devfs_open("/dev/blk0");                        /* 客户端：拿到一条通往它的端点 */
```

**为什么不做成平行的「名字 → 句柄」注册表**：devfs 节点是 VFS 里的一等公民，
天然可列举（`ls /dev` 与 `ls /mnt` 走同一个 `readdir`）、可挂载、可被将来的 WRP
按 inode 施加权限。平行的注册表这三样都得重新造一遍，而且会多出一个与 VFS
语义不总一致的命名空间。

一条安全性质单独说：**同名发布会被拒绝**（`FE_ERR_EXIST`）。否则任何服务都能抢注
`/dev/blk0` 把真服务顶掉，「按路径找服务」立刻退化成「谁先注册谁说了算」。
认领硬件用资源池的互斥语义，认领名字用 devfs 的互斥语义，两者一致。

**为什么第一块块设备走 ATA PIO 而不是 AHCI/virtio**：端口 `0x1F0-0x1F7` 与 `0x3F6`
是**固定**的，不需要 PCI 枚举就能用；PIO 用轮询完成，行为完全确定。
先打通「能读磁盘 → 能解析文件系统 → 保护机制有附着点」这条链，
需要 PCI 的 AHCI / virtio-blk 留给 PCI 枚举之后那一代。

#### 实测（两个环境，同一份镜像）

```
QEMU + WHPX                                      VirtualBox
[blkd] 型号 "QEMU HARDDISK"                      [blkd] 型号 "VBOX HARDDISK"
       LBA28 容量 100352 扇区（49 MiB）                  LBA28 容量 100352 扇区（49 MiB）
[blkd] 分区 0: 类型 ef, 起始 LBA 2048, 98304 扇区  分区 0: 类型 ef, 起始 LBA 2048, 98304 扇区
=== 块设备客户端（M7：devfs + IPC + 分区解析）===
    [1] 按路径打开 /dev/blk0 -> 句柄 1
      OK   通过 devfs 按路径找到块设备服务
      OK   打开不存在的设备名被拒绝
      OK   IPC 取得设备信息
      OK   IPC 读回一个完整扇区（512 字节）
      OK   LBA 0 是合法的 MBR（签名 0x55AA）
      OK   MBR 里找到第一个分区
           分区类型 0xef，起始 LBA 2048，98304 扇区
      OK   读分区引导扇区（非 0 的 LBA）
      OK   分区引导扇区签名 0x55AA
```

两个环境读到的是**同一块盘的同一份数据**，连分区表、簇数、卷标都逐字一致。
这正是「双环境对照」的意义：数字一样，说明看到的是内核与驱动的行为，
而不是某个模拟器的私货。

这条链上没有一环是"提前塞进来的句柄"：`blkread` 只有路径 `/dev/blk0`，
它经由 devfs 找到服务、用 IPC 请求数据、自己解析 MBR 与 BPB。
devfs 没用就找不到服务；端口权限没生效 `blkd` 读不出数据；
IPC 载荷上限不够 512 字节的扇区就装不下。

#### 这一轮踩到的坑

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | `blkd` 读 LBA 0，BPB 字段**全是 0**，但签名 0x55AA 是对的 | **分层摆错了**：分区表解析不属于块设备驱动。LBA 0 是 MBR，FAT32 引导扇区在分区起始处（本镜像 LBA 2048） | 驱动只校验 MBR、只打印分区表原始表项；分区与文件系统的解析交给客户端（将来的 `fsd`）。那个全 0 本身就是这条边界在报错 |
| 2 | QEMU 下 `IDENTIFY` 找不到主盘 | `-machine q35` **没有传统 IDE 控制器**，只有 AHCI；`if=ide` 会被挂到 AHCI 下面，0x1F0 上什么都没有 | QEMU 改用 `-machine pc`（i440fx/PIIX3）——它才有 PIIX IDE。写成显式参数并注明「换回 q35 要等块设备换成 AHCI」 |
| 3 | QEMU 落进 UEFI 内置 Shell 而不是启动 Limine | `ovmf_vars.fd` 是 q35 时期生成的，启动项还指着旧设备路径 | 删掉让它重新生成。**换机器类型必须一并清 NVRAM**，否则启动项会指向不存在的设备 |
| 4 | QEMU 里读出的文件系统是 FAT16、OEM `MSWIN4.1`、没有卷标，而 VirtualBox 里是 FAT32、`FEKERNEL` | QEMU 的 `-drive fat:` 会**现场合成**一个文件系统，合成出来的是 FAT16。两个环境看到的根本不是同一块盘——「换环境对照」于是失去意义 | QEMU 改用我们自己构建的 `disk.img`（与 VBox 同一份）。vvfat 的用处本来是「不用建镜像就能启动」，而我们现在本来就建镜像 |
| 5 | VirtualBox 下 `blkd` 同样找不到主盘 | VBox 虚拟机挂的是 **SATA/AHCI**（`IntelAhci`），ATA PIO 够不着 | 存储控制器改为 PIIX4 IDE。**这个改动必须 `--reset` 重建虚拟机**——存储控制器类型不能在已有虚拟机上改 |

第 1 条和第 4 条是同一类问题的两面：**「谁该知道什么」如果放错了地方，
症状会伪装成「数据不对」**。第 1 条是驱动去解释它不该解释的东西（读出全 0），
第 4 条是测试环境悄悄换了一块语义不同的盘（读出的东西"对"但根本不是我们的盘）。
两条都不是崩溃，都是静默地给出一个看似合理的结果。

#### 交付内容

```
kernel/fs/devfs.c         devfs 后端：名字 → 端点能力的表 + 发布/打开 + 同名互斥
kernel/include/fe/devfs.h
kernel/fs/vfs.c           VFS 接口层（挂载表 + 路径归一化 + 属性转发）
kernel/fs/ramfs.c         initramfs 后端（已退化为纯后端，不再做路径解析）
kernel/include/fe/syscall.h  FE_SYS_DEVFS_PUBLISH / FE_SYS_DEVFS_OPEN
user/servers/blkd/main.c  ATA PIO 块设备服务，发布 /dev/blk0
user/bin/blkread/main.c   客户端：devfs 找服务 → IPC 读盘 → 自己解析 MBR/BPB
user/include/fe_drv.h     libdrv 接口（构建系统按目录分层：servers 才链它）
tools/run_qemu.py         改用真实 disk.img；机器类型 pc；构建镜像
tools/run_vbox.py         存储控制器 SATA/AHCI → PIIX4 IDE
```

顺带把 IPC 的内联载荷上限从 256 提到 1024——一个 ATA 扇区 512 字节，
256 连一个扇区都装不下，服务端就得把一次读拆成两条消息，
而拆消息的边界处理是纯粹的额外复杂度。**这不是长久方案**：
真正的批量传输应该走「随消息传一个内存对象、由服务端直接写进去」，
让内核完全不碰数据，那件事留给 DMA 那一代。

### 双环境验证：QEMU(WHPX) 接入，以及它立刻揪出的一个真 bug

**为什么要第二个环境**：此前所有验证都在 VirtualBox 里做，而 VBox 的节拍源实测只有
49~169 Hz（声明 1000 Hz），调度器自检还出现过一次 12 次一遇的
「睡眠 100 节拍实际 546 节拍」。**只有一个虚拟化环境的样本，无法判断这是内核的问题
还是 VBox 的问题。** QEMU + WHPX 一接上，答案立刻分明。

#### 修复前：同一份内核、同一次启动，两个 TSC 锚定的测量差 10 倍

```
[时间] 节拍校验: 20ms 内 20 个节拍 → 实测 999 Hz（目标 1000 Hz）      ← 启动时
中断投递速率: TSC 计时 100ms 内产生 10 个节拍 (实测 99 Hz / 声明 1000 Hz)  ← 自检时
睡眠请求 100 节拍, 实际 100 节拍；独立时基(TSC)实测 1000 ms          ← 等于 100 Hz
```

#### 根因：自检把系统节拍源重编了，而且不恢复

`schedtest.c` 里为了「把计数速率不对」和「中断投递被限流」两种可能分开，
直接操作了 LAPIC 定时器寄存器：

```c
while (fe_rdtsc() - c0 < tsc_freq / 10) { fe_pause(); }   /* 注释写 "10ms" */
u32 counts_10ms = 0xFFFFFFFFu - cur;                       /* 实际是 100ms 的计数 */
...
fe_lapic_timer_start_periodic(FE_VEC_LAPIC_TIMER, counts_10ms / 10);  /* 拿它重编系统节拍 */
```

两个错误叠在一起：

1. **窗口算错**：`tsc_freq / 10` 是 **100 ms**，不是 10 ms（要 10 ms 得 `/100`）。
   于是数出的计数大 10 倍。
2. **更严重的是污染全局状态**：它拿这个偏大的值**把系统节拍源重编了一遍而且从不恢复**。
   节拍率被静默改成 100 Hz，后面所有以节拍为单位的量——时间片、睡眠、超时——
   全部一起偏，而且**没有任何报错**。在已经退到 8254 的机器（VirtualBox）上，
   它还会把 LAPIC 定时器**重新启动**，造成 LAPIC 与 8254 两个节拍源同时跑，
   `g_ticks` 以两者的合成速率前进。**那个 546 节拍的离群值就是这么来的。**

对得上账：实测 1,251,066 计数 / 94.5 ms（真实 TSC 3187 MHz）= 13,239 计数/ms，
与启动校准的 12,519 计数/ms 是同一个量级——**硬件是好的，启动校准是对的，
是自检把系统改坏了**。

#### 修法：把「改完必须恢复」和「破坏」写在一起

新增两个由**时间子系统自己**提供的入口，自检不再直接碰 LAPIC 寄存器：

```c
/* 按 g_hz 重新武装当前节拍源（LAPIC 周期 / LAPIC TSC-deadline / 8254） */
void fe_time_restart_tick(void);
/* 测一次 LAPIC 计数速率，测完自动恢复节拍源 */
bool fe_time_measure_lapic_rate(u32 *out_counts_10ms);
```

外加：`fe_time_init` 退到 8254 时显式 `fe_lapic_timer_stop()`——
**两个节拍源同时跑不是「快了一点」，而是所有以节拍为单位的量一起失真。**

分工的道理：内核里唯一有权改节拍源编程的应该是时间子系统自己。
自检的职责是**测量并报告**，不是「顺便把系统重编一遍」。

#### 修复后：三个独立测量收敛

**QEMU + WHPX：**

```
[时间] 节拍校验: 20ms 内 20 个节拍 → 实测 999 Hz（目标 1000 Hz）
LAPIC 计数速率实测: 125203 计数/10ms (= 12520 计数/ms)   ← 与启动校准的 12519 吻合
中断投递速率: TSC 计时 100ms 内产生 100 个节拍 (实测 999 Hz)   ← 修复前是 99 Hz
睡眠请求 100 节拍, 实际 100 节拍；独立时基(TSC)实测 100 ms      ← 修复前是 1000 ms
```

两个**独立**测得的 LAPIC 计数速率（启动校准 12519 与自检实测 12520）收敛到同一个值，
说明窗口改对了；节拍率与声明值 1000 Hz 一致。

**VirtualBox（4 次连跑，全部失败项 0）：**

```
中断投递速率: TSC 计时 100ms 内产生 5 个节拍 (实测 49 Hz)
睡眠请求 100 节拍, 实际 100 节拍；独立时基(TSC)实测 1450 ms
```

100 节拍 @ 49 Hz ≈ 2.0 s，实测 1.45 s（速率在运行中会波动）——**两个数字终于自洽了**。
以前是「投递 49 Hz 却声称 100 节拍只花了 1 秒」，两个测量互相打架。

#### 结论

| 问题 | 归属 |
|---|---|
| VBox 节拍投递只有 49~169 Hz | **VirtualBox 的中断投递限流**，内核无责（QEMU 下同一份内核 999 Hz） |
| 「100 节拍实际 546 节拍」的离群值 | **内核 bug**（自检污染节拍源），已修复 |
| 「投递速率与睡眠实测互相矛盾」 | **内核 bug**，同一个根因，已修复 |
| 引导器声明的 TSC 频率偏低约 6% | 引导器/固件（QEMU 声明 2996 MHz，实测 3187 MHz）；不影响以节拍为单位的结论 |

这一轮的教训值得单独记：**自检可以去测量系统，但不能改变系统的状态；
一旦必须临时改变，恢复逻辑要和破坏逻辑写在同一个函数里。**
我此前在资源池自检上已经踩过一次同类问题（自检清空池子后没恢复），
当时只当成个案处理；这次它以一个更隐蔽的形式复现了——
因为节拍率的改变**不会报错**，只会让所有依赖它的量静默偏掉。

### M6 前半：PS/2 键盘与鼠标（两个独立的用户态服务）

**决策**：「允许两个服务分别认领键盘和鼠标。」这句话背后有一个硬件事实必须先说清楚：

| 资源 | 键盘 | 鼠标 | 能否分开 |
|---|---|---|---|
| 中断线 | IRQ1 | IRQ12 | ✅ 天然分开 |
| 端口 | 0x60（数据）/ 0x64（命令/状态） | **同一对** | ❌ 8042 控制器只有一个寄存器对 |

所以「两个服务各自认领自己的设备」在实现上只能落到**「中断各自独占 + 端口共享」**这个组合。
为此资源池补上了两个东西：

1. **可共享区间**：`fe_resource_pool_add_shared()` 放进去的区间，认领后**留在池中**，
   允许多个持有者（上限 4 个）。独占区间仍是「认领即移出」。
2. **控制器锁**：共享区间上配一把锁，用来把「读状态 → 写命令 → 写数据」串起来。

> ★ 这把锁是**协作锁，不是安全边界**。★ 内核无法让一串用户态的端口访问变成原子操作，
> 一个不守规矩的驱动完全可以不申请锁就动手。它防的是「两个都守规矩的服务撞在一起」，
> 也就是实际会发生的那类问题。安全边界是 I/O 权限位图，那是另一回事，别混为一谈。

**没验证到的部分（如实记录）**：

- 鼠标数据包路径：VBox 没有对应的注入命令，没有物理鼠标就没有位移包。
  目前验证到「设备已被 ACK 使能」为止，包解析逻辑（3 字节、bit3 同步）**未经实测**。
- `0xF3`（设采样率）在 VBox 的 8042 模拟上无应答；默认采样率本来就是 100Hz，
  所以不影响功能，但真机上是否响应没有证据。

### M6 前半踩到的坑

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | 键盘初始化「使能扫描 0xF4」读到一个空白应答，之后注入的按键**完全没反应** | PS/2 的 `0xFE` 是 **RESEND**（设备没听懂，要求重发），我没处理，于是「使能扫描」这条命令实际没生效 | `fe_ps2_device_cmd` 遇到 `0xFE` 重发，最多 4 次；并在每条命令前 `flush()` 掉输出缓冲里的陈旧字节 |
| 2 | `[mouse] 设采样率 (0xF3 0x64) -> fe （无 ACK）`——`fe` 是键盘服务的输出 | 控制台是**多个服务共用**的，而每次 `fe_write` 是一次独立系统调用，逐段打印的一行被从中间劈开 | libfe 加**行缓冲**：攒齐一行（遇 `\n` 或缓冲满）才发一次系统调用，行内原子。放在用户态是因为「什么算一行」是输出方的事 |
| 3 | 鼠标的设备命令（0xF4/0xF3）全部读超时，但控制器命令（0xA8/0xA9）都正常 | 初始化顺序错了：先和鼠标对话、最后才开 IRQ12。端口没真正启用时设备不应答 | 照 Linux `i8042` 驱动的顺序：**先开辅助端口 + IRQ，再和设备对话**。改完 0xF4 立刻拿到 ACK |
| 4 | 参数字节的应答同样会撞上 `0xFE`，但被当成「无 ACK」 | 我只在命令字节上做了重发，参数字节没做（协议规定**每个字节都要单独 ACK**） | 新增 `fe_ps2_device_cmd_param`，两个字节都走 flush + 重发 |

第 5 条是这一轮最值得记的：**一个测不到东西的测试，和一个测出问题的测试，必须给出不同的结论**。
把「没测到」报成失败，等于训练人去忽略红色结果；而这个自检恰恰因为偶发误报，
已经骗过我两轮（前面那次报的是「睡眠迟到过多」，症状不同、根因相同）。

### M5 的承重证据：反向测试

只证明「认领之后能跑通」是不够的——那也可能是因为权限位图压根没生效，而 `in` 本来就不检查权限。
所以另有一个**故意越权**的程序 `user/drvdeny/`：它不认领端口就去执行 `in`。

```

        找到模块 /boot/servers/drvdeny.elf（29 KiB）
```

### M5 交付内容

```
kernel/resource.c               硬件资源池：空闲/已认领两组区间 + 切分 + 归还合并
kernel/irq.c                    中断投递：GSI → 通知对象置位；电平线「屏蔽到确认」
kernel/include/fe/gdt.h         TSS 改为「TSS + 6 个 I/O 位图槽位」的整块结构
kernel/include/fe/resource.h    资源种类与认领语义
kernel/include/fe/irq.h         fe_irq_register / fe_irq_ack
kernel/arch/x86_64/syscall.c    新增 5 个能力类系统调用 + 3 个通知类系统调用
user/drvtest/main.c             ring 3 驱动能力测试（端口/MMIO/DMA/中断）
user/drvdeny/main.c             故意越权，验证 #GP 真的会来
user/libfe/libfe.c              端口 I/O 内联封装 + 能力类 syscall 封装
```

**设计要点**：

1. **端口权限是每任务一份**。TSS 的 `iopb_offset` 是相对 TSS 基址的 16 位偏移，所以位图必须紧跟 TSS
   之后（64 KiB 内）。做法是 `struct fe_tss_block { struct fe_tss tss; u8 iopb[6][8193]; }`，
   任务切换时只改 `iopb_offset` 一个 16 位字段——**不搬 8 KiB 位图**，切换开销与位图无关。
   槽位惰性分配：只有真正申请过端口的任务才占用（一共只有 6 个）。
2. **「认领」而不是「申请」**。资源是有限且互斥的：同一段端口不能被两个驱动同时持有。
   资源池里没有的东西——**包括内核自己在用的 COM1**——任何权限都拿不到。
   这是「能力」与「权限检查」的分水岭：权限检查是「我允许你做」，能力是「东西只有一个，先到先得」。
3. **MMIO 必须拒绝可用内存**。若允许把普通内存当 MMIO 映射，驱动就拿到一段可写映射直接改内核
   数据结构，任何权限检查都形同虚设。实现是在 PMM 初始化时留档引导器报告的可用区间。
4. **中断投递到通知对象，不是回调函数**。微内核里内核不执行驱动的代码；中断到达时内核只做
   三件事——置位、唤醒、决定是否暂时屏蔽。回调（Linux 的 `request_irq`）会让驱动代码在内核栈上跑。
5. **电平触发必须「屏蔽到确认」**：先屏蔽中断线，再 EOI，再置位通知。顺序反了会在驱动还没跑到
   之前被同一个中断淹没。边沿触发没有这个问题。
6. **DMA 对象物理连续**，否则设备没法用（散页要靠 IOMMU 拼）。`fe_mem_info` 只对 DMA 对象开放
   ——否则等于给驱动一个「任意内存物理地址」查询接口。

### M5 续：进程模型与根文件系统（学 Linux）

原计划里 M5 只有「驱动能力 ABI」。铺完之后紧接着做了**进程模型**，因为驱动服务
（M6）第一件事就是「init 把各个服务拉起来」，而「怎么拉起一个程序」这件事必须先定下来。

提问时给了三个选项（按模块名 / 内核注册表 id / 跳过 spawn），答复是**「学 Linux」**。
那就照字面做：

| Linux 的做法 | FEKernel 的做法 |
|---|---|
| 可执行文件由**路径**标识 | 同左。没有「模块名」也没有「注册表 id」 |
| 内核启动的最后一步是 exec 根文件系统的 `/init` | 同左。`fe_process_start_init()` 是 `kmain` 的最后一件事 |
| 没有磁盘文件系统时用 **initramfs**：引导器把文件塞进内存，内核解成 rootfs | Limine 模块就是 initramfs，`/init` 与 `/sbin/*` 直接从模块构建 |
| 初始栈放 `argc, argv[], NULL, envp[], NULL` | 同左，字符串也在栈上，用户态 `_start` 写法与 Linux 一致 |
| `wait4` 取子进程退出状态 | `fe_wait`，但**认句柄不认 pid** |
| `pid` 是全局可猜的整数，谁都能 `kill`/`wait` 别人 | spawn 返回新任务的**句柄**（能力），不可伪造，只能 wait 自己持有的任务 |
| `fork` 复制地址空间 | 不做。Linux 自己也在往 `posix_spawn` 靠（glibc 用 `clone(CLONE_VM\|CLONE_VFORK)+execve` 实现） |

**架构上最重要的一条**：内核里再没有一行「运行某个用户程序」的代码了。
原来 `fe_selftest_user()` 里挨个跑 `hello.elf`/`bench.elf` 的编排全部搬进了 `user/init/`，
内核只检查 init 自己的退出码与它留下的异常向量。

启动后的镜像布局也因此长得像一个 Linux 根文件系统：

```
[模块] 共 5 个:
        /sbin/bench (47 KiB)      /sbin/drvdeny (29 KiB)
        /sbin/drvtest (41 KiB)    /sbin/hello (35 KiB)
        /init (35 KiB)
```

### M5 续的交付内容

```
kernel/fs/ramfs.c            根文件系统：由引导模块构建的只读树，父/子/兄弟三叉链
kernel/include/fe/fs.h       路径查找 + 目录遍历 + 模式位（沿用 Linux 的 S_IF* 取值）
kernel/task/process.c        初始栈布局、按路径装载、spawn/wait、init 启动
kernel/include/fe/process.h  进程模型接口（形状对齐 Linux，pid 换成句柄）
kernel/mm/uaccess.c          fe_user_write_space：往**别的**地址空间写（经 HHDM 逐页写）
user/libfe/start.asm         从 rsp 读 argc/argv/envp（与 Linux 的 _start 完全一致）
user/init/main.c             用户态第一个进程：spawn/wait 拉起并校验其余所有程序
tools/build.py               模块路径改为 /init 与 /sbin/<名字>
```

顺带修掉的一个真问题：**任务对象的引用计数是错的**。原来线程只是「指向」任务，
不持有引用，于是父进程一旦关掉子任务的句柄，还在跑的子任务对象就被销毁了；
反过来内核侧创建的任务也从来没人释放（每跑一个程序漏一个任务对象 + 一份地址空间）。
现在线程持有任务引用、任务销毁时回收地址空间，两头都堵上了。

### M5 续踩到的坑

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | init 打印 `spawn /sbin/hello` 之后**永远卡住**，而 hello 明明已经跑完并打出了退出码 | `exit_isr` 里漏了 `fe_process_on_thread_exit()`——线程正常死了，但没人唤醒正在 `wait` 的父进程 | 在 `exit_isr` 挂钩子。选这里是因为它是**所有**线程死亡的唯一必经之路（正常退出/被异常打死/被杀死都走它），挂一处就不会漏 |
| 2 | 编译报 `use of undeclared identifier 'usize'` | `usize` 是用户态 `fe_user.h` 里的类型，内核侧没有（内核用 `uN`） | 内核代码统一用 `u32`/`u64` |
| 3 | 用户程序编译报 `NULL` 未定义 | 没有 libc，`NULL` 得自己给 | 在 `fe_user.h` 里补上 |
| 4 | 调度器自检**偶发**报「睡眠迟到过多」（5 次里 1 次） | 判定上限写死成「3 个时间片 + 2」，但当时有 6 个同级线程在排队，最坏情况要等**两轮**轮转（实测 100 节拍睡成 189 节拍）。这是「一个测试测两件事」：睡眠语义与排队延迟混在同一个数字里 | 硬性约定（**不得早醒**）仍然严格判定；迟到上限改成按「两轮轮转」计算，并在日志里打出竞争者数量 |
| 5 | 改完 4 之后连跑 6 次**仍然全部失败**，日志里还是旧文案 | 用了 `run_vbox.py --no-rebuild`——它复用旧磁盘镜像，**虚拟机里跑的是旧内核**（这个坑早先已经记过一次，这次又踩了） | 验证任何内核改动都必须让 `run_vbox.py` 重新生成镜像；改完先确认产物里有新字符串再下结论 |

第 1 条值得记：症状是「子进程一切正常，父进程却永远等下去」，而**日志里根本看不到错误**——
父进程没有崩，它只是睡着了。这类「沉默的挂起」只能靠沿着同步路径逐个检查钩子来定位：
谁负责唤醒？在哪个函数里？那个函数真的被调用了吗？

第 4、5 条合起来是另一半教训：**一个会偶发误报的自检，比没有自检更糟**——
它训练你去忽略红色的结果。所以判定口径必须能从机制上解释（这里是「两轮轮转」），
而在把它改对之前，先确认你测的确实是新代码。

## M11 前半：句柄传递与批量 IPC（能力模型补成可用）

> 详细设计与理由见 `docs/09-handle-transfer.md`（本文只记交付内容与实测）。

### 为什么这一步排在最前

内核的 `build_message()` 早就会把发送方给的句柄查出来（带 `FE_RIGHT_TRANSFER`
权限检查）放进消息，接收方 `fe_endpoint_recv(..., out_transferred)` 也会把它
安装进自己的句柄表——**但用户态够不着**：`sys_endpoint_send()` 最后传的是 `NULL`，
ABI 里根本没有传句柄的通道。于是用户态服务之间只能靠 1024 字节的内联载荷
交换数据，而块设备"一次最多 2 个扇区"的真正原因就在这里（不是驱动能力限制）。

所以 M11 前半做的不是"加功能"，是**把已经写好的机制接到用户态**。

### 交付内容

```
kernel/arch/x86_64/syscall.c   0x11/0x12 增加句柄数组通道（含"先校验后接收"）
kernel/ipc/ipc.c               传递时记录发送方权限；接收侧按「发送方权限 - TRANSFER」安装
kernel/ipc/ipctest.c           句柄传递 / 句柄复制 两组自检（含 5 条反向对照）
kernel/mm/vmm.c                fe_selftest_vmm_unmap：撤销映射的语义自检
kernel/mm/uaccess.c            fe_copy_str_from_user：有界字符串拷贝（修 EFAULT 真 bug）
kernel/fs/devfs.c              条目记住发布方权限，打开时取交集（修能力泄漏真 bug）
kernel/include/fe/syscall.h    FE_SYS_MEM_UNMAP / FE_SYS_HANDLE_DUP 落地 + 新签名说明
user/include/fe_user.h         权限位、FE_MSG_MAX_HANDLES、新函数原型
user/libfe/libfe.c             新 syscall 包装 + 补上 atoi / fe_snprintf 的实现
user/bin/hxtest/main.c         端到端测试客户端（两个真实任务之间传内存对象）
```


★ **1 MiB / 2000 us 这一行是本轮最值钱的数字** ★
它证明"搬数据"这件事已经和 `FE_MSG_MAX_PAYLOAD = 1024` **完全脱钩**：
载荷只有 16 字节（请求头），1 MiB 走的是页映射，内核一个字节都不碰。
这条上限从此只约束控制面。

### 本轮修掉的两个内核真 bug（都是端到端测试逼出来的）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `spawn` 一个**真实存在**的程序报 `EFAULT` | 路径参数用定长 256 字节从用户指针拷；字符串落在映射区末尾时，往后读 256 字节跨进未映射页 | `fe_copy_str_from_user()`：逐页校验、遇 `'\0'` 即停，**从不读越过终止符的字节** |
| 2 | 服务端"只能收"的端点，别人按名字打开就能**发**（甚至能收走消息） | `fe_devfs_open` 一律装 `SEND\|RECV\|DUP\|TRANSFER`，不保留发布时的权限 → "发布时收窄"只是装饰 | devfs 条目记住发布方**当时**的权限，打开时取交集；反向对照进 `fe_selftest_devfs` |

第 1 条是"潜伏 bug 被新用法照出来"的又一例：它一直存在，只是此前的路径字符串
离页边界都够远。第 2 条更值得记——**它是一处能力泄漏**，
而症状是"一切正常"：没有报错、没有异常，只是别人多了不该有的权限。

### 另外 4 条是"我按习惯猜接口语义"（记在 `09-handle-transfer.md` §7）

句柄号跨任务传（号码不是能力）、把 `fe_endpoint_recv` 的返回值当错误码、
用 `send` 当请求-应答（没有回复端点，应答进黑洞）、分块校验和用 XOR 聚合
导致 16 个相同块互相抵消成 0。四条全部表现为"IPC 不通"，
而根因各不相同——定位它们的唯一有效手段是看**内核侧**的收发追踪。

### 顺带补上的一个"声明了却没实现"

`user/include/fe_user.h` 里宣告了 `atoi` 与 `fe_snprintf`，而 `libfe.c` 里
**从来没有实现**——于是任何调用它们的程序都能编过、到链接时才报
`undefined symbol`。声明而没有实现比"没有这个函数"更糟：读头文件的人
会以为它可用。现在两个实现都补齐了（`fe_snprintf` 按 C 标准返回**本该写入**
的长度，于是调用者能检测截断）。

## M11 续：线程局部存储（TLS）与每线程 `%fs` 基址

> 内核能力矩阵与下一步顺序见 `docs/11-kernel-next.md`（本轮新建）。
> 本文只记这一项本身。

### 为什么它必须在核心里

`__thread` / `thread_local` / libc 的 `errno` 都编译成 `mov %fs:...` 访存，
而 `%fs` 基址是**特权寄存器**、并且必须**每线程一份**：

- 用户态不能写 `IA32_FS_BASE`（特权指令）；
- 它必须在**每次线程切换时**跟着换，否则两个线程会看到同一份 TLS
  ——那正是"线程局部变量莫名其妙变了"这类只在多线程下出现的错。

★ **为什么用户的 TLS 落在 `%fs` 而不是 `%gs`** ★
我们的 `%gs` 已经被内核拿去做每 CPU 的 syscall 暂存区（`gs:0`/`gs:8`），
而且 syscall 入口**不做 swapgs**。Linux 在 x86-64 上的分工正好相反
（`%fs` 给 per-CPU、`%gs` 给用户 TLS），所以那边的汇编片段不能照搬。

### 内核做了三件事

```
kernel/ld/elf.c          解析 PT_TLS：记下初始化映像、p_memsz、对齐
                         （用 p_memsz 而不是 p_filesz：多出来的是 .tbss，
                           用 p_filesz 的后果是"某个 __thread 变量带着上一个线程的值"）
kernel/include/fe/task.h 映像挂在**任务**上（新建线程时早已找不到 ELF）
kernel/sched/sched.c     每线程分配一块：复制映像、写 %fs:0 自我指针、填 user_fs_base
                         切换时 wrmsr(IA32_FS_BASE, next->user_fs_base)
```

### 实测（双环境，`fe_selftest_tls`）

```
QEMU + WHPX 与 VirtualBox 7.2 输出一致：
  两个线程的 TLS 块不同: 0xffffffffa0012000 / 0xffffffffa001a000（相差 32768 字节）
  两个线程往同一个 TLS 偏移各写自己的值、交叉让出 128 次：互不可见
  TLS 初始化映像已复制（0x1122334455667788 / 0x99aabbccddeeff00），块 4160 字节含 TCB 64 字节
  当前线程 main 的 TLS 基址 0xffffffffa0004040
  => TLS 失败项: 0
```

三条断言各自对应一类真实错误（**这就是反向对照**）：

| 断言 | 它排除的错误 |
|---|---|
| 两块 TLS **不同** | "`%fs` 基址没跟着线程换"——值碰巧相同只是运气，基址相同一定是机制没生效 |
| 交叉让出 128 次后**互不可见** | "两个线程共用一份 TLS"——只在多线程下现形 |
| 初始化映像**已复制** | "`PT_TLS` 没被处理"——`__thread` 初值全是垃圾 |

### 本轮踩的坑：内核线程那条路径漏了

第一版只在 ring3 的创建路径上装了 TLS，结果内核线程跑起来时 `%fs` 仍是 0，
第一次访存就 **内核 `#PF`（出错地址 0x0）**。

教训与 FPU 状态区是同一条：**"没有"不能靠"不设"来表达**——
切换路径不区分线程种类，它会把上一个线程的值留在这儿。
所以 `fe_thread_create`（内核线程）、`fe_thread_create_ring3`（用户线程）、
以及 `fe_sched_init` 里**手工造的 main 线程**（它不走 create、复用引导栈）
三处都要装。自检里那条"当前线程 main 的 TLS 基址"就是为了不让这种半成品漏过去。

## M12：按需分页与栈自动增长（K1）

> 设计、机制、三条 bug 的完整记录见 `docs/11-kernel-next.md` §6–§7。

### 之前为什么做不了

用户内存是**启动时全预映射**的：ELF 的 `p_memsz` 逐页分配并映射、栈一次映射
64 KiB。于是三件事无从表达：栈不能自动增长（用超就是死）、大 BSS 必须全映射
（声明 64 MiB 就真占 64 MiB）、任何 `mmap` 语义都不成立。而 `#PF` 只有一条路：
杀线程——因为它无从判断"这次缺页是不是合法的"。

### 现在有什么

**区间表（VMA）**回答那个问题："这个地址**被允许**存在映射吗？按什么权限？"
VMA 与页表的分工是硬边界：
**VMA = 意图**（这段地址属于什么），**页表 = 事实**（这一页现在有没有帧）。
"区间里只有一部分页有映射"是按需分页的正常状态；
"页表里有映射而区间里没有"才是非法状态。

**`#PF` 的两条出路**：落在可增长区间内 → 补一页、`iretq` 回原现场继续跑；
否则仍然杀线程。补页只承认三种情况（栈的紧邻下方一页 / 匿名区间 / 有后备帧的区间），
其余一律拒绝——**一个"什么缺页都补"的实现会把段错误变成静默的内存增长**。

**只预映射栈顶 4 页**，其余留给 `#PF`：程序一用到更深处就真的走一次增长路径。

### 实测（双环境，同一份镜像）

内核自检：`按需分页失败项: 0`、`区间表失败项: 0`（8 项按需分页含 7 条反向对照、
9 项区间表性质），另有既有 13 组自检全部 0 失败。

端到端（`user/bin/posixprobe` 递归到栈的深处）：

```
[posixprobe]   递归 700 层（每层约 96 字节栈）……
[posixprobe]   递归完成，内核解析缺页 5 次（栈是**长**出来的，不是预映射的）
[init] posixprobe 退出码 = 0  期望 0  —— 相符
```

★ 这一条为什么必须有 ★ "栈能长"有两种实现：(a) 真按需补页；
(b) 一开始就把整个保留区映射好。**从用户态看两者行为完全一样**——都不崩。
只有新增的 `FE_SYS_PF_STAT`（累计解析次数）能把它们分开：`>0` 才说明是 (a)。

### 本轮撞出来的三个 bug（都是"看起来在工作"）

| # | 症状 | 根因 |
|---|---|---|
| 1 | **一次成功的缺页解析被当成致命异常，系统 panic** | `fe_isr_dispatch` 里 `user_fault(r)` 之后**缺 `return`**。该函数原来标 `FE_NORETURN`（所以不需要），加了按需分页后它有了"正常返回"这条结局，于是成功路径直接落到 `exception_fatal`。症状误导性极强：panic 打印的是**用户态**现场，看起来像"用户程序把内核弄崩了" |
| 2 | 栈"能补页"却**永远长不动** | 栈区间建成整个保留范围 → 要增长的地址本来就在区间里 → 命中的是"区间内补页"分支；而增长分支又要求"地址不在区间内"。两个条件互相矛盾，增长代码是死代码。修法：区间只覆盖**已映射**段 |
| 3 | 删中间一段后，前半段整段消失 | `fe_vma_remove_range` 的锚点写成 `end < v->end`（切尾）——移除范围恰好到区间末尾时为假，"从内部开始、到末尾结束"于是被当成"只切头"，把头整个砍掉。正确判据是"区间在移除范围左侧/右侧**有没有剩**" |

**另外两个附带发现也修了**（都值得记）：

- **`exception_fatal` 会因读用户栈而二次异常**：它直接解引用 `r->rsp`，
  而用户栈越界时那就是**未映射的用户指针** → 内核态 `#PF` → 再进
  `exception_fatal` → 递归到栈耗尽。**任何用户程序的栈溢出都能把内核带崩。**
  修法：只在内核栈范围内才 dump。教训是"诊断代码也必须遵守
  「异常处理是终点、不能自己再出异常」这条纪律"。
- **区间表指针会被插入失效**：`fe_vma_add` 会 memmove 数组，
  旧指针于是指向别的区间。实测踩到：测试里拿旧指针继续用，
  "撞邻居"该报 `NOSPC` 却报成 `NOTSUP`。修法：加下标版查找，
  **跨插入/删除一律用下标**。

★ 这三个 bug 有一个共同点 ★ 它们都让机制"看起来在工作"：
自检里那些**只检查正向**的断言全都过了，是**反向对照**把它们逼出来的
（"跳过保留区不补页""撞邻居被拒""越界仍然杀线程"）。
这与项目里那条老结论一致：**没有反向对照的自检，等于没有自检。**

## M14：磁盘 DMA + 共享内存批量（D4，virtio-blk）

完整设计与实测见 `12-drivers.md` §9；这里只记**验收口径**和
**这一轮真正值钱的东西**。

### 验收口径

| 项 | 要求 | 实测（QEMU + WHPX） |
|---|---|---|
| 每 KiB 搬运成本 | 批量路径至少比内联路径低 **4 倍**（写成断言，可失败） | **103 倍**：130416 → 1266 周期/KiB |
| 折算吞吐 | 目标是 200 MB/s 量级 | 21 → **2253 MiB/s** |
| "走的是 DMA" | 必须有独立于吞吐数字的证据 | 毒值差分（每个字节都被写过）+ 跨路径对照（读的是这一段）+ MMIO 窗口被驱动独占 |
| 反向对照 | ≥4 条 | 4 条：MMIO 窗口不可映射 / 普通内存冒充 DMA 缓冲被拒(4) / 越界 LBA 被拒(3) / 长度两个方向被拒(3) |
| 老路径不受影响 | `blkread`、`fsd` 一行不改 | ✅ 块协议与 `blk_info` 前缀未变 |

### 这一轮真正值钱的三件事

1. **"这台机器上没有那样硬件"被承认成一个独立的类别。** `struct unit` 多了
   `needs` 字段。三种"没启动"必须分开，否则 `失败项 N` 这条汇总在不同机器上
   含义不同：依赖没就绪（算失败）、负向测试的预期跳过（是**测试结论**）、
   硬件前提不成立（**既不是缺陷也不是测试**）。而且判据要在依赖检查**之前**判，
   否则报出来的是由它派生的假原因——**报错指向错误的原因是排查里最贵的一种浪费**。
2. **三处"测试自己的错"比被测对象的错更难发现**：一条断言照着一句
   **与实现不符的注释**写（断言假装有一道不存在的护栏，于是一个正确的驱动被判红）；
   一处测试代码自己手搓协议还搓错了（"失败"说明的是测试自己的 bug）；
   一处计时器分辨率不够（两个数字都是 `5000 us`，正好一个时钟刻度）。
   这三条的共同教训：**测试也是代码，它说的每句话同样要有证据。**
3. **一个只在 VirtualBox 上复现的内核竞态**：`fe_resource_note_init` 原先写在
   `fe_process_create` 返回之后，而新线程在它返回之前就已可运行（`rq_push`）。
   QEMU 上从不出现、VBox 上每次出现，症状是"内核自检全过、用户态整个没起来"——
   这是最容易误判的一种形状。修法与代价见 `11-kernel-next.md` §9。

### 边界

- **VBox 上这两条结论不成立**（那边没有 virtio-blk 设备），日志里明说，
  不是悄悄少几行；
- 批量路径**只读**，没有批量写；
- **同一个驱动跑两个实例**（`/dev/blk0` = IDE 系统盘、`/dev/vblk0` = virtio 数据盘），
  块协议里没有"设备号"——那是上层概念，今天没有消费者；
- `wait_any` 的用户态 ABI 仍然挂着：virtio 的完成判据是 used ring 下标，
  **它并不需要"等中断与等请求合流"**，所以 §8 预期的那个"第一个真实调用者"
  实测没有出现。**不要为了兑现文档里的一句话而造一个调用者。**
