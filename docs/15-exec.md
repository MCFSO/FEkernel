# 替换映像（K6：`exec`）

> 今天"换个程序跑"只有一个办法：`fe_process_spawn`——**新建一个任务**。
> 而那意味着**能力全丢**：新任务有新的句柄表、新的设备认领、新的 devfs 名字、
> 新的资源池身份。于是"服务换一版、但还叫 `/dev/vblk0`"这件事今天做不到，
> "shell 跑一条命令"也做不到（命令跑完，它认领的东西全散了）。
>
> 本文只处理内核机制：**同一个执行体，换掉它当前跑的那份程序**。
> 先写"为什么这样做 / 代价是什么 / 什么时候会咬人"，再写实现清单。

## 1. 判据：这一项挡谁

`11-kernel-next.md` 的 C1 写着用户态执行模型要完整，其中一条是
**"创建 / 替换映像"**。创建（`SPAWN`）有了，替换（`exec`）没有。

| 谁 | 今天怎么绕 | 绕不过去的地方 |
|---|---|---|
| 服务升级（A/B 更新） | 只能"新任务起来 + 老任务死掉" | devfs 名字、端点、设备认领都换了主人；父进程还得从外面协调 |
| shell / 任何命令执行 | 只能 spawn 一个新进程 | 无法"替换自己"，于是 `sh` 只能是"拉一个子进程然后等"的集合 |
| D6 `drvhost`（驱动宿主） | 加载驱动 = 新任务 | 宿主想"我变成这个驱动"就不行；每个驱动都要重新认领一遍硬件 |

★ 这三条有一个共同点 ★ 它们要的都是**身份不变、映像变**。所以 `exec` 的
设计问题不是"怎么装载一个 ELF"（那部分 `fe_process_create` 已经做完了），
而是**"身份"在这个内核里到底是什么，以及在哪些地方它和"映像"绑在了一起**。

## 2. 决定一：身份 = 任务，映像 = 任务当前的地址空间

在这个内核里，"身份"具体是这些：

- 句柄表（`task->handles`）——端点、通知、内存对象、任务句柄；
- 设备认领与资源池归属（按任务 id 记的）；
- devfs 里的名字（发布时记的是任务 id）；
- TSS 的 I/O 位图槽位与已授予端口（`iopb_slot` / `granted_ports`）；
- 任务 id 本身（`ps`、`RESOURCE_GRANT_ID`、`TASK_TERMINATE` 都认它）；
- 父子关系（父进程 `WAIT` 的是一个**任务句柄**）；
- 保护模块的"更新器豁免"（按任务 id 钉死、不可撤销，见 §6.5）。

而"映像"具体是这些：

- `task->space`（页表）；
- `task->vmas`（区间表：按需分页的"意图"）；
- `task->user_map_next` / `user_stack_next` / `stack_low`（分配指针与栈已长到哪）；
- 主线程的入口与用户栈（**在返回帧里**，见 §3）；
- `task->tls_init / tls_size / tls_align`（新线程的 TLS 模板，指向映像内部）；
- 每个线程的 TLS 块与 FPU 状态区。

**所以 `exec` = 换掉上面这一整组，其它一个字都不动。** 这就是它和
`spawn` 的本质区别，也是"服务换一版还叫同一个名字"能成立的原因。

★ 但"一个字都不动"里有一个例外，必须单独处理 ★ 见 §6.5：
凡是**按身份钉死的授权**（今天就有一个是保护模块的更新器豁免），
换映像时都不能默认它跟着人走——要么显式重新判定，要么直接拒绝。

### 为什么不走"新建任务 + 传句柄"

`spawn` + 句柄传递（`09-handle-transfer.md` 那套）在**功能上**能拼出一个
近似效果，但拼出来的东西是错的：

1. 它是**两步**，中间有一个"新的已经起来、老的还没死"的窗口。窗口里
   devfs 名字归属谁？资源池认领算谁的？这个中间态**没有正确的答案**。
2. 任务 id 会变。`RESOURCE_GRANT_ID` 是拿 id 授权的，`TASK_TERMINATE`
   也是拿 id 认人的——id 变一次，所有外部的引用都要跟着更新一遍，
   而"更新一遍"就意味着每一个持有者都可能漏掉。
3. 做不到"原子"：`exec` 失败时原程序必须**完好无损**（§4），
   而"新任务起来了但最后一步失败"要么留下半个服务，要么要写回滚代码。

代价如实说：`exec` 换不掉任务 id，于是**"一个任务的历史"会在 `ps` 里
连续下去**（同一个 id 先后跑过两个程序）。诊断时要意识到这一点。

## 3. 决定二：换映像 = 改**栈上的那个返回帧**

这是本内核里 `exec` 便宜的原因，值得单独说清楚。

所有上下文切换都发生在返回路径上：中断与 `syscall` 都把现场压成一个
`struct fe_regs` 帧，调度器只是"换一个 rsp"，返回路径照常弹寄存器、
`iretq` 或 `sysret`（`kernel/arch/x86_64/syscall.asm`）。
帧里有 `rip / cs / rflags / rsp / ss`（`kernel/include/fe/regs.h`）。

于是"让当前线程回到用户态时从**别的地方**开始跑"这件事，落到实现上就是：

```
帧->rip    = 新映像的入口
帧->rsp    = 新栈的初始 rsp（argc 在那里）
帧->rflags = 一个规范值（见 §6.2）
（CS/SS 不动：它们是入口桩压进去的固定用户选择子）
```

**为什么这在本内核里成立**：`sysret` 路径正是从帧里读 `[rsp]`（rip）、
`[rsp+16]`（rflags）、`[rsp+24]`（rsp）——它**本来就只认帧**。所以不需要
任何汇编蹦床（trampoline）：Linux 要在内核栈上搭一段恢复现场、
再 `ret` 到用户入口，我们这里"帧就是权威"。

**代价有两条，都要认**：

1. **`exec` 只能从 `syscall` 路径发起。** 它依赖"当前这次返回会经过这个帧"。
   从异常路径（比如异常处理者内部）发起需要另一套写法，今天不做。
2. 它是本内核**第一个需要改返回帧的系统调用**。分发函数今天只有
   `r->rax = ret` 这一个出口，`exec` 要把整个 `struct fe_regs *` 传进去。
   这会让"哪个系统调用会改现场"变成一件必须显式说明的事——
   所以签名写成 `sys_exec(struct fe_regs *r, ...)`，让它在调用点就看得见。

## 4. 决定三：**先准备，后提交**

`exec` 必须保证 Linux 也保证的那条性质：

> **失败时原程序继续跑，就像什么都没发生过。**

这条性质不是"更好"，是**可用性的前提**：`exec` 是唯一一个"我可能失败、
但你还能接着用我"的操作，`sh` 靠它执行命令、`exectest` 靠它测回滚（§10）。

于是整个操作切成两段：

**准备（全部可能失败的事都在这里，此时还没动自己）**

1. 从用户态拷 path（`fe_copy_str_from_user`）——逐页校验、遇 `\0` 停；
2. 拷 argv 进内核缓冲（`copy_user_argv`，与 `SPAWN` **复用同一个函数**，
   于是 `FE_ARGV_MAX=16` / `FE_ARG_MAX=128` 这两个上限也只有一份定义）；
3. `fe_vfs_lookup` + `is_dir` / `is_exec` / `data` 三重检查；
4. 建**候选地址空间**与候选区间表；
5. 在候选空间里：建栈、装载 ELF、构造初始栈（argv/envp 布局与 `SPAWN`
   完全一致——同一段代码，见 §5）。

**提交（除第一步外都是不能失败的操作）**

★ 提交阶段的第一步是**唯一可能失败**的那一步 ★ 杀其它线程并等它们死透
（§8 第 1 条；机制见 `13-tasks-and-kill.md` §6）。于是顺序被钉死为
**"准备成功 → 杀 → 换 CR3"**：杀**不能**提前到准备里做（准备可能失败，
那时不该已经杀过人），也**不能**放到换 CR3 之后（那时还在内核里的受害者
会拿旧映像的用户指针写新空间）。它失败时返回 `FE_ERR_TIMEOUT`，而且
**不可回滚**——`exec` 没做成，但进程已经残缺（被标记的线程下一次经过
闸门时死掉）。这是本文里唯一一处"失败之后原程序不再完好"。

6. 换 CR3 到候选空间（`fe_vmm_switch`）；
7. 把候选现场**挂**到任务上（§5 的 `fe_task_attach_space`）；
8. 重建调用者线程的 TLS 块、换 FPU 状态区（§6.3、§6.4）；
9. 写帧（§3）、更新名字与保护模块的"谁是更新器"（§6.5）；
10. 放掉旧空间（**必须在第 6 步之后**，见 §6.6）。

★ 准备阶段还在旧空间里跑，这件事顺带解决了一整类问题 ★
path 与 argv 都是**旧空间里的用户指针**，而它们在第 1、2 步就被拷进了
内核缓冲；候选栈是在这之后、用内核缓冲里的字符串写进去的。
所以"换个空间之后用户指针就失效了"这个坑**根本没有机会出现**——
不需要为 `exec` 另立一条"必须先拷字符串"的规矩。

## 5. 决定四：准备阶段**不许碰任务对象**

这是本轮最容易写错、也最值得先写下来的一条。

`fe_elf_load(struct fe_task *t, ...)` 今天不是纯函数：它把
`t->tls_init / tls_size / tls_align` 一并写好（`kernel/ld/elf.c:55-57`），
`fe_user_map_stack(t, ...)` 同样顺手写 `t->vmas` 与 `t->stack_low`
（`kernel/task/user.c:432`）。

在 `SPAWN` 里这没问题——那个任务本来就是刚生的，改坏了就销毁。
但 `exec` 的准备阶段一旦失败，**原程序还活着**，而它的
`tls_init` 已经指向了另一个程序的映像。症状是**离原因最远的那种**：

> 原程序安然无恙地继续跑；等到它**下一次创建线程**时，
> 新线程的 TLS 块是从别人的映像里拷出来的 → 线程局部变量读到垃圾。
> 而这个时刻可能离那次失败的 `exec` 几百万条指令。

所以准备路径要改成对**候选现场**操作，而不是对任务操作：

```c
/* 候选现场：准备出来的东西全在这里，任务对象在提交前不动 */
struct fe_new_image {
    struct fe_address_space *as;
    struct fe_vma_table      *vmas;
    u64 stack_low, user_map_next, user_stack_next;
    u64 entry, sp;                  /* 帧要写的两个值 */
    const void *tls_init; u64 tls_size, tls_align;
    char name[FE_TASK_NAME_MAX];    /* 新映像的 basename */
    bool ready;
};
```

三个"准备"函数因此各开一个口子：

| 今天 | 改成 | 调用者（全部，已核对） |
|---|---|---|
| `fe_elf_load(t, elf, size, &entry)` | `fe_elf_load(as, vmas, elf, size, &entry, &tls_out)` | `process.c:173`、自检 |
| `fe_user_map_stack(t, top, size)` | `fe_user_map_stack(as, vmas, top, size, &stack_low)` | `process.c:167/462`、`user.c:249/511` |
| `build_initial_stack(t, path, argv, argc, &sp)` | `build_initial_stack(as, ...)` | `process.c` 内部 3 处 |

**代价**：动了三个函数的签名，其中两个是导出函数（`fe/user.h`）。
**收益**：`SPAWN` 与 `exec` 走**同一条**装载路径——两次写"怎么把 ELF 变成
一个能跑的进程"是必然要出错的（本项目已经有过一次教训：
`FE_TASK_STRIDE` 在两个头文件里各写一遍，写法不一致，直到有人真的枚举任务
才暴露）。

提交时用一个函数把这组字段一次性挂上去，**不要逐项赋值**：

```c
void fe_task_attach_space(struct fe_task *t, const struct fe_new_image *img);
```

理由是"漏掉一项"的症状各不相同且都很难查：

| 漏掉 | 症状 |
|---|---|
| `vmas` | 新程序第一次 `#PF` 时区间表是旧程序的 → 该补的页不补 / 不该补的补了 |
| `stack_low` | 栈"长不动"或"一长就越过保留区" |
| `user_map_next` | 新程序第一次 `mmap` 落进旧程序的地址范围 |
| `space` | 当然是最明显的（回到旧程序） |

所以 `fe_process_create` 也改用这个函数——**一处定义，两处使用**。

## 6. 那些"不写下来一定会错"的细节

### 6.1 帧里的 `rax`

`sys_exec` 成功时不再返回，但 `r->rax` 仍会被分发函数写成返回值。
新程序从入口开始时不需要任何寄存器约定（它只认栈上的 argc/argv），
所以这里**不设**特殊约定——但要在注释里写明"成功路径上 `rax` 是垃圾"，
免得以后有人写出依赖它的小聪明。

### 6.2 `rflags` 必须置成规范值

帧里的 `rflags` 是**旧程序**在 `syscall` 时的值。直接留着会有两个问题：

- 旧程序如果设了 **DF**，新程序一进来就是"字符串操作反向"——
  这是 C 代码里最难查的一类错（`memcpy` 变成从后往前拷）；
- 旧程序如果设了 TF/AC/IOPL，新映像会继承这些**权限位**，
  而"换了一份可能不完全可信的映像却继承旧映像的 I/O 特权"是错的。

所以提交时写死 `rflags = 0x202`（IF | 保留位 1），其余全清。
**代价**：`exec` 后新程序不能继承任何 `rflags` 设置——这正是我们要的。

### 6.3 FPU 状态区要换一块新的

`fe_fpu_area_alloc()` 返回的是**初始化成干净状态**的区
（`kernel/include/fe/fpu.h` 写明："这不是可选项"）。
`exec` 里必须 `fe_fpu_area_free(旧)` + `fe_fpu_area_alloc()`。

不这么做的后果是**跨映像信息泄漏**：旧程序留在 XMM/YMM 里的数据
（可能是一段密钥、一次口令比较的中间值）会被新映像的第一条
`movaps` 读出来。用户态**不能**自己清（`XRSTOR` 需要一块合法状态区，
而 `XCR0` 是特权寄存器），所以这件事只能由 `exec` 做。
撤销分配失败（返回 NULL）时按 `fpu.h` 的约定走"恢复成干净状态"那条路，
**不允许**为了"保证有区"而继续用旧的那块。

### 6.4 TLS 块要重建，而那个函数今天是 `static`

`thread_setup_user_tls()` 在 `kernel/sched/sched.c:187`，是 `static`，
而且它读的正是 `task->tls_*`——也就是 §5 里"准备阶段不许改"的那三个字段。

`exec` 的提交阶段必须：换掉 `task->tls_*`（改成候选现场的）→ 释放旧 TLS 块
→ 重建调用者线程的块 → 更新 `user_fs_base`。

★ 为什么不自己再写一份 ★ 因为"TLS 块长什么样"是一个已经写在两处注释里的
约定（`%fs:0` 指向块首，块首是数据段起始，见 `fe/user.h` 的
`FE_TLS_SELF_OFFSET` 说明）。再抄一份就是第三处，而这三处不一致的症状是
"线程局部变量读到别人的值"——`fe_selftest_tls` 当初就是为这一类错写的。
所以把 `thread_setup_user_tls` 导出成 `fe_thread_tls_rebuild(struct fe_thread *)`，
`exec` 只调它。

另外注意：TLS 块在内核堆上，`%fs` 基址是它的**内核线性地址**；
本内核的内核映射在**所有**地址空间里完全一致（`00-architecture.md` §2），
所以它跨这次 CR3 切换仍然有效。这条前提如果哪一天变了，`exec` 与
线程切换会同一天坏掉——值得记住它们共用这个前提。

### 6.5 名字与"谁是更新器"

- `t->name` 要换成新映像的 basename。不换的话 `ps` 会长期撒谎，
  而 `ps` 正是 K3 那一轮做出来的诊断工具——**诊断工具撒谎比没有更坏**。
- **保护模块的更新器身份必须挡住 `exec` 的两个方向。** 这一条不是"顺便
  记一下"，`kernel/protect.c` 的实现让 `exec` 在这里开了一个真的口子：

  ```c
  void fe_protect_note_process(const char *path, u64 task_id)
  {
      if (!path || !g_updater_path[0] || g_updater_task != 0) return;  /* 先到先得 */
      if (strcmp(path, g_updater_path) != 0) return;                   /* 按路径匹配 */
      g_updater_task = task_id;                                        /* 不可撤销 */
  }
  ```

  也就是说豁免是**按任务 id 钉死的、先到先得、没有撤销接口**。它背后那条
  推理是"**一个任务跑的就是它启动时那个映像**"——而 `exec` 恰恰否掉了这个
  前提。两个方向都出事：

  | 方向 | 后果 |
  |---|---|
  | 更新器任务 `exec` 成别的程序 | 它**仍然**能碰另一个槽（撤不掉）。于是"谁在写 B 槽"和"谁拿着更新器豁免"可以是两件事 |
  | 别的任务 `exec` 成更新器映像 | 如果更新器身份还没被认领，它就**拿到了豁免**——而且是**叠加**在自己原有能力上的（spawn 不会：子任务是干净的） |

  所以规则定为：**更新器身份既不能由 `exec` 得到，也不能由 `exec` 丢掉。**
  提交前两个判断，任一成立就 `FE_ERR_NOTSUP` 拒绝：
  调用者是当前更新器任务；或新映像路径等于清单里的更新器路径。

  代价如实说：更新器**不能换映像**（今天它是个短命程序，无所谓）。
  将来真要"更新器换一版"，正确做法是在 `protect.c` 里把豁免改成
  **跟着映像走**（加"重新指定 / 撤销"），而不是让 `exec` 悄悄改变权限。
  这一条与 §5 是同一类东西：**系统里凡是"按身份钉死"的授权，
  换映像都必须显式处理**，不能默认它跟着人走。

### 6.6 旧空间的释放顺序：**先换 CR3，再放旧空间**

反过来的写法（先 `fe_object_unref(旧 space)` 再 `fe_vmm_switch`）意味着
**释放正在使用的页表**。这条路上我们已经交过一次学费：K2/K3 那一轮，
空闲线程在 CR3 还指着某个地址空间的时候把它销毁了，症状先是
"用户线程在自己的代码地址上 `#PF`"，接着是
`fe_pmm_free_frames 参数非法: base=0x0`（见 `sched.c:425` 那段注释）。
`fe_vmm_space_destroy` 现在有一条"正在销毁当前 CR3"的告警，
它的存在就是为了让这个顺序错误**当场可见**，而不是几步之后才炸。

同时：换 CR3 之后我们现在跑在新空间里，而内核栈在**内核映射**里
（所有空间一致），所以此时释放旧空间是安全的。这条推理依赖的正是 §6.4
结尾那条前提。

### 6.7 CR3 由谁切（以及为什么调度器帮不上忙）

`fe_sched_maybe_switch` 只在**切换到另一个线程**时比较两个任务的 `space`
并切 CR3（`sched.c:441-445`）。`exec` 之后当前线程没换，只是它任务的
`space` 变了——所以**调度器不会替我们切**，`exec` 必须自己调
`fe_vmm_switch`。而这一调用之后，下一次调度看到的 `prev_as` 与 `next_as`
都已经是新空间（它们都从 `task->space` 读），于是比较结果相等、不再切换——
这正是我们要的：CR3 与"任务认为自己是谁"始终一致。

## 7. ABI

```c
/* fe/syscall.h */
#define FE_SYS_EXEC  0x90          /* (path, argv, argc) —— 成功不返回 */
#define FE_SYS_MAX   0x91
```

```c
/* user/include/fe_user.h + libfe */
/* 用新映像替换当前程序。成功时**不返回**；失败返回负错误码，原程序继续跑。 */
static inline int fe_exec(const char *path, char *const argv[], unsigned argc);
```

参数形状与 `SPAWN` **完全一致**（`user_path`、`user_argv`、`argc`），
理由：两者干的是同一件事（把一份映像变成"正在跑的程序"），
让调用者只需要记一套规矩；实现里也复用同一个 `copy_user_argv`。

错误码（除 `FE_ERR_TIMEOUT` 外全部在**准备**阶段产生，返回后原程序完好；
那一个例外产生在**提交阶段的第一步**——杀其它线程——而且**不可回滚**，
原因就写在它自己那一行里）：

| 码 | 什么时候 |
|---|---|
| `FE_ERR_INVAL` | path 为空 / `argc > FE_ARGV_MAX` / 调用者不是本任务的主线程 |
| `FE_ERR_NOENT` | 路径不存在 |
| `FE_ERR_ISDIR` | 是个目录 |
| `FE_ERR_NOTSUP` | 文件在，但没有可执行位（与 `SPAWN` 同义，对应 Linux 的 `ENOEXEC`）；**或触及更新器身份**（§6.5：调用者就是更新器，或新映像就是更新器路径） |
| `FE_ERR_NAMETOOLONG` | 路径过长 / 某条 argv 超过 `FE_ARG_MAX` / 字符串没终止符 |
| `FE_ERR_NOMEM` | 建空间 / 装载 / 建栈时内存不足 |
| `FE_ERR_TIMEOUT` | **唯一一个不在准备阶段产生的错误**（发生在提交阶段的第一步）：叫停其它线程之后，有线程在 `FE_EXEC_KILL_ROUNDS`（= **200000** 次让出，见 `13-tasks-and-kill.md` §6.4）内没有走到 `DEAD`。今天能落到这里的有两种：卡在没有取消点的等待上，或睡在一个很长的 `SLEEP` 上。内核会先打一行日志直接指认凶手（卡住线程的 `name`/`id`/`state` + 它登记的等待点），并明说"这个进程已经残缺"。此时**已经有线程被标记"必须死"，且标记不撤回**，原程序不再完好——见 §8 第 1 条与 `13-tasks-and-kill.md` §6.4 |

★ `FE_ERR_BUSY` 从这张表里**消失**了，但它没有从 ABI 里消失 ★
多线程不再是拒绝 `exec` 的理由（§8 第 1 条）。`BUSY` 留给它真正存在的
三个场景：中断线的第二次登记（`kernel/irq.c:217`）、独占资源被别人先占
（`kernel/resource.c:237`）、同一线程对共享区间重复加锁这种调用方 bug
（`kernel/resource.c:576`）。`exec` 里不再有"忙"这个语义——它要么做完，
要么在**已经动过线程集**之后超时。

## 8. 限制（今天明确不做，以及什么时候会咬人）

1. **多线程 `exec` = 先杀掉调用者之外的其它线程**（POSIX 语义）。
   机制与代价见 `13-tasks-and-kill.md` §6：闸门从任务级（`task->dying`）
   扩成**每线程一票**（`struct fe_thread::kill_pending`），`exec` 在
   **准备成功之后、换 CR3 之前**叫停其它线程，并等到它们全部
   `state == FE_THREAD_DEAD` 才动地址空间。
   原来那条限制为什么可以不保留：地址空间确实属于**任务**，但"别的线程的
   用户现场全在旧映像里"这句话有解——把它们杀掉，它们就不会再返回用户态。

   ★ 什么时候会咬人（这些是本轮新机制的真实风险，不是"以后可能"）★
   - **杀的那一步不可回滚**：等到超时才放弃的话返回 `FE_ERR_TIMEOUT`，
     而进程已经少了线程——§4 那条"失败时原程序完好"只覆盖**准备**阶段。
   - **两处没有取消点的等待**会让 `exec` 一路等到超时：`fe_process_wait`
     （`kernel/task/process.c:391-404`）与共享区间的控制器锁
     `fe_resource_lock`（`kernel/resource.c:566-581`）。任何"拉起子进程
     再等它"的服务线程都长成前者那个样子。
   - **睡着的线程叫不醒**：`fe_sched_wake` 只认 `BLOCKED`
     （`kernel/sched/sched.c:546`），所以 `SLEEP` 很长的线程要睡到点才死
     （`FE_SYS_SLEEP` 的入参是纳秒）。
   - **被杀的线程握着的控制器锁不会自动放**：清理它的 `lock_forget_owner`
     只在**任务销毁**时跑（`kernel/resource.c:524`），而 `exec` 之后任务
     还活着——后来者会一直等在锁上。
   - **SMP 之后整条推理都不成立**：今天"别的线程没有在跑"靠的是单核 +
     系统调用期间 IF=0；多核需要 IPI + 确认（`06-smp.md` §7/§8，K10）。
     这是**明确的债**，见 `13-tasks-and-kill.md` §6.5——今天的实现只在
     单核上正确。
2. **没有 `envp`**：`build_initial_stack` 今天压一个 NULL 终止符，
   环境为空。加环境需要同一个"先拷进内核"的处理（那时真的需要，
   因为环境可能来自别处），今天不做。
3. **不能从一个已经打开的句柄 `exec`**（Linux 的 `fexecve`）：
   内核的 VFS 今天没有 fd 概念，`fe_vfs_data` 只对**能直接给出字节**的
   后端有效（ramfs/引导模块）。所以要 `exec` 的东西必须在 ramfs 里。
4. **不支持 shebang / 解释器**：第一行 `#!` 不做解释。今天没有解释器，
   加了就是"没有东西能测的代码"。
5. **不保留旧映像的任何映射**：`mmap` 进来的内存对象、MMIO 窗口、
   DMA 缓冲**全都没了**（映射属于空间）。句柄与资源池认领还在，
   所以驱动换版之后要**重新映射**它需要的那几段——这是"身份=任务、
   映像=空间"这个划分的直接后果，不是缺陷，但要在驱动文档里写明。
6. **`exec` 不改变父子关系**：父进程 `WAIT` 的还是同一个任务句柄，
   拿到的是**新映像**最终的退出码。这与 POSIX 一致，但值得写下来，
   因为"同一个句柄背后的程序换过"这件事在别处不常见。

## 10. 验证方案

原则与 `13`/`14` 两轮一致：**每个正向断言配一条会失败的反向对照**，
并且至少要有一个真实客户端走真 syscall 路径。

### 10.1 内核自检 `fe_selftest_exec`（可证伪组）

| # | 断言 | 反向对照（必须失败/不变） |
|---|---|---|
| 1 | 候选现场构建成功：入口页可执行、栈顶已映射、argv 写在栈上（经 HHDM 读回并比对字符串） | 路径不存在 → `NOENT`；目录 → `ISDIR`；非可执行 → `NOTSUP`；`argc=FE_ARGV_MAX+1` → `RANGE` |
| 2 | **准备失败后原任务对象一个字段都没变**：准备前把 `space/vmas/tls_*/stack_low/user_map_next/user_stack_next` 快照下来，失败后逐项比对 | 这一条本身就是反向对照：它证明"准备阶段不碰任务对象"（§5）。任何一处顺手写都会让它失败 |
| 3 | 提交后 `t->space` 是新空间、CR3 也是新空间、帧里的 `rip/rsp/rflags` 等于候选值（`rflags == 0x202`） | 提交前把旧空间指针存下，提交后断言**它已被销毁**（PMM 可用帧计数回到基线 ±0） |

| 5 | 多线程任务 `exec`：**先杀掉其它线程，再换映像**——换 CR3 之前任务的存活线程只剩调用者（`fe_task_thread_count(t) == 1`）、其它线程全部 `state == FE_THREAD_DEAD`、调用者自己没被误杀（`kill_pending == false`）；换完之后它照常回到用户态跑新映像。★ "杀线程"那一半**不在本条验**★：它的判据是 E1–E5（见下面第二组），宿主 `fe_selftest_kill`，2a 那一刀就位 | 反向：**没有**被标记的线程在同一轮数内仍然存活、`cpu_ticks` 继续增长（证明"死"来自这次 `exec`，不是恰好自己退出了）；另一个任务的线程完全不受影响；再反向：把探针线程**故意**标记一位，它必须在下一次让出时死在闸门（证明"排除调用者"不是可选的） |

| 7 | **更新器身份的两个方向都被挡住**（§6.5）：调用者是更新器 → `NOTSUP`；新映像路径 == 清单里的更新器路径 → `NOTSUP` | 反向：同一时刻，换成任何别的路径都能进准备阶段（证明拒绝的是"身份"，不是"这个调用"） |

### 10.2 真实客户端 `user/bin/exectest`

同一个可执行文件分饰父与子，三种模式：

| 模式 | 做什么 | 判据 |
|---|---|---|
| **A 成功**（默认） | `fe_exec("/slot_a/bin/exectest", {"exectest","child"}, 2)`；若返回就打印错误码并 `exit(1)` | 子模式读 `argv[1] == "child"`，`exit(0x5A)`；父进程 `init` 检查退出码 **0x5A** |
| **B 回滚** | 先 `fe_exec` 一个不存在的路径 → **必须返回错误**；然后原程序继续干活（打印一行）并 `exit(0x5B)` | `init` 检查退出码 **0x5B**。★ 如果提交发生在准备之前，这里会崩或静默变成别的程序——这正是它与模式 A 的分工 |
| **C 连换** | 连续 `exec` 自己两次，第二次 argv 不同 | 退出码 = 第二次 argv 指定的值（**0x5C**）。★ 它顺带证明旧空间真的被回收了：不回收的话第二次装载就会 `NOMEM`（在 462 MiB 下不一定触发，所以真正管用的是自检第 3 条的 PMM 计数断言） |

模式 A 一次覆盖：路径装载、新栈构造、argv 传递、入口重置、
旧空间释放（否则第二次装载会撞地址）、TLS 重建（`libfe` 的 errno 是
`__thread`，它能正常工作就说明新 TLS 生效了）。

### 10.3 双环境

QEMU+WHPX 与 VirtualBox 7.2 都要跑：`=> 用户态失败项: 0`、
`M5 里程碑自检全部通过`、`init 结束，失败项 0`。

## 11. 代价清单（一句话版）

- 多一个系统调用号、一个会改返回帧的分发分支；
- 三个准备函数改签名（调用者已全部核对，共 8 处）；
- `exec` 后**所有用户映射丢失**，要重新 `mmap`；
- 多线程 `exec` 要先杀掉其它线程，而那一步**不可回滚**（超时 `FE_ERR_TIMEOUT`
  之后进程已经少了线程），并且今天有两处没有取消点的等待会让它等到超时
  （见 §8 第 1 条、`13-tasks-and-kill.md` §6.3/§6.6）；
- 峰值内存短暂翻倍（两个地址空间同时存在）——这是"原子回滚"的价格，
  与 Linux 一样，只是我们的空间更小。
