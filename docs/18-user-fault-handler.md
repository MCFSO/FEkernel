## 1. 判据与今天的缺口

### 1.1 判据

`11-kernel-next.md:15` 的 C1 写着：用户态能表达的**执行模型**要完整，其中一项是
**"异常处理者"**（`11-kernel-next.md:15` 的表格第一行）。
`11-kernel-next.md:52` 的 K5 那一行给出后果："挡容错：一个 `#PF` 就死一个线程"。

`10-posix-layer.md:73` 把这件事的必要性说得更具体：
"用户态异常不要杀线程，交给注册的处理者"**只能内核做**（`#PF`/`#GP` 的现场
在内核手里），并明确代价是"中。内核要加'每任务异常处理端点' + 修改
`user_fault` 路径"。

判据因此可以写成一句可测的话：

> 一个用户任务登记了处理者之后，它的一条线程触发 `#PF`/`#GP`/`#UD`/`#DE` 时，
> **现场（`struct fe_regs`）会被交到用户态**，用户态可以处置它，
> 并且**处置之后那条线程按用户态的决定继续跑或退出**。

反面（同样必须可测，见 §5）：**没有登记处理者的任务遇到同样的错，必须仍然被杀**。

### 1.2 今天从 `#PF` 到线程死掉的完整链条

逐段读 `kernel/arch/x86_64/idt.c` 与 `kernel/task/user.c`，链条是六步：

1. **硬件把现场压在"当前线程的内核栈"上，并因为中断门而清 IF。**
   所有 IDT 项都建成中断门（`kernel/arch/x86_64/idt.c:85` 写 `type_attr = GATE_INTERRUPT`，
   定义在 `idt.c:16`），异常桩统一跳到 `isr_common`
   （`kernel/arch/x86_64/isr.asm:49-69`），后者 `cld` 之后直接调
   `fe_isr_dispatch(r)`（`isr.asm:66-69`）——**入口桩里没有 `sti`**。
   → 这一步的事实很重要，§2.6 整节都在讲它的后果。

2. **分发按"CS 的 RPL"区分内核态与用户态异常。**
   `kernel/arch/x86_64/idt.c:306`：`if ((r->cs & 3) == 3 && vector < 32)`。
   成立就调 `user_fault(r)` 并**立刻 return**（`idt.c:307-308`）。
   `idt.c:290-305` 那段注释解释了为什么必须有这个 `return`
   （缺了它，"一次成功的缺页解析"会落到 `exception_fatal` 上变成 panic）。

3. **`user_fault` 先给 `#PF` 一次"合法缺页"的机会。**
   `kernel/arch/x86_64/idt.c:254-260`：只对向量 14 调
   `fe_user_resolve_fault(fe_task_current(), cr2, r->error)`；
   成功则 `g_pf_resolved++` 并 **`return`**（`idt.c:258`）——
   异常路径随后 `iretq` 回原现场，出错的那条指令重新执行。

4. **`fe_user_resolve_fault` 只承认三种情况，其余一律 `false`。**
   `kernel/task/user.c:132` 起：
   - 先问"这一页是不是紧挨着**已映射**的栈底"（`user.c:164-165`，判据是
     `t->stack_low` 而不是 VMA 的 base），是则权限检查
     （`user.c:172-180`）→ `fe_vma_grow_down` → `demand_map_page`
     （`user.c:181-195`）；
   - 不是紧邻，再查区间表（`user.c:198`）：查不到 → `false`（`user.c:199-202`）；
     区间内还要过写/读/取指三道权限（`user.c:206-216`）→ `demand_map_page`（`user.c:217`）。
   `kernel/include/fe/user.h:92-109` 的注释把这三情况写死了：
   ① 栈区间下方紧邻一页、② 标了 `ANON` 的区间内、③ 有后备帧的区间内；
   "其余一律拒绝，包括'落在区间内但没有 ANON/后备'"。

5. **回到 `user_fault`：解析失败就走到"杀线程"那几行。**
   `idt.c:262-281`：
   ```
   g_last_user_fault_vector = r->vector;   （idt.c:262）
   g_user_fault_count++;                   （idt.c:263）
   打印 "[用户态异常] 线程 %s 触发 %s …"    （idt.c:264-266）
   #PF 时打印出错地址与区间表 dump           （idt.c:267-278）
   打印 "出错指令 %#llx —— 该线程被终止"     （idt.c:279-280）
   fe_thread_exit(-1);                     （idt.c:281，不返回）
   ```

6. **`fe_thread_exit(-1)` 之后线程变成僵尸，退出码 `-1`。**
   `kernel/sched/sched.c:738-747`（`int FE_VEC_THREAD_EXIT`）→
   `exit_isr`（`sched.c:722-736`）→ `thread_mark_dead(t, t->exit_code)`
   （`sched.c:684-717`）→ 僵尸链 + `fe_process_on_thread_exit`（`sched.c:716`）。
   主线程走这条路时任务随即结束（`kernel/task/process.c:417-435`，
   只有主线程退出才算进程结束：`process.c:425-427`）。

### 1.3 "一律杀"这个决定在哪一行

**在 `kernel/arch/x86_64/idt.c:281`：`fe_thread_exit(-1);`。**

理由：链条的第 1–4 步都是**判据**（这是不是一次合法的缺页？），只有第 5 步末尾
那一次调用是**决定**。它也是 `user_fault` 的**唯一**出口（另一个出口是
`idt.c:258` 的"按需分页消化掉了"）。K5 要改的就是这一处：
在走到 `fe_thread_exit(-1)` 之前，先问一句"这个任务登记了处理者吗"。

★ 但要注意一个容易忽略的事实：`user_fault` 的两个出口之一（`idt.c:258` 的
`return`）意味着**"按需分页成功"与"要杀线程"之间没有第三个选项**。
K5 加的正是第三个选项，而它引入的第一个设计问题就是"它排在那两个的哪一边"
——见 §2.5。

### 1.4 现状里值得一提的两件事（都不是缺口，但决定了怎么改）

1. **用户态的 `#BP` 今天也被一律杀。** `g_handlers[]` 只有一个注册者：
   `kernel/main.c:572` 给向量 3 装了 `breakpoint_handler`（`main.c:98-103`），
   而那是**内核态** `int3`（自检 `main.c:105-115`）。来自 ring 3 的 `int3`
   走的是 `idt.c:306` 那条路，`g_handlers[3]` 根本轮不到。
   所以"用户态能不能接管 `#BP`"今天即使在内核里也没有第二个答案。
   （投递集合在 §2.3.0 定：`#BP` 也在里面——它同样是"来自 ring 3 的异常"，
   今天同样被一律杀，没有理由把它排除在这套机制之外。）

2. **内核已经能区分"被 `#GP` 挡下来"与"碰巧也返回 -1"。**
   `fe_last_user_fault_vector()` / `fe_user_fault_count()`
   （`idt.c:225-238`，声明在 `kernel/include/fe/idt.h:24-27`）是
   `fe_selftest_user`（`kernel/task/user.c:30-48`）的判据。
   ★ 这一对计数器的语义会被 K5 改变 ★：处理者消化掉的异常**不再**经过
   `idt.c:262-263`，所以它们不计入。谁依赖这两个数——**全仓只有一个消费者**
   （`kernel/task/user.c:33-45`；`user/` 下一个引用都没有，证据与逐行分析见
   §6.1.1）——必须知道这件事，并且**必须显式改判据**，不能让它"看起来还通过"。

## 2. 设计

### 2.0 一句话的形状

```
#PF/#GP/#UD/#DE 来自 ring 3
  → 先试按需分页（今天的路径，不动）
  → 失败：这个任务登记了处理者吗？
      没有 → fe_thread_exit(-1)（**今天的行为，一个字不改**）
      有   → 把现场拷成 fe_fault_regs，用端点消息投给处理者，
             然后**在异常上下文里让出**，等处理者的回复
  → 回复 = "已处理"：把用户改过的现场装回 r，return（异常路径 iretq 回去继续跑）
     回复 = "照旧杀"：fe_thread_exit(-1)
     没有回复 / 投递失败 / 嵌套超限：fe_thread_exit(-1)
```

下面每一小节都是这个形状里的一处决定，各自写"为什么 / 代价"。

### 2.1 投递给谁：登记在**任务**上（每任务一个端点），但消息带上线程 id

**决定：处理者登记在任务上；每任务至多一个处理者端点。线程需要区分时靠消息里的
`thread_id`。**

为什么是任务而不是线程：

| 理由 | 依据 |
|---|---|
| 项目已经把"身份"钉在任务上 | `15-exec.md` §2 的划分："身份 = 任务、映像 = 地址空间"；`15-exec.md:29-37` 列出身份包含句柄表、devmgr 身份、设备认领、任务 id |
| 端点是**句柄**，而句柄表是**任务**的 | `struct fe_handle_table handles` 在 `struct fe_task` 里（`kernel/include/fe/task.h:21`）；`process.h:8-10` 明写"spawn 返回的是新任务的**句柄**……句柄不可伪造" |
| 运行库的形态就是"一个进程一个崩溃处理器" | C++ 的 `std::terminate`、JIT 的 SIGSEGV 兜底、GC 的写屏障都是**进程级**的；没有哪个运行库要求"线程 3 与线程 7 用不同的崩溃处理器" |
| 每线程一个端点会把注册/注销变成 N 份 | `FE_HANDLE_TABLE_SIZE` 是 256（`kernel/include/fe/object.h:47`），每个线程一个端点句柄是纯浪费 |

代价（必须认的三条）：

1. **同一个任务里无法给不同线程配不同处理者。** 想按线程分派，处理者只能靠
   消息里的 `thread_id`（`fe/ipc.h:440-444` 已有"`sender_task` 由内核填、
   不可伪造"的先例，这里同理：`thread_id` 也由内核填）。
   → 何时会咬人：一个进程里同时跑"不可信的 JIT 代码"与"可信的调度器线程"时，
   处理者必须自己按 `thread_id` 分流。
2. **注销是多线程共享状态。** 一个线程注销处理者，另一个线程的异常就失去投递点。
   解法见 §2.3 的回复/注销语义（注销**不影响**正在等回复的那一次）。
3. **端点的生命周期必须与句柄解耦。** 用户态可以 `HANDLE_CLOSE` 掉那个句柄，
   但内核的登记里还存着端点指针——所以登记时内核**自己对端点对象加一次引用**
   （`fe_object_ref`，`kernel/include/fe/object.h:37`），任务销毁路径上
   （`kernel/task/task.c:35-96` 那个 `case FE_OBJ_TASK`）显式 `fe_object_unref`。
   ★ 漏掉这一次 unref 就是"端点对象永不销毁"，而它挂着消息队列与等待者表；
   多加一次就是"用户关掉句柄之后端点还在"。两种都不报错，只是慢漏或不漏。
   → 这是本节最容易被写错的一处，实现清单里单列（§4）。

**另一个选择（被否掉的）**：把处理者做成端点句柄号（`u32`）存在任务上，
投递时用 `fe_endpoint_send(t, h, ...)` 查表。为什么否掉：
`fe_endpoint_send` 走 `fe_handle_lookup`（`kernel/ipc/ipc.c:289`），
而句柄可以被用户关掉、可以被 `HANDLE_DUP` 换成另一个权利集合；
更硬的一条是**它要求 `FE_RIGHT_SEND`**（`ipc.c:289`）——
于是"处理者能不能收到异常"变成了"那个句柄此刻有什么权限位"，
而权限位是用户态可以自己收窄的。**内核的异常投递不该依赖用户态当前的权限位。**

### 2.2 现场怎么给用户态：拷进用户缓冲区，`struct fe_fault_regs`

#### 2.2.1 要不要整份交

**决定：整份交，一个字段都不裁。** 理由是"能不能处置"取决于现场完整性：
处理 `#PF` 要 `cr2` 与错误码（`idt.c:249` 今天就在读 `fe_read_cr2()`），
跳过出错指令要 `rip`，从处理者返回要 `rsp`/`rflags`，
判断"这是不是我的 JIT 代码"要 `cs`。少任何一个都会逼出第二套 syscall 去补读。

**代价**：176 字节的定长拷贝 + 一条消息（`FE_MSG_MAX_PAYLOAD` 是 1024，
`kernel/include/fe/ipc.h:30`，所以放得下）。没有别的代价——它不是流式数据。

#### 2.2.2 怎么交：**拷贝**，不是共享内存对象

**决定：用 `fe_copy_to_user`（`kernel/include/fe/user.h:125`）拷进用户缓冲区，
缓冲区地址由处理者在注册时给出。**

为什么不是"随消息传一个内存对象"（`fe/ipc.h:184-189` 那套）：

| 方案 | 代价 |
|---|---|
| **拷贝进用户缓冲**：内核侧的现场 `struct fe_regs` 是 **176 字节**（22 × 8，`kernel/include/fe/regs.h:40` 的 `FE_STATIC_ASSERT` 就是这个数），交给用户态的 `fe_fault_regs` 是 **200 字节**（25 × 8，多了 `cr2`/`thread_id`/`fault_count`） | 一次 `fe_user_range_ok` 逐页校验（`kernel/mm/uaccess.c:18-48`）+ 一次 `memcpy`；**不分配、不加锁、不阻塞** |
| 内存对象 + 映射 | 要预先 `MEM_ALLOC` + `MEM_MAP`，多一个对象的生命周期、多一处 `FE_PTE_NOFREE` 要记得置（`kernel/include/fe/mm.h:76-90` 记着漏置的症状）、多一份"谁在什么时候 unmap"的约定 |

关键判据是**投递代码跑在异常上下文里、IF=0**（§1.2 第 1 步的实测依据）：
那条路上能做的事越少越好。200 字节的拷贝是这条路径上最便宜的动作，
而分配一个消息对象已经是它的几十倍代价（`build_message` → 消息池，`ipc.c:299`）。

★ 但"投递"这一半还是走消息 ★：拷贝是把现场交给用户态的**方式**，
而"该处理者现在被叫醒"这件事必须走已有的唤醒机制（端点消息 → `wake_receiver`，
`ipc.c:315`）。两条路都要，各有各的职责。

★ 用哪个拷贝原语（§6.1.3 查清）★ 投递跑在**出错线程自己的上下文**里、
当前 CR3 就是它的地址空间，而缓冲区按 §2.3.2 属于同一任务 →
**`fe_copy_to_user`（`kernel/include/fe/user.h:125`，实现 `kernel/mm/uaccess.c:64-75`）**。
它不切 CR3、不分配，并且**逐页校验"这块内存确实可写"**。
另一条路 `fe_user_write_space`（`uaccess.c:116-142`）虽然能对**任意**地址空间写，
但它**只查"这一页有没有映射"，不查 user 位、不查可写**（`uaccess.c:132-135`）——
用它把现场写进只读页或 MMIO 页是可能的，那不是 K5 该引入的口子。

#### 2.2.3 ABI 草案

```c
/* kernel/include/fe/regs.h 尾部新增；user/include/fe_base.h 镜像一份。
 *
 * ★ 顺序与 struct fe_regs **逐字段一致**，只换掉两个"内核内部记账"字段 ★
 *   fe_regs.vector → fe_fault_regs.vector      （同义：异常向量号）
 *   fe_regs.error  → fe_fault_regs.error_code  （改名只是为了让用户态别猜语义）
 * 于是"现场怎么摆"这件事仍然只有一个来源（regs.h 顶部那段布局推导），
 * 而用户态拿到的仍然是一份**完整**现场——只是多了两个伴生字段。 */
struct fe_fault_regs {
    u64 r15, r14, r13, r12, r11, r10, r9, r8;
    u64 rbp, rdi, rsi, rdx, rcx, rbx, rax;
    u64 vector;         /* 0..31，异常向量号 */
    u64 error_code;     /* CPU 压入的错误码；无错误码的向量由桩补 0（isr.asm:21-35） */
    u64 rip, cs, rflags, rsp, ss;
    /* ---- 下面是"现场"之外、但缺了就处置不了的三项（只读）---- */
    u64 cr2;            /* 出错线性地址；只有 #PF(14) 有意义，其余为 0 */
    u64 thread_id;      /* 出错线程的 id —— 处理者要按线程分流时用（§2.1 代价 1） */
    u64 fault_count;    /* 本线程第几次被投递（含本次，从 1 起；见 §2.4） */
} FE_PACKED;

FE_STATIC_ASSERT(sizeof(struct fe_fault_regs) == 25 * 8,
                 "fe_fault_regs 布局变了（用户态按 200 字节读）");
/* ★ 这一条才是真正的钉子：两份结构的"现场部分"必须逐字段对齐 ★ */
FE_STATIC_ASSERT(sizeof(struct fe_fault_regs) > sizeof(struct fe_regs),
                 "fe_fault_regs 必须包含整份现场再加上伴生字段");
```

**投递用的一整条消息**（`FE_MSG_MAX_PAYLOAD` = 1024，放得下）：

```c
/* 消息头：协议号与操作码在 fe/syscall.h 里定（与 TASK_LIST 同一套"共享 ABI"
 * 做法：内核按**偏移常量**填，用户态按同一批常量读，两边各写一次并各自
 * _Static_assert —— 见 fe/syscall.h:322-351 那段"为什么必须这样"）。 */
#define FE_FAULT_PROTO   0x4641554Cu   /* 'FAUL' */
#define FE_FAULT_OP_EVENT 1u           /* 内核 → 处理者：出事了（消息载荷 = 现场）*/
/* 处理者的决定**不走消息**，走 FE_SYS_FAULT_REPLY（理由见本节末尾）——所以
 * 这里**没有** FE_FAULT_OP_REPLY：一个不存在的常量不值得留一行。 */

#define FE_FAULT_REGS_SIZE  200u       /* sizeof(struct fe_fault_regs)，内核侧 */
#define FE_FAULT_REGS_SIZE_X 200u      /* 同一数值的用户态镜像（两边各写一次）*/
```

**对齐与钉法**（项目里所有跨边界的 ABI 都是这么钉的）：

1. `FE_PACKED`（`kernel/include/fe/compiler.h:7`）——与 `struct fe_regs` 一样
   （`kernel/include/fe/regs.h:38`），保证没有编译器填充。
2. `FE_STATIC_ASSERT`（`compiler.h:25`）钉字节数。数值写成"字段数 × 8"而不是
   字面量：改一个字段没改断言时，编译器会说"结构体大小变了"，
   而**宏与结构体的对不上**正是 `docs/13-tasks-and-kill.md` §2 记的那次实测事故
   （`FE_TASK_STRIDE` 两个头文件都写成 48，实际 64）。
3. **用户态那一份必须逐字段镜像**，并在 `user/` 侧也用 `_Static_assert` 钉住
   同一个数字（`fe/syscall.h:311-312` 的 `fe_clock_info` 就是范例）。
   两边的名字可以不同，**偏移与大小必须相同**。

★ 待查已查清（§6.1.2）★ 镜像的落点是 **`user/include/fe_user.h`**，不是 `fe_base.h`
（后者全文只有整数 typedef，`user/include/fe_base.h:18-37`；共享 ABI 结构体的
既有落点 `fe_user.h` 里有 11 个先例，从 `fe_msg_header`（`fe_user.h:137`）到
`fe_msi_info`（`fe_user.h:572`））。内核侧仍然放 `kernel/include/fe/regs.h`：
它是"现场怎么摆"的唯一来源（`regs.h:1-16` 的布局推导）。
用户侧**要主动加** `_Static_assert`——`fe_clock_info`（`fe_user.h:432-437`）今天
就没有，别照它抄；照 `fe_task_info`/`fe_thread_info` 那两行抄（`fe_user.h:341-344`）。

#### 2.2.4 `rip` 的语义要写清楚：**内核不改 `rip`**

**决定：`#PF`/`#UD`/`#GP`/`#DE` 的 `rip` 指向出错的那条指令（fault 类异常）；
内核**不替处理者推进 `rip`**。跳过指令是处理者的事。**

依据是硬件语义 + 本内核已有的先例：`#BP` 的 `breakpoint_handler`
（`kernel/main.c:98-103`）拿到 `r` 之后**什么都不改**就返回，
而 `main.c:110-111` 的判据是"进入内核 → 分发 → iretq 返回原现场"仍然通过——
因为 `#BP` 是 **trap** 类，CPU 压入的 `rip` 已经指向 `int3` 之后。
故障类（`#PF`/`#UD`/`#DE`/`#GP`）压入的是**出错指令本身**的地址。

代价：**处理者必须自己知道出错指令有多长**才能跳过它，而内核今天
**不提供指令长度**（要提供就得反汇编，见"明确不做"§3）。
→ 何时会咬人：最典型的用法"忽略这一条非法指令往下跑"在长指令上会做错。
写下来的正确做法是：**处理者自己要跳过时，读 `rip` 处的前若干字节自己解码**，
解不出来就回"照旧杀"——**不要猜**。

### 2.3 处理者能做什么：**三个返回值**，语义与内核动作逐条钉死

#### 2.3.0 哪些向量可以投递（先定集合，再谈语义）

**决定：投递集合 = { 0 `#DE`, 6 `#UD`, 13 `#GP`, 14 `#PF`, 3 `#BP` }，
以及其余 0..31 里"来自 ring 3 且不是 abort 类"的向量。**
**永远不投递**：8 `#DF`、18 `#MC`（abort 类，走 IST 栈，见 §3），
以及任何 `(r->cs & 3) != 3` 的异常（§3.1）。

向量号的数值来自 `kernel/arch/x86_64/idt.c:47-68` 那张名字表
（`names[32]`，索引就是向量号），0..31 的范围判据来自 `idt.c:306` 的 `vector < 32`。

为什么把 `#BP`（3）也纳进来：它是**用户态 `int3` 的自然后果**
（调试器、`__builtin_trap`、JIT 的断点桩都用它），而今天 ring 3 的 `int3`
同样是一律杀（§1.4 第 1 条）——既然机制就在那里，没有理由把它排除在外。
代价：`#BP` 是 **trap** 类（压入的 `rip` 已经指向 `int3` 之后），
与 `#PF` 的 fault 类语义**不同**（§2.2.4），处理者必须知道这一点。

投递时**不改**任何现场字段：内核只是"报告 + 等决定"。
唯一被内核改写的东西是下面 §2.4/§2.5.2 里那三个**记账字段**
（`fault_depth`、`last_fault_rip`、`last_fault_cr2`），它们不进现场。

#### 2.3.1 回复的形状与语义

回复走一个系统调用（不是消息，理由见本节末尾）：

```c
/* fe/syscall.h：两个调用号（取号理由见 §4.1 那一行） */
#define FE_SYS_FAULT_HANDLER 0x90   /* (ep_handle, regs_user_ptr) —— 登记 / 注销 */
#define FE_SYS_FAULT_REPLY   0x91   /* (verdict, regs_user_ptr) —— 处理者的决定 */

/* verdict（低 4 位是动作，高位是标志） */
#define FE_FAULT_ACTION_MASK   0xFu
#define FE_FAULT_RESUME        1u   /* 已处理：按我给的现场继续跑 */
#define FE_FAULT_KILL          2u   /* 我不管：照旧杀线程（今天的行为） */
#define FE_FAULT_RETHROW       3u   /* 再抛一次：让**本线程**再吃一次同样的异常 */
#define FE_FAULT_FLAG_KEEP_REGS 0x10u  /* 与 RESUME 同用：现场用原来的，不改 */
```

| 返回值 | 内核要做的动作 | 为什么需要它 |
|---|---|---|
| `FE_FAULT_RESUME` | 用用户缓冲区里的 `fe_fault_regs` **逐个通用寄存器 + `rip`/`rsp`/`rflags`** 覆盖 `r`；**拒绝** `cs`/`ss` 的任何改动（不是等于原值就 `FE_ERR_INVAL`）；`return` 回 `user_fault` 上游 → `isr_common` → `iretq` | "修好映射继续跑""跳过出错指令""改 `rip` 去错误处理器"都要它 |
| `FE_FAULT_KILL` | `fe_thread_exit(-1)`（**与今天完全同一条路**，退出码也一致：`init` 里 `drvdeny` 的期望值是 `-1`，`user/bin/init/main.c:744`） | 处理者只处理它认识的那几种，其余交回内核 |
| `FE_FAULT_RETHROW` | 把这次投递**算作已回复**，然后**重新进入投递判据**（不回到用户态、不重新执行指令）：即"按新的一轮投递"，`fault_count` 加一，受 §2.4 的递归上限约束 | 处理者的典型形态是"我看不懂，转交给上游/记录一下再让它死"；没有它，处理者只能选"继续跑"或"杀"，而"记录 + 让它死"会被迫实现成后者（丢掉了上游处理的机会） |

**为什么回复走系统调用而不是"回一条消息"**：

- 内核在异常上下文里等的是一个**决定**，不是一段数据流；`fe_msg_reply`
  （`kernel/include/fe/ipc.h:118`）要求处理者先 `recv` 拿到 `reply_ep`，
  那是"同步 RPC"的形状，而我们这里内核**不在** `recv` 里等（§2.6）；
- 系统调用天然携带"谁在回复"（`fe_task_current()`），
  而消息的 `reply_ep` 是可转交的——**"谁能替我回复"必须不可伪造**，
  否则另一个任务可以替处理者做决定。

**回复必须校验"这是不是等我这一个回复"**：登记里记 `(task_id, thread_id, fault_seq)`，
回复时三项都要对上，对不上返回 `FE_ERR_INVAL` 并**不做任何事**。
理由：一个任务里可能有两条线程同时等回复（两条线程可以同时出错），
没有这个校验就是"A 的决定被装到 B 的现场上"——那是**跨线程现场伪装**，
它是安全边界问题，不是健壮性问题。

#### 2.3.2 ★ 处理者线程不许是"出错的那条线程"自己 ★

这一条是实现时**一定会漏**的，因为它只在"单线程程序自己给自己登记处理者"
这个最自然的用法下暴露：

> 一条线程在异常上下文里等回复，而**能产生回复的线程正是它自己**——
> 它被卡在 `user_fault` 里让出，永远不会去 `recv` 那条消息。
> 结果：等满 `FE_FAULT_WAIT_ROUNDS`，然后被杀。
> 症状是"登记了处理者，但每一次异常都要等很久才死"，而不是"立刻死"
> ——比崩溃难查得多。

**决定：登记时把"谁来收"钉住，投递前比一次。**

注册接口的形状不变（`FE_SYS_FAULT_HANDLER(ep_handle, regs_user_ptr)`，
见 §2.3.1 的常量块）；多出来的只是"注册时内核记下调用线程的 id"，
投递前比一次：`if (出错线程 == 收件线程) → 不投递，fe_thread_exit(-1)`。

**"谁来收"选谁**：**登记时的调用线程**（不是主线程）。
理由：端点的接收权不受线程限制（同一个端点可以被同任务的任意线程 `recv`），
但"我登记的时候打算让谁收"只有调用者自己知道；钉成主线程会在
"工作线程登记、主线程收"这种布局下强迫用户改代码，而钉成调用线程
只需要用户遵守一句自然的约定：**谁登记，谁收**。

**代价（写在明处）**：

1. 用户不能用"线程 A 登记、线程 B 收"——**这是故意的**：
   那种布局下"B 死了怎么办"没有答案，而它带来的灵活性今天没有任何调用者需要。
2. 出错线程恰好是收件线程时，**异常直接杀**，处理者连通知都收不到。
   这是"自己救不了自己"的诚实表达：处理者路径要求至少有一条**别的**线程能跑。
3. 由此得到一条给用户的规矩，要写进 `faulttest` 的注释里：
   **处理者线程不要做会出异常的事**（它与"出错线程"必须不是同一条）。
   一个任务只跑一条线程时，它能用处理者的唯一方式是"再开一条线程"。
4. ★ 这条判据与 §2.4 的深度判据**不重复**，两条都要有 ★
   深度判据拦的是"处理者在处理中又出错"（那时出错的是**收件线程**自己，
   `fault_depth` 已经是 1）；这里拦的是"出错线程与收件线程是同一条"
   （`fault_depth` 还是 0，深度判据**放行**）。
   缺了这一条的直接后果见上面那段引文：等满轮数才死，而不是立刻死。

### 2.4 不许无限递归：**投递深度 1**，第二次就杀

**决定：任务上记一个"已投递未回复"的计数 `fault_depth`（0 或 1）。
`fault_depth != 0` 时再次发生用户态异常 → 不投递，直接 `fe_thread_exit(-1)`。**

★ 计数器在**任务**上，但它必须有主 ★ `fault_depth` 加一的同时记下
"这一次是谁在等"（`fault_owner` = 出错线程指针）。两个理由：

1. **它必须是任务级的，否则上限能被绕过**：两条线程各自持有一个 0/1 的
   线程级计数，就能同时各投递一次——"深度 1"退化成了"深度 N"；
2. **回复槽必须是每线程的**（`struct fe_thread` 上，§4.1），
   所以加一的那一处必须同时说清"谁的槽在等"。只有 `fault_depth` 一个数时，
   "回复到了，交给谁"没有答案。

**投递时还要清一次回复槽**（`fault_reply.arrived = false`），
理由与 `wait` 类的重试循环同一族：**上一轮的回复**不能变成这一轮的答案。
漏了它的症状是"处理者这次没回复，出错线程却拿着上次的现场继续跑了"——
那比卡住更难查，因为它表现为"程序偶尔接着跑，但状态是上一次的"。

为什么不是"嵌套上限 2 或 3"：

- **处理者自己要能跑，就必须有一块已经映射好的栈、已经映射好的代码。**
  一个 `#PF` 处理者如果因为自己的栈没映射而 `#PF`，那是它**没有准备好**；
  再给它一层机会只会把"没准备好"变成"有时能跑"——而"有时能跑"是这个项目
  反复列为最坏的一类症状（`11-kernel-next.md:414-417`）。
- 深度 1 的规则可以被一句话说清并**被证伪**（§5 的负向对照）：
  "处理者自己出错 → 线程死"。深度 2 的规则就需要额外的语义说明
  （第二层是谁？它的现场给谁？），而今天**没有任何调用者需要它**。

**代价（写在明处，这是本节最重要的三条）**：

1. **处理者不能依赖任何"第一次访问才映射"的内存。** 它的栈、它的代码、
   它要写的日志缓冲、它 `malloc` 出来的堆页，**都必须在注册处理者之前
   已经映射好**。`malloc` 一个还没碰过的页、或在处理中第一次 `printf`
   到一个没映射过的缓冲，都会把"处理者自己出错"变成现实。
   → 何时会咬人：**第一次写这个处理者的人一定会踩**，因为它违反
   "按需分页是常态"这条今天已经成立的习惯（`11-kernel-next.md` §6）。
   缓解手段只能靠文档与客户端示范（`user/bin/faulttest` 要把它显式写出来）。
2. **`fault_count` 只增不减**（§2.2.3 的字段）：它记录"本线程第几次被投递"，
   便于处理者判断"这是不是第二次"。它是诊断用的，不参与判据——
   判据只有 `fault_depth`（0/1）。为什么不是同一个数：
   一个是**历史**，一个是**此刻有没有人在处理**，混成一个字段就会在
   "回复之后又出错"这件事上给出错误答案。
3. **省不掉的竞态**：`fault_depth` 在**投递之前**加一、在**回复或放弃**时减一，
   两处都在同一个关中断区间里（投递路径本来就在 IF=0 的异常上下文里）。
   减一漏掉一次，这个任务的异常处理就**永久失效**（所有异常直接杀）——
   症状是"处理者工作过一次之后再也不工作了"，很难查。所以减一只写一处：
   见 §4 的清单（`fe_fault_deliver` 的**唯一**返回路径）。

### 2.5 ★ 与按需分页的关系：**先试按需分页，再问处理者** ★

这是本文最关键的一个结论，要分开讲"顺序"和"边角"两件事。

#### 2.5.1 顺序：按需分页在前

**决定：保持今天的顺序**——`idt.c:254-260` 先调 `fe_user_resolve_fault`，
只有它返回 `false` 时才进处理者路径。

三条理由，每条都能单独否掉"先问处理者"：

1. **栈增长是内核的合法职责，不该让每个程序都去处理它。**
   `11-kernel-next.md:93-96` 把栈的模型写清楚了（区间 `base` = 已映射到哪儿，
   缺页时向下移动），`kernel/task/user.c:140-196` 是那段判据的实现。
   如果先问处理者，那么**每一个** C 程序在栈长出预映射的 4 页
   （`kernel/task/user.c:431` 的 `STACK_PREMAP_PAGES`）之后都要自己接管缺页，
   否则就是崩溃。这不是"更灵活"，是把内核该做的事推给了每个程序。
2. **用户态补不了页。** 处理者要做内核今天做的事，得有能力
   "在这段地址上给我一页"。项目里有内存对象，但**没有一个"按 VMA 的权限给这一页"
   的原语**——`MEM_MAP`（`fe/syscall.h:56-64` 那一段的 syscall 号与语义）
   映射的是**对象已有的帧**，不是"按需零页"。也就是说"先问处理者"这条路
   今天根本走不通，要走通得先造一个和 `demand_map_page`
   （`kernel/task/user.c:90-130`）等价的东西，
   而那个函数的名字里就写着它是内核的活。
3. **两个判据不重叠，所以"按需分页在前"不会吃掉处理者该看见的异常。**
   `fe_user_resolve_fault` 只承认三种情况（`kernel/include/fe/user.h:100-104`），
   其余一律 `false`——**"其余"恰好就是处理者要认领的那一类**。
   顺序在这里不会造成漏投。

#### 2.5.2 边角：处理者**不能**认领"内核已经决定要拒绝的那一页"

按需分页失败之后把异常交给处理者，有一个容易忽略的坑：

> 处理者回 `FE_FAULT_RESUME` 但**没改 `rip`**，那条指令会**再犯一次**，
> 于是再投递一次、再回填一次……这是一个**用户态可控的活锁**，
> 而且是纯用户态代码就能构造的（不需要恶意：一个"我处理不了但我不想让它死"
> 的处理者就会写成这样）。

**决定：加一条"同一个 (rip, cr2) 连续两次"的判据。**
本线程记 `last_fault_rip` / `last_fault_cr2`；投递前比对，两个都相同就
**不再投递**，直接杀（并打印一行 ASCII 日志说清"同一现场被重复投递"）。

- **代价**：两个 `u64`（每线程 16 字节）+ 一条判据。
- **什么时候会咬人**：处理者想"重试一次"时会发现第二次直接被杀了。
  这是**故意的**：重试的意义在于"这次改动让条件不同了"，
  而 `(rip, cr2)` 完全相同就说明条件没变。想真的重试，处理者应该改 `rip`
  或改内存映射，让下一次进去时现场不同——那是它自己的责任。
- **另一条更简单的备选（被否掉）**：让 `RESUME` 必须带"我改了什么"的位图。
  否掉的理由：多一个字段、多一处两边要对齐的 ABI，
  而它换来的只是"更早发现处理者写错了"——`(rip, cr2)` 判据已经能发现它。

★ 本节与 §2.3 的 `FE_FAULT_RETHROW` 不冲突 ★：`RETHROW` 是**处理者主动**
要求再走一轮（比如转交给上游），它算一次新的投递但**不受**这条判据约束
（否则"再抛一次"等于"立刻自杀"）；不受约束的代价由 §2.4 的深度 1 兜住：
再抛一轮之后如果处理者自己出错，就是死。

### 2.6 ★ 同步还是异步：投递后**就地让出、有界等待**，绝不阻塞 ★

这一节是本文里第二难的一处，因为它取决于两条**读代码得到的事实**。

#### 2.6.1 事实一：`user_fault` 跑在 IF=0 里

- 所有 IDT 项都是中断门（`idt.c:16`、`idt.c:85`）→ 中断门**清 IF**；
- `isr_common` 里没有 `sti`（`isr.asm:49-69`），只有 `cld`（`isr.asm:66`）；
- 系统调用入口也一样：`SFMASK` 清 `IF/DF/TF`（`kernel/arch/x86_64/syscall.asm:127-131`），
  入口桩不再开中断；
- 全内核只有两处**汇编级 `sti`**：`kernel/arch/x86_64/idt.c:105-108`
  （`fe_interrupts_enable`）与 `kernel/sched/sched.c:1149-1150`
  （空闲线程的 `sti; hlt`，注释在 `sched.c:1147-1148`）——
  `docs/13-tasks-and-kill.md:612` 已经写过这句话，我按读到的代码确认它今天仍然成立。
  ★ 注意"只有两处 `sti`"说的是**汇编指令**，不是 `fe_sti()` 这个宏 ★：
  驱动中断路径（`kernel/irq.c`）另外用 `fe_irq_save`/`fe_irq_restore` 开关中断，
  但那与"异常入口进来时 IF 是什么"无关——异常入口到 `user_fault` 之间
  **没有任何一处**放开了中断。

**所以：`user_fault` 全程 IF=0。**

#### 2.6.2 事实二："让出"不依赖 IF，但"等一段时间"依赖节拍

- 让出、阻塞、睡眠三条路都是**软中断转发**（行号取自写作当时；
  `kernel/sched/sched.c` 正被另一个执行体改动，**以函数名为准**）：
  `fe_thread_yield` → `int FE_VEC_YIELD`（`kernel/sched/sched.c:756-759`，
  向量号 48 见 `kernel/include/fe/vectors.h:22`），
  `fe_sched_block_current` → `int FE_VEC_YIELD`（`sched.c:578-587`），
  `fe_sched_sleep_until` → `int FE_VEC_YIELD`（`sched.c:530-563` 末段）。
  软件中断**不受 IF 影响**，所以这三条在 IF=0 的上下文里都进得去。
- 但 `IF=0` 意味着**节拍不跳**（`fe_sched_tick` 是节拍中断调用的，
  `sched.c:642-664`），于是：
  - `fe_thread_sleep_ms` 的"醒来"由 `wake_sleepers(fe_time_ns())`
    在节拍里驱动（`sched.c:565-576`、`sched.c:645`）→ **睡下去就没人叫**；
  - 任何"过一会儿超时"的写法在 IF=0 里都不会到点。

**所以：能不能阻塞的答案是——"阻塞"这个动作做得到，
但"依赖时间或中断的等待"在 IF=0 里一定死锁。**

#### 2.6.3 决定：投递后**就地让出**（有界轮询），而不是阻塞

```c
/* 形状（不是最终代码）：在 user_fault 里，投递成功之后 */
for (u32 i = 0; i < FE_FAULT_WAIT_ROUNDS; i++) {
    if (fe_fault_reply_arrived(thread)) {  /* 回复由 syscall 写入线程上的结果槽 */
        break;
    }
    if (fe_thread_should_die(thread)) {    /* §2.7：正在被杀就不再等 */
        break;
    }
    fe_thread_yield();                     /* int 0x30，不受 IF 影响 */
}
```

为什么是"让出 + 有界轮询"而不是 `fe_sched_block_current`：

| 维度 | 让出轮询（选它） | 阻塞（否掉） |
|---|---|---|
| IF=0 里能不能用 | 能（软中断） | 也能，但**只能靠显式唤醒** |
| 谁能唤醒它 | 不需要 —— 它自己会回来看 | 必须有另一个执行体显式 `fe_sched_wake`，而"处理者回复"发生在**另一个线程的系统调用里**，它得先找到"哪条线程在等"（新登记 = 第六处等待登记 + 一条新的取消路径，`docs/13-tasks-and-kill.md` §6.3 那张表的教训） |
| 死锁面 | 有界：轮数用完就杀线程 | 无界：唤醒源丢了就**永远卡住**，而且卡在 IF=0 的异常上下文里 |
| 代价 | 空转轮询：这段时间片本来是**别的就绪线程**可以用的（浪费的是 CPU 时间，不是内核内存）——之所以可接受，是因为它是**有界**的，而且只在故障路径上 | 需要新增一条等待登记与摘除路径，且漏摘就是悬空指针 |

★ 为什么"让出"在异常上下文里是安全的（这一条要写下来，否则实现时会犹豫）★
`fe_sched_maybe_switch` 只在**返回用户态的路上**判闸门与切线程
（`isr.asm:76-78`、`syscall.asm:66-68`），而它自己跑在 IF=0 里
（`docs/13-tasks-and-kill.md:606-613` 已经论证过"读到 `DEAD` 那一刻是可信的"）。
异常上下文里的让出走的是同一条路径：现场留在本线程的内核栈上
（`struct fe_regs` 就压在那儿），切回来时 `rsp` 恢复，一切照旧。
**没有任何"从函数中间切走再切回来"的新形态**——这正是
`kernel/include/fe/sched/thread.h:5-11` 那段设计说明想要的性质。

#### 2.6.4 三条必须一起定的边界

1. **`FE_FAULT_WAIT_ROUNDS` 的数值今天不能拍。**
   它与 `FE_EXEC_KILL_ROUNDS = 200000`（`15-exec.md` §10.1 的引用、
   `kernel/include/fe/process.h:169`）同族，但**判据不同**：那里等的是
   "线程死透"，这里等的是"另一个线程跑完一段用户代码并系统调用回来"。
   我在本文里**不写一个实测上界**（没跑过就不能写，项目铁律）。
   实现时的做法照 `docs/13-tasks-and-kill.md:805-810` 那一套：
   给一个保守的大值，并在**第一次双环境实跑之后**把它记下来（§6 待查）。
2. **投递失败（端点队列满）只能杀线程。**
   `fe_endpoint_send` 在队列满时返回 `FE_ERR_AGAIN`（`kernel/ipc/ipc.c:305-309`），
   而队列上限是 `FE_MSG_QUEUE_MAX = 64`（`fe/ipc.h:32`）。
   不能等（IF=0 里等就是死锁），也不能丢（丢了线程就永远挂着）。
   → **代价说清楚**：处理者自己积压 64 条不处理时，下一个故障线程**直接被杀**。
   这是"处理者必须及时收"的硬约束，要写进处理者的文档里。
3. **回复之前，本线程不会再执行任何用户指令。**
   这与 K2 那条"被终止的任务不会再回到用户态"是同一个形状的保证
   （`fe/syscall.h:248-252`）：现场在我们手里，回不回去是我们说了算。
4. **日志要克制**（§6.1.4 查清的事实）：`fe_kprintf` 在这条路径上**能用**
   （无锁、不分配、不睡眠、串口是轮询输出不依赖中断），但每个 `\n`
   会多一次有界自旋（最多 10 万次 LSR 读，`kernel/arch/x86_64/serial.c:46-63`）。
   所以规则是：**允许一次性的一行总结，禁止在等待循环里逐轮打印**。

### 2.7 与终止（K2）的关系：**闸门判据在前，投递在后**

`docs/13-tasks-and-kill.md` §6.1 把闸门从任务级扩到了线程级
（`task->dying` 或 `thread->kill_pending`，判据函数
`fe_thread_should_die`，`kernel/sched/sched.c:368-371`）。K5 必须与之对齐：

| 情形 | 决定 | 理由 |
|---|---|---|
| 出错时 `fe_thread_should_die(当前线程)` 成立 | **不投递**，直接 `fe_thread_exit(-1)` | 现场就算交给处理者、处理者就算"修好"了它，闸门仍会在下一次回用户态时把它杀掉（`sched.c:395-398`）。投递一次只是浪费一次往返，并且给了处理者一个"我救活了它"的错觉 |
| 处理者线程自己被杀（`kill_pending`） | 它下一次经过闸门就死（`sched.c:395-398`），于是**回复永远不会到** → 出错线程在轮询里等完 `FE_FAULT_WAIT_ROUNDS` 后被杀 | 这是"处理者死得比我快"的正常结局，不需要新机制。★ 但它是"有界轮询"存在的最硬理由 ★：如果等的是阻塞唤醒，这里就是**永久卡住** |
| 整个任务正在被终止（`task->dying`） | 同上，两边都成立：出错线程不投递、处理者也不回 | 终止是"异步"的（`process.h:137-139`）：`fe_task_terminate` 返回时只保证标记完成 |
| 出错线程正阻塞在某个等待对象上？ | **不可能**：异常发生在用户态执行时，"阻塞在内核里"的线程不在用户态跑 | （写下来是因为实现时容易加一条多余的判据） |

**一条由此得到的实现顺序**：`user_fault` 里"闸门判据"这一句
要**放在 `fe_user_resolve_fault` 之前**——一个正在被终止的任务没必要再补页，
补了它也回不去。代价：`fe_selftest_user` 依赖的
"drvdeny 触发一次 `#GP` 的计数"不受影响（那不是终止路径），但**这一句的顺序
需要一个负向对照来证明**（§5 的 F2）。

## 3. 明确不做

| 不做 | 理由 |
|---|---|
| **完整 POSIX 信号语义**（进程组、作业控制、`SIGCHLD`、`sigsuspend`、信号屏蔽字） | `10-posix-layer.md:156` 已经把它写在"明确不做"里，理由是"只需要 K3（=本文的 K5）那一小块；其余等有程序要"。而且这些是**策略**：`10-posix-layer.md:61-65` 把"POSIX 兼容性是策略、放用户态"这条定死了。K5 只提供"异常能交给用户态"这个机制，`sigaction` 那一层由 `libposix` 去搭 |
| **用户态接管内核态的异常** | 见下面单独一段。这是本文里唯一一条**安全边界**，不是"暂时不做" |
| **`#DF`（8）与 `#MC`（18）交给用户态** | 它们走独立的 IST 栈（`idt.c:91-97`：`g_idt[8].ist = 1`、`g_idt[18].ist = 3`），设计前提是"栈已经损坏"（`idt.c:39-40`）。这种异常发生时内核自己的状态已经不可信，把现场交给用户态等于让用户态在**内核已验证不了任何东西**的时刻做决定 |
| **反汇编 / 提供"出错指令长度"** | 见 §2.2.4。要做就得在内核里放一个 x86 解码器，而它只为一个用法服务（跳过指令），并且今天没有调用者要求它。处理者自己解码是可以的——它读 `rip` 处的字节没有任何特权 |
| **处理者能改 `cs`/`ss`/`rflags` 的任意位** | 见 §2.3：`cs`/`ss` 一律拒绝；`rflags` 只允许条件码与 `TF`/`DF`。放开的后果见下一段 |
| **"异常收不到处理者时自动重启线程"** | 重启意味着回到出错指令之前，而这要求"指令是幂等的"——那是**语言运行时**的假设，不是内核的 |
| **一个任务多个处理者端点（按向量分流）** | 今天没有调用者需要它；一个端点 + 消息里的 `vector` 字段已经能表达分流（代价：处理者自己 `switch`，零内核代价） |
| **处理者的超时内建告警**（"处理者 100 ms 没回复就打印一行"） | IF=0 里没有**可等**的时间源（§2.6.2）。★ 已查清（§6.1.4）★ 打印本身是**能用的**（`fe_kprintf` 无锁、不分配、不睡眠、串口轮询），所以这里拒绝的不是"打印"，而是"**在等待循环里按时间判断**"——那需要一个在 IF=0 期间会推进的时钟，而节拍不跳、`fe_time_ns()` 只能给"现在几点"不能给"时间过去了"。有界轮数是这个位置上唯一诚实的机制 |

### 3.1 ★ 内核态的异常永远不能被用户态接管 ★

这一条要说清为什么，因为它是**提权漏洞**与"特性"的分界线。

**今天的分界是 `idt.c:306` 的 `(r->cs & 3) == 3`。** 它不是随手写的：
来自 ring 3 的异常，`cs` 的 RPL 是 3（用户选择子是 `0x23`/`0x1B`，
`kernel/sched/sched.c:175`、`sched.c:178`）；来自 ring 0 的异常，
`cs` 是 `FE_SEL_KCODE`（`kernel/arch/x86_64/idt.c:83` 把 IDT 项的选择子设成它）。

如果允许用户态接管内核态异常，攻击链是这样的：

1. 用户在 ring 3 做一件**让内核自己出错**的事——最现成的形态是
   "内核解引用一个用户提供的坏指针"（`kernel/include/fe/user.h:4-5` 明确写着
   "内核**永不信任用户指针**"，但内核 bug 的存在恰恰是"永不信任"这条纪律存在的理由）；
2. 内核态 `#PF` 发生，现场里 `cs` 是 `0x08`（ring 0）；
3. 内核把现场交给用户态处理者；
4. 处理者改 `rip` 与 `rsp`，回"已处理"；
5. 内核照它说的 `iretq` —— **回到 ring 0、在攻击者选的地址上、用攻击者选的栈**。

第 5 步就是任意内核代码执行。★ 注意它不需要任何一句"用户态能改 `cs`" ★：
`iretq` 从栈上弹的 `cs` 就是那个 `0x08`，我们只是**把它弹回去了**。
所以"拒绝处理者改 `cs`/`ss`"（§2.3）与"内核态异常不投递"这两条
是**同一个洞的两个入口**，两条都必须有。

**代价（必须认）**：内核自己的 `#PF` 仍然是 `exception_fatal` → `fe_panic_halt`
（`idt.c:140-200`、`idt.c:199`）。这看起来"很脆"，但它是**对的**：
内核 bug 不能变成"用户态负责兜住的东西"，否则内核的正确性就没人负责了
（`idt.c:138-139` 那段注释里写着这条纪律的早期版本）。
另外 `idt.c:153-178` 记着一个实测教训：诊断代码自己再出异常会把内核带崩，
所以这条路上"只打印能确认可读的东西"。

## 5. 验证方案

原则（`11-kernel-next.md:446`）：内核自检（含反向对照）+ 一个走**真实路径**的客户端。

### 5.1 内核自检 `fe_selftest_fault`（宿主 `kernel/task/faulttest.c`）

自检的宿主形态照 `fe_selftest_kill`（`main.c:670` 注册；探针机制见
`13-tasks-and-kill.md:763-766` 的描述）：造探针任务、探针线程、临时换 `cur->task`。

| # | 正向断言（判据） | 反向对照（必须失败 / 必须不变） |
|---|---|---|
| **F1** | 投递可达：探针任务登记处理者端点 → 手动构造一个现场调 `fe_fault_deliver` → 处理者的端点里**真的有一条消息**，且消息里的 `fe_fault_regs` 与传进去的现场**逐字段相等**（含 `vector`/`error_code`/`cr2`/`thread_id`） | 把 `vector` 换成另一个值再投一次 → 消息里必须是**新值**（证明拷的是现场而不是常量）；再反向：`thread_id` 必须等于**出错线程**的 id，而不是处理者或主线程的 |
| **F2** | 闸门优先：`task->dying = true` 之后投递 → **端点里一条消息都没有**，且线程被 `fe_thread_exit` 带走（判据用"线程 `state == FE_THREAD_DEAD`"） | 同一时刻，另一个**没有**被终止的任务用同一个现场投递 → 端点里**有**消息（证明"没投递"是 `dying` 造成的，不是投递路径坏了）。★ 这一条同时是 §2.7 那句"判据顺序"的判据 ★ |
| **F3** | 顺序（§2.5.1）：一个 ANON 区间内的缺页 → `fe_user_resolve_fault` 返回 true → **不进处理者**（端点空），且 `fe_pf_resolved_count()`（`kernel/include/fe/user.h:159`）加一 | 同一个区间的**区间外**地址 → `fe_user_resolve_fault` 返回 false → **进处理者**（端点有消息）。两条一起才有约束力：它们互相排斥 |
| **F4** | 递归上限（§2.4）：`fault_depth = 1` 时投递 → **不投递**（端点空）且线程被杀 | 反向：`fault_depth = 0` 时同样的现场 → 端点**有**消息（证明"不投递"是深度造成的）。再反向：注销处理者（`fe_fault_clear_handler`）之后投递 → 端点空（证明"没登记"这条判据独立于深度） |
| **F5** | 活锁判据（§2.5.2）：同一个 `(rip, cr2)` 投递两次（第二次由"回复=RESUME 且不改 rip"驱动）→ 第二次**不投递**且线程被杀 | 换一个 `rip`（或换一个 `cr2`）再投 → **投递成功**（证明判据比的是"同一个现场"，不是"第二次就杀"） |
| **F6** | 回复校验（§2.3）：`fe_fault_reply` 用**错的** `thread_id` 回复 → `FE_ERR_INVAL`，等待中的线程**没有**被唤醒（判据：回复槽仍为空、端点里那条消息仍在） | 用**对的** `(task_id, thread_id, fault_seq)` 回复 → 返回 `FE_OK`，回复槽被写满，等待线程被唤醒。★ 这一条的正反两面缺一不可：只测正面的话，"无条件接受任何回复"也能通过 |
| **F8** | 自投递（§2.3.2）：把探针任务的"收件线程"设成**出错线程自己**，再投递 → **不投递**（端点空）且线程被杀 | 把收件线程设成**另一条**线程，同一个现场 → 端点**有**消息（证明"不投递"是那条判据造成的，不是投递坏了）。★ 这条最容易漏，因为它在单线程用法下才暴露 ★ |
| **F9** | 回复槽必须清（§2.4）：先完成一次正常的"投递 → 回复"，再投递第二次而**不回复** → 第二次的等待必须**等到轮数用完**（判据：`arrived` 在投递后立刻是 `false`） | 反向：如果不清槽，第二次会**立刻**看到 `arrived == true` 并拿上一次的 verdict 走——断言就是在读那一位的值，所以"不清"当场可见 |

### 5.2 真实客户端 `user/bin/faulttest`

一个程序，四种模式（同一可执行文件分饰多角，照 `killtest` 的做法，
`init/main.c:768-775`）。**屏幕上显示的字一律 ASCII**（项目铁律）：

| 模式 | 做什么 | 判据 |
|---|---|---|
| **A 越界写**（`--segv`） | 登记处理者 → 故意往一个**没有映射**的地址写 → 处理者在现场里看到 `vector==14`、`cr2` 等于那个地址、`error_code` 的写位为 1 → 回复 `RESUME` 并**把 `rip` 改到一段"我处理完了"的标签** | 进程**没有死**，且打印 `[faulttest] segv handled rip=... cr2=...` 后**从标签处继续跑对**：它算出的数与预期相等（用累加器对，不是"没崩"） |
| **B 非法指令**（`--ud`） | 执行一条 `ud2`（或 `.byte 0x0f,0x0b`）→ 处理者看到 `vector==6` → 回复 `RESUME` 并把 `rip` **加上那条指令的长度**（`ud2` 是 2 字节，客户端自己知道，不猜） | 越过错指令之后的那条指令被执行（用一个哨兵变量证明），退出码 0 |
| **C 除零**（`--de`） | 整数除零 → 处理者看到 `vector==0` → 回复 `RESUME`，把现场里的**除法的商寄存器改成约定的值**并跳过该指令 | 后续计算用到了处理者填的那个值（判据是"结果等于按那个值算出来的数"，不是"没崩"） |
| **D 反向：没登记处理者**（`--nohandler`） | **不登记**处理者，做与 A 完全相同的一次越界写 | ★ 这个进程**必须仍然被杀**：`init` 侧看到退出码 `-1`（与今天的 `drvdeny` 完全一致，`init/main.c:744` 期望 `-1`）。**这一条是本文最重要的反向对照**：没有它，"投递机制生效"与"内核干脆不杀了"无法区分 |

处理者侧还要自带两条：

| # | 断言 | 反向对照 |
|---|---|---|
| **E** | 同一个处理者在一次运行里接管 A/B/C 三次异常，三次都拿到**正确**的 `vector`；且每次 `fault_count` 递增（1、2、3） | 反向：三次的 `cr2`/`rip` **互不相同**——证明处理者拿到的是各自的现场，而不是第一份被重复使用 |
| **F** | 处理者自己出错的路径（`--recursive`）：处理者内部**故意**再触发一次越界写 → 内核按 §2.4 **杀掉那条线程**，进程随后按自己的策略退出（判据：退出码是一个客户端自己打印并核对的确定值） | 反向：先注销处理者再触发同样的错 → 也死，但**不是**"处理者被再投递一次"。两条的区别要用日志行数证：递归那条路径上处理者的打印**只出现一次** |

**真实路径覆盖**（`faulttest` 一次运行就覆盖）：
登记 syscall → ring 3 真异常 → `isr_common`（`isr.asm:49-69`）→ `fe_isr_dispatch`
（`idt.c:284`）→ `user_fault`（`idt.c:242`）→ 投递 → 消息唤醒处理者线程 →
处理者 `recv` → `FAULT_REPLY` syscall → 出错线程从 `iretq` 回到**处理者指定的
新 `rip`**。这一条链上任何一环没实现，A/B/C 里至少有一个会失败。

**init 单元表**：加一行
`{ .name = "faulttest", .path = "/bin/faulttest", .expect = 0, .check = 1 }`。
**不需要 `require`**：它不用文件系统、不用块设备、不用控制台名字
（它的输出走 `fe_debug_write`，与 `clocktest` 一样——`init/main.c:757-759`）。
代价：`check_init.py:119` 的 28 → 29，`build/serial-ref.txt` 要刷新
（`13`/`14`/`15` 三轮都这么做过）。

### 5.3 失败时最先看哪里

按"最可能的原因 → 症状"排序，写给下一次调试的人：

| 症状 | 最可能的原因 | 先看哪里 |
|---|---|---|
| `faulttest --segv` 直接以 -1 退出，日志里没有任何 `[用户态异常]` | 处理者没登记成功（`FE_SYS_FAULT_HANDLER` 返回负值被忽略了）；或登记成功但 `user_fault` 的新分支没编译进去 | 先看登记 syscall 的返回值（客户端要打印它），再看 `idt.c` 里三段分支的顺序 |
| 日志里出现 `[用户态异常]`，然后**卡住不返回也不死** | 投递成功但回复永远不到：处理者线程没被唤醒（端点消息的唤醒路径 `ipc.c:315`）或它自己在等别的东西 | 用 `ps`（K3，`init/main.c:754` 那个单元）看处理者线程的 state；它是 `BLOCKED` 就是等错了对象 |
| 登记了处理者，但异常仍然要"等一会儿"才死（不是立刻死） | **出错线程就是收件线程**（§2.3.2）：它自己在异常上下文里等自己回消息，只能等满轮数 | 看登记时是不是在**主线程**里调的、而异常发生在**工作线程**里；正确写法是"谁登记谁收"，且收件线程必须是另一条线程 |
| 处理者拿到了现场，但"改完现场后程序继续跑"跑出了错的值 | `RESUME` 的现场回填漏了某个寄存器（尤其是 `rax`/`rcx`/`r11` 这些被指令隐式使用的） | 回填代码要**逐字段列全**，并在自检 F1 里做"逐字段相等"的断言——不要抽样比 |
| 第一次异常处理成功，第二次同一个线程再出错就直接被杀（没有投递） | `fault_depth` 没减回去（§2.4 代价 3） | 看 `fe_fault_deliver` 的**每一条返回路径**是否都减了一；把"加一/减一"写在同一层，别分散 |
| 处理者接管了一次之后，**所有**异常都不再投递 | 同一现场判据（§2.5.2）误命中：`last_fault_rip`/`last_fault_cr2` 在**回复成功**之后没有清 | 只在"新的一次投递"时更新这两个字段，不要在处理完时留着 |
| 用户程序取指 `#PF` 之后整个系统崩（不是只死线程） | 处理者缓冲区地址校验漏了（用户给了内核地址）→ `fe_copy_to_user` 应返回 `FAULT`（`uaccess.c:64-75`），若被忽略就是内核往非法地址写 | 登记时的指针校验必须当场做（像 `sys_task_list` 那样"校验 + 一次拷贝"） |
| `ps` 里任务数一直涨 | 处理者端点的那次 `fe_object_ref` 没有对应的 `unref`（§2.1 代价 3） | `task.c` 的 `case FE_OBJ_TASK` 里那一句 |

**这个消费者依赖什么语义**——逐行读 `kernel/task/user.c:30-48`：

```c
if (fe_user_fault_count() == 0) { 打印"drvdeny 应当触发一次 #GP"; return 1; }   /* :33-36 */
u64 vec = fe_last_user_fault_vector();                                          /* :37 */
if (vec != 13) { 报错 fail++; }                                                 /* :38-41 */
else { 打印 "用户态异常向量 = 13 (#GP)，累计 %llu 次"; }                          /* :42-46 */
```

它要的是：**"最近一次用户态异常"就是 `drvdeny` 那次 `#GP`**（`vec == 13` 是向量判据，
`count == 0` 是"根本没人异常过"的兜底）。也就是说它依赖的语义是
**"每一次走到 kill 分支的用户异常都记账"**——因为只有那一条路会写这两个变量。

**K5 会不会改掉它**：**会，而且改的是"哪些异常算数"**。K5 之后被处理者消化的异常在
`idt.c:254-260`（按需分页成功）与新的投递分支上就 `return` 了，**走不到 `idt.c:262-263`**。
所以：

- `g_user_fault_count` 的含义从"用户态异常次数"变成 **"没有被任何机制消化的用户态异常次数"**；
- `g_last_user_fault_vector` 从"最近一次用户异常"变成 **"最近一次<u>没能被消化</u>的用户异常"**。

**今天它仍然会通过，但那不是因为判据还对，而是因为恰好没有受害者**：
`user/bin/drvdeny/main.c:18-28` 里**没有登记处理者**（全文 29 行，只做了 `fe_inb(COM2)`），
所以它那次 `#GP` 仍然写这两个变量。★ 这正是最坏的一种"绿"：判据依赖的语义已经变了，
而它**看起来仍然通过**（项目里已经为这一类付过两次学费：
`11-kernel-next.md` §8 的 `wait_any` 自检与 `13-tasks-and-kill.md` §4 的两条计数类断言）。

**必须做的事（写进 §4.1 的实现清单）**：

1. 新增"**全部**用户态异常"的计数与向量（K5 的投递路径里也记一次），
   并把 `fe_user_fault_count()` / `fe_last_user_fault_vector()` 的语义**明确写成
   "全部"**（`idt.h:24-27` 那段注释要改）；
2. 若还想区分"被消化的"，**新增**一个 `fe_user_fault_handled_count()`，
   而不是把旧接口改成"未消化"——旧接口的读者（`user.c:33-45`）依赖的是"全部"；
3. `fe_selftest_user` 的判据本身要加一条**顺序无关**的断言：`drvdeny` 那次 `#GP`
   必须在计数里被看见（例如"`#GP` 计数 ≥ 1"），而不是依赖"最近一次"——
   后者在多线程/多异常的真实系统里本来就脆弱。

**代价**：一个 `u64` + 一处写入点 + 一次自检判据调整。**收益**：一个既有诊断接口的含义
不会被 K5 悄悄改掉。

#### 6.1.2 第 2 条：镜像放 `user/include/fe_user.h`，不放 `fe_base.h`

注意文件在 `kernel/mm/uaccess.c`（不是 `kernel/task/`），四个原语：

#### 6.1.4 第 4 条：`fe_kprintf` 可以用，但它在异常上下文里"能用"的边界要写清

**读了三层实现**（`kernel/lib/kprintf.c` 全文 372 行）：

1. 格式化核心 `format_impl`（`:182-307`）：纯计算 + 栈上 `char tmp[72]`（`:58`、`:111`），
   每个字符回调一次 `emit`（`:17-21`）；
2. `fe_kprintf` / `fe_kvprintf`（`:319-331`）：回调 `console_emit`（`:313-317`）
   → `fe_console_putc(c)`；
3. `fe_console_putc`（`kernel/arch/x86_64/serial.c:91-94`）→ `fe_serial_putc`
   （`serial.c:46-63`）→ `fe_outb`/`fe_inb`（`kernel/include/fe/io.h:13/28`，
   纯端口 I/O 内联）。

**结论：能用（有条件）**，理由逐条对上"会不会阻塞/睡眠/加锁"：

- **没有锁**：全路径没有互斥量、没有 `spin_lock` 一类东西（`kprintf.c` 与 `serial.c`
  里除了 `g_console_port` 这个静态变量之外没有任何共享状态）；
- **不分配内存**：格式化缓冲全在栈上（`kprintf.c:58`、`:111`），不走内核堆；
- **不睡眠、不让出**：全路径没有任何 `fe_sched_*`、`fe_thread_yield`、`int` 调用；
- **串口初始化时**已经关掉串口中断并用轮询输出（`serial.c:37` 的注释与
  `fe_outb(port + REG_IER, 0x00)`），所以它**不依赖中断**——这正是它能在 IF=0 里工作的原因。

**代价（这是"有条件"的部分）**：`fe_serial_putc` 每个字符都有**有界自旋**
（`serial.c:48-53`：最多 10 万次读 LSR），而且字符是 `'\n'` 时**再来一次**
（`serial.c:54-61`）——所以最坏情况是每次 `\n` 两轮 × 10 万次端口读。
串口不存在或 FIFO 卡住时，它不会死循环（注释 `:48` 明说"加超时保护"），
但**故障路径上的日志会先烧掉这段时间**。

**由此得到两条对 K5 的具体约束**（写进 §2.6.4 的实现注意）：

1. 故障路径上**允许**打印，但要用**固定短串**（`idt.c:279-280` 今天就是这么做的：
   一行"该线程被终止"），不要在异常上下文里组装大段 dump——
   `idt.c:267-278` 那次区间表 dump 已经是一个"有必要但昂贵"的先例；
2. 别在投递/等待的**循环里**打印（每次循环一行会把有界自旋乘以轮数）。
   `FE_FAULT_WAIT_ROUNDS` 用完之后打**一行**总结即可。

★ 顺带一条事实 ★ 今天 `idt.c:264-278` 已经在 IF=0 里调用 `fe_kprintf`（含 `%s` 与多个
`%llx`），所以"在异常上下文里打印"不是 K5 新引入的风险，而是**既有做法的确认**。

#### 6.1.5 第 5 条：`exec` 之后**清掉**处理者登记（这是设计结论，不是查代码）

先把两半分开，因为结论取决于"登记的哪一部分属于身份、哪一部分属于映像"
（`15-exec.md:27-49` 的划分）：

| 登记里的东西 | 属于 | `exec` 之后 |
|---|---|---|
| 处理者**端点**（内核持有一次引用的对象） | **身份**：`exec` 不换句柄表（`15-exec.md:48`"其它一个字都不动"） | 仍然有效 |
| 用户**现场缓冲区地址** | **映像**：它是旧地址空间里的一个虚拟地址 | 换空间后可能变成未映射（或被新映像的别的东西占用） |
| **收件线程指针**（§2.3.2） | **映像**：`exec` 会先杀掉调用者之外的**全部**线程（`15-exec.md:362-366`） | 大概率已死 |

**★ 先否掉"悄悄留着"★** 如果什么都不做地留着，`exec` 换完映像之后这个任务仍然
"登记着处理者"，而那个处理者的**代码在新映像里根本不存在**：
下一次异常会被投递给一段**不属于新程序**的地址。于是新程序会看到
"我没登记过处理者，异常却被别人接走了"——这正是 `13-tasks-and-kill.md` §6.5 那条
先例要防的形状：**"系统里凡是'按身份钉死'的授权，换映像都必须显式处理，
不能默认它跟着人走"**（`15-exec.md:295-296` 原文）。处理者端点确实按身份钉着，
所以它必须被显式处理——**"显式处理"的两种合法形态是"重新判定"或"拒绝"，
不包括"默认保留"**（`15-exec.md:51-53`）。

**★ 也否掉"重新判定（重新校验缓冲区地址、保留登记）"★** 它在技术上做得到
（换完 CR3 之后用 `fe_user_range_ok(新 space, buf, 200, true)` 查一次，
见 §6.1.3 的表格），但它**把处理者的存活寄托在新映像恰好把同一段地址映射成可写**上。
那是一种"看起来在工作"的状态：新程序既没有登记过处理者，也拿不到任何通知，
却可能在某次异常里被一段陌生代码接管。**代价大、收益为零**——
`exec` 的语义是"换一个程序"，新程序不该继承旧程序的异常策略。

**结论（建议）**：**清掉**，并且**不能静默清**：

1. 提交阶段（`15-exec.md:124-138` 的第 6–10 步那一段里，与 `t->name` 的更新相邻，
   `15-exec.md:265-266`）做三件事：`fe_object_unref` 端点那次引用 → 清空端点指针、
   缓冲区地址、收件线程指针 → `fault_depth = 0`；
2. **留一个可观察的后果**：新映像的第一次 `FE_SYS_FAULT_REPLY`（或任何
   "处理者相关"的调用）返回 **`FE_ERR_NOENT`**（"没有登记"），
   而不是 `FE_ERR_INVAL`。两者对用户的含义不同：`NOENT` 说"登记不在了"，
   `INVAL` 说"你参数写错了"——而这里**不是参数错**。
   ★ 这条判据可证伪 ★：`exectest` 的模式 B（回滚）之后紧接着问一次
   "我还有处理者吗"，必须是 `NOENT`；
3. `fault_depth = 0` 这一条**不能省**：`exec` 可能发生在"上一个映像里有人正在等回复"
   的极窄窗口里（等待是**有界**的，但 `exec` 的系统调用可以插进那段时间）。
   不清它，新映像会带着"已投递未回复"的计数开局，于是**它的第一次异常直接被杀**
   （§2.4）。症状是"exec 之后新程序第一次崩溃特别干脆，连处理者都不叫"。

**代价（如实说）**：

- 用户态**没有**"跨 `exec` 保留崩溃处理器"这个能力（POSIX 也没有：
  `exec` 之后信号处置要么复位要么保持默认，处理器函数在新映像里同样是陌生地址）；
- 想在 `exec` 之后继续有处理者，新程序必须**自己重新登记**——
  代价落在用户态（一行 syscall），内核不多一个机制；
- `exec` 的实现者要为这段清理写 3–4 行，并加一条断言；
  归口在 `15-exec.md` 的 §5/§9 清单里（那张表正在被另一个执行体写，
  **这条要作为 K5 对 K6 的要求提过去**，不是本文能单独落地的）。

### 6.2 代价清单（一句话版）

1. 两个 syscall 号（`0x90`/`0x91`，可能顺延）、一个 200 字节的共享 ABI（两边各一份镜像 + `_Static_assert`）；
2. `struct fe_task` 多 5 个字段（其中一个是对象指针，**必须**在销毁路径上 `unref`）：处理者端点、现场缓冲地址、收件线程指针、`fault_depth`+`fault_owner`、`fault_seq`；`struct fe_thread` 多 3 个字段（两个 `u64` 现场记忆 + 一个回复槽）；
3. `user_fault` 从"两条出口"变成"四条出口"（按需分页 / 投递 / 闸门杀 / 照旧杀）——**这是本文结构上最贵的一处**，因为它是异常分发里唯一一个多分支的地方，而 `idt.c:290-305` 那段注释记着"漏一个 `return` 就把成功当致命"的实测事故。代价的形态是**可读性**，缓解手段只能是注释与自检（§5.1 的 F2/F3 各堵一条出口）；
4. 出错线程在等待期间**占用一个时间片空转**（§2.6.3）。它是"有界"的，但一个高频出错的进程会让 CPU 空转——**这是处理者自己的责任**，内核只保证有界；
5. **处理者必须预先把内存准备好**（§2.4 代价 1）：这一条违反"按需分页是常态"的习惯，第一次写处理者的人一定会踩。没有内核侧的缓解手段，只能靠文档与 `user/bin/faulttest` 的示范；
6. 处理者积压 64 条消息时下一个故障线程**直接被杀**（§2.6.4 第 2 条，队列上限来自 `fe/ipc.h:32`）；
7. **一个既有诊断接口的含义会被改**（§6.1.1）：`fe_user_fault_count()` / `fe_last_user_fault_vector()` 从"全部用户态异常"变成"没被消化的用户态异常"。代价是：一个 `u64` 计数、一处写入点、`idt.h` 的注释、以及 `fe_selftest_user` 的一条判据（`kernel/task/user.c:33-45`）。**不做这件事的代价更大**：那个自检会"看起来还通过"；
8. `user/bin/init` 单元数 28 → 29，`tools/check_init.py:119` 与 `build/serial-ref.txt` 要跟着改（我实测参考日志里就是 28）；
9. **单线程程序用不了处理者**（§2.3.2）：出错线程自己不能是收件线程，所以"一个进程一条线程"的程序必须先开第二条线程。代价落在**用户态**（多一条线程 + 它的栈），内核一行都不用改；
10. **K6 那边多一段清理代码**（§6.1.5）：`exec` 提交阶段要清掉处理者登记（3–4 行 + 一条断言），否则新映像会继承一个指向旧映像代码的处理者。
